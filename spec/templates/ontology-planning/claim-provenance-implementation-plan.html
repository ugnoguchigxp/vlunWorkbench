1. Purpose

persisted Static Intelligence generationから公開されるgraph node、edge、module candidate、risk community、および将来のclaimについて、どのsource、revision、producer、generator、rule、入力targetから生じたかを機械的に追跡できるようにする。lineageは説明表示だけでなく、stale判定、再計算、改ざん検知、監査、consumer側の安全な採否判断に使える形で保持する。

この計画はClaim Provenanceだけを実装可能な粒度へ具体化する。semantic handoff validation、security vocabulary alignment、ontology contract versioning、competency question、rule inferenceを同時に設計・実装しない。

実装は二つのtrackへ分ける。Core Provenance trackは現行graph、module、community outputのlineageを同じprojection passで生成し、ledger、binding、persistence、bounded queryを完成させる。Semantic Validation Integration trackは、Semantic Handoff Validationがowner承認済みprofileを公開した後に、そのresultを新target / ruleとして接続する。Core trackはintegrationを待たず完了でき、既存validation profile v1を変更しない。

2. Target Outcome

source rows / persisted artifacts / semantic result
  -> build graph, module, or community and provenance draft together
  -> bind draft to exact source revision and generation
  -> canonicalize records and target bindings
  -> persist normalized provenance ledger beside the generation
  -> validate completeness and hashes
  -> publish only a bounded descriptor in handoff / manifest
  -> resolve one target's lineage through a bounded read-only query
  • 各targetはwhole-object bindingを最低1件持ち、profile指定の重要propertyはproperty bindingも持つ。
  • 同じlineage内容はtarget間で1つのrecordへdeduplicateされ、targetはrecord IDを参照する。
  • observed、deterministic derived、semantic candidate、LLM interpretationを混同しない。
  • 同じrevision、producer version、generator version、rule、source、inputから同じprovenance IDを生成する。
  • ledgerが欠落または不正でも既存generation artifactは失わないが、不正なledgerは公開しない。
  • NightWorkersはmanifest descriptorを検証するが、full ledgerをtask eventへ複製しない。
  • consumerはtarget refを指定して必要なlineageだけを取得し、raw artifactやraw evidenceは取得しない。

4. Fixed Decisions

  • initial implementationはnormalized JSON ledgerとtarget bindingを採用する。
  • node / edge schemaへ同じprovenance objectをinline複製しない。
  • ledgerは既存scan_artifactsとgeneration lifecycleを再利用し、別DBを導入しない。
  • RDF、PROV-O serializer、triple store、Semantica runtime dependencyを導入しない。
  • provenanceはtruth、approval、correctnessを保証しない。出所と処理経路だけを保証する。
  • confidence欠落を0へ補完せず、既存target confidenceとprovenance confidenceを別fieldとして扱う。
  • global insertion-order hash chainを採用しない。record単位とledger単位のcontent-addressed hashを使う。
  • raw source quote、raw evidence snippet、raw artifact body、secret、absolute pathをledgerへ保存しない。
  • full ledgerをknowledge source manifest、NightWorkers task event、model promptへinlineしない。
  • persisted generationに結び付かないad hoc outputをrevision-backed lineageとして表示しない。
  • builderとlineageを別々に再計算せず、同じprojection passからpayloadとprovenance draftを作る。
  • profile v1のrule ID、required target、property path、assertion kindはimmutableとする。
  • base recordは同一generationで一括finalizeするため、generatedAtはledgerに1回だけ持たせる。source固有時刻はtarget / source artifactのfieldとして追跡し、deduplicated recordへ複製しない。
  • rule semanticsを変える場合はrule versionまたはprofileを更新し、既存record IDを再解釈しない。
  • consumer-first migrationを採用し、NightWorkersがoptional descriptorを読める状態を先にreleaseする。
  • producer writerより先にtolerant readerをreleaseし、新artifact kindをderivedとしてsourceStateHashから除外できるversionをrollback floorにする。writer有効化後はそれ以前のproducer binaryへ戻さない。
  • artifactMode（off / shadow / required）とpublishEnabledを既存方針に合わせてsource-controlled typed constantで管理する。未検証の環境変数やrequest inputから切り替えない。
  • Slice 1 / 2 merge時のproduction defaultはoffとし、graph + module coverage後に別changeでshadowへ上げる。
  • legacy 3-artifact generationは読み続け、新規4-artifact generationへのin-place backfillをしない。
  • Core Provenance completionとSemantic Validation integration completionを別milestone / DoD / GOにする。 integration未実装を理由にcore ledgerをpartial扱いせず、逆にcore completionを理由にvalidation integration済みと表示しない。
  • provenance availability、coverage、confidenceをclaim truth、validation severity、security confirmationへ自動変換しない。consumer policyは別のtyped decisionとして保持する。

8. Claim and Lineage Semantics

8.1 Assertion Kinds

profile v1のepistemic classification
Kind Meaning Promotion rule
observed 保存済みrow / artifactが直接表す存在、状態、識別子 source ref必須。consumer成功では昇格しない。
deterministic_derived 固定ruleがobservedまたはderived inputから再計算できる投影 rule IDとinput ref必須。observedとは呼ばない。
semantic_candidate embedding / semantic queryにより選択された候補 常にcandidate-only。observed / declaredへ自動昇格しない。
llm_interpretation scan review等のLLM出力から投影した説明、command、関係 source reviewとgenerator fingerprint必須。observedへ自動昇格しない。

8.2 Provenance Is Not Truth

  • 完全なlineageがあってもsourceが誤っていればclaimは誤り得る。
  • confidence=1はtruth、approval、安全性を意味しない。
  • deterministic ruleの再現性はconfidenceではなくassertion kindとgenerator versionで表す。
  • coverageは観測範囲を表し、未観測領域の安全性を主張しない。
  • lineage欠落を空配列で成功扱いせず、missing / partial / invalidを明示する。

8.3 Confidence Semantics

provenance confidenceのproducer内意味
Semantics Meaning Profile rule
source_reported source rowまたはtoolが明示した0..1値 source refとmethod catalog entryを必須とし、文字列confidenceを推測変換しない。
derivation_support 固定ruleが定義した入力充足度 formulaをrule catalogへ固定する。targetのconfidence fieldを自動コピーしない。
similarity semantic providerが返した正規化済みsimilarity semantic candidateだけに必須とし、model fingerprint、threshold、topKと結び付ける。

moduleやcommunity payloadのconfidenceはtarget valueであり、property bindingの valueHashで追跡する。provenance confidenceへ同じ数値を複製する場合は、rule catalogに独立した意味とmethodが定義されている場合だけ許可する。

8.4 Coverage Semantics

  • completeはtotalCount必須かつobservedCountと同数とする。
  • partial / unknownは固定reason codeを必須とし、totalCountがある場合はobservedCount <= totalCountとする。
  • coverage未設定は「このruleに件数coverageを適用しない」を意味し、unknownの代用にしない。
  • source rowやartifactのretention切れは来歴refを削除せず、query結果でsource unavailableを示す。

manifestとhandoffへ入れるのはdescriptorだけである。recordsとbindingsはartifactまたはbounded query responseから取得する。

base ledgerのrequiredBindingCountはgeneration handoffに含むgraph node / edge / moduleのwhole-object bindingとrequired property bindingを対象にする。projectionのsummaryは、そのresponseが実際に返すcommunityまたはagent-query targetのwhole-object / required property bindingだけから再計算する。projectionのparentLedgerHashは検証済みbase ledgerと完全一致し、bindingのvalueHashは同じresponse内のtarget valueと一致しなければならない。

projection summaryのrecord / binding countはprojection内の配列だけを数える。bindingがparent ledgerのrecord IDを参照する場合、そのrecordをprojectionへ複製せず、projection record countにも加えない。

reachable parent recordのpartial / unknown coverageはouter partial envelopeのreasonCodesへ伝播するが、projection summaryのrecord / coverage countには加えない。

byAssertionKindとbyCoverageStatusはrecord数、 byTargetKindはbinding数を数え、zero件のenum keyも省略せず0で出力する。

community / agent-query response rootのclaimProvenance envelope自体はwire compatibilityのためoptionalとする。new persisted-generation pathは必ず4 statusのいずれかを返し、legacy producerだけがfieldを省略できる。

9.3 Cross-field Invariants

  • observed recordはsourceRefsを1件以上持ち、inputRefsは空にする。
  • deterministic derived、semantic candidate、LLM interpretationはinputRefsを1件以上持つ。
  • semantic candidateのconfidence semanticsはsimilarityだけを許可する。
  • semantic candidateはconfidence自体も必須とし、欠落を0として扱わない。
  • semantic candidateはsemantic_query input、model / deployment fingerprintを表すgenerator version、minVectorScore / topKを表す semanticParametersを必須とする。それ以外のassertion kindはsemanticParametersを持たない。
  • confidenceがない状態とvalue=0を区別する。default値を補わない。
  • coverage.status=completeはtotalCountを必須とし、observedCountと一致する。
  • coverage.status=partialまたはunknownはreasonCodesを1件以上持つ。
  • totalCountがある場合はobservedCount以上でなければならない。
  • git revisionはheadを必須とし、tree_hash_onlyはhead / dirtyHashを持たない。
  • recordとledgerのrevisionは完全一致する。
  • generatorのrule IDはprofile v1のimmutable rule catalogに存在し、recordのassertion kindと許可された組合せでなければならない。regexだけを通過したunknown ruleを受理しない。
  • confidence methodとcoverage reason codeもrule catalogで許可された値だけを受理する。
  • artifact / snapshot / static intelligence export / reference set参照はcontentHashを必須とする。
  • file refはproject-relative pathだけを許可し、absolute / external pathは kindをredactedへ変えてredacted:sha256:<hash>形式にする。
  • bindingの全provenance IDが同じledgerまたは明示されたparent ledgerのrecordに存在する。
  • provenance_record input refは同じledger / projectionまたは明示されたparent ledgerのrecord IDへ解決できなければならない。
  • provenance_record dependency graphのcycleはinvalidとし、query側cycle detectionもdefense-in-depthで残す。
  • ledger / projection内の全recordは少なくとも1つのbindingから到達可能とし、orphan recordをinvalidにする。
  • 同一target kind / target ref / property pathのbindingを重複させない。
  • target refのprefixとproperty pathはtarget kind別のprofile catalogに一致させる。property pathはRFC 6901 JSON Pointerとして有効でも、catalog外なら拒否する。
  • valueHashはwhole targetまたはproperty valueをcanonical JSON化したhashと一致する。
  • records、bindings、sourceRefs、inputRefs、provenanceIds、reasonCodesはcanonical順かつ重複なしとし、loaderも非canonical ledgerを拒否する。
  • summaryはrecords / bindings / required binding profileから再計算した値と一致する。
  • coveredRequiredBindingCount + missingRequiredBindingCountはrequiredBindingCountと一致する。
  • byAssertionKindとbyCoverageStatusの合計はrecordCount、byTargetKindの合計はbindingCountと一致する。
  • missingRequiredBindingCount、partial coverage、unknown coverageのいずれかが1以上ならdescriptor statusをpartialにする。すべて0の場合だけavailableにする。
  • partial descriptorはsummaryから導出した固定reason codeを1件以上持ち、available descriptorはreasonCodes fieldを持たない。
  • published descriptorのledgerRef suffixはdescriptor generation IDと一致する。
  • hash不一致、dangling provenance ID、revision不一致はunavailable descriptorのinvalidとして扱い、ledgerRef、hash、summaryを公開しない。

14.2 Provenance Draft

graph / module / community builder時点ではgeneration IDとsource revisionが未確定の場合があるため、builderはhash済みrecordではなくdraftを返す。draftはtarget、assertion kind、rule、source / input ref、target value、confidence、coverageだけを持ち、finalizerがrevisionを加えてrecord IDとvalue hashを計算する。

  • module-global mutable collectorを使わない。
  • draft作成失敗を握りつぶしてpayloadだけ成功扱いにしない。
  • same targetへの複数sourceはdraft mergeでunionし、最後の1件で上書きしない。
  • payload生成後のreverse engineeringでsourceを推測しない。
  • testはpayloadのみwrapperとmaterial APIのpayloadが完全一致することを確認する。

14.3 Query-time Projection

moduleはontology handoffの一部なのでbuild時にmaterialを作り、graphと共にbase ledgerへ固定する。communityはquery条件やsemantic resultに依存するためbase ledgerを改変せず、query-time projectionとして返す。

  • base ledger scopeはgeneration_handoffであり、graphとmoduleをrequired targetにする。
  • ontology handoffで再計算したmoduleはbase bindingのvalueHashと一致する場合だけ対応lineageを公開する。
  • deterministic / semantic community projectionはbase ledger hashをparentとして、追加records / bindingsとprojection hashを返す。
  • projection statusは自身のrequired bindingsと、実際に参照するparent recordsのcoverageから決める。parent ledgerが別target理由でpartialでも一律partialへせず、reachableなpartial / unknownだけを伝播する。
  • semantic communityはsemantic resultのsource identityが揃う場合だけlineageをavailableにする。
  • ad hoc live exportから作ったcommunityはclaimProvenance.status="missing"とし、revisionを推測しない。
  • community projectionはcommunityを返した同じresponseへ含める。後続requestでsemantic contextを推測して再生成しない。
  • persisted agent-query responseがprofile対象communityを0件返す場合は、baseがvalidならparentLedgerHashとzero summaryを持つavailable empty projectionを返す。対象0件をmissingと扱わない。
  • projectionはrecords 2,000、bindings 2,000、serialized 2 MiBを上限とする。超過時はlineageだけをcanonical 順で切り、target payloadは切らず、partial envelopeとrecord / binding / projection size reasonを返す。
  • projection recordをbase ledger artifactへ追記しない。

14.4 Finalization and Persistence Boundary

現行persisterがgeneration IDを内部生成するため、ledgerをbuild serviceで先に確定しない。 PersistStaticIntelligenceGenerationInputへoptional claimProvenanceDraftとtyped claimProvenanceArtifactModeを追加し、persister内で次の順に処理する。

  1. source bundleを再loadし、expectedSourceStateHashを既存処理どおり検証する。
  2. generation ID、source revision、既存3 payloadのserialized bytes / content hashを確定する。
  3. source state一致後にdraftをfinalizeし、record ID、binding valueHash、summary、ledgerHashを生成する。
  4. ledgerをserializeし、claim provenance artifact contentHashとrole-specific metadataを生成する。
  5. modeに従い3件または4件を保存し、DB transactionへ進む。
  • source state mismatchはprovenance degradationではなくgeneration全体の既存failureとする。
  • build serviceはdraftを集約するが、generation IDやledgerHashを先取りしない。
  • persister returnへbounded provenanceBuild outcome（status、reasonCodes、durationMs、optional artifact identity）を追加し、build serviceは内部telemetryへ使う。public build resultのbuild_claim_provenance stageへ投影するのはpublishEnabled=trueの場合だけとする。
  • offではdraftをfinalizeせず3 artifact、shadowではfinalize失敗をdegraded 3 artifact、requiredではfinalize失敗をgeneration failureにする。
  • query-time community projectionはloaded base ledger identityを使い、persisterを通さない。

  • artifact row sha256、metadata contentHash、実bytes hashの3値を一致させる。
  • metadata ledgerHash、ledger bodyのledgerHash、bodyからの再計算値を一致させる。
  • ledger generation / project / scan / revisionを他の3 artifact metadataと一致させる。
  • record ID、binding参照、canonical順、summaryを全件検証する。
  • invalid provenance artifactはfull ledgerを返さず、generation本体はread-onlyでload可能に保つ。
  • load結果はprovenanceをavailable、missing、invalidのdiscriminated unionで返す。invalid時はraw ledgerを返さない。
  • loaded stateのavailableは「ledgerをstructuralに読める」を意味し、published descriptorのavailable / partialとは別である。publication resolverだけがdescriptor statusを決める。
  • latest generation選択はcore 3 artifactの妥当性を基準にする。provenanceだけがinvalidでも古いgenerationへsilent fallbackせず、最新core generationをprovenance=invalidとして返す。
  • retention / deletionはgeneration artifact setと同じpolicyに従う。

15.3 Structural and Publication Validation

  1. repository loaderはschema、artifact / ledger hash、identity、record / binding、summaryだけを検証し、structural provenance stateを返す。
  2. 共通publication resolverはpersisted exportのgraph targetと、persisted project structure / exportから再計算したmodule targetをbinding valueHashへ照合する。
  3. manifest、ontology handoff、base lineage queryは同じresolver結果を再利用し、個別surfaceでstatusを再判定しない。

publication target mismatchはpublication_value_mismatchを持つinvalid descriptorへ写像する。core generation自体は利用可能なままとし、Claim Provenanceだけを公開しない。community projectionは同じresponseのtarget valueと直接照合する。

23. Security, Privacy, and Abuse Resistance

  • lineage queryは既存project / scan owner authorizationを通す。
  • target refとproperty pathは長さ制限し、regex backtrackingへ依存しない。
  • API target refはJSON bodyで受け、access logのURL / query stringへ記録しない。
  • artifact pathをclient inputから直接組み立てず、repositoryでgeneration IDから解決する。
  • ledgerRefをfilesystem pathとして解釈しない。
  • raw evidence、artifact body、LLM prompt / response、secretをrecord metadataへ入れない。
  • validation exception textをwireへ出さず、固定reason codeへ変換する。
  • lineage traversalはcycle、depth、record、byte budgetを強制する。
  • hashはintegrity checkであり、signatureまたはtrusted attestationとして表示しない。
  • source deletion / retention要求はgeneration artifact set全体へ適用し、orphan ledgerを残さない。

24. Performance and Payload Budget

  • draft生成は既存builder loop内で行い、追加complexityをO(targets + refs)にする。
  • finalizeはrecord / binding sortを含みO(N log N)、working memoryはO(N)とする。
  • shadow fixtureでbuild wall timeの増加をbaseline比20%以内にする。
  • ledger bytesはexport bytesの2倍以内かつ64 MiB未満をqualification targetにする。
  • budget超過時はpartial ledgerを保存しない。shadowはbounded reason code付きdegraded、requiredはnew generation失敗とする。
  • manifest descriptorは8 KiB未満、NightWorkers event追加分は4 KiB未満とする。
  • single-target queryはp95 100 ms以内、serialized 1 MiB未満をlocal fixture targetにする。
  • source availabilityはkindごとにbatch lookupし、ref単位のN+1 DB / storage callを作らない。
  • community / agent-query provenance projectionはserialized 2 MiB未満とする。
  • full ledgerを毎requestでparseし続けないよう、request-local validated ledgerを再利用する。
  • 性能値はmachine、fixture、target / record countと共に保存する。

26. Rollback Plan

26.1 Rollback Triggers

  • valid generationがprovenance artifact追加によりload不能になる。
  • record IDまたはledger hashが同一inputで不安定になる。
  • raw path、evidence、secretがledger / manifest / eventへ出る。
  • missing required binding、invalid ledger、consumer schema failureがqualification thresholdを超える。
  • build / payload budgetを継続して超える。
  • NightWorkers fallbackまたはhandoff availabilityが非劣化条件を破る。

26.2 Rollback Order

  1. source-controlled producer descriptor publish gateをOFFにしてdeployする。
  2. manifest bundle省略とHTTP route固定404を確認する。local diagnostic CLIは残す。
  3. artifactModeをrequiredからshadowへ戻し、ledger失敗時の3-artifact generationを許可する。
  4. 必要ならartifactModeをoffへ戻し、draft / ledger build自体を停止する。
  5. NightWorkers optional schema supportは害がなければ残す。

rollbackで既存generation artifactを削除しない。保存済みprovenance artifactはgeneration retentionに従いread-onlyで保持し、producerが再publishしない。producer binaryはSlice 2A rollback floorより前へ戻さない。

27. Definition of Done

27.1 Core Provenance Definition of Done

  • base ledgerのgraph node / edge / moduleと、各response projectionのemitted communityについてwhole-object binding coverageが100%である。
  • required property binding coverageが100%である。
  • observed、deterministic、semantic、LLMの分類fixtureがreviewされている。
  • 同一inputでrecord ID / ledger hashが決定的である。
  • revision、rule、source変更で期待どおりidentityが変わる。
  • legacy 3-artifactとnew 4-artifact generationを両方loadできる。
  • Slice 2A tolerant readerがnew kindをsourceStateHashへ混入させず、rollback floorとしてdeploy済みである。
  • provenance-only corruptionでlatest core generation selectionが変わらない。
  • hash / revision / dangling binding corruptionを検出し、不正ledgerを公開しない。
  • graph / module valueHashを共通publication resolverが検証し、全surfaceが同じdescriptorを返す。
  • 捕捉可能な4-artifact persistence失敗後にorphan DB row / fileが残らない。
  • descriptorなし既存fixtureのexport / manifest hashが導入前から変わらない。
  • manifest / handoffはdescriptorだけを公開し、full ledgerをinlineしない。
  • single-target base queryがboundedで、unknown / truncated / invalidを明示する。
  • community lineageが同じresponseのvalidated projectionから取得できる。
  • NightWorkersがlegacy / new manifestとstrict bundle requirementsを処理し、既存manifest保存を維持しつつfull ledgerを複製しない。
  • raw evidence、artifact body、absolute path、secretのleak testがpassする。
  • baseline 7 CLI failureを解消またはowner承認済みの独立known issueへ分離する。
  • 関連test、typecheck、cross-repository fixture、docs checkがpassする。
  • performance / payload budgetを満たすevidenceが保存される。
  • rollback rehearsalとconsumer-first migrationが完了する。

Core DoDはSemantic Handoff ValidationまたはSecurity Vocabularyのprofileが未実装でも満たせる。 未実装profileは公開descriptorへ含めず、core coverageの分母にも入れない。

27.2 Semantic Validation Integration Definition of Done

  • owner承認済みvalidation profile、rule catalog、target / binding contractを参照している。
  • validation input / result / revisionのwhole-objectとrequired property bindingが100%である。
  • unknown profile / rule、valueHash mismatch、missing lineageでvalidation passへ補完しない。
  • producer / consumer fixtureがbyte-equivalentで、core-only rollbackがgreenである。
  • profile v1、既存validation result、core generation selectionのbytes / behaviorが不変である。

29. GO / NO-GO Gate

29.1 Core Provenance GO

  • producer / consumer ownerとsource-controlled rollout gate ownerが決まっている。
  • Slice 0 fixtureとtarget / property coverage matrixが承認されている。
  • shared contractとprofile v1 rule catalogが承認されている。

29.2 Semantic Validation Integration GO

  • Core Provenance DoDを満たし、required ledgerとconsumer readerが安定している。
  • Semantic Handoff Validation ownerがprofile ID、rule ID、target、required binding、severity / failure authorityを承認している。
  • unknown / partial / invalid lineage時のvalidation behaviorとrollback ownerが決まっている。
  • core-only / integrated両fixtureとcross-repository reader floorがgreenである。

29.3 NO-GO

  • source row / artifactからrequired targetへ安全なrefを作れない。
  • payloadとlineageを別passで推測する実装しか成立しない。
  • full ledgerをmanifestまたはNightWorkers eventへ複製する必要がある。
  • raw evidence / path / secretを保存しないとlineageを表現できない。
  • legacy 3-artifact generationを壊さずに4-artifact setへ移行できない。
  • missing required binding、hash不安定、性能超過がshadow qualificationで解消しない。
  • provenance availabilityだけでclaim truth、validation pass、security findingを確定する。
  • Semantic Validationのprofile / rule / failure effectが未確定のままintegration fieldを推測する。

30. Implementation Handoff

実装開始時はSlice 0だけを最初の作業単位とする。fixture、manual trace期待値、CLI baseline、NightWorkers consumer harnessがreviewされるまでSlice 1以降へ進まない。各Sliceは独立PRとし、Claim Provenance以外のontology計画を混ぜない。
