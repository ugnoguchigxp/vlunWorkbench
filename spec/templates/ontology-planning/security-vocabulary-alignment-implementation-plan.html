1. Purpose

scanner固有のrule、advisory、weakness、package identifierを、CWE、CVE、GHSA、CAPEC、OWASP Top 10、Package URL（purl）、CPEのversioned namespaceへ決定的に投影する。同じidentifierの表記揺れを吸収しつつ、findingへの分類、component identity、advisory alias、概念間alignmentを混同しないcontractを作る。

この計画はSecurity Vocabulary Alignmentだけを実装可能な粒度へ具体化する。Semantic Handoff Validation、Claim Provenance v1、ontology contract diff、competency question、rule inferenceの実装をやり直さない。Claim Provenance v1はpreceding planの成果物を前提とし、そのcontractを変更せず、接続だけを明示的なv2 profileとして扱う。

実装は四つのworkstreamへ分ける。Foundationはoffline registry、normalizer、identity、 unresolved preservationまで、PublicationはClaim Provenance v2とreader-first projection / descriptor / query、Candidate Communityはrouting / grouping候補、 Finding Dedupe v2はfinding identityを変え得る独立した高risk変更である。各workstreamは別DoD、 GO、rollbackを持ち、後二者を実装しなくてもcore vocabulary publicationを完了できる。

8. Semantic Model

8.1 Assignment Is Not Alignment

混同してはいけない4つの関係
Concept Example Contract
identifier normalization cwe_79 -> CWE-79 same identifierのcanonicalization
finding assignment finding F has weakness CWE-79 role=weakness
advisory alias GHSA-X and CVE-Y are aliases according to a source role=advisoryの複数assignment + source binding
concept alignment an OWASP category is broader than a CWE concept SKOS-inspired alignment relation

assignmentは「findingにどの役割でreferenceが付くか」を表す。alignmentは2つのconcept reference間の意味的な近さまたは広狭を表す。assignment methodがdeterministicでも、relationがexactになるわけではない。

  • exact_matchは同じ検索用途で置換可能なほど近い概念を表すが、object identityやowl:sameAsを意味しない。
  • close_matchは置換可能性を保証しない高い類似を表す。
  • broad_matchはtargetがsourceより広い概念であることを表す。
  • narrow_matchはtargetがsourceより狭い概念であることを表す。
  • related_matchは階層を主張しない関連を表す。

8.2 Reference Validation and Assignment Evidence

identifierの検証とfinding出典の強さを分離する
Axis Value Meaning Initial use
reference validation authority_snapshot pinned official catalog indexにidentifierが存在する。 CWE、CAPEC、OWASP
reference validation spec_validated pinned specification parserでcanonical formへ変換できた。 purl、CPE syntax
reference validation syntax_only syntaxは妥当だがauthority existenceをofflineで確認していない。 CVE / GHSA fallback、CPE dictionary未確認
assignment evidence source_asserted trusted scanner/advisory sourceがそのidentifierまたはaliasを明示した。 risk metadataのCWE / CVE / GHSA
assignment evidence registry_curated review済みmapping registry entryが明示的に参照した。 scanner rule mapping
assignment evidence deterministic_projection source fieldを決定的規則で変換したが、source自身のsemantic assertionではない。 rule ID syntax、package component projection

validationは共有referenceへ、evidenceはfindingごとのassignmentへ置く。同じCVE referenceをsource-asserted assignmentとsyntax-only由来のassignmentが共有しても、confidenceを混同しない。

9.2 Resolved and Unresolved Reference

const vocabularyReferenceIdSchema = z.string().regex(/^vr_[a-f0-9]{64}$/);
const unresolvedReferenceIdSchema = z.string().regex(/^vu_[a-f0-9]{64}$/);

const resolvedVocabularyReferenceSchema = z.object({
  status: z.literal("resolved"),
  referenceId: vocabularyReferenceIdSchema,
  namespace: vocabularyNamespaceSchema,
  identifier: z.string().min(1).max(2_000),
  canonicalUri: z.string().min(1).max(2_000),
  authorityKey: z.string().regex(/^[a-z0-9_.-]+$/),
  authorityRelease: z.string().min(1).max(100),
  validation: referenceValidationSchema,
  lifecycle: z.enum(["active", "deprecated", "reserved", "unknown"]),
}).strict();

const unresolvedVocabularyReferenceSchema = z.object({
  status: z.literal("unresolved"),
  unresolvedId: unresolvedReferenceIdSchema,
  rawNamespace: z.string().min(1).max(64).optional(),
  rawNamespaceHash: z.string().regex(/^sha256:[a-f0-9]{64}$/),
  rawIdentifier: z.string().min(1).max(200).optional(),
  rawValueFingerprint: z.string().regex(/^sha256:[a-f0-9]{64}$/),
  fingerprintMode: z.enum(["value_sha256", "source_scoped_redaction"]),
  normalizationVersion: z.string().min(1).max(100),
  reasonCodes: z.array(vocabularyReasonCodeSchema).min(1).max(8),
}).strict();
  • rawNamespaceHashは常に保持し、safe token patternと64文字上限を満たすnamespaceだけをliteralでも保持する。
  • safe token patternと200文字上限を満たすraw identifierだけをliteralで保持する。
  • rawIdentifierを省略できるのはempty、非string、制御文字、secret-like value、200文字超過の場合だけとし、reason codeと整合させる。出典はassignmentのfindingId / sourcePathsへ保持する。
  • secret-likeでないJSON valueは型を問わずshared/canonical-json.tsの出力をhashし、fingerprintMode=value_sha256とする。empty stringもcanonical JSON stringのsha256を使い、zero sentinelを導入しない。canonical化不能valueはsource_scoped_redactionへ送る。
  • secret-like valueは値自体をhashせず、findingId、sourcePath、rawNamespaceHash、normalizationVersionのdomain-separated hashを source_scoped_redaction fingerprintとして使う。同じsecretの辞書照合に使えるfingerprintを残さない。
  • resolved reference IDはnamespace、canonical identifier、authority key / releaseから生成する。
  • canonical URIをnetwork availabilityの保証として扱わない。

const vocabularyAlignmentSchema = z.object({
  alignmentId: z.string().regex(/^al_[a-f0-9]{64}$/),
  sourceReferenceId: vocabularyReferenceIdSchema,
  targetReferenceId: vocabularyReferenceIdSchema,
  relation: alignmentRelationSchema,
  method: z.enum(["source_declared", "registry_curated"]),

  • mappingEntryIdはsource tool / rule、role / target、relation / methodだけを含むsemantic content hashから作る。owner、reviewer、label、evidence URLは含めない。
  • registry_curated assignmentはmappingEntryIdを必須とし、それ以外のmethodではfieldを禁止する。
  • scanner_declaredはsource_asserted、registry_curatedはregistry_curated、component_projectionはdeterministic_projectionを要求する。deterministic_identifierはsource catalogに従い、semanticにtypedなadvisory fieldではsource_asserted、generic ruleId syntaxではdeterministic_projectionを使う。
  • alignmentのsourceとtargetが同じreference IDならinvalidとする。
  • 同じpair / relation / mappingEntryIdを重複させない。
  • inverse relationは自動materializeしない。query時にexact / close / relatedは同relation、broadとnarrowは相互inverseという固定catalogで両endpointを検索するが、responseはpersisted source / target / relationをrewriteせず返す。

  • 全alignment endpointはresolved referenceを指す。
  • unresolved referenceは少なくとも1 assignment、resolved referenceは少なくとも1 assignmentまたはalignmentから到達可能とする。budget適用後のorphanを禁止する。
  • assignment findingIdは同じexport graphに存在するfinding sourceIdを指す。
  • sourceTool / ruleIdは同じfinding nodeまたはpersisted source findingと一致する。
  • 全assignment / unresolved referenceのnormalizationVersionはprojection registry.normalizationVersionと一致する。
  • fingerprintMode=source_scoped_redactionはrawIdentifierを禁止し、sensitive_value_redactedまたはsource_value_unsupportedとexactly 1件・sourcePaths length 1のassignmentを要求する。value_sha256はsource-scoped inputを禁止する。
  • roleとnamespaceの組合せはprofile catalogで許可する。
  • sourcePathsはUTF-16 code-unit順、重複なしとする。これはsource locatorなのでarray indexを許可し、Claim Provenance target property pathとは別に検証する。
  • reference / assignment / alignment countとnamespace / role countは配列から再計算した値と完全一致する。
  • candidateAssignmentCount = assignmentCount + omittedAssignmentCount、candidateAlignmentCount = alignmentCount + omittedAlignmentCount、assignmentCount = resolvedAssignmentCount + unresolvedAssignmentCountとする。
  • discoveredCandidateCount = processedCandidateCount + omittedCandidateCountとする。
  • candidateAssignmentCountはraw candidate budget適用・normalize / merge後かつassignment budget前、candidateAlignmentCountはfinal assignment集合確定後かつalignment固有budget前の値とする。
  • coveredFindingCountはresolved assignmentを1件以上持つfinding、unresolvedFindingCountはresolvedを持たずunresolved assignmentを1件以上持つfindingを数える。uncoveredFindingCountは残りを数え、3集合は排他的で合計がfindingCountと一致する。
  • componentConflictFindingCountはdistinct resolved versioned purlを2件以上持つfindingから再計算し、1件以上ならstatus partial + component_identity_conflictを要求する。
  • zero finding exportはavailable、全count 0、reasonCodes空のprojectionを持てる。
  • unresolved reference、deprecated assignment、component conflict、budget omissionのいずれかがあればpartial + corresponding reasonを要求する。source_asserted CVE / GHSAのsyntax_only validationとCPE dictionary未導入は、それだけではpartialにしない。
  • partialは少なくとも1 reason codeを持ち、availableはreasonCodes空とする。
  • unresolved referenceはidentifier / source / parser系reasonだけ、projectionはidentifier_deprecated / component_identity_conflict / coverage / budget / claim系reasonだけ、missing / invalid descriptorはrollout / integrity系reasonだけを許可する。共通enumをそのまま全surfaceで受理しない。
  • registry_entry_invalid / registry_entry_conflict / registry_hash_mismatch / registry_release_unsupportedはpartial projectionへ入れず、registry loadまたはpublicationをinvalidにするfatal reasonとしてだけ使う。
  • 全配列はIDのUTF-16 code-unit順でcanonical sortし、duplicateを拒否する。
  • projectionHashはgeneratedAtとprojectionHashを除いたprojection全体から計算する。

11.2 Precedence and Conflict

extractorはcatalogに列挙したpointerだけを読み、1 findingあたり512 candidates、1 projection / grouping runあたり100,000 candidatesを上限とする。finding ID、catalog order、array indexの順で選び、超過分は値をmaterialize / hashせずcountだけ加算して candidate_budget_exceededでpartialにする。

  1. 同じfinding内のcandidateをsource pointer付きで全件抽出する。
  2. catalog対象valueにcanonical source pointerを作れない場合はunresolvedへ偽装せずprojection build errorにする。
  3. 各candidateをnamespace-specific normalizerへ渡す。
  4. resolved / unresolvedをdeduplicateせずsource assignmentとして保持する。
  5. 同一finding / role / reference / method / evidence / mappingEntryIdへの複数sourceは複数assignmentにせず、最大16件の sourcePathsへcanonical集約する。
  6. registry mappingとscanner-declared valueが異なるreferenceを示しても、role上複数値を持てるため自動的にconflict扱いせず、両assignmentをsource別に保持する。
  7. 同一referenceでもmethod / evidence / mappingEntryIdが異なれば別assignmentを維持し、curated値でscanner値を上書きしない。
  8. 例外として同一findingにdistinct resolved versioned purlが複数ある場合はcomponent_identity_conflictを付け、どれもsame_dependency / finding-dedupe-v2へ使わない。

sourcePathsが16件を超える場合はcanonical sort後の先頭16件をassignmentへ保持し、projectionをpartialにして source_path_budget_exceededを付ける。Claim Provenance recordでは完全なsource pointer集合へcommitするreference setを使い、assignment valueとlineageのsource coverageを別々に検証する。

raw valueのliteral / value-derived hash判定は、最大depth 8、256 container entries、各string 4,096 UTF-16 code units、canonical JSON UTF-8 8 KiBのbounded traversal内で行う。上限超過、cycle、non-plain object、unsupported scalarは値をhashせずsource_scoped_redaction + source_value_unsupportedへ送る。bounded valueでもsensitive key / token pattern検査をcanonical hashより先に行う。

12. Mapping Registry Lifecycle

12.1 Registry Shape

  • entry keyはexact sourceTool + exact ruleIdである。
  • tool / rule entry配下の各assignment / alignment itemが固有mappingEntryIdを持つ。1つのtool / rule entry全体へ同じIDを使い回さない。
  • regex、glob、substring mappingはprofile v1で禁止する。
  • registryはmappingRegistryVersionを、各entryはowner、reviewer、reviewedAt、evidenceRefsを持つ。
  • evidenceRefsはallow-listed HTTPS URLまたはrepository-relative fixture refだけを許可する。
  • fixture refはfixture:<canonical-posix-path>#<case-id>形式とし、absolute path、..、空segmentを拒否してCIで存在確認する。
  • entryはassignmentとoptional concept alignmentを別配列に持つ。
  • alignmentはmethodがsource_declaredでも必ずreview済みregistry entryを経由する。このmethodはevidence sourceがrelationを明示したことを表し、raw findingから無審査でalignmentを生成する許可ではない。
  • 1 entryはreview済みの複数targetを最大16件まで持てる。同じsourceTool / ruleIdのentry重複、同一semantic assignment / alignment重複、同じmappingEntryIdで異なるsemantic payloadはregistry load時に拒否する。

12.2 Review and Release

  1. mapping candidateと代表raw fixtureをPRへ追加する。
  2. schema、duplicate、authority membership、negative fixtureをCIで検証する。
  3. security normalization owner以外のreviewer 1名がrelationとroleを確認する。
  4. canonical JSON hashを更新し、semantic versionを上げる。
  5. baseline corpusでassignment diffとcommunity diffを生成する。
  6. unexpected mergeまたはexact relation増加があればreleaseを停止する。

owner / reviewer / evidenceRefsだけが変わりmapping semanticsが同じ場合もmappingRegistryVersion / hashを更新するが、mappingEntryIdは維持する。既存generationを再解釈せず、新generationでのみ新hashを使う。

12.3 Authority Snapshot Maintenance

  • maintenance commandは明示実行のみとし、application buildやqueryから呼ばない。
  • download URL、取得時刻、HTTP metadata、raw sha256、parser version、output index hashをreceiptへ記録する。
  • minimal indexはidentifier、lifecycle、canonical label hashだけを含み、full descriptionを含めない。
  • release diffでadded、deprecated、removed、status-changed countを出す。
  • receipt / label hash / lifecycleだけの変更はauthorityRegistryVersion / hashを更新する。authority semantic releaseが同じなら既存resolved reference IDは維持する。
  • removed identifierを即dropせず、新snapshotでdeprecated / unresolvedになる影響をreviewする。

assignment / registry_curated deterministic_derived static_intelligence.vocabulary.registry_curated.v1 finding tool / rule、mapping receipt、authority release

vocabulary recordのsourceRefsはfinding rowと、curated mappingの場合だけregistry receiptを持つ。inputRefsはsource JSON pointerとauthority release refを持つ。raw metadata bodyやfull registry entryをledgerへコピーしない。

全vocabulary recordはdeterministic_derivedとし、inputRefsを1件以上要求する。confidenceは付けず、coverageは参照したsource pointer / mapping evidence集合が完全ならcomplete、reference_setへcommitできない場合だけpartialとする。

base ledgerの100,000 record / 100,000 binding上限に対し、persist前に既存v1 countへassignmentとalignmentそれぞれ1件あたりrecord 1件 + whole-object binding 1件を加えて検査する。assignmentを先に選択し、alignmentは残存capacity内で選ぶ。超過分は決定的に切り詰めてprojectionをpartialにし、persistしたassignment / alignmentについてrecordまたはrequired binding欠落が1件でもあればpublishしない。

same_cwe / same_cve / same_dependency community lineageはpreceding planどおりbase ledgerへ入れず、community responseのClaim Provenance query-time projectionへ追加する。projectionの2,000 record / 2,000 binding上限を超えてもbase ledgerやvocabulary descriptorを変更せず、community lineageだけをpartial + query_truncatedにする。

capacity計算とtruncationはprojectionHash / exportHashを確定する前のbuild phaseで行う。persisterは完成済みprojectionを追加で切り詰めず、planned assignment / alignment / record / binding countとfinal ledger countの不一致をintegrity failureとして拒否する。

15.3 Provenance Gate

  • Claim Provenance v2 readerがない環境ではvocabulary writerをoffのままにする。
  • shadow buildはpure projectionを評価できるが、revision-backed descriptorをpublishしない。
  • publishEnabled=trueはvalid v2 ledgerと、budget適用後にpersistした全vocabulary assignment / alignmentに対するrequired binding coverage 100%を要求する。raw candidate coverage 100%を意味しない。
  • vocabulary partialだけで既存v1 ledgerをinvalidにしない。v2 capabilityだけをpartialにする。
  • v2 ledgerを1件でもpersistした後はv1-only provenance readerへrollbackしない。

16. Generation Lifecycle and Rollout

16.1 Reader-first Compatibility

現行generation loaderはexport JSONをZod parseした後にexport hashを再計算する。旧schemaはunknown fieldをstripするため、新writerがsecurityVocabularyを追加すると旧readerはhash mismatchとしてgenerationを拒否する。このためoptional fieldでもreader-first releaseが必須である。

  1. new readerがoptional envelopeをparse・保持し、legacy exportも同じhashで読めるようにする。
  2. writer offのままreaderをproductionへdeployする。
  3. rollback floorのversion / commitをrelease evidenceへ記録する。
  4. その後だけwriter shadowを有効化する。

16.2 Generation Marker

  • summary.securityVocabularyRegistryInputHashと summary.securityVocabularyProjectionHash、 summary.securityVocabularyAssignmentCount、 summary.securityVocabularyAlignmentCountをscalarで置く。

  • reference focusのalignmentはfocus endpointへ接続するもの、finding focusのalignmentは当該findingのassignmentが参照するresolved endpointへ接続するものだけを返す。
  • reference focusがprojection内で一致した場合はrowが0件でもfocus referenceをreferencesへ1件含め、一致しない場合だけreferenceId=null + 全配列emptyにする。
  • lineageは返したassignment / alignmentだけのbounded Claim Provenance projectionとし、empty resultでもvalid empty projectionを返す。
  • vocabulary assignment / alignment lineageはprofile v2だけを返す。v1 ledgerからlineageを推測・合成しない。
  • raw reference inputをresponseへechoせず、focusにはcanonical identifierと、projectionで一致した場合だけreference IDを返す。
  • descriptorがpartialならprojectionStatusもpartialを維持し、availableへ昇格しない。

24. Security, Privacy, Performance, and Observability

24.1 Security and Privacy

  • external URI template originをallow-listし、query時fetchを禁止する。
  • mapping registryのarbitrary path、command、template interpolationを禁止する。
  • raw namespace / identifierをsecret classifierとlength / character gateへ通し、secret-like valueは値由来hashも残さない。
  • absolute project path、artifact body、evidence snippetをprojectionへ含めない。
  • query inputをlogへliteral出力せず、namespaceとidentifier hashだけをtelemetryへ送る。
  • snapshot maintenance downloadをchecksum / content-type / maximum bytesで制限する。
  • full catalog license / attribution requirementをrelease reviewへ含める。

24.2 Performance Budgets

  • raw candidateをper finding 512 / per build 100,000で打ち切り、bounded traversal外のvalueをserialize / hashしない。
  • normalizationはfinding + raw candidate数に対してO(n)、registry lookupはO(1) mapとする。
  • payload size selectionはcanonical prefixのbinary searchでO(n log n)以下とし、1件ずつ再serializeするO(n²) truncationを禁止する。
  • community groupingはreference IDごとのbucketでO(assignments log assignments)以下とする。
  • representative corpusのp95 build overheadを500 ms以下にする。baseline p95が5秒以上のcorpusでは、これに加えてtotal p95をbaselineの1.10倍以下にする。短時間fixtureの比率は判定に使わない。
  • securityVocabulary envelopeは4 MiB、manifest descriptor deltaは4 KiB以下にする。
  • query p95はlocal artifact load込み500 ms以下、response 1 MiB以下をqualification targetにする。
  • authority indexesはprocess単位でimmutable cacheし、requestごとに再parseしない。

24.3 Observability

  • projection status、duration、bytes、registry input hash prefix
  • namespace別resolved / unresolved / deprecated count
  • discovered / processed / omitted candidate count、component conflict finding count、omitted assignment / alignment count、Claim record / binding remaining slots
  • reason code別failure count
  • new community basis別count / average size / max size
  • dedupe v1 / v2 same / different / ambiguous diff count
  • v2 grouping registry input hash prefix、identity projection failure count、v2 snapshot reuse / rebuild count
  • publication invalid、query 400 / 404 / 409、cursor invalid count
  • identifier literal、raw mapping content、full hashesをmetric labelにしない。

25. Rollback Plan

25.1 Triggers

  • unexpected finding mergeが1件以上
  • old / new readerのexport hash mismatch
  • registry conflictまたはauthority snapshot corruption
  • manifest / NightWorkers schema rejection
  • raw secret / absolute path / unbounded external content exposure
  • build / payload / query budget超過
  • v2 provenance assignment / alignment coverage欠落
  • v2 grouping runのregistry context欠落またはfinding set hash不一致

25.2 Rollback Order

  1. finding-dedupe-v2 promotionをoffへ戻し、v1 selectionへ戻す。
  2. candidate community promotionをOFFにし、legacy community basis / orderingへ戻す。vocabulary projectionとexact queryは維持する。

  4. projectionModeをshadowへ戻し、evidence採取を継続する。
  5. 必要ならprojectionModeをoffへ戻し、legacy export generationを再開する。
  6. NightWorkersのoptional consumer toleranceとproducer reader floorは残す。
  7. 既存vocabulary-enabled generationとv2 ledgerを削除・書換えず、read-only evidenceとして保持する。

new exportまたはv2 ledgerをpersistした後、producerをSlice 2より前へrollbackしない。authority / mapping registryだけを旧versionへ戻す場合も、新generationとして再buildし、既存generationを再解釈しない。
