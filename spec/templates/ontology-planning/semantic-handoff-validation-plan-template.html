Semantic Handoff Validation Plan Skeleton

  • Status: Candidate plan skeleton / not approved for implementation
  • Priority candidate: P0
  • Primary owner candidate: vulnWorkbench static-intelligence producer
  • Semantica clue: SHACL generation and ontology validation lifecycle
  • Detailed plan: Semantic Handoff Validation Implementation Plan

1. Purpose

ontology handoffを公開する直前に、JSON shapeだけでは検出できないgraph-wideな意味制約を検証し、 machine-readableな違反一覧をproducerとconsumerへ返す。

2. Current Evidence

  • shared/schemas/static-intelligence.schema.tsはnode / edgeの型をZodで検証する。
  • 現状はedge endpointの実在、domain / range、ID一意性をschema contractとして包括検証しない。
  • api/modules/static-intelligence/evidence-graph.tsはdeterministic graphを生成する。
  • ontology-handoff.tsとmanifestはhash、generation、source refを既に持つ。
  • semantic-query.tsの結果はcandidateOnly: trueである。

3. Scope

  • node IDとedge IDの一意性、およびedge endpointの参照整合性
  • edge kindごとの許可されたsource / target kind
  • evidence、artifact、module、source refの存在とrevision整合性
  • semantic-only candidateがconfirmed / observedへ昇格していないこと
  • manifest generation、content hash、freshness、readinessの整合性

3.1 Non-goals

  • RDFをcanonical storageへすること、triple storeを導入すること
  • vulnWorkbenchへcanonical ontology ownershipを移すこと
  • scanner adapterまたはfinding detection logicを変更すること

4. Contract Sketch

type ValidationViolation = {
  code: string;
  severity: "error" | "warning";
  focusRef: string;
  path?: string;
  message: string;
  sourceRefs: string[];
};

type ValidationReport = {
  conforms: boolean;
  ontologyContractVersion: string;
  violations: ValidationViolation[];
  checkedAt: string;
};

report shapeは W3C SHACL のconformance / result modelを参考にするが、初期実装をRDFへ拘束しない。

5. Implementation Options

  1. A: TypeScriptの専用validatorでgraph-wide ruleを明示する。
  2. B: JSON Schema / Zodへcustom semantic rule registryを追加する。
  3. C: JSONをRDFへexportするadapterを作り、SHACL engineを検証用途だけに使う。

初期候補はA。Cはinteroperability需要が確認された後のadapter候補とする。

6. Verification and Exit Evidence

  • 各ruleにvalid / invalid fixtureを1件以上持つ。
  • 同一inputとversionから同じreport orderingとhashが得られる。
  • error時はhandoff publishを止め、warning時の挙動はpolicyで固定する。
  • NightWorkersが未知のviolation codeを安全に表示または無視できる。
  • 既存wire contractとの互換性とperformance budgetを記録する。

7. Open Questions

  • publishを止めるerrorと、診断だけを出すwarningの境界は何か。
  • domain / range ruleはどのpackageを正本にするか。
  • consumer固有ruleをproducer validationへ含めるか、consumer側へ分離するか。
  • SHACL export adapterを必要とする具体的consumerは存在するか。

8. Next Discovery Checklist

  • 現行graph fixtureから想定違反を棚卸しする。
  • node / edge kindのdomain-range matrix案を作る。
  • validation reportをhandoffへ追加した場合のNightWorkers compatibilityを調べる。
  • prototype前にGO / NO-GOとrollback条件を決める。
