Claim Provenance Plan Skeleton

  • Status: Candidate plan skeleton / not approved for implementation
  • Priority candidate: P0
  • Primary owner candidate: fact producer for observed lineage; inference owner for derived lineage
  • Semantica clue: entity / relationship / property-level lineage and confidence

1. Purpose

node、edge、community、将来のderived claimが、どのsource、revision、generator、ruleから生じたかを consumerが機械的に追跡できるようにする。説明可能性だけでなく、stale判定、再計算、監査の基礎にする。

2. Current Evidence

  • manifestとontology handoffはsource ref、generation、content hashを持つ。
  • evidence graphはdeterministicだが、各edge / communityの導出ruleを統一contractで公開していない。
  • 長期ロードマップはObservedClaimにsource、confidence、coverage、validForRevisionを要求する。
  • NightWorkers側の将来contractにもgeneric provenance recordのseedがある。

3. Scope

  • observed、deterministic derived、semantic candidate、LLM interpretationの区別
  • producer / generator nameとversion、rule ID、source artifact / entity reference
  • generatedAt、validForRevision、confidence、coverageの表現
  • 同一provenanceのdeduplicationとcanonical hashing

3.1 Non-goals

  • confidenceをtruth scoreとして使うこと
  • LLM解釈を宣言済みまたは観測済みclaimへ自動昇格すること
  • PROV-O準拠のためだけにstorageをRDFへ変更すること

4. Contract Sketch

type ClaimProvenance = {
  provenanceId: string;
  assertionKind:
    | "observed"
    | "deterministic_derived"
    | "semantic_candidate"
    | "llm_interpretation";
  generator: { name: string; version: string; ruleId?: string };
  sourceRefs: string[];
  generatedAt: string;
  validForRevision: string;
  confidence?: number;
  coverage?: { kind: string; value: number };
};

role namingとlineage関係は W3C PROV-O を参照する。ただしwire contractはこのプロジェクトのJSON利用者を優先する。

5. Implementation Options

  1. A: node / edge / claimへ共通provenance fieldをinlineで持たせる。
  2. B: normalized provenance ledgerをmanifestへ置き、各対象はID参照する。
  3. C:内部JSONを維持し、PROV-O export adapterを別途提供する。

Bを基本候補とし、payload sizeと参照解決コストをfixtureでAと比較する。

6. Verification and Exit Evidence

  • すべてのderived edge / community / claimからsourceまで辿れる。
  • 同一input、generator version、ruleからprovenance IDとhashが決定的に生成される。
  • revision不一致とsource欠落をvalidationが検出する。
  • model-facing projectionへsecret、不要なabsolute path、raw sensitive dataを出さない。
  • confidence欠落と0を区別し、値の意味をproducer単位で定義する。

7. Open Questions

  • edge生成ruleとcommunity生成ruleを同じprovenance typeで表せるか。
  • sourceRefsはentity ID、artifact path、content hashのどれを必須にするか。
  • provenance ledgerのretentionとredaction ownershipはどこか。
  • producer間でconfidence scaleを共通化するか、opaqueに扱うか。

8. Next Discovery Checklist

  • 現行manifest / graph / community fieldのlineage coverage表を作る。
  • 典型finding 3件をsource artifactまで手作業でtraceし、不足fieldを記録する。
  • inlineとledgerのpayload / lookup比較を行う。
  • PROV-O exportが必要なconsumerを確認してからadapterを判断する。
