Competency Question Evaluation Plan Skeleton

  • Status: Candidate plan skeleton / not approved for implementation
  • Priority candidate: P1 cross-cutting; baseline work may start before other P1 plans
  • Primary owner candidate: ontology contract / consumer integration maintainers
  • Semantica clue: competency question registry and ontology quality evaluation

1. Purpose

ontologyを「大きいgraph」や「新しいschema」で評価せず、consumerが必要な問いへ正確・決定的・ provenance付きで答えられるかをregression suiteにする。他の5計画の価値判定にも共通利用する。

2. Current Evidence

  • semantic queryは候補検索を提供するが、answerabilityをproduct contractとして測っていない。
  • read model resolverはreadinessを返せるため、回答不能理由を区別する土台がある。
  • graph、community、manifest、handoffに個別testはあるが、consumer question単位の横断評価は限定的である。
  • Semanticaのcompetency question機能は参考になるが、現行実装の単純なkeyword判定をacceptance根拠には使わない。

3. Scope

  • question ID、対象persona、必要fact、期待回答、許容不能理由のregistry
  • golden project / scan fixtureと期待provenance
  • exact queryまたはdeterministic evaluatorによるanswerability判定
  • coverage、orphan reference、freshness、candidate leakage、latencyのmetric
  • contract変更前後のregression report

3.1 Non-goals

  • 自然言語keyword matchだけで回答可能と判定すること
  • LLMの流暢さをontology correctnessの代理metricにすること
  • すべての将来queryを初回から列挙すること

4. Initial Competency Questions

  1. このfindingを支持するevidence、scanner、artifactは何か。
  2. このfindingが影響するmoduleまたはfileは何か。根拠は何か。
  3. この関係はobserved factか、deterministic derivedか、semantic candidateか。
  4. 欠落、stale、revision不一致のevidenceはあるか。
  5. 2つのscan revision間で、何が追加・削除・変更されたか。
  6. 同じCWE / CVE / dependencyに属するfindingは何か。そのmapping strengthは何か。

5. Evaluation Sketch

type CompetencyQuestionCase = {
  id: string;
  question: string;
  fixtureRef: string;
  requiredFacts: string[];
  expectedAnswerRefs: string[];
  expectedProvenanceRefs: string[];
  allowedUnavailableReasons: string[];
};

metric候補はanswerability rate、provenance coverage、false confirmation count、orphan count、p95 query latencyとする。

6. Implementation Options

  1. A: TypeScript fixtureと既存query APIを使うdeterministic test suite。
  2. B: machine-readable question catalogと複数consumer adapter。
  3. C:自然言語questionを補助的に評価するLLM judge。正本判定には使わない。

Aでbaselineを作り、複数consumerが必要になった段階でBへ広げる。

7. Verification and Exit Evidence

  • 各questionがexpected answerだけでなくprovenanceとassertion kindも検証する。
  • unknown / not-ready / absent / staleを混同しない。
  • semantic candidateがconfirmed answerへ混入するnegative fixtureを持つ。
  • contract変更PRでbefore / after結果を再現できる。
  • metric改善がpayload増加やlatency悪化を隠さない。

8. Open Questions

  • 最初のpersonaは人間reviewer、coding agent、NightWorkersのどれか。
  • expected answerをentity IDで固定するか、semantic propertyで固定するか。
  • fixtureをsyntheticとreal sanitized caseのどちらで構成するか。
  • answerabilityをrelease gateへ昇格する閾値は何か。

9. Next Discovery Checklist

  • 上記6問を現行APIで手動回答し、欠落factと探索手順を記録する。
  • 現行baselineのanswerability / provenance coverageを測る。
  • P0計画で追加するfieldがどのquestionを改善するかmatrix化する。
  • release gate化はbaselineと安定性を確認してから判断する。
