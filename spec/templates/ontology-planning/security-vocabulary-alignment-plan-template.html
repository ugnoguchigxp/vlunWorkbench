Security Vocabulary Alignment Plan Skeleton

  • Status: Candidate plan skeleton / not approved for implementation
  • Priority candidate: P1
  • Primary owner candidate: vulnWorkbench normalization boundary
  • Semantica clue: explicit namespace management and ontology alignment

1. Purpose

scanner固有identifierを、CWE、CVE、CAPEC、OWASP、purl、CPEなどのsecurity vocabularyへ version付きで対応づける。同値と類似を区別し、grouping、query、consumer projectionの意味を安定させる。

2. Current Evidence

  • landscape schemaはsame_cwe、same_cve、same_dependencyを宣言する。
  • 現行community builderは主にsame_file、same_scanner_rule、same_scanner、graph_connected、semanticを生成する。
  • 宣言済みのrisk basisと実装済みnormalization / groupingの間に差がある。
  • scanner出力には外部identifierが存在しても、そのauthority、version、match strengthが統一されていない。

3. Scope

  • namespace、identifier、authority version、canonical URIのregistry
  • exact_match、close_match、derived_matchの区別
  • scanner固有rule IDから外部vocabularyへのversioned mapping
  • unknown / unresolved identifierを失わないnormalization
  • CWE / CVE / dependency単位のgroupingを有効化する条件

3.1 Non-goals

  • embedding similarityだけでexact equivalenceを確定すること
  • runtime中に外部network lookupを必須化すること
  • すべてのscanner ruleを初回から網羅すること

4. Contract Sketch

type VocabularyReference = {
  namespace: "cwe" | "cve" | "capec" | "owasp" | "purl" | "cpe" | string;
  identifier: string;
  authorityVersion?: string;
  canonicalUri?: string;
  matchRelation: "exact_match" | "close_match" | "derived_match";
  mappingVersion: string;
  provenanceRef: string;
};

5. Implementation Options

  1. A: repository管理のversioned mapping registryをnormalizerから参照する。
  2. B: scanner adapterごとにmappingを持ち、共通contractへ出力する。
  3. C:外部knowledge sourceをbuild時にsnapshotし、offline registryを生成する。

Aを中心に、scanner固有の抽出だけをBへ残す構成を初期候補とする。

6. Verification and Exit Evidence

  • 同一raw identifierとmapping versionから同一referenceが得られる。
  • unknown identifierをdropせず、raw valueとprovenanceを保持する。
  • exact / close / derivedの誤昇格をnegative fixtureで検出する。
  • 同一findingのscanner差を吸収できる代表corpusを用意する。
  • 現行wire contract、grouping ordering、content hashへの影響を記録する。

7. Open Questions

  • authority versionをfinding観測時とmapping更新時のどちらへ固定するか。
  • deprecated / split / merged identifierをどう表すか。
  • CVE不在のscanner ruleをCWE / CAPECへ対応づけるreview processは誰が持つか。
  • purl / CPEのcomponent identityと現行dependency identityをどう接続するか。

8. Next Discovery Checklist

  • 各scannerのraw identifier fieldと現行coverageを棚卸しする。
  • CWE、CVE、dependencyから各10件程度のgolden fixtureを選ぶ。
  • 現在未実装のsame_cwe / same_cve / same_dependencyが必要なqueryを確認する。
  • mapping review、release、rollbackのownerを決める。
