Explainable Rule Inference Plan Skeleton

  • Status: Candidate plan skeleton / not approved for implementation
  • Priority candidate: P2
  • Primary owner candidate: NightWorkers task / run scoped consumer
  • Semantica clue: bounded forward / backward rules, Datalog-style inference, explanations

1. Purpose

validatedされたobserved factから、taskに必要な少数のderived claimだけを決定的に生成し、 rule ID、premise、confidence、説明を返す。NightWorkersの既存boundary / verification選択を補助する。

2. Current Evidence

  • vulnWorkbenchはtask-neutralなobserved structure / security factのproducerである。
  • NightWorkersは.agent-ontologyとruntime logicでmodule、boundary、verificationを決定的に扱う。
  • 長期ロードマップはinferred claimにrule、input refs、confidenceを要求し、declaredへの自動昇格を禁じる。
  • Semanticaは豊富なreasonerを提供する一方、すべてをこの用途へ導入する根拠はまだない。

3. Scope

  • allowlistされた少数のside-effect-free rule
  • rule version、premise refs、conclusion、confidence、human-readable explanation
  • task / run / repository revisionでboundedなevaluation
  • contradiction、unknown、not-ready、candidate inputの扱い
  • iteration / result count / latencyのhard limit

3.1 Non-goals

  • Semantica runtimeや全reasonerを本番dependencyとして一括導入すること
  • inferred claimからcanonical declarationを自動更新すること
  • LLMにrule truthやpremise selectionを委ねること
  • vulnWorkbenchへtask policyを持ち込むこと

4. Initial Rule Candidates

  • affectsModule: findingのlocated fileとmodule membershipが揃う場合だけ導出する。
  • artifactBacked: findingからevidence / artifactへの完全なtraceがある場合だけ導出する。
  • requiresReview: severity、evidence completeness、task policyの明示条件から候補化する。

現行graphのverified_byはscan runからverificationへの関係であるため、 finding単位のverified conclusionは対応contractが導入されるまでrule候補にしない。

5. Contract Sketch

type InferenceResult = {
  conclusion: { subjectRef: string; predicate: string; objectRef: string };
  ruleId: string;
  ruleVersion: string;
  premiseRefs: string[];
  confidence?: number;
  explanation: string;
  status: "candidate";
};

6. Implementation Options

  1. A:既存NightWorkers runtimeへtyped forward-chain rule evaluatorを追加する。
  2. B:安全なDatalog subsetを定義し、declarative rule fileとして評価する。
  3. C:Semantica bridgeを実験adapterとして比較し、runtime dependencyにはしない。

Aで3 rule以下の価値を検証し、rule authoring需要が確認された場合だけBを評価する。

7. Verification and Exit Evidence

  • 同一fact、rule version、task contextから同一result orderingが得られる。
  • すべてのresultに存在するpremise refsと説明がある。
  • semantic-only candidateをpremiseに使うruleは明示的opt-inとし、confirmedへ昇格しない。
  • max iteration、max result、timeoutにより停止性を保証する。
  • contradictionと欠落factを黙ってtrueにしない。
  • 既存module / boundary / verification behaviorの非劣化をfixtureで確認する。

8. Open Questions

  • 最初のruleが実際に削減する探索または判断コストは何か。
  • rule repositoryとapproval ownerはNightWorkers内のどこか。
  • confidenceを計算する必要があるか、deterministic true / unknownで十分か。
  • derived claimをrun終了後に保持するか、再計算可能なcacheに留めるか。

9. Next Discovery Checklist

  • NightWorkersの現在のmodule / boundary / verification logicと候補ruleの重複を確認する。
  • 1つのreal task fixtureで手動premise / conclusion traceを作る。
  • P0 validation / provenanceがrule premiseを十分に支えるか確認する。
  • Semantica比較は同一fixtureでの説明性と運用コストに限定する。
