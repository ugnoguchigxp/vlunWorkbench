1. Purpose

Static Intelligenceのwire schema version、generation identity、export / content hashとは別に、consumerが依存するontologyの意味面を明示的なcontractとしてversion管理する。entity kind、edge kind、field、identity、constraint、validation rule、claim rule、security vocabulary semanticsの変更を、不変snapshotとcanonical diffで説明できる状態を作る。

この計画はOntology Contract Versioningだけを実装可能な粒度へ具体化する。先行3計画が所有するvalidator、claim ledger、vocabulary registryを再実装しない。先行contractのimmutable profileを参照し、profileの追加・削除・意味変更がontology contractへ与える影響だけを分類する。

実装は二つのtrackへ分ける。Bootstrap trackは現行production-visible contractだけをinventoryし、snapshot、hash、diff、version policyをproduct path外で完成させる。 Publication / Enforcement trackはconsumer reader、generation descriptor、release governanceを追加する。Bootstrapは先行profileの実装を待たずに完了できるが、PublicationはStage 0 GO、baseline test green、consumer release windowを必須とする。

2. Target Outcome

source-controlled semantic catalogs
  -> build a normalized ontology contract snapshot
  -> validate stable element IDs and bounded semantics
  -> serialize with one canonical JSON profile
  -> hash a MAJOR.MINOR.PATCH candidate
  -> diff the registry head and candidate by stable element ID and semantic path
  -> derive required version bump from fixed reason codes
  -> verify declared version, deprecation policy, readers, approvals, and evidence
  -> stage immutable snapshot / coverage inventory / diff / evidence
  -> publish with registry-last commit point
  -> verify the published release in CI
  -> publish a bounded descriptor with each new generation
  -> let each consumer evaluate an explicit support policy
  -> retain exact historical readers; never rewrite old generations in place

Bootstrap trackの完了時点では、次の限定されたoutcomeを得る。

current production-visible schemas / builders / consumer fixtures
  -> closed coverage inventory
  -> baseline 1.0.0 candidate snapshot
  -> canonical hash and deterministic diff
  -> read-only verification in CI
  -> no descriptor publication and no persisted payload change

Publication / Enforcement trackは、bootstrap artifactとowner承認済みactive profileだけを入力にし、 reader-first、shadow、optional、requiredの順で進める。planned profileを推測でsnapshotへ追加しない。

  • 同じcatalog inputからbyte-identical snapshot、hash、diffを生成する。
  • 同じversionに異なるsnapshotを登録できず、公開済みsnapshotを上書きできない。
  • contract hashの差を、決定的なchange listと必要なSemVer増分へ解決できる。
  • unknown major、未対応profile、required capability欠落は推測せずfail closedにする。
  • legacy generationは限定した移行期間だけpre-descriptor-wire-v1としてdegradedに扱い、未証明のsemantic versionを割り当てない。new writerではdescriptorを必須にする。
  • NightWorkersを先にlossless readerへ更新し、producer descriptor publishはその後に開始する。

4. Fixed Decisions

  1. Bootstrap trackとPublication / Enforcement trackは独立したmerge / revert単位にする。Bootstrap completionはwire、artifact metadata、DB、manifest、handoff、NightWorkers runtime behaviorを変更しない。
  2. Semantic Handoff Validation、Claim Provenance、Security Vocabularyの未実装profileはplanned sourceとし、 owner contract、immutable catalog view、positive / negative fixtureが揃うまでactive adapterを作らない。
  3. Bootstrap trackではconsumer support window、deprecation telemetry、remote commit approvalをproduction gateにしない。これらはPublication trackのevidenceと実consumer運用に基づいて確定する。
  4. 初期実装はvulnWorkbench repo内のlibraryとsource-controlled release artifactで行う。共有packageはStage 3 entry gate後、独立serviceはStage 4 mandatory trigger後に再評価する。
  5. ontology contractは生成dataではなく、consumer-visibleな意味面の集合である。finding件数、graph instance、registry receipt、timestamp、deployment metadataはsnapshotへ含めない。
  6. baseline semantic versionは1.0.0とする。wireのv1、descriptor schemaのv1、semantic versionの1.0.0を別fieldとして保持する。
  7. snapshotはZod schemaをruntime introspectionして作らない。enum / profile constantはZodとcatalogで同じreadonly constantを正本とし、field semanticsは明示catalogとschema mutation fixtureを同じreview単位で管理する。
  8. element IDはversionを含まない。renameは旧IDのdeprecationと新IDのadditionで表し、同じIDへ別の意味を再割り当てしない。
  9. change type、compatibility、required SemVer bumpを別fieldにする。最終bumpは全changeの最大impactから機械導出し、author入力で弱められない。
  10. consumerはSemVerのmajor一致だけではacceptしない。tested range、descriptor profile、required capability、referenced profileを全て評価する。
  11. historical generationはversion固有readerで読む。既存generationへのcontract descriptor追加、hash再計算、data migrationを行わない。
  12. shadow modeはcontractをmemory内で計算・検証し、bounded metrics / logだけを残す。artifact metadata、export、manifest、handoff、DBへdescriptorやmarkerを永続化しない。
  13. contract snapshot / diffのcanonicalizationにはshared/canonical-json.tsを使う。既存exportHash / contentHashの実装置換はgolden parityが証明されるまで別変更として扱う。
  14. rollout policyはtarget contract version / hashをexactにpinする。registryのlatest、request parameter、environment variableからtarget releaseを暗黙選択しない。
  15. catalog sourceはsource-controlledなclosed registryへ静的登録する。file存在確認、directory scan、dynamic import、実装順による自動参加を禁止し、active sourceのadapter欠落はbuild failureにする。
  16. checked-in contract JSONはbyte上限を確認した後、duplicate-key-aware parserで読む。 JSON.parse後の再serializeだけでduplicate keyを検出できるとはみなさない。
  17. registry内部の自己整合性に加え、PR base commitとのappend-only history比較をrequired checkにする。hashを再計算して過去releaseを書き換える攻撃・事故をcandidate単体の検証だけで見逃さない。

8.1 Contract Inclusion Rule

「consumerのcontrol flow、identity、validation結果、projection結果、または意味解釈が変わるか」をinclusion testとする。yesならsemantic elementとしてsnapshotへ含め、noならoperational metadataとして除外する。

  • Include: node / edge kind、field presence / type / enum、identity input、canonicalization rule、endpoint constraint、validation severity、claim target / rule、vocabulary role / relation、fail-safe status、capability contract
  • Exclude: generatedAt、owner名、reviewer名、説明文、evidence URL、registry取得時刻、HTTP metadata、counts、instance IDs、raw graph data、deployment fingerprint
  • Conditional: registry schemaやnormalization algorithmは含めるが、同じ意味を保ったauthority snapshot / mapping receiptの更新は含めない。

8.2 Wire-only Change

JSON envelope、field名、serialization placementだけが変わり、§8.1のmeaning-bearing surfaceが不変ならontology contract releaseを作らない。wire profileを別versionへ上げ、lossless readerを先行配備し、runtime descriptorのwireProfilesだけを切り替える。descriptor v1のliteral profile IDでは新wireを表せないため、その場合はdescriptor v2のreaderも先行配備する。descriptor field 自身を既存wireへ追加するbootstrapもこの扱いとし、baseline ontology contract 1.0.0を不要に1.1.0へ上げない。

wire-only変更とsemantic変更を同じreleaseで行う場合は両方のgateを満たす。wire profileが対応済みでもsemantic version / hashがunknownならacceptせず、semantic contractが既知でもwire profileがunsupportedならacceptしない。

candidate treeだけのschema / hash検証では、過去snapshotを書き換えてregistry hashも再計算する変更を検出できない。 そのため全PRで、CIが明示するlocal base commitとcandidate working treeを比較するappend-only verifierを実行する。

  1. --base-commitは40 / 64 lowercase hexだけを受け、local objectとして存在し、candidate HEADのancestorであることを確認する。environment variable、remote latest、network fetchから暗黙選択しない。
  2. base側のregistry / snapshot / inventory / diff / evidence bytesはgit show相当のread-only object accessで読む。checkout切替やworking tree mutationを行わない。
  3. base / candidateの両方にregistryがない期間はpre_bootstrapとし、release / diff / evidence artifactがまだ0件であることを要求する。Bootstrap B1 / B2のpure implementation PRだけに許可し、一度でもregistryがbaseに現れた後はこのmodeへ戻れない。
  4. 通常PRではbase registryとcandidate registryをbyte-identicalにし、全historical artifactの変更・削除・renameを0件にする。 current catalogがregistry tail snapshotと異なる場合はcandidate releaseを同じPRへ含めない限りfailする。planned-only registry metadataのようにnormalized snapshotへ影響しない変更はこの差分へ数えない。
  5. release PRではcandidate registryがbase entriesを同順・同値のprefixとして保持し、exactly 1 tail entryだけを追加することを要求する。過去artifactはbyte-identical、新規snapshot / coverage inventory / adjacent diff / release evidence / qualification fileだけをtail entryのversion-derived pathへ追加できる。
  6. bootstrapはbaseにcontract registryが存在せず、candidateが1.0.0の1 entryだけを持つ場合に限定する。 baseに一部artifactが存在するambiguous状態は自動採用せずfailする。
  7. verifier outputはmode、base / candidate registry hash、added paths、historical mutation count、verified release versionを持つbounded JSONとし、historical mutationが1件でもあればexit 2にする。

registry fileのcandidate replaceがreleaseのpublication commit pointである。snapshot / diff rename後のcrashで 未参照fileが残ってもreaderは公開releaseとして扱わず、§17のreviewed recovery手順でだけ除去する。 複数file更新全体をfilesystem atomicと呼ばない。

10. Canonicalization and Hashing

  1. raw file sizeをparse前に検証し、4 MiBを超えるsnapshot / inventory / diff / registry / evidence inputを拒否する。
  2. tokenizer段階でnesting depth 64、document token 1,000,000、single object key 1,024を上限にし、 schema / canonicalizationへ渡す前に過深・過密JSONを拒否する。
  3. checked-in JSONはparseOntologyContractJsonDocumentでtokenizeし、duplicate object key、trailing token、comment、invalid UTF-8 / escapeをJSON.parse前に拒否する。
  4. 各source catalogとparsed JSON valueをstrict schemaでparseする。
  5. element ID重複、dangling reference、lifecycle invariantを検証する。
  6. set semanticsを持つarrayをelement kind別comparatorでsort / deduplicateする。
  7. snapshotのelementsをuniqueなelementIdのUTF-16 code unit順へsortする。
  8. shared/canonical-json.tsでserializeする。
  9. UTF-8 bytesをSHA-256へ渡し、sha256: prefix付きlowercase hexにする。
  10. snapshot schemaとregistry entryのversion / hashをcross-checkする。
  11. adjacent snapshotからdiffを再計算し、checked-in diffの全field、diffHash、registry entryをexactにcross-checkする。
  12. checked-in JSONをdeterministic pretty JSONへ再serializeし、raw bytesとexact比較する。duplicate keyはparse step、非標準whitespace、key / array order driftはraw byte比較で拒否する。
  • Unicodeはcanonical JSON実装の規則に従い、lone surrogate、NaN、Infinity、BigInt、cycleを拒否する。
  • object key orderはcanonical serializerへ任せ、array orderはbuilderが意味ごとに固定する。
  • sort comparatorにlocaleCompareを使わず、shared canonical JSONと同じUTF-16 code unit順を使う。locale / ICU差でsnapshot / diff orderを変えない。
  • undefinedを意味ある欠落として使わず、optional fieldはobjectから省略する。
  • timestamp、file mtime、absolute path、hostname、locale、environment variableをhash inputへ入れない。
  • existing knowledge-source-manifest.ts / generation-types.ts canonicalizerの共通化は、全golden hashが一致する専用testを先に追加してから別sliceで行う。contract導入の必須条件にしない。

11.2 Diff Algorithm

comparison前にsnapshot elementをdiff専用のclosed viewへ変換する。このviewではsnapshotのtop-level lifecycle、replacementElementId、deprecatedSinceを lifecycle: { status, replacementElementId?, deprecatedSince? }へまとめ、元の3 fieldは残さない。したがって/lifecycleは実在するatomic object pathであり、before / after hashとpathの指す値がずれない。それ以外のfieldはsnapshot schemaと同名を維持し、set semantics配列はstable IDをkeyにしたobjectへ投影して、array indexをJSON Pointerへ出さない。

  1. from / to snapshotをそれぞれnormalized comparison viewへ変換し、elementId mapへ正規化する。
  2. fromだけのIDをremoved、toだけのIDをadded、両方のIDをfield-by-field comparisonへ送る。
  3. 同じelement IDのlifecycleがactiveからdeprecatedへ変わる場合はreplacementElementIdとdeprecatedSinceを含む1件のatomic deprecated changeにする。初回replacement指定を別のmodified changeへ展開しない。
  4. classifierはhard invariant、lifecycle transition、kind-specific rule、generic additionの順で評価する。constraint / validation / claim / vocabulary / capabilityの追加をgeneric optional additionへ先に分類しない。
  5. normalized comparison viewのraw path deltaを先に全件作り、target snapshot全体のreference graphを使って分類する。たとえばoptional field追加ではfield elementのadditionとownerのoptionalFieldIds追加を同じfield_added_optional policyで分類し、reference側を未分類または別impactへしない。各raw pathはexactly once消費し、意図しないcoalescingを禁止する。
  6. added elementはfrom snapshotのvalue-set policyとdependency graphを調べ、open setまたはmay_ignore capabilityだけから参照される場合に限りoptionalとする。
  7. removed elementはregistry historyを遡り、deprecation release、support window、replacement chainを検証する。現在のfrom / to snapshotだけでremovalを承認しない。
  8. kind別classifierがpath単位のreason code、compatibility、required bumpを返す。
  9. canonicalization semantics、claim requirement、vocabulary semantics、identity、edge direction等、同一elementをbreakingに再解釈するreasonをemitした場合はsemanticRevision更新も必須にする。open enum追加やdeprecationのようにstructural fieldだけで意味を完全に表せるminor変更では更新しない。更新漏れはsemantic_revision_not_updatedでrelease validationをfailする。
  10. unclassified pathが1件でもあればdiff_rule_missingでrelease verificationをfailする。
  11. changesをelementId、path、operation、reasonCode順にsortする。
  12. summaryをchangesから再計算し、declared version incrementと照合する。

JSON Pointerのpathはlogical object pathを使い、array indexを禁止する。set memberはescaped stable IDをkeyのように表す。たとえば/allowedTo/entity_kind.findingとし、/allowedTo/3を使わない。 classifierは比較前にset semantics arrayをstable ID keyed objectへ投影し、このnormalized comparison viewに対してpointerを解決する。raw snapshot arrayへこのpointerを直接適用しない。

12. Semantic Version Policy

12.1 Major

次の変更は少なくともmajorを要求する。

  • active elementの削除、同じ概念内でのsemanticRevision変更。無関係な意味へのID再割り当てはversion bumpで許可せずreleaseを拒否する。
  • required field追加、requiredからoptional、nullability変更
  • value type / enum / range / edge endpointのwideningまたはnarrowing
  • edge direction、identity input、domain separator、canonicalization semanticsの変更
  • warningからerror、non-blockingからblocking、fallback許可からfail closedへの変更
  • claim assertion kind、required target / binding、vocabulary role / relation意味の変更
  • 既存capabilityをrequiredにする、旧profile readerで安全に無視できない追加

12.2 Minor

次の後方互換変更はminorを要求する。

  • old readerがlosslessに保持または明示的に無視できるoptional field / element / capability追加
  • open setへのentity / edge / enum追加。ただしconsumerがexhaustive switchを持つclosed setならmajor
  • non-blocking validation warning、optional claim target、new vocabulary semanticの追加
  • active elementのdeprecationとreplacement宣言
  • 既存fieldをalways presentへ強める変更。ただし値の意味削除を伴う場合はmajorとする。

12.3 Patch and No Release

  • documented semanticsを変えず、誤ったdeterministic outputだけを後方互換に修正する場合はpatchとする。修正behaviorを表すsource-controlled behaviorRevisionをsnapshotへ反映する。
  • patch fixはelement ID、identity input、persisted ID、enum / type、validation status、claim assertion、vocabulary role、consumer control flowを変えてはならない。いずれかが変わる場合はbug fix名目でもmajor ruleを適用する。
  • message、説明、evidence link、owner、review date、test追加だけならsnapshot不変でありcontract releaseを作らない。
  • registry receiptやgenerated dataだけが変わる場合もcontract releaseを作らない。
  • 同じhashに別version、または同じversionに別hashを割り当てることを禁止する。

14. Reader, Deprecation, and Historical Migration Policy

14.1 Version-specific Readers

  • wire profile reader、ontology contract compatibility evaluator、profile validatorを別dispatch tableで管理する。
  • exact contract snapshot hashをregistryから解決できる場合だけversion-specific behaviorへdispatchする。
  • unknown hashを同じversionの既知snapshotへ丸めない。
  • descriptor欠落legacyはpre-descriptor-wire-v1 readerへだけdispatchし、ontology contract 1.0.0 readerとして扱わない。
  • old snapshot fileとreader fixtureはsupport window中削除しない。
  • generationに保存されたdescriptorと現在のlatest contractを比較しても、old payloadの意味をlatestへ再解釈しない。

14.2 Deprecation Window

  • element削除前に少なくとも1 minor releaseでdeprecatedにする。
  • deprecationはreplacement IDとdeprecatedSinceを必須にする。
  • replacementは同じtarget snapshotに存在する同じkindのactive elementを指し、self-reference、cycle、8段を超えるchainを拒否する。removal時もchain終端がactiveであることを再検証する。
  • default support windowはdeprecatedSince releaseより後に同一majorで2回のminor incrementが公開済み、かつそのreleaseのreleasedOnからremoval releaseのreleasedOnまで90 UTC calendar days以上の両方を満たした時点とする。patch releaseはminor回数へ数えない。
  • removal GOにはvulnWorkbench / NightWorkers両方でdeprecated element usageが連続14日0件、rollback reader保持、major release approvalを要求する。
  • security / correctness上の緊急時もrelease CLIはsupport windowを黙って迂回しない。まず別のincident pathで危険なwriter / capabilityを停止し、window免除が不可避なら本schemaとclassifierへ明示的なemergency evidence contractを追加するreviewed changeを先に行う。ad hoc flagやsilent removalを許可しない。

14.3 Migration Policy

  • migration対象はconsumer code / fixture / declarationであり、persisted generation dataではない。
  • renameはdual-read期間にold / new elementを別IDで共存させる。
  • old write停止後もhistorical readerをsupport window中維持する。
  • rollbackはdescriptor continuity floorを保ったままwriter targetをknown-good contractへ戻し、新generationをそのcontractで再buildする。legacy cutoff後にunmarked generationへ戻さない。
  • inferred relationをmigrationでdeclaredへ昇格しない。

15. Generation and Artifact Integration

15.1 Descriptor Placement

  • StaticIntelligenceExportV1.ontologyContract?
  • StaticIntelligenceKnowledgeSourceManifest.ontologyContract?
  • StaticIntelligenceOntologyHandoff.ontologyContract?
  • generation artifact metadata summary: ontologyContract?: OntologyContractArtifactMarkerV1

schema上optionalなのはmigrationのためである。optionalでdescriptor buildに成功したgenerationとrequiredの全generationでは、exportと、そのgenerationに存在する全derived artifact metadataにdescriptor / markerをexactly once要求する。manifest / handoffはpersisted generationのdescriptorだけから投影し、current configから再生成しない。 wire readerのoptional field型はtransport envelopeとしてlosslessに保持し、producer input / publication resultへ昇格する前にversion-specific strict schemaを通す。

15.2 Reader-first Risk

現行exportはnon-strict Zod object、manifestとhandoffはstrict objectである。unknown fieldをstripまたはrejectする旧readerへdescriptor付きpayloadを先に書くと、再serialize時のexportHash mismatchやparse failureが起こり得る。したがって次をwriter開始前gateとする。

  1. vulnWorkbench generation loaderがoptional descriptorをlosslessにparse / preserveする。
  2. manifest / handoff readerがoptional descriptorを認識する。
  3. NightWorkersがoptional descriptorを認識し、snapshotでmay_ignore と宣言された未対応capabilityだけを安全に無視する。
  4. 旧descriptor欠落generationのhashが一切変わらないgolden testを通す。
  5. reader deploy commit / versionをrelease evidenceへ固定する。

15.3 Generation Consistency Invariants

  • export descriptor、全artifact metadata marker、manifest、handoffのversion / hashは一致する。
  • descriptorのcontract hashはregistryの同version snapshot hashに一致する。
  • descriptor capabilityはそのgenerationに実際にpersistされたprofileだけを宣言する。
  • descriptor capabilityは同じcontract snapshotで宣言されたcapabilityのsubsetであり、ID / profileがexactに一致する。
  • exportHashはdescriptorを含むpersisted exportから計算する。
  • manifest contentHashもpublishされたdescriptorを含むmanifest contentから計算する。
  • mixed marker、unknown hash、capability artifact欠落はgeneration loadをfailさせる。
  • optional fallbackはdescriptorと全metadata markerがともに欠落したall-or-none状態だけをlegacyとして受理する。markerだけ、descriptorだけ、一部artifactだけの状態はlegacyへfallbackしない。
  • legacy generationはdescriptor欠落のまま保持し、現在のdescriptorを注入しない。

24. Rollback Plan

24.1 Triggers

  • old payloadのexport / content hash regression
  • consumerでunknown field loss、parse failure、unsupported contract rejection
  • generation metadata / export / manifest / handoffのdescriptor mismatch
  • same catalogからnondeterministic snapshot / diff hash
  • unclassified change、誤ったminor判定、deprecated element利用継続
  • performance budget超過、shadowでのpersisted / public diff

24.2 Rollback Order

  1. descriptorContinuity="legacy_allowed"のbootstrap期間だけ、producer modeを required → shadow → offの順で戻せる。optionalへのrollbackもbaseline 1.0.0 descriptor transport期間だけに限定する。
  2. descriptorContinuity="required_only"ではmodeをrequiredのまま維持し、target version / hashだけをregistry上のprevious known-good releaseへ戻す。known-good descriptorを構築できなければgeneration persistenceを停止し、descriptor欠落payloadを作らない。
  3. NightWorkersとvulnWorkbenchのreaderは残し、障害releaseのsupport rangeも既存generation / in-flight handoffのusageが0かつ通常support window終了までは削らない。新規writer targetだけを先に戻す。
  4. 障害contractでのnew writeを停止し、known-good contractでnew generationを再buildする。
  5. 公開済みsnapshot / registry entry、old reader、historical generationを削除・上書きしない。
  6. 誤releaseは同じversionを修正せず、適切なnew patch / minor / major releaseで訂正する。

rollback成功条件は障害versionのnew descriptor publish 0、known-good descriptor付きhandoff成功、既存legacy handoffの継続可用性、hash mismatch 0である。required_onlyでは「descriptor publish 0」ではなく「障害version publish 0」を測る。rollback中もStage 4 serviceやin-place data migrationへ逃げない。

  • support policy、security / size / latency budget、observability、rollback drillが承認済みである。
  • Stage 3 package / Stage 4 service trigger未充足を再確認し、premature extractionを行っていない。

27. GO / NO-GO Gate

27.1 Bootstrap GO

  • Stage 0 GOまたはarchitecture ownerによるquality-infrastructure例外が記録されている。
  • baseline inventory scopeとstable element ID方針がproducer / consumer ownerに承認されている。
  • 現行consumerのclosed / open set behaviorをfixtureで確認できる。
  • source-controlled snapshotを正本とし、runtime authoringを行わないことに合意している。
  • B0–B2がwire、persistence、runtime behaviorを変えないことをtestで保証できる。

27.2 Publication GO

  • Bootstrap DoDと関連baseline testsがgreenである。
  • active化するprofileのownership、immutable boundary、catalog view、fixtureが承認済みである。
  • NightWorkers consumer-first担当、release window、exact reader commitが確保されている。
  • protected cross-repository approval gateとrollback floorを実行できる。
  • descriptor publication、support policy、legacy continuityのownerが決まっている。

27.3 NO-GO

  • instance dataやregistry receiptをsemantic snapshotへ含める要求が未整理である。
  • planned profileを実装前にactive elementとしてfreezeする必要がある。
  • consumer behaviorを確認できず、minor / major分類を固定できない。
  • writer-first publication、offline自己申告だけのremote approval、old generation再hashが前提になる。
  • CIがhistorical mutationをbase commitと比較できない。
  • Stage 4 workflow、shared service、runtime authoringを同じ変更へ含める要求がある。

28. Implementation Handoff

  1. 共通CLI baselineを独立fixでgreenにし、before / after test名と件数を保存する。
  2. Bootstrap B0で現行surfaceだけのsource registry、inventory、candidate snapshotをreviewする。
  3. B1でstrict schema、canonicalization、hash、no-write candidate verifierをproduct path外で完成させる。
  4. B2でdiff classifierとhistory checkを完成させ、Bootstrap DoDを満たした時点でmilestoneを閉じる。
  5. 先行profileの実装を待つ間、planned sourceをactive化せず、runtime descriptor fileを変更しない。
  6. Publication GO後にだけP0 reader floorとrelease authoringへ進む。
  7. P1 shadow、P2 optional、P3 requiredを別PR・別rollout decisionで進める。
  8. major removal前にdeprecation usage、support window、rollback readerを確認する。

BootstrapとPublicationを同じPRへまとめない。各trackの未解決decisionはproposed defaultを黙って採用せず、 対応するGO gateで停止する。Bootstrap完了はPublication完了を意味せず、Publication未着手を理由に candidate snapshot / diff toolingを未完了扱いに戻さない。
