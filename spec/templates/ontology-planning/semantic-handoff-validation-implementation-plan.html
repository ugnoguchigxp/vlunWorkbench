1. Purpose

persisted Static Intelligence generationからontology handoffを公開する直前に、ZodによるJSON shape validationだけでは検出できないgraph-wideな意味制約を検証する。検証結果を決定的な machine-readable reportとしてAPI、knowledge source manifest、NightWorkers consumerへ渡し、 不正なhandoffをtask / run contextへ利用させない。

この計画はSemantic Handoff Validationだけを実装可能な粒度へ具体化する。claim provenance、 security vocabulary alignment、contract diff、competency question、rule inferenceは本計画で設計・実装しない。

2. Target Outcome

persisted generation
  -> build deterministic ontology handoff projection
  -> validate identity / graph / module / summary constraints
  -> emit structured validation report
  -> merge report into readiness
  -> publish diagnostic payload
  -> consumer activates only passed or passed_with_warnings payload
  • validなhandoffは既存と同じprojectionを返し、validation reportを追加する。
  • warningだけの場合はhandoffを利用可能なまま、既存availableを degradedにする。既存stale / failedは弱めない。
  • errorがある場合もgenerationとreportは保持するが、handoff statusをfailedにする。
  • NightWorkersはfailed reportを受け取ってもmodule / task contextへ取り込まない。
  • 同一generationから常に同じreport orderingと同じmanifest content hashを生成する。

4. Fixed Decisions

  • 初期validatorはTypeScriptのpure functionとして実装する。
  • RDF変換、SHACL file生成、pySHACL、Semantica runtime dependencyを導入しない。
  • validationはpersisted generationを削除または無効化せず、handoffの利用可否だけを制御する。
  • validation reportは時刻を持たず、generationだけから決定的に生成する。
  • static-intelligence-ontology-handoff-v1のrule集合とseverityはimmutableとし、 rule追加・削除・severity変更時は別profileを定義する。
  • error / warningの判定はrule profileで固定し、consumerがmessage文字列を解析しない。
  • API / CLIの実行成功とontology conformanceを分離する。
  • validator内部例外のraw errorをwireへ通さず、固定messageのfailed reportへ変換してfail closedにする。
  • 同じrequest / build内ではprojectionとreportを一度だけ評価し、readinessとwire outputで共有する。
  • consumer-first migrationを採用し、NightWorkersがoptional reportを読める状態を先にreleaseする。
  • 既存のcandidateOnly semantic queryはgraphへ投影されていないため、本計画のrule対象にしない。

SHACL標準ではwarningを含むvalidation resultが1件でもsh:conforms=falseになり得るが、 本profileのconformsは「errorがなくconsumer利用可能」を意味する。したがってwarningだけなら conforms=trueとする明示的な差分がある。

8. Validation Contract

8.1 Shared Schema

const diagnosticRefSchema = z.string().min(1).max(256);
const countSchema = z.number().int().nonnegative().max(Number.MAX_SAFE_INTEGER);

const ontologyValidationViolationSchema = z.object({
  code: z.string().max(128).regex(/^ontology\.[a-z0-9_.]+$/),
  severity: z.enum(["error", "warning"]),
  focusRef: diagnosticRefSchema,
  path: z.string().min(1).max(256).optional(),
  message: z.string().min(1).max(512),
  sourceRefCount: countSchema,
  sourceRefsTruncated: z.boolean(),
  sourceRefs: z.array(diagnosticRefSchema).max(20),
}).strict();

const ontologyValidationReportSchema = z.object({
  version: z.literal("v1"),
  profile: z.literal("static-intelligence-ontology-handoff-v1"),
  generationId: z.string().min(1),
  status: z.enum(["passed", "passed_with_warnings", "failed"]),
  conforms: z.boolean(),
  summary: z.object({
    errorCount: countSchema,
    warningCount: countSchema,
    emittedCount: z.number().int().nonnegative().max(1000),
    truncated: z.boolean(),
  }).strict(),
  violations: z.array(ontologyValidationViolationSchema).max(1000),
}).strict();
  • codeはforward-compatibleなstringとし、consumerは未知codeを安全に扱う。
  • messageは人間向けであり、control flowには使用しない。
  • messageはrule codeごとの固定文とし、node label、path、metadata、exception textをinterpolateしない。対象はfocusRef / path / sourceRefsで示す。
  • focusRefはnode / edge / module / generationの安定IDを使う。
  • pathはgraph.edges.toのような論理field名とし、array indexへ依存しない。
  • sourceRefsへabsolute path、raw evidence snippet、secretを含めない。
  • sourceRefCountはdeduplicate後の総数、sourceRefsはその先頭20件、 sourceRefsTruncatedは省略有無を表す。
  • code 128文字、focus / source ref 256文字、logical path 256文字、message 512文字をhard limitとする。countはJavaScript safe integer以内とする。
  • 時刻fieldは持たせない。reportはgeneration contentだけから再生成可能にする。
  • errorCount / warningCountは検出総数、emittedCountはviolations配列の件数を表す。

8.2 Derived Field Invariants

  • errorが1件以上ならstatus=failed、conforms=false。
  • errorが0件でwarningが1件以上ならstatus=passed_with_warnings、conforms=true。
  • error / warningが0件ならstatus=passed、conforms=true。
  • summary countはcode / focusRef / pathでdeduplicateした後、1,000件capを適用する前にvalidatorが算出し、 caller入力を受け取らない。
  • 1,000件を超える場合も総数を数え、先頭1,000件だけをemitしてtruncated=trueにする。
  • emittedCountはviolations.lengthと一致する。
  • schemaのsuperRefineで、truncated=falseならtotal countとemit内訳の一致、 truncated=trueならtotal count > emittedCountかつemittedCount=1,000を検証する。
  • status / conformsはemitされた一部ではなくtotal error / warning countから導出する。
  • violation orderingはerror優先、code、focusRef、path、sourceRefsの順で固定する。
  • sourceRefsは各violation内でもdeduplicateしてlexicographic sortする。
  • violationごとのsource refは全件を数えた後に先頭20件をemitする。 violation schemaのsuperRefineで、非truncate時は sourceRefCount=sourceRefs.length、truncate時は sourceRefCount>20かつsourceRefs.length=20を要求する。
  • profile v1のrule集合、severity、参照正規化規則を変更しない。message修正だけではprofileを変えない。

8.3 Wire Placement

  • StaticIntelligenceOntologyHandoff.validation: producer APIの詳細report
  • StaticIntelligenceKnowledgeSourceManifest.ontologyValidation: CLI consumer用report
  • StaticIntelligenceBuildResult.ontologyValidation: build / refresh diagnostic
  • manifest fieldはconsumer-first migrationのためschema上optional、producer emissionはpersisted generationから作る経路で必須とする。
  • projectionを生成できた場合、ontology handoff builderが返すreportはproducer側で常に必須とする。

ontology handoff API responseは次のdiscriminated unionへ固定する。

type StaticIntelligenceOntologyHandoffResponse =
  | { handoff: StaticIntelligenceOntologyHandoff }
  | { handoff: null; status: "missing" }
  | {
      handoff: null;
      status: "failed";
      validation: OntologyValidationReport;
    };
  • semantic data violationでprojectionが存在する場合は、 handoff.status=failedとhandoff内のvalidationを返す。
  • projection生成自体がunexpected exceptionで失敗した場合は、空のhandoffを捏造せず、 top-level status=failedと ontology.validator.execution_failed reportを返す。
  • generationが存在しない、またはpersisted generationのshapeをloadできない現行経路だけを status=missingとする。validation failureをmissingへ変換しない。

9.1 ID and Reference Conventions

  • evidenced_byはtarget evidenceのsource ID、stored_asはsource evidenceのsource IDをexactly 1件持つ。located_inは同じfindingのevidenced_by target集合と一致し、 その他のedge kindは空配列とする。
  • module risk.findingIdsはraw finding source IDとし、validatorは finding:${id}へ解決する。
  • handoff sourceRefsはqualified refとし、project:、scan:、snapshot:、file:、 finding:、evidence:をcurrent builderと同じ規則でexact projectionする。
  • artifactとverificationはprofile v1のhandoff sourceRefsへ含めない。追加する場合は新profileで扱う。
  • file pathはunknownまたは正規化済みproject-relative POSIX pathだけを許可する。absolute path、URI、backslash、control character、空segment、 . / .. segmentを許可しない。
  • 不正なfile pathをreportへ再掲しない。対象のfocusRefは redacted_ref:sha256:${sha256Utf8(rawRef)}とする。不正file node、そのincident edge、不正file refを扱う全ruleで同じ変換を適用し、diagnostic sourceRefsにもraw pathを入れない。
  • 256文字を超えるdiagnostic refも同じSHA-256 refへ置換し、schema上限超過を内部例外へ変えない。
  • node ID suffixが空の場合はshape validationまたはkind mismatch ruleでerrorにする。

9.5 Explicitly Valid Unknowns

  • file:unknownとconfidence 0のlocated_inはinvalidにしない。
  • findingが0件のgraphをinvalidにしない。
  • review / verification nodeが0件のgraphをinvalidにしない。
  • scanner / artifact nodeがfindingから未参照でも、source inventoryとして許可する。
  • semantic indexがmissing / staleでもontology graph validation自体は実行する。

9.6 Rule Evaluation Order and Cascade Suppression

  1. generation identity / provenanceを検証する。
  2. node ID重複、kind prefix、sourceId対応を検証してnode indexを作る。
  3. edge ID重複とcanonical IDを検証してedge indexを作る。
  4. edge endpoint実在性を検証する。
  5. endpointが確定したedgeだけdomain / range、confidence、evidence refを検証する。
  6. 参照が確定したnode / edgeだけrelation cardinalityを検証する。
  7. 最後にverification projection、graph summary、source ref、module projection、degraded reasonを検証する。
  • missingまたはduplicateでambiguousなendpointを持つedgeではdomain / range errorを重ねて出さない。
  • endpoint kindがinvalidなedgeではconfidence ruleをskipする。未解決evidence refを1件でも持つedgeでは evidence ref mismatchを重ねない。
  • 未解決stored_as targetのresolution warningは1件だけ出し、target kind checkをskipする。confidence 0.5 ruleは引き続き評価する。
  • duplicate edgeはcode / focusRef / path単位で1件にまとめ、代表edgeだけを後続ruleへ渡す。
  • duplicate module ID / path prefixは1件報告し、そのmoduleのdependent summary ruleをskipする。
  • node sourceIdがmissingなら同じnodeのsourceId mismatchを重ねない。module structure mismatch時は同じmoduleのdependency warningを重ねない。
  • candidateが0件の場合はmodule_candidates_empty warningだけを出し、module集合比較をskipする。 candidateが一部だけ欠落または余剰の場合はmodule_projection_mismatch errorとする。
  • module集合が一致しない場合はmodule order ruleをskipし、共通moduleだけをfield検証する。
  • 同じcode、focusRef、pathのviolationは1件へdeduplicateし、sourceRefsはunionしてからsort / count / truncateする。messageはrule codeごとの固定templateを使う。

9.7 Comparison Semantics

  • validatorはactual arrayをsortしてから比較しない。独立に作ったcanonical expected arrayとのsequence equalityで、duplicateと順序差も検出する。
  • sourceRefs、degradedReasons、edge evidenceRefs、moduleのrole / symbol / risk refはdeduplicate後のlexicographic順をexpectedとする。
  • 本書のlexicographic順はJavaScriptのUTF-16 code-unit比較 a < b ? -1 : a > b ? 1 : 0を意味する。 ICU依存のlocaleCompareはreport、handoff、module candidateのcanonical orderingに使わない。
  • verification commands、entrypoint、dependency、confidence reasonはpersisted sourceの順序を保持する。
  • module candidate自体はcritical、high、medium、low、info、unknownのseverity rank降順、findingCount降順、pathPrefix昇順とする。
  • graph node / edge配列の格納順は意味を持たず、validatorのindex作成前に順序へ依存しない。
  • violation comparatorではoptional pathの未設定を空文字として比較する。

10. Validator Design

10.1 Public Functions

buildStaticIntelligenceOntologyHandoffProjection(generation)
  -> handoff fields without status and validation

validateStaticIntelligenceOntologyHandoff({ generation, projection })
  -> OntologyValidationReport

evaluateStaticIntelligenceOntologyHandoff(generation)
  -> { projection, validation }

safeEvaluateStaticIntelligenceOntologyHandoff(generation)
  -> {
    projection: OntologyHandoffProjection | null,
    validation: OntologyValidationReport
  }

buildStaticIntelligenceOntologyHandoff({ generation, status?, evaluation })
  -> StaticIntelligenceOntologyHandoff | null

applyOntologyValidationReadiness({ current, report, scope })
  -> IntelligenceCapabilityReadiness

projection生成とvalidationを分離し、testが意図的に壊したprojectionをvalidatorへ渡せるようにする。 product call siteはsafeEvaluateStaticIntelligenceOntologyHandoffを一度だけ呼び、public API builderはそのevaluationを必須で受け取る。projectionがnullならbuilderもnullを返し、API envelopeまたはbuild / manifest diagnosticへfailed reportを渡す。unit testだけがraw validatorを直接呼ぶ。

10.2 Complexity and Determinism

  • node、edge、module、source refを先にMap / Setへindexする。
  • project structureからfile path→moduleを一度作り、fileRiskIndexを1回だけ走査してmodule riskを集計する。 structure fileのrole / symbol集計も1回で行い、moduleごとのfilterは行わない。
  • rule traversalはO(nodes + edges + modules + sourceRefs)とする。
  • 入力要素数をI、violation数をVとすると、canonical array作成はO(I log I)、deterministic report orderingはO(V log V)とする。profile v1では1要素あたりのrule数が固定なのでV=O(I)である。
  • working memoryはindexとdedup keyを含めO(I + V)、wire payloadは最大1,000 violationsとする。
  • validation中にDB、filesystem、network、clock、LLMを呼ばない。
  • errorをthrowして最初の違反で止めず、全violationを収集する。
  • raw validatorはprogramming errorだけをthrowし、data violationはreportへ変換する。
  • safe evaluatorはunexpected exceptionをcatchし、raw error textを含まない ontology.validator.execution_failed reportへ変換する。
  • schema parse後にreportのUTF-8 byte lengthを検証し、8 MiB以上ならviolationsを破棄して単一の ontology.validator.execution_failed reportへ置換する。
  • raw validatorだけが失敗した場合は生成済みprojectionを保持する。projection builderが失敗した場合はprojection=nullとし、空moduleや空summaryを代替生成しない。

10.3 Call-site Evaluation Ownership

1 request / buildにつき1 evaluationを共有する
Call site Evaluation owner Consumers
build service persist直後に一度評価する。 validation stage、build readiness、manifest、build result
project intelligence view resolverがgeneration load後に一度評価する。 readiness、view manifest
ontology handoff API routeがgeneration load直後に一度評価する。 readiness status、handoff response
knowledge source CLI generation load後に一度評価する。 manifest

10.4 Independent Expected Values

validatorがprojection自身をexpected値として再利用すると自己検証になるため、expected値は次のsourceから独立に作る。

  • identity / provenance: persisted generation metadataとexport payload
  • graph node source mapping: 9.1のcanonical node ID suffixとverification ordinal
  • graph summary: export payloadのnode / edge配列
  • source refs: generation identityとfileRiskIndexから再構築したqualified ref集合
  • module集合、file、dependency: project structure snapshot
  • module risk: project structure module membershipとfileRiskIndexから再集計した値
  • verification commands: export payload handoff.verificationCommands。handoffがなければ空配列
  • degraded reasons: structure metadataのdegraded reasonと、module候補が空の場合の module_candidates_missingをdeduplicate / sortした集合

expected値の計算でcandidateのgraphSummary、sourceRefs、 verificationCommands、degradedReasons、module各fieldを読まない。 共通化するのはseverity比較などのprimitiveだけとし、projection builder全体をexpected builderとして呼び直さない。

11. Readiness and Publish Policy

11.1 Status Precedence

ontology handoff statusの優先順位を次で固定する。

existing failed condition or failed semantic validation
  > stale generation
  > existing missing condition
  > existing degraded condition or validation warning
  > available
validation reportからreadinessへの写像
Report evidenceGraph ontologyHandoff Stable reason code
passed 現行statusを維持 現行statusを維持 追加なし
graph warning warning impactをmerge warning impactをmerge ontology_semantic_validation_warning
handoff-only warning 現行statusを維持 warning impactをmerge ontology_semantic_validation_warning
validator execution failed failed failed ontology_semantic_validation_failed
graph error failed failed ontology_semantic_validation_failed
handoff-only error 現行statusを維持 failed ontology_semantic_validation_failed

capability reasonCodesへ個々のviolation codeを展開しない。詳細はreportを参照し、 readiness contractはboundedな2 reasonだけを使用する。

warning impactはavailableだけをdegradedへ変更し、既存の failed、stale、missingを弱めない。impact対象の reason codeは既存reasonへ追加してdeduplicate / lexicographic sortする。

11.2 Publish Semantics

  • buildはsemantic validation errorでもgeneration artifactsを保存する。
  • build resultはpartialとなり、validation stageとreportを返す。
  • StaticIntelligenceBuildStage.nameへ validate_ontology_handoffを追加する。reportがpassedならstage completed、warning / error / execution failureならstage degradedとし、 operational stage型へfailedを追加しない。
  • StaticIntelligenceBuildResult.ontologyValidationは必須とする。reportがpassed以外なら、 他stageが成功していてもbuild resultをpartialにする。
  • semantic error時もpersisted generation statusは書き換えず、readiness capabilityだけを failedにする。
  • ontology handoff APIはHTTP 200でfailed reportを返し、diagnostic visibilityを維持する。 projectionがあればhandoff内、なければ8.3のtop-level failed envelopeへ載せる。
  • knowledge source CLIもJSON生成に成功した場合はexit 0でreportを返す。
  • HTTP 200 / CLI exit 0はconformanceを意味しない。consumerはreport statusを確認する。
  • unexpected validator exceptionも固定messageのfailed reportとして同じconsumer gateを通し、 raw exceptionは既存のredaction policyを通したserver logだけへ記録する。
  • CLIはunexpected exceptionのraw message / stackをstdoutまたはstderrへ出さない。
  • CLI manifest result全体が10 MiB以上ならpublishせず、固定messageのfailure JSONとnon-zero exitを返す。
  • NightWorkersはfailed reportをunavailableへ変換し、task contextへactivateしない。

12. Manifest and Hash Policy

  • ontologyValidationをmanifest top-level optional fieldとして追加する。
  • producerはpersisted generationからmanifestを作るすべての経路で必ずreportを渡す。
  • reportはcontentHashInputへ含め、validation内容の差をcontent hashへ反映する。
  • reportは時刻を持たないため、同じgenerationのrebuildでcontent hashを変えない。
  • manifest builderはreport generation IDとgeneration IDの不一致をthrowする。
  • ontologyValidationが存在する場合はmanifest generationも必須とし、両方の generation ID一致をschema superRefineでも検証する。
  • readinessは従来どおりcontent hash対象外とし、validation reportとは区別する。

18. Security and Privacy

  • validation messageへraw node metadataをJSON stringifyしない。
  • file focus refはproject-relative pathだけを許可する。
  • unsafe file refを扱うviolationはraw値を決定的SHA-256 refへ置換する。
  • sourceRefsへraw artifact body、evidence snippet、review output、secretを含めない。
  • NightWorkers eventはprofile、status、errorCount、warningCount、先頭10件のrule code、report / rule code truncation状態だけを保存し、messageとsource refを保存しない。
  • consumerはreport messageをcommand、path、promptとして実行しない。
  • exception loggingでgeneration payloadやraw node / edgeをserializeしない。
  • validatorはnetwork / filesystem accessを持たないため、validation inputからside effectを起こさない。

19. Performance and Payload Budget

  • rule traversalはO(N + E + M + R)、canonicalizationを含む全体はO(I log I + V log V)を維持し、module単位のrisk全走査を禁止する。
  • reference machineでは10,000 nodes / 25,000 edges / 1,000 modulesで100ms以内、他環境では同一 machineのSlice 1 baselineの1.2倍以内をqualification targetとし、machine / runtime versionをevidenceへ記録する。
  • 同一violationの重複発行を防ぎ、violations配列はdeterministicな先頭1,000件、各 sourceRefsは先頭20件でtruncateする。
  • truncate時はsynthetic violationを追加せず、summaryのtotal count、emittedCount、truncatedで表す。
  • normal fixtureのreport追加payloadは10KB未満をtargetとする。
  • UTF-8 serialized reportはhard limit 8 MiB、manifest result全体はNightWorkers maxBufferと同じ10 MiB未満とし、producer publish前にbyte lengthを検証する。
  • 巨大なinvalid graphでもraw objectをviolationへ複製しない。

20. Observability

  • build stageへduration、status、bounded reason codeを記録する。
  • refresh responseへreportを含め、error / warning countを確認可能にする。
  • readinessには詳細codeを展開せず、reportへの導線だけを保つ。
  • NightWorkers warning eventはvalidation summaryだけを保持する。
  • validation report専用DB tableやlong-term telemetryは本計画では追加しない。

  • absolute path、raw evidence、secretがreportへ漏れる。

21.2 Rollback Order

  1. vulnWorkbench manifest emitterからontologyValidation出力を停止し、同じrevertでcontent hash inputからも外す。
  2. build resultの必須ontologyValidation、validation stage、build / read readinessへのenforcementを同じrevertで外し、pure validatorとtestは残す。
  3. ontology handoff APIを戻す場合は、required validation schema、response union、builder emissionを同じrevertで戻す。
  4. rollback triggerがordering / hash差分なら、ontology handoffとmodule candidateのcanonical comparator変更も同じproducer revertへ含める。
  5. NightWorkersのoptional parserはlegacy compatibilityのため残す。
  6. persisted generationは削除・再生成しない。

rollbackでscanner、finding、artifact、review dataを変更しない。DB migrationがないためschema down migrationも不要である。

既に保存されたNightWorkers run eventは書き換えない。failed eventを持つrunはterminalのままとし、 rollback後のproducerを使う場合も新しいrunで再収集する。

22. Definition of Done

  • profile v1の全ruleとseverityがコードと本書で一致している。
  • 各ruleにpositive / negative testがある。
  • ID / sourceId対応、raw / qualified ref、source ref exact projectionがcontractどおりである。
  • unsafe file pathをerrorにし、report / log / NightWorkers eventへraw値を出さない。
  • report上限時もtotal count、emitted count、truncated flagが正しい。
  • violation source ref上限時もtotal countとtruncated flagが正しい。
  • 同一generationからreport orderingとmanifest content hashが決定的に生成される。
  • canonical orderingにlocaleCompareが残っていない。
  • 同一request / build内でvalidation evaluationを重複実行しない。
  • APIがpassed / semantic-failed / projection-failed / missingを契約どおり区別する。
  • graph errorがevidenceGraph / ontologyHandoff readinessをfailedにする。
  • handoff-only errorがontologyHandoffだけをfailedにする。
  • warningはdegradedになるがconsumer利用を停止しない。
  • failed generation artifactsが診断用に保持される。
  • NightWorkers consumer-first migrationが完了し、legacy / new fixtureが両方greenである。
  • NightWorkersがfailed reportをtask contextへactivateしない。
  • NightWorkersがfailed reportのmanifest artifactを作成せず、10 rule code上限のsummaryだけを残す。
  • NightWorkers eventがgeneration IDを保持し、same-run failureから別generationへ暗黙切替しない。
  • redaction、performance、payload budgetを満たす。
  • targeted verification、typecheck、lint、docs checkがpassする。
  • full suiteのbefore / after差分と既知baseline failureが記録される。
  • 実装外のontology候補へscopeが広がっていない。
