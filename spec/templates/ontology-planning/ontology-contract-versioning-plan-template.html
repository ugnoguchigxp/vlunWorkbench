Ontology Contract Versioning Plan Skeleton

  • Status: Candidate plan skeleton / not approved for implementation
  • Priority candidate: P1
  • Primary owner candidate: shared producer-consumer contract maintainers
  • Semantica clue: version storage, comparison, change management, migration lifecycle

1. Purpose

content hashやgenerationとは別に、ontology contractの意味変更をversionとcanonical diffで表す。 vulnWorkbenchとNightWorkersがconsumer-firstまたはdual-readで安全に移行できる契約を用意する。

2. Current Evidence

  • knowledge source manifestはwire version、generation、export hash、content hashを持つ。
  • hashはcontentの差を示せるが、追加・互換・破壊的変更の意味分類は示さない。
  • NightWorkersはvulnWorkbench handoff v1をconsumer schemaへ反映している。
  • 長期ロードマップはshared contracts、canonicalization、validation、diff、deterministic projectionを要求する。
  • 独立Ontology Coreはapprovalやmulti-producer mergeが必要になるStage 4まで前倒ししない。

3. Scope

  • wire versionとsemantic ontology contract versionの区別
  • entity kind、edge kind、claim field、constraint、vocabulary mappingのcanonical diff
  • additive、compatible、deprecated、breakingのchange classification
  • consumer capability negotiation、dual-read期間、fixture-based migration
  • versionごとのvalidator / canonicalizer / projection behavior

3.1 Non-goals

  • 単なるfinding content更新ごとにcontract versionを上げること
  • Stage 4条件を満たす前に独立ontology serviceを作ること
  • breaking changeをversion番号だけで安全とみなすこと

4. Contract Sketch

type OntologyContractDescriptor = {
  wireVersion: string;
  ontologyContractVersion: string;
  vocabularyVersions: Record<string, string>;
  canonicalizationVersion: string;
};

type OntologyContractDiff = {
  from: string;
  to: string;
  classification: "additive" | "compatible" | "deprecated" | "breaking";
  changes: Array<{ path: string; kind: string; migrationHint?: string }>;
};

5. Implementation Options

  1. A: handoffへcontract descriptorを追加し、repo内libraryでdiffする。
  2. B: project-ontology-contracts共有packageへschema / canonicalizer / diffを分離する。
  3. C: revision / approval / mergeを持つ独立Ontology Core serviceへ移す。

Aから開始し、複数producer / consumerでrelease cycleを共有する必要が出た時点でBを評価する。CはStage 4 gate対象とする。

6. Candidate Migration Sequence

  1. 新旧contractのgolden fixtureとdiff expectationを固定する。
  2. NightWorkersが新descriptorをoptionalに読める状態へ先行更新する。
  3. vulnWorkbenchが新旧互換のhandoffをpublishする。
  4. unknown version telemetryとrollback条件を確認する。
  5. deprecation期間後に旧contract writeを停止する。

7. Verification and Exit Evidence

  • 同一contractから同じcanonical representationとdiff orderingが得られる。
  • additive / breakingのpositive、negative fixtureを両repositoryで共有する。
  • unknown major versionはfail-safeで拒否し、unknown optional fieldは安全に扱う。
  • upgrade / downgrade / rollbackをfixtureで再現できる。
  • content hash変更とcontract version変更を独立して説明できる。

8. Open Questions

  • semantic versionのmajor / minor / patchを何の変更へ割り当てるか。
  • vocabulary mapping versionをcontract versionへ含めるか、外部参照にするか。
  • 共有packageのrelease ownerと互換性support期間は誰が持つか。
  • historical handoffをどのversionまで再読込可能にするか。

9. Next Discovery Checklist

  • 現行v1 contractのcanonical descriptorを手作業で作る。
  • 過去のschema変更をadditive / breakingへ分類し、分類規則を試す。
  • NightWorkersのunknown field / version behaviorをfixtureで確認する。
  • Stage 4 triggerが未充足であることをGO判断時に再確認する。
