1. Executive decision

現行コードのままavailabilityだけをstableへ変更してよい experimental profileはない。実行経路は存在するが、profileが公称する範囲と実装範囲の差、 profile単位のrelease qualification不足、古いcommitへ結び付いたbenchmark evidenceが残る。

昇格作業は次の4 waveに分ける。waveの件数は固定仕様ではなく、各profileが個別のexit gateを 満たした場合だけ進める。あるprofileの失敗を、同じwaveの別profileの昇格で相殺しない。

2. Scope and non-goals

2.1 In scope

  • experimental profileごとの公称capabilityと実装capabilityの一致
  • profile単位のversioned qualification schema、builder、verifier、Docker receipt
  • orchestrator flowとdedicated flowに共通するcatalog admission contract
  • 脆弱版／修正版、negative、fault injection、repeatabilityのE2E
  • scanner、rule、database、container image、source snapshotのimmutable binding
  • 安全境界、secret redaction、cleanup、rollbackのpromotion gate
  • catalog、API、CLI、Web、report、coverage表示の段階的切替

2.2 Non-goals

  • professional-fullの実装または昇格。本計画とは別計画で扱う。
  • 外部またはproduction targetへのactive scan対応。R3はinternal disposable targetだけを扱う。
  • 一つのscannerや一つのfixtureを「包括的なプロ診断」と表示すること。
  • すべての言語、framework、認証方式、databaseを一度にsupport対象へ加えること。
  • stable昇格とsafety classの混同。stableなR3 profileはあり得るが、R3の承認要件は緩和しない。
  • 環境不足時にfallbackでhost実行すること。stableでもpreflightは正当にblockedを返せる。
  • 既存legacy profile IDの削除。安全性と成熟度を分けるscope narrowingは行うが、historic runは当時の catalog hash/copyで表示し、新IDへの履歴書換えはしない。

4. Stable contract

4.1 Meaning of stable

stableは次のすべてを意味する。

  • 公称する入力、capability、対象、limitationが実装と一致する。
  • supported environmentでは同じ入力に対して再現可能なexecution planを生成する。
  • required capabilityが欠落、失敗、不明の場合にpassまたはcompleteへ誤分類しない。
  • tool failure、invalid output、timeout、cancel、cleanup failureを区別して保存する。
  • 安全境界違反を実targetへのrequest前に拒否する。
  • finding、artifact、coverage、limitation、result policyを同じcanonical profileへ結び付ける。
  • supported scope外は明示的にnot_applicableまたはblockedとし、暗黙fallbackしない。

4.2 Absolute safety gates

次の値はprofileごと、platformごとにすべて0でなければならない。

4.1 Non-negotiable safety metrics
Metric Required value
publicまたはproduction targetへの未承認request 0
read-only/passive profileのscan phaseからstate-changing methodがupstreamへ到達 （認証profileのallowlisted login transactionは別計上） 0
credential/secret canaryのlog、artifact、finding、event漏洩 0
host repositoryの内容またはGit status変化 0
owned container、network、listener、temporary pathのcleanup漏れ 0
required tool failure、全transport failure、invalid outputのfalse pass 0
catalog/preflight/plan/input hash不一致後に開始したrun 0

4.3 Quality and operation gates

  • supported contractのpositive/negative fixture coverageを100%にする。
  • 各finding detectorはvulnerable/fixed pairを持ち、false-fixedを0にする。
  • 同一candidate commitで3回連続実行し、normalized resultとcleanup verdictが一致する。
  • support対象platformをqualificationに列挙し、未検証platformをstable supportと表示しない。
  • 各profileの最大request、rate、timeout、memory、CPU、artifact sizeをpolicyとして固定する。
  • release branchではprofile qualification verifierをrequired checkにする。

qualification/policy/manifestには新しいshared/canonical-json.tsのRFC 8785実装を使う。既存 catalog entry hashはhistoric run互換のため現行scan-profile-catalog-hash-v1を維持し、新しい canonicalizerで再計算しない。hash fieldごとのalgorithm IDをreceiptへ必須化し、algorithmの暗黙切替を拒否する。

testsはprofile policyが宣言する全case IDを3 repetitionずつ持ち、 artifactsの参照先が存在しなければならない。argvとoutput本文にはsecretを残さず、argvは server-owned command identityのredacted表現、stdout/stderrはdigestだけを保存する。 metricsはprofile IDでdiscriminateするstrict schemaとし、未知metricや欠落metricを許可しない。 repeatability group内のnormalized result hashとcleanup verdictは3件一致を要求する。timestamp/duration、UUID、 container ID等の非決定値はnormalized resultに含めない。

reviews entryはkind、platform user IDのSHA-256、decision、decidedAt、reviewed artifact refs、candidate commitを持ち、生の氏名/emailを持たない。R3とbusiness logic policyは1件以上の security_reviewer decision=approvedを要求する。それ以外のPR approvalはrepository branch protectionで検証し、receipt内reviewの代替にしない。

secret、absolute home path、生のrequest/response body、Docker socket pathをschemaで禁止する。 artifact pathはrepository-relativeまたはqualification run directory-relativeに限定する。

5.4 Exact promotion sequence

  1. 実装、claim、limitation、testをexperimentalのままmergeする。
  2. promotion branchではavailability、表示badge、experimental opt-in、qualification policy bindingだけを変更する。 実行code、schema、scanner imageを同commitで変更した場合はpromotion verifierが拒否する。
  3. Docker qualificationはそのcandidate SHAのclean checkoutでreceiptとpromotion manifestを生成する。
  4. Docker実行ごとのreceiptをSHAで集約し、verify:scan-profile-promotionsがcatalog diff、candidate commit、entry hash、receipt hash、全verdictを再検証する。
  5. verifier passとmaintainer approval後にmergeし、必要に応じて利用者が同artifactをrelease assetへ添付する。
  6. 一つでもblocked/failed/missingならavailability変更をmergeしない。

6. Wave A1 — api-readonly

6.1 Product contract

最初のstable contractを次へ限定する。

15. Rollout and rollback

15.1 Rollout

  1. claimとlimitationを先に修正し、experimentalのままqualificationを実行する。
  2. candidate branchでavailabilityをstableへ変更し、Dockerでpromotion verifierを実行する。
  3. Web/API/CLIの表示とopt-inを同じcommitで変更する。
  4. 最初のreleaseではsupport platformとinput variantを明示し、未検証variantを起動不能にする。
  5. release後のrun outcome、blocked reason、cleanup failure、false-pass reportをprofile ID別に監視する。

15.2 Rollback

  • rollbackはcatalog availabilityをexperimentalへ戻すだけで実行definitionを削除しない。
  • historic stable runの表示は当時のcatalog entry hashとresolution envelopeを使う。
  • 新規runだけにexperimental opt-inを再要求する。
  • qualification failureを隠すためにlimitationやrequired capabilityを弱めない。
  • resource leakまたはunauthorized requestを1件でも確認した場合は即時rollback条件とする。

16. Definition of Done

16.1 Per-profile DoD

  • 公称scopeと実装scopeが一致し、非対応範囲がUI/API/reportに表示される。
  • profile-specific positive/negative/fault/repeat E2Eが全件passする。
  • Section 4.2のabsolute safety metricsがすべて0。
  • scanner/runtime/input/policy/catalogのhash bindingが保存される。
  • required failureをpassまたはcompleteへ誤分類しない。
  • candidate commitのqualification receiptがverifierをpassする。
  • catalog、API、CLI、Web、report、docsが同じavailabilityを返す。
  • rollback testがpassする。

  • Wave Aの2 profileが限定scopeでstable。
  • dynamic testとsanitizer/fuzzのmaturityが分離される。
  • Wave B以降は各独立gateを満たしたprofileだけがstable。
  • experimentalを残すprofileに具体的なpromotion blockerが表示される。
  • professional-fullは本計画の結果だけでは昇格しない。
  • 全promotion receiptがcandidate commitとDocker image digestへ結び付く。

18. Normative references and design consequences

  • OWASP SAMM — Security Testing: automated baselineとapplication/business logicを理解したmanual expert testingを分離し、 business-logic profileの自動実行を包括診断と表示しない。
  • OWASP SAMM — Scalable Baseline: 広い未検証coverageより、限定範囲を信頼できる精度で検出し、false positive/negativeを計測して 段階的に拡張する。
  • OWASP SAMM — Control Verification: 修正済みsecurity bugを回帰testへ組み込み、expected pass/failとして継続実行する。
  • NIST SP 800-115: intrusive testでは事前のscope、assumption、limitation、risk、Rules of Engagementを固定する。
  • ZAP Automation Framework — Authentication: auth methodだけでなくverificationとauthentication statisticsをE2Eで確認する。
  • OpenAPI Initiative — Published OAS versions: 初回stable contractを2.0、3.0.0〜3.0.4、3.1.0〜3.1.2へ固定し、3.2.0は別qualificationまで拒否する。
  • RFC 6901 — JSON Pointer: 自己完結schemaで許可するinternal fragment referenceのparse/evaluationを独自記法にしない。
  • RFC 8785 — JSON Canonicalization Scheme: receipt、policy、manifestのhash前canonical JSONをruntime依存のproperty順にしない。
  • Schemathesis CLI filtering: exact method filter、rate limit、request timeout、retry 0、redirect 0を明示し、read-only operation contractをscannerとgatewayで共有する。
  • OSS-Fuzz documentation: fuzzを通常test executionと同一成熟度にせず、harness、engine、sanitizer、継続実行を独立してqualifyする。
  • OWASP Web Security Testing Guide v4.2: testing objective、scope、positive/negative requirement、reportingをprofile contractへ反映する。
