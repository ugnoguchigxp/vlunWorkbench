vulnWorkbench スキャンワークスペース刷新 コンポーネント設計

この文書は、スキャン画面、登録済みプロジェクトの削除、LLM生成Markdownレポート、 初回自動展開するLLMコメントを、再利用可能でテスト可能なReactコンポーネントとして 実装するための設計を定義する。

基準日 2026-08-20

ドキュメントレビュー結果

初版は画面構成と責務分割を説明できていたが、実装時に選択肢が残る箇所があった。 この版では以下を確定し、実装者が別案を検討しないで済む状態にする。

初版で残っていた実装上の曖昧さと、この版で確定した内容
優先度 初版の不足 確定内容

実装時に変更しない前提

  1. 新しいUI libraryを追加しない。React、Lucide、既存CSS変数と既存依存だけを使う。
  2. leaf componentからAPI、router、useScans() を呼ばない。
  3. route search paramsへ as never や as any を追加しない。
  4. 初回表示判定に localStorage、sessionStorage、cookieを使わない。
  5. project削除で repoPath、Git working tree、remote repositoryを変更しない。
  6. 旧画面と新画面をfeature flagで長期並行運用しない。work package 6で一度だけ切り替える。
  7. この設計書にない機能追加は同じ変更へ含めない。

目的

  • 最初の3秒で「対象プロジェクト」「スキャン開始」「最新結果」を判別できる。
  • 画面を大きな一枚のコンポーネントにせず、役割ごとの部品を組み合わせて構築する。
  • 登録情報の削除と、ローカルリポジトリのファイル削除を明確に分離する。
  • LLM生成レポートを安全にレンダリングし、Markdownソースとの切り替えを可能にする。
  • LLMコメントをユーザーごと・レポートごとの初回閲覧時に必ず展開する。
  • 既存のスキャン実行・診断・finding・report機能を失わず、段階的に移行できる。

対象外

  • スキャナー実行ロジック、検出精度、LLMプロンプト自体の変更。
  • プロジェクトのアーカイブ、復元、ゴミ箱機能。
  • プロジェクト削除時のローカルディレクトリやGitHubリポジトリの削除。
  • 既存の全スキャン関連コンポーネントを一度に削除する全面移行。
  • モバイル専用UI。狭い画面では一列へリフローするが、主対象はデスクトップとする。

参照モック

設計判断

  1. 既存コントローラーを境界として残す。 ScansProvider と useScansController は移行中も維持する。 新しい表示コンポーネントがAPIを直接呼ばないよう、コンテナからpropsを渡す。
  2. 表示部品はContext非依存にする。 useScans() を呼ぶのはページ、プロジェクト列、レポートの各コンテナまでとし、 カード、表、メニュー、ダイアログ、アコーディオンは純粋なpropsコンポーネントにする。
  3. ルートを選択状態の正とする。 projectId、scanRunId、tab、reportId は URL searchに保持する。再読み込みや共有URLでも同じ表示を復元する。
  4. 危険操作はサーバーでも確認する。 削除ダイアログの入力一致だけに依存せず、APIもプロジェクト名と所有者を検証する。 queued/runningのスキャンが存在する間は削除を拒否する。
  5. 初回表示はサーバーで永続化する。 localStorage ではなく、ユーザーとレポートの組に閲覧済み時刻を保存する。 別ブラウザでも初回条件が一貫する。
  6. Markdown表示は既存の安全化処理を再利用する。 raw HTMLと画像を無効化し、安全なURL schemeだけを許可する現行 renderMarkdownToSafeHtml を共通レンダラーへ抽出する。

Web APIエラー型

type ApiErrorBody = {
  message: string;
  code?: string;
  details?: unknown;
};

export class ApiRequestError extends Error {
  readonly status: number;
  readonly code: string | null;
  readonly details: unknown;
}

function isApiRequestError(error: unknown): error is ApiRequestError;

web/src/api/core-request.ts の requestJson は、非2xx応答で ApiErrorBody を安全にparseし、ApiRequestError を送出する。JSONでない応答は 既存のfallback messageを使い、code=null、details=null とする。 use-project-delete-controller.ts は isApiRequestError でnarrowingし、statusとcodeの組み合わせだけでUI状態を決める。 as any、message文字列の部分一致、HTTP clientの二重実装は禁止する。

サーバー処理

  1. routeはrequestをvalidateし、ProjectDeletionService.deleteOwnedProject だけを呼ぶ。
  2. serviceは projectId でprojectを読み、認証ユーザーの所有権を検証する。
  3. requestの confirmation と保存済みproject名を完全一致で検証する。
  4. transaction内でproject-owned active workを列挙し、一件でもあれば409を返す。
  5. 同じtransaction内でartifact cleanup manifestを作り、cleanup jobをpendingで保存する。
  6. ProjectRepository.deleteOwnedProject でproject行を削除し、transactionをcommitする。
  7. commit後に ProjectArtifactCleanupRunner.enqueue(jobId) を呼ぶ。
  8. runnerはstorageごとのrun directoryを削除し、jobをcompletedにする。
  9. cleanup失敗時もproject削除は取り消さず、jobをfailed/retryableとして保存する。
  10. server起動時にpending/failed jobを再queueする。

active work guard

次のproject-owned tableについて、statusが queued または running の行を activeとして扱う。tableがscan runを介してprojectへ属する場合はscanRunIdでjoinする。

  • scan_runs
  • static_intelligence_prepare_jobs
  • scan_reviews、scan_reports、scan_diagnostic_runs
  • dast_runs、dynamic_runs、reproduction_runs
  • active_assessment_runs
  • threat_model_runs、business_logic_runs

response detailsにはkindと件数だけを返し、process IDやcommandを返さない。guard queryは api/modules/scans/project-deletion-active-work.ts に集約し、routeへSQLを置かない。

artifact cleanup manifest

type ProjectArtifactCleanupManifest = {
  scanRunIds: string[];
  dastRunIds: string[];
  dynamicRunIds: string[];
  reproductionRunIds: string[];
};

IDはproject削除前にDBから取得した値だけを使う。client入力や repoPath をmanifestへ入れない。 ArtifactStorage、DastArtifactStorage、 DynamicArtifactStorage、ReproductionArtifactStorage に removeRunDirectory(runId) を追加する。各methodはbase directoryからのpath containmentを 検証してから fs.rm(target, { recursive: true, force: true }) を行う。

project配下のDBデータは外部キーの ON DELETE CASCADE で削除する。 repoPath はcleanup manifestへ含めず、ローカルのrepositoryには一切触れない。

LLM Markdownレポート設計

データ源

  • Markdown本文: completed ScanReport のreport artifact。
  • LLMコメント: 同じscanの最新completed ScanReview からViewModelを組み立てる。
  • 重大finding導線: findingTriageHints と実findingをIDで結合する。
  • 目次: Markdownをparseした見出しから生成し、LLMに目次生成を依頼しない。

report workspaceの取得契約

  1. URLの reportId からselected reportを決める。
  2. GET /api/scan-reports/:id でmetadataとownershipを確認する。
  3. statusがcompletedの場合だけ、既存 GET /api/scan-reports/:id/download からMarkdown本文を取得する。
  4. 同じscanの scanReviews から最新completed reviewを選び、LLM comment ViewModelを組み立てる。
  5. LLM commentが存在する場合だけviewer stateを取得する。
  6. 3つのrequestはreportIdごとのrequest sequence番号を持ち、古いresponseを捨てる。
report workspaceの画面状態と表示
条件 表示 操作
scan未選択 「スキャンを選択するとレポートを確認できます」 履歴tabへのlink
reportなし 「このスキャンのレポートはまだありません」 既存の生成可能条件を満たす場合だけ「レポートを生成」
queued/running 「レポートを生成中…」とstatus なし。既存pollingで更新
failed 保存済み errorMessage の安全な要約 既存の再生成条件を満たす場合だけ再生成
completed・本文loading toolbarとarticle skeleton download buttonは有効、copyは無効
completed・本文取得失敗 「レポート本文を読み込めませんでした」 「再読み込み」とdownload
completed・LLM reviewなし accordionを出さず「LLMコメントはまだ生成されていません」 report本文は通常表示
completed・全取得成功 comment accordion、Markdown本文、目次 render/source、copy、download

LLM comment ViewModelの決定規則

  1. reviewは status === "completed" のうち createdAt が最新の一件を使う。
  2. headline はcritical/high findingがあれば「最優先で確認が必要な問題があります」、 なければ「LLMによる確認結果」とする。
  3. summary は riskOverview、次に summary を使う。両方なければaccordionを出さない。
  4. priorityFinding は findingTriageHints 内のfindingIdが実findingに存在するものだけを候補にし、 critical、high、medium、low、infoの順、同一severityは配列順の最初を使う。
  5. secondaryNotes は recommendedNextActions の先頭2件だけを使う。
  6. 存在しないfindingId、自由形式HTML、providerのraw outputを表示へ渡さない。

Markdown安全性

  • raw HTMLは描画しない。
  • 画像は描画しない。
  • linkは http:、https:、mailto: のみ許可する。
  • Markdownソース は textContent 相当で表示し、HTMLとして挿入しない。
  • 外部linkは新規タブへ強制せず、既存のproduct policyに合わせる。
  • 見出しIDは同一文書内で一意になる決定的sluggerを使う。

現行 MarkdownEditor から安全化関数を web/src/components/safe-markdown.ts へ移し、 editorとviewerの両方が同じ関数を利用する。viewerは編集toolbarやtextareaを持たない。
