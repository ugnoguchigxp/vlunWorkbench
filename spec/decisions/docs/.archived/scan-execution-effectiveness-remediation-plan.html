1. 結論

現在の問題はscannerの数ではない。scan profile、project capability、preflight、runner、 outcome、diagnostic、reportが別々に妥当そうな判定を行い、その境界で情報が失われるため、 全体としては「実行したが確認できていない」runが生まれている。

改善の中心は、実行前に一つのScanExecutionPlanを確定し、全componentが同じplanと verdict contractを参照することである。profileの配列を順番に回して後からwarningを集める方式をやめ、 applicability、readiness、coverage requirement、実行順、証跡要件を先に固定する。

実装順は次で固定する。

  1. 最新runを再現可能なcharacterization baselineとして固定する。
  2. project別のapplicabilityとreadinessを持つexecution planを導入する。
  3. strict profileのpreflightをfail closedへ変更し、version/provenanceを実測値へ結び付ける。
  4. source SAST、runtime target、API schema、dependency scopeをproject適合型へ組み直す。
  5. lifecycle、coverage、assessment verdictを分離し、UI/API/reportの表示を統一する。
  6. diagnosticとLLM reviewをplan・preflight・実在commandに拘束し、reportを一つに確定する。
  7. 複数種類の実repositoryと障害注入でend-to-end gateを閉じる。

完了基準は「scanner processが終了した」ではない。strict profileでは、全applicable required stepが readyで、実行され、必要なartifactとcoverageを残し、最終reportがその事実を正しく表示した場合だけを completeとする。

本計画自体の完了には、productionで提供するscanner/scan modeを一件ずつ通すreal E2Eを実装し、 後述する全caseが同一commitでpassすることを必須とする。unit test、mock executableを使うCLI test、normalizer fixture test、runner直呼びtestだけではE2E合格と数えない。

2. 既存計画との関係

本計画はBackend Scanner Hardening and todolist Validation Planを置換しない。同計画で実装済みの tool-run単位artifact、atomic metadata update、profile_outcome、typed preflight、 isolated todolist acceptanceを前提とし、productionの総合profileが実repositoryで完走するまでの残件を扱う。

次の項目は再実装しない。

  • ScanArtifactSinkによるartifact owner分離とSHA-256保存
  • scan_runs.profile_outcomeのcanonical field化
  • scan preflight check、binding、source revisionの保存
  • Schemathesisのrepository schema-first applicability判定
  • todolist acceptance用の一時DB、artifact root、isolated runtime target

Planning baseline時点のworktreeには、RuntimeTargetProvider、immutable todolist source snapshot、 Docker image identityに関する作業中差分がある。これらを破棄または上書きせず、最初のPRでtestを通して 本計画のruntime/evidence contractへ取り込む。

5. 目標状態と不変条件

次の不変条件をproduction contractとする。

  1. strict profileは、applicable required stepに既知blockerが一つでもあればscanner processを一つも起動しない。
  2. not_applicableは、project capability evidenceとstable reason codeがある場合だけ成立する。 missing configuration、unknown、probe errorをN/Aへ落とさない。
  3. applicable stepのfailed、skipped、0 request、artifact欠落はcompleteへ昇格しない。
  4. supported source languageを検出したstrict profileでは、対応SAST engineが実行されない限りcompleteにしない。
  5. reproducible=trueは、profile、target snapshot、rule/data digest、actual binary/image identity、 sanitized argumentsがすべて保存され、互換checkを通った場合だけ設定する。
  6. scan scopeの宣言とrunner argument、raw artifactの対象集合が一致しない場合はcoverage gapにする。
  7. finding 0、N/A、未実行、失敗を同じ数値へ畳み込まない。
  8. canonical final reportはdiagnostic終了後に一つだけ存在し、同じplan hashとevidence snapshotを参照する。
  9. protected CI、またはqualification admission controlを明示的に有効化したstrict profileの全applicable scanner stepは、同一vulnWorkbench commit、toolbox/data/image lock、case contractで合格したE2E qualificationへ結び付く。admission control下ではqualification欠落・identity不一致でscanner processを 起動しない。通常の個別scanは、CI artifact未配置だけではblockしない。
  10. LLMはdeterministic verdictを上書きせず、存在しないcommand、対象外technology、未保存の証拠を提案へ使えない。
  11. target repository、target DB、original worktreeをscan実行とtest harnessが変更しない。

7. Profile policyの再設計

7.1 Strictとbest effortを分ける

現在のfull-security-scanはstrict profileへ変更する。部分結果を保存したい用途は別profile security-inventory-best-effortへ分離し、同じ名称・色・完了表示を共有しない。

  • strict: applicable required stepが一つでもblockedならrunを開始しない。
  • strict: 実行中にapplicable required stepが失敗したらoutcomeはincompleteまたはfailed。
  • best effort: 実行できるstepを保存するが、coverage gapを常に前面表示する。
  • completed_with_warningsはupdate notice等、coverageを減らさないwarningだけに使う。

7.2 Capability compiled profile

profiles.tsの固定step配列を直接実行せず、technology pluginとproject factsを使ってplanへcompileする。

  • TypeScript/JavaScript/Python/Go/Javaを検出し、対応rule setがある場合はSemgrepをrequired-if-applicableにする。
  • Semgrep adapterのenvironment opt-inをstrict profileの参加条件に使わない。
  • API evidenceがないprojectではSchemathesisを証拠付きN/Aにし、coverage gapや改善要求にしない。
  • API evidenceがあるのにschemaがない場合はN/Aではなくapi_schema_required_but_missingでblockedにする。
  • Web runtime evidenceがないlibrary/CLIではruntimeをN/Aにできる。
  • server capabilityがあるprojectでstart planがない場合はN/Aではなくblockedにする。
  • project kindがunknownの場合は安全側のapplicability=unknownとし、strict runを止める。

technologyPlugins.capabilityPlanと実際のprofile stepが矛盾しないことをassertする。 たとえばSemgrepがplan上coveredなのにtool runが存在しない状態をschema validationで拒否する。

7.3 Strict profile requirement matrix

requiredとfailurePolicyを既存定数のまま流用せず、compiled planで次の requirementへ確定する。applicableな行はすべてrequired_if_applicableであり、失敗・未実行・ artifact/coverage不足をwarningへ落とさない。

full-security-scan Web runtime applicable dast:web_passive_standard、nuclei:safe、zap:baseline

8. Fail-closed preflightとprovenance

8.1 Mode

  • Web、CLI、integrationのstrict profileは常にenforcedを指定する。
  • 環境変数未設定時のproduction defaultをenforcedへ変更する。
  • shadowはpreview、migration観測、明示best-effort profileだけに限定する。
  • UIはblocked checkとactionをstart前に表示し、strict run buttonを無効化する。

8.2 Observed tool identity

scanner-provenance.tsのmanifest由来reproducibleを廃止し、preflightとrunnerの実測を統合する。

  • host runnerはresolved executable path、normalized version、可能ならbinary SHA-256を保存する。
  • Docker runnerはimage ref、RepoDigest、image ID、platformを分けて保存する。
  • expected/observed versionまたはdigest不一致はcompatible=false。
  • runner開始直前にpreflight bindingを再確認し、TOCTOU差分をpreflight_changedで停止する。
  • tool run metadataはexpected identityとobserved identityを両方保存する。
  • scanner E2E qualificationはprotected CIのrelease gateで必須とする。通常の個別プロジェクトscanを CI artifact未配置だけで止めてはならない。regulated deploymentでのみ VULN_WORKBENCH_REQUIRE_SCANNER_E2E_QUALIFICATION=trueを設定し、 observed scanner identityとの不一致をscanner_e2e_qualification_mismatch、manifest欠落を scanner_e2e_qualification_missingとしてpreflight blockerにする。
  • scanPreflightCheckKindSchemaへscanner_e2e_qualification、 scanPreflightActionSchemaへrun_scanner_e2e_qualificationを追加する。
  • reportはreproducibleだけでなく、compatible checkの内訳を表示する。

8.3 Orchestrator identity

scannerだけでなく、scanを組み立てたvulnWorkbench runtimeのidentityを保存する。

  • Git commitまたはrelease version
  • dirty state
  • server bundle/build digest
  • profile compiler version
  • normalizer versionとreport/diagnostic pipeline version
  • scanner E2E qualification manifest hashとqualified CI commit

identity不明のdevelopment runtimeはlocal diagnosticとして実行できるが、authoritativeまたはreproducible claimに使わない。

9. Runtime target lifecycle

9.1 Start planの優先順位

  1. projectに保存された明示的・versionedなruntime target config
  2. pinned container imageまたはimmutable source snapshotから作るsandbox plan
  3. framework pluginが生成するsafe start plan
  4. 標準package scriptから生成するplan
  5. 根拠付きN/Aまたはblocked。任意commandの推測実行はしない。

project runtime configはcommand文字列をshellへ渡さず、executable、args、cwd、env allowlist、port、 readiness path、sandbox policyをtyped fieldで保存する。host executionは明示consentを要求し、可能な対象は containerまたはsandboxを優先する。

9.2 Single preparation phase

DAST、Nuclei、ZAP、Schemathesisが個別にtargetを起動しない。RuntimeTargetProviderが一度だけ prepare/start/readinessを実施し、全applicable runtime stepへ同じoriginとtarget identityを渡す。

  • target preparation失敗は一つのroot cause eventとして保存する。
  • 下流stepはblocked_by_target_preparationとし、同じerror messageを複製しない。
  • request gateway metricsをstep別とaggregateで保存する。
  • applicable runtime stepのrequest count 0は必ずgapにする。
  • target stopとcleanupは成功・失敗・cancel・timeoutの全経路で一度だけ実行する。

9.3 spec-htmlの扱い

spec-htmlへ診断都合のdev、start scriptやAPI schemaを追加しない。 対象はlocal viewer/CLIであり、runtime診断を行う場合は、immutable snapshotをbuildし、fixture documentを指定して loopback上で起動する明示configをvulnWorkbench側に保存する。API surfaceがないことはSchemathesis N/Aの根拠とする。

10. Static sourceとdependency coverage

10.1 Source SAST

  • strict full profileではsupported languageのowned Semgrep rulesをrequiredにする。
  • rule catalog digest、rule count、target file count、parsed line率、parse errors、ignored file countをartifact metadataへ保存する。
  • parse errorまたはignoreがcoverage thresholdを超えた場合はpartial/incompleteにする。
  • raw resultのcandidate countとnormalized finding countの差を理由付きで保存する。
  • false-positive triageはfinding reviewとして行い、ruleを無効化して0件へ合わせない。

10.2 Dependency scope

ScanScopePolicyからrunner optionへの写像を一か所へ集約する。

  • includeInstalledDependencies=trueならTrivy filesystemとSBOMへ--include-dev-depsを渡す。
  • development、optional、peer、workspace dependencyのcoverageを別々に記録する。
  • OSV lockfile package setとSBOM component setをecosystem別に比較し、差分理由を保存する。
  • scannerが依存区分を表現できない場合は「covered」ではなくpartialにする。
  • stderrにscope縮小noticeが出た場合はnon-blocking logへ埋めず、typed limitationへ変換する。

11. Outcome、API、UI

11.1 Verdict model

次の三層を混ぜない。

Scan verdict layers
層 例 用途
Lifecycle status queued / running / terminal process制御
Execution outcome blocked / completed / incomplete / failed / cancelled / timed_out planを実行できたか
Coverage verdict covered / partial / gap / not_applicable 診断面を確認できたか

finding countはこの三層へ影響させない。finding 0でもcoverage gapならincomplete、findingが存在しても全stepが 完走していればexecutionはcompletedである。

profile_outcomeへblockedとincompleteを追加し、legacy completed_with_warningsを新規coverage gapへ使用しない。migrationとAPI schemaを同じPRで更新する。

11.2 UI rules

  • profile選択時にapplicable、N/A、blocked、必要actionをpreviewする。
  • strict blockerがある場合はstart buttonを無効化し、修復導線を表示する。
  • blockedとincompleteに成功色・check icon・「完了」を使わない。
  • finding 0の近くに、executed/applicable、request count、source SAST、dependency scopeを表示する。
  • workflow completionはterminal statusだけでscanner stepをcompleteにしない。
  • N/A stepは「skip」ではなく、理由とevidenceを持つ「対象外」として分母から除外する。

主要変更先はweb/src/domains/scans/workflow-completion.ts、 web/src/domains/scans/diagnostic-dashboard.ts、 web/src/domains/scans/scan-profile-display.ts、profile preview/start UIとする。

12. Diagnostic、LLM review、report

12.1 Deterministic bundle

ScanReviewBundleへ次を追加する。

  • execution plan summaryとplan hash
  • preflight summary、全limitation code、required/optional blocker
  • source SAST coverage、parser/ignore statistics
  • runtime target applicability、start plan、request metrics
  • dependency scopeとpackage class coverage
  • project execution facts: project kind、存在するpackage scripts、schema evidence、allowed verification commands
  • orchestrator/scanner actual identityとcompatibility verdict

collectBundleLimitations()はruntimeだけでなく、preflight、source SAST、dependency scope、 artifact integrity、orchestrator identityを収集する。既知blockerをLLMが言及しなくてもdeterministic reportへ必ず出す。

12.2 Recommendation validator

scan-review-output-validator.tsへproject fact validationを追加する。

  • verificationCommandsはbundleに保存したallowed commandまたは製品標準commandだけを許可する。
  • 存在しないpackage scriptを参照したoutputをrejectする。
  • N/Aと確定したtechnologyの導入を、coverage修復として自動要求しない。
  • preflight blockerごとに少なくとも一つの対応taskまたは明示的非対応理由を要求する。
  • scanner findingがない場合も、execution gap IDを改善taskへ参照できるtyped referenceを導入する。
  • LLMがdeterministic severity、applicability、readiness、coverage verdictを変更できないようにする。

12.3 Single canonical final report

scan直後に必要ならpreliminary reportを作れるが、finalとは呼ばない。 diagnostic終了後にcanonical final reportを生成し、scanごとに一つだけcurrentにする。

api/modules/scans/scan-finalization-service.tsを追加し、deterministic diagnostic、 optional LLM review、canonical final report transactionをこのserviceだけが所有する。 runProfileScanはscanner executionとpreliminary reportまでに限定し、CLI、Web worker、 recovery job、E2E harnessはscan成功後に同じfinalization serviceを呼ぶ。

  • scan_reportsへstageとsupersedes_report_idを追加する。
  • current final reportのunique partial indexまたはguard付きtransactionを実装する。
  • final reportはplan hash、diagnostic snapshot hash、review ID、pipeline versionを表示する。
  • 古いpreliminary reportは履歴として保持するが、UI default downloadにしない。
  • diagnostic/report failure時はfinal absentを明示し、preliminaryをfinalへ昇格しない。

14. Scanner単位の必須real E2E gate

14.1 この計画でE2Eと呼べる条件

scanner E2Eは、target入力からexecution plan、enforced preflight、real scanner process、normalization、DB、artifact、coverage verdict、deterministic diagnostic、canonical final report、cleanupまでを一つのcaseで通す。全caseはrunProfileScanを通り、success scenarioは同じproduction finalization serviceで終了する。

次の条件を一つでも外すtestはunitまたはintegrationであり、scanner E2E合格へ数えない。

  1. scannerはlocked toolbox内のreal binaryまたはpinned Docker imageを使う。mock executable、 canned scanner stdout、normalizerへのfixture直投入は禁止する。
  2. 対象はversioned fixtureまたはpinned clean repositoryのimmutable snapshotで、caseごとに一時DB、 artifact root、target runtime、Docker resourceを分離する。
  3. preflightのexpected identityとrunner直前のobserved identityが一致し、 compatible=trueである。
  4. plan上のstep ID、applicability、readiness、requirementと、実tool run/step resultが一対一である。
  5. raw artifactはDB owner、storage key、SHA-256、size、content typeを持ち、保存bytesを再読込して scanner固有schemaでparseできる。
  6. scanner固有のwork counterが下限を満たす。process起動だけ、空artifactだけ、request 0だけではpassしない。
  7. case contractの期待artifact roleとverdictを照合する。tool/data更新時に実行結果から contractを自動更新しない。
  8. final reportを有効にし、deterministic diagnosticを通す。外部LLM transportだけは固定response adapterを 注入できるが、scanner、target、gateway、normalizer、repositoryをmockしない。
  9. case終了後にtarget repositoryのHEAD/status、temporary process、container、network、volume、DB writer、 artifact handleが残っていないことを検証する。
  10. protected CIではcase resultがpassed以外ならjobを失敗させる。 skipped、blocked、not_runは未合格である。

14.2 Scanner inventoryとcase registry

scripts/scanner-e2e-case-registry.tsはbuildScanProfiles()のenabled profileとcreateStaticScannerAdapterRegistry()から次のproduction inventoryを導出し、 scanner-e2e-cases.v1.jsonとの全単射を検証する。

  • 登録済みstatic adapterはgitleaks、osv、trivy、 semgrepの全4件であること。Semgrep executableの有無はpreflightで判定し、adapterから除外しない。
  • buildScanProfiles()から到達できる全scanner-bearing stepを、engine、input mode、安全性contract、artifact roleの組でcanonical modeへ変換した集合

同じengineでも入力・安全性・artifact contractが異なるmodeは別caseにする。OSVのmanifestと installed tree、Trivyのfilesystem/SBOM/image、SchemathesisのN/A/read-onlyは それぞれ別gateである。case registry testは重複ID、未知scanner、未対応inventory、削除済みstep、 fixture path不存在を失敗させる。

standalone DAST API、disabled profile、active assessmentは本計画のinventory外とする。それらをgeneric profileまたはdefault production profileへ追加するPRは、追加と同時にscanner E2E caseを作らなければ inventory gateを通らない。

14.4 E2E evidence contract

現在のshared/schemas/scanner-e2e-evidence.schema.tsは一case一成功runを記録する。 必須fieldはcase/contract、scan run、executionSurface=profile_orchestrator、 execution plan hash、preflight hash、target source revision、manifest/execution binding、case-scoped scannerIdentityHash、tool version、image digest、artifact ID、 diagnostic run/status、canonical final report/artifact IDである。scripts/scanner-e2e.tsは runProfileScanの後にproduction ScanDiagnosticRunnerと finalizeScanAfterDiagnosticを実行し、finalization失敗をcase失敗にする。browser-only passive DASTはscanner container imageを持たないためimageDigestsを空にできるが、browser runtimeを含むscannerIdentityHashは必須とする。

以下のsuccess/fail-closed scenarioを一bundleへ拡張する案はv2の作業項目であり、v1 evidenceへ 任意fieldを足して互換性を壊してはならない。v2を開始する際はschema、verifier、qualification builder、 case contractを同一変更で更新し、v1のqualificationを再利用しない。

top-levelにscenariosを持ち、successとfail_closedを ちょうど一件ずつ要求する。scenarioはexecuted_success、 not_applicable_success、preflight_blocked、 execution_incomplete、cleanup_failedのdiscriminated unionとし、 適用不能fieldをnullableで埋めない。preflight blockedはartifact/reportを持たず、execution incompleteは生成済みartifactとcurrent finalの有無をcase contractどおり検証する（v2設計）。

14.6 Assertion catalogとcase別必須集合

verifierは文字列messageではなく、次のstable assertion IDを検証する。case contractは後述する case種別ごとの必須集合をそのまま使い、任意にassertionを除外しない。

  • INV-01: production inventoryとcase registryが全単射
  • ENT-01: production service entrypointを通過
  • PLAN-01: plan stepと実step resultが一対一
  • PREF-01: enforced preflightがsuccess contractどおりreadyまたはnot_applicableで、 fail-closed scenarioではblocked、binding再確認済み
  • PROV-01: expected/observed identity一致、compatible true
  • WORK-01: scanner固有work counterがcontract下限以上
  • ART-01: 必須artifactが存在し、owner/storage/SHA/size/schemaが有効
  • NORM-01: reviewed expected finding/rule集合とnormalized結果が一致
  • VERDICT-01: execution outcomeとcoverage verdictがcase contractどおり
  • REPORT-01: current canonical finalが一件でplan/evidence hash一致。preflight_blockedではfinal 0件であることを検証する。
  • SAFE-01: public request、禁止method、credential leakage、target mutationが0
  • CLEAN-01: repository不変、process/container/network/volume残数0
  • FAIL-01: companion failureがstable reason codeでfail closed

14.7 terra向け固定実装順

  1. S8でevidence schema、JSON contract、case registry、inventory test、evidence verifierを先に追加する。 この時点ではproduction挙動を変更しない。
  2. 現行todolist-scan-acceptance.tsからscanner別処理を scripts/scanner-e2e.tsへ移し、全generic caseをrunProfileScan経由にする。 aggregate profile検証だけを元scriptに残す。
  3. toolbox manifest、scanner data lock、ZAP image digestを検証し、real toolが不足した時点でcaseを失敗させる。 自動downloadやpublic network fallbackは追加しない。
  4. E2E-GL-01、E2E-OSV-MANIFEST-01、E2E-OSV-INSTALLED-01、E2E-TRIVY-FS-01、 E2E-SEMGREP-01、E2E-SBOM-01の順にS9を実装する。一caseがpassするまで次へ進まない。
  5. RuntimeTargetProviderをproduction entrypointへ接続した後、E2E-DAST-01、E2E-NUCLEI-01、 E2E-ZAP-BASELINE-01を実装する。三caseでtarget preparation/start/stopが各profile runにつき一回であることをassertする。
  6. E2E-SCHEMATHESIS-NA-01、E2E-SCHEMATHESIS-RO-01、E2E-TRIVY-IMAGE-01を実装する。
  7. 全個別case合格後だけS11のspec-html/todolist/full profileを実行し、A1-A10と連続2回の再現性を閉じる。
  8. S12でprotected CI jobとrelease verifierを必須checkへ登録する。job未実行、case欠落、evidence欠落をmerge可能にしない。

各scannerのproduction codeを変更するPRは、対応E2E caseの追加または既存caseのpass evidenceを同じPRへ含める。 「S12でまとめてE2Eを書く」は禁止する。fixtureの期待値を実装結果に合わせて弱める変更と、 production codeとbaselineを同時に無review更新する変更も禁止する。

14.8 固定package command

package.jsonの実装済みcommandは次である。全12件は一つのevidence bundleで実行するため、個別--onlyの出力をqualificationへ渡してはならない。

scanner-e2e:qualify = verified evidenceから artifacts/scanner-e2e/qualification.v1.json を生成
test:scanner-e2e = contract && run && verify && qualify

個別調査はbun run scripts/scanner-e2e.ts --toolbox-image vuln-workbench-toolbox-semgrep:local --only gitleaks --evidence /tmp/gitleaks-evidence.jsonのようにinternal case IDを指定する。 partial bundleはscanner-e2e:verifyで必ず拒否され、release evidenceにならない。

14.9 E2E合格をrelease/runtime条件へ結ぶ

protected CI collectorはscanner-e2e:runとscanner-e2e:verifyが全12 caseを 成功させた後にだけscanner-e2e:qualifyを実行し、 artifacts/scanner-e2e/qualification.v1.jsonを生成する。schemaは shared/schemas/scanner-e2e-qualification.schema.tsで固定する。

qualification manifestは次を必須とする。

  • case contract hash、qualification生成時刻、scanner manifest hash、execution hash
  • 全12 case IDとcase evidence SHA-256
  • 全caseが同じmanifest/execution bindingであること、およびcaseごとのscanner identity hash

qualification loaderは12件のcase ID、case evidence hash、case scanner identity hashの集合がcanonical contractと 完全一致しないmanifestをrejectする。protected CIはscanner-e2e:verifyの成功後にだけmanifestを release artifactとして発行し、deploymentはそのartifactをread-onlyで供給する。CI外で任意ファイルを配置できる 環境では暗号的なartifact attestationは別途deployment基盤で担保する（v1 loaderだけで署名検証を主張しない）。

protected CIはqualificationをrelease artifactとして必ず検証する。ここで比較するidentityはcaseごとの scanner/tool data/image/browser runtimeであり、利用者プロジェクトのsource revisionやtarget start planは 比較対象に含めない（それらはscanごとのpreflight bindingで別途証跡化する）。通常のscanはqualification artifactがローカルにないだけでblockedにしない。regulated deploymentだけは VULN_WORKBENCH_REQUIRE_SCANNER_E2E_QUALIFICATION=trueでこのadmission controlを有効にし、 entry欠落をscanner_e2e_qualification_missing、identity不一致を scanner_e2e_qualification_mismatchとしてrequired blockerにし、scanner processを0件にする。

16. Failure injection

  • preview後のprofile/manifest/source revision変更
  • scanner binaryのmissing、version mismatch、実行直前差し替え
  • scanner data missing/stale/digest mismatch
  • Docker daemon unavailable、image digest/platform mismatch
  • runtime target start timeout、readiness timeout、途中停止
  • gateway request 0、budget exhaustion、response truncation
  • invalid JSON、partial parse、normalized finding/artifact count mismatch
  • artifact file missing、size/SHA mismatch、duplicate final report
  • LLM unavailable、invalid structured output、存在しないcommand提案
  • cancel、wall-clock timeout、server restart、diagnostic recovery

各caseは期待status、outcome、coverage、reason code、event順、artifact数、外部process残存数をassertする。 error textの部分一致だけを受け入れ条件にしない。

第14章の各scanner caseは最低一つのfail-closed companionを同じcase ID配下に持つ。 successだけ通るcase、失敗をcompleted_with_warningsへ落とすcase、scanner processをmockして failure injectionを成立させるcaseは未合格とする。

19. Rollout

  1. execution planをshadow生成し、現行実行との差分だけを記録する。
  2. focused profileでenforced planを有効化する。
  3. 第14章のscanner別real E2Eを一件ずつ有効化し、全caseを通す。
  4. strict full profileを管理者・local環境でopt-inし、A1-A10を通す。
  5. Web defaultのfull profileをstrictへ切り替える。
  6. best-effort profileを別名・別表示で公開する。
  7. 旧completed_with_warningsrunは履歴表示のみとし、current baseline選択から除外する。

rollout中も、実測version mismatchをreproducibleと表示する既存bugと、存在しないverification commandの生成は feature flagなしで先に修正する。これらは互換機能ではなくtruthfulness defectである。

20. Rollback

  • schema migrationはadditiveにし、legacy readerを一release維持する。
  • execution plan builder障害時に旧full profileへ自動fallbackしない。strict runをblockedにする。
  • runtime providerの問題はruntime stepをN/Aへ偽装せず、blockedへ戻す。
  • LLM review障害時もdeterministic reportは生成するが、LLM review未完了を明示する。
  • UI rollback時もAPIのblocked/incomplete semanticsをcompletedへ変換しない。
  • historical artifact、report、review、decisionを削除または再解釈しない。

21. Definition of Done

次をすべて満たした時だけ本計画を完了とする。

  1. 最新baseline runの問題E-01からE-11に対応するregression testがある。
  2. full-security-scanがstrict execution planを使う。
  3. blocked required preflightでscanner processが一つも起動しない。
  4. supported languageのsource SAST未実行runがcompleteにならない。
  5. runtime applicable stepはrequest count > 0またはincompleteになる。
  6. API不在projectへAPI schema追加を要求せず、APIありschema欠落はblockedになる。
  7. full deep dependency scanとSBOMがdevelopment/test dependencyを含む。
  8. actual tool identity不一致をreproducibleと表示しない。
  9. orchestrator、profile、normalizer、report pipelineのidentityをrunから追跡できる。
  10. UI/API/reportがblocked、incomplete、N/A、finding 0を区別する。
  11. canonical final reportがscanごとに一つで、diagnostic/reviewを含む。
  12. E2E-GL-01、E2E-OSV-MANIFEST-01、E2E-OSV-INSTALLED-01、E2E-TRIVY-FS-01、 E2E-SEMGREP-01、E2E-SBOM-01がreal toolboxでpassする。
  13. E2E-DAST-01、E2E-NUCLEI-01、E2E-ZAP-BASELINE-01、E2E-SCHEMATHESIS-NA-01、 E2E-SCHEMATHESIS-RO-01、E2E-TRIVY-IMAGE-01がpassする。
  14. 全scanner E2Eがproduction service entrypointを通り、mock executableまたはstep runner直呼びを realScanner=trueとしていない。
  15. production scanner inventoryとcase registryが全単射で、全caseにreal success evidenceがある。 preflight blocker・partial bundle拒否・finalization拒否はunit/integrationのfail-closed gateで検証する。
  16. 全case合格からqualification manifestを生成し、protected CIのrelease gateで同じscanner/tool data/image identityを検証する。regulated deploymentでadmission controlを有効にした場合だけ、同じidentityのstrict preflightをreadyにする。
  17. A1-A10とfailure injection matrixが同一commitでpassする。
  18. 2回連続runでplan/evidenceの再現性とcleanupを確認する。
  19. typecheck、lint、docs:check、verify:strictがpassする。
  20. protected CI artifactへplan hash、target digest、scanner identities、result digest、final reportを保存する。
  21. 必須CI check scanner-e2e-realとscanner-e2e:verifyが同じevidence bundleに対してpassする。

22. Stop conditions

次のいずれかが発生したPRはmergeしない。

  • strict blockerをwarningへ降格しないとtestが通らない。
  • N/Aを増やすことでcoverage率を上げている。
  • full profileからSemgrep、runtime、dependency classを黙って外している。
  • finding 0と未実行0件を同じ表示・API値へ戻している。
  • version/digest mismatchを許容してreproducible=trueとしている。
  • request 0のruntime stepをcompletedとしている。
  • LLM出力でdeterministic applicability、coverage、severityを変更している。
  • preliminary reportをfinalとしてdefault表示している。
  • target repositoryまたはoriginal worktreeをtest/scanが変更している。
  • baseline threshold、分母、expected resultを実装結果に合わせて弱めている。
  • real scanner E2Eをmock executable、canned stdout、normalizer fixture直投入で代替している。
  • runtime scanner E2Eがprofile orchestratorを迂回してstep runnerを直接呼んでいる。
  • scanner inventoryに対応caseがない、またはcaseがskip/not-runのまま必須CIを通している。
  • scanner変更PRが対応E2E evidenceなしでmergeされようとしている。
  • qualification manifestがない、別commitである、またはidentity不一致なのにstrict scanを起動する。

23. Non-goals

  • active attack、認証突破、production targetへの侵襲的診断
  • scanner数を増やすこと自体を成果とする変更
  • spec-htmlやtodolistの製品コードをscan都合で変更すること
  • APIのないprojectへOpenAPIを追加すること
  • manual SAST 6候補を未検証のまま脆弱性と断定すること
  • false-positiveを消すためにowned ruleを一括無効化すること
  • historical runを新contractへ推測変換すること
  • LLM reviewをexecution completenessの判定主体にすること
