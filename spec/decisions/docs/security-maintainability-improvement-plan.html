セキュリティ境界・検出証跡・保守性の改善実装計画

Status: 実装・検証完了（個別再実行を含む / 2026-09-13）

作成日: 2026-09-12 / Owner: vulnWorkbench maintainers

計画基準コミット: ab1d6c2a44b5e9eba06f39361ed8f4cd058dad32

提示された20項目の改善案と、そのコード照合評価をもとにした実装計画。CI/CD関連を除き、妥当性の高い対策を先行する。条件付きの提案は依存調査・小規模実装・実測を完了条件に組み込み、調査前に大規模移行や削除を確定しない。

1. 目的と対象範囲

  • Webからのローカルファイルアクセスとスキャン実行の境界を一貫させる。
  • 検出能力の主張を固定入力・実行条件・証跡へ結び付け、未達理由を説明できるようにする。
  • 既存の能力別所有方針に沿って実装を整理し、設定・障害解析・引き継ぎを改善する。
  • 認証、project所有者制御、SQLite Writer経由の書込み、bounded scanner、秘密情報の非伝播という既存契約を維持する。

対象外: GitHub Actions等のworkflow変更、CIへのlint・生成物差分チェック追加、pre-commit/pre-push変更、release/tag自動化、GHCR公開、署名・provenance配布、CODEOWNERS・必須自動レビュー、定期CI演習。既存のローカル検証コマンドは利用する。以下に着手時の計画と実施結果を併記する。外部公開は実施対象に含めない。

3. 着手前の確認と比較基準

各作業の開始時に対象コードを再確認する。レビュー時の数や欠落を固定的な事実として扱わない。基準コミット、実行コマンド、対象テスト結果、入力ハッシュ、設定の非秘密部分を記録し、変更後に同条件で比較する。

  • Web登録・一覧・スキャン開始、CLI、MCP、NightWorkersのパス解決、所有者確認、snapshot生成経路を一覧化する。
  • 実行モードの環境変数・SQLite保存値・既定値の優先順と、初回起動・既存環境の挙動を記録する。
  • mutationの入力源、Zodのparse/safeParse/zValidator、service側検証、認可処理を区別して記録する。
  • 検出能力の実測と再現に既存のLinuxクリーン測定とJava独立fixtureが記載されている。P04・P05はこれらの実装・証跡を確認し、重複した測定器を作らない。
  • READMEの版管理証跡とローカル結果は別実行として扱う。版管理されていることと、測定時にworking treeがcleanだったことを区別する。
  • 所要時間・ファイル数等は開始時の実測を記す。ベンチマークや全件検証を今回実行済みとは扱わない。

5. P01 許可ルートと実行時再確認（優先度: 高 / 規模: L）

対象: api/security/project-path-policy.ts、api/routes/projects.route.ts、project-scan route、snapshot・実行入口、env/settings、project表示。

  1. アプリ共通の許可ルート設定を設計する。MCP/client別制限がある場合は共通制限との積集合とし、既存の狭い制限を統合によって広げない。設定更新権限は管理者に限定する。
  2. Webの登録・folder picker結果・pathPolicy表示・スキャン開始・snapshot作成前に共通policyを適用する。CLIの扱いも棚卸し表に明示し、暗黙の迂回経路を残さない。
  3. 許可ルート未設定は実行を拒否し、ローカル初期設定で管理者が対象を設定できる導線を用意する。起動失敗やデータ削除ではなく、設定不足の理由を返す。
  4. 既存projectは保存データを保持してblocked/missing理由を表示する。既存artifact閲覧と新規ホスト読取りを区別し、設定変更後はpolicyを再評価する。
  5. realpath後の境界判定に加え、内部symlinkとsnapshot追跡方針を確認する。実行直前の再確認だけでTOCTOUを解決したとは主張しない。

完了条件: 許可内、許可外、空設定、兄弟prefix、symlinkによる外部参照、存在しないパス、設定変更後の既存projectを検証する。拒否時にscanner起動・snapshot生成がないこと、他ユーザーのprojectは許可ルート内でも利用できないことを確認する。ルートを広げる自動フォールバックを設けない。

6. P02 Docker既定化（高 / M）

対象: api/config/runtime-settings.ts、api/app/env.ts、preflight、bootstrap、設定UI。

  1. 設定未指定時の既定を環境によらずdockerにする。現行キーSCAN_EXECUTION_MODEと保存済み設定の優先順を維持・文書化する。
  2. daemon・image・資格確認に失敗した場合は実行前に理由と復旧方法を返す。hostへ自動変更しない。
  3. 保存済みhost指定は維持して明示表示する。過去の既定値を保存しただけか識別できない場合は、その限界を記録して管理者に選択状態を示す。
  4. hostは環境設定または管理者UIによる明示選択に限定する。非対話CLIやAPIから対話的な確認待ちを発生させない。

完了条件: 新規・既存環境、明示host/docker、daemon不在、image不在、資格不備のケースを確認する。隔離・resource limit・秘密情報非伝播に回帰がなく、失敗時にhost processを起動しない。

7. P03 入力検証と認可（高 / M）

対象: api/routes/、関連service、shared/schemas/。

  1. route台帳を作り、body/param/query、検証位置、所有者照合、管理者要件、副作用を記録する。GETの機密読取りも認可監査に含める。
  2. 欠落だけを修正する。既存parse/safeParseは有効な検証として扱い、共通形状のみshared schemaへ寄せる。
  3. 不正JSON、上限超過、enum不正、未知IDの扱いとエラー応答を整理する。本文のないmutationに無意味なJSON検証を強制しない。
  4. ユーザーAのIDをユーザーBが指定する参照・更新・削除・実行をテストし、副作用がないことまで確認する。

完了条件: 全対象routeの検証・認可位置または適用不要理由が台帳にある。発見した欠落に回帰テストがある。zValidator出現数を安全性指標にしない。middleware名だけを見る禁止lintは追加しない。

8. P04 再現可能な証跡と未達理由（高 / M）

対象: scripts/benchmark/と既存capability測定、spec/evidence/、README日英版、検証手順。

  1. 既存verify:capability:linux等の固定入力・clean checkout・出力分離機能を確認し、不足だけ補う。
  2. gateごとに期待条件、観測値、失敗理由、根拠ファイル、利用者への影響、再確認手順を残す。検出不足・未実行・環境不備・証跡不備を分離する。
  3. READMEは承認対象の保存済み実行を参照し、最新ローカル値で自動上書きしない。既存測定がnot_metならそのまま説明する。
  4. source commit、corpus/ruleset/scanner/DB/imageのhash、時刻、clean状態、run IDを結び付ける。測定後に証跡をコミットしても測定時の状態を書き換えない。

完了条件: READMEから未達条件へ1リンクで到達できる。OSV fixture成功とgate falseなどの差を根拠付きで説明できる。固定条件で再実行可能で、異なるrunの数値を混ぜない。全gate合格を文書整備の必須条件にはせず、未達を隠さない。

9. P05 Java解析の方針と実コーパス評価（高 / L）

対象: Java tool実装、既存Java holdout、benchmark runner、spec/decisions/。

  1. 独自解析を維持する暫定方針のADRを作り、対応構文・framework・検出範囲・既知の限界・保守責任を明記する。adapter内部に保持できる場合は移動しない。
  2. 既存独立fixtureの範囲を確認し、外部実コーパスで不足する一般化評価を追加する。WebGoat等は候補としてライセンス・固定版・ラベル作成可能性を調査する。
  3. 少なくとも外部コーパス1件を選び、対象脆弱性の位置・分類・検出単位と修正版等の負例を確定する。依存CVEをそのままsource SAST正例にしない。
  4. 調整用データと評価用データを分離し、評価後にルール調整へ利用したケースは開発用へ移す。性能閾値は結果を見る前に定義する。
  5. TP/FP/FN、precision/recall、対象外、未実行、解析時間をOWASP値と別掲する。母集団全体のラベルがない場合は、そのコーパス全体のrecallを主張しない。

完了条件: ADR、固定コーパスmanifest、正解ラベルと根拠、再実行コマンド、独立した結果がある。失敗・未実行をゼロ件成功として処理しない。能力基準未達は次の検出改善課題として記録する。

10. P06 環境変数文書の生成（中 / M）

対象: EnvSchema、.env.example、設定リファレンス生成用script。

型・説明・既定値・任意性・秘密区分・再起動要否・保存設定との優先順をメタデータ化する。Zodのdescribeで表現できない情報は補助メタデータへ置く。完全な設定一覧を生成し、exampleは最小起動用と任意例に分ける。内部専用キーも区分して説明する。

完了条件: 全EnvSchemaキーが説明または内部専用として対応付く。同一入力で生成結果が一致し、実環境・SQLiteの秘密を読まない。example読込みで意図しない上書きが起きず、P01・P02の初期設定を再現できる。ローカル生成・照合コマンドを用意し、CI設定は変更しない。

11. P07 構造化ログと監視（中 / M、metricsは条件付き）

対象: app logger、scan lifecycle、Writer client health、LLM providerエラー境界。

まずlevel/event/scanRunId/durationMs/errorCodeを持つJSON loggerを導入する。scan開始・終了・失敗、Writer接続失敗、LLM呼出し失敗から移行する。既存の永続化イベントと重複した状態管理を作らない。secret、ソース本文、prompt、機密パスの出力を抑止する。

Writerの既存queueDepthを再利用する。継続的なscrape需要が確認できた場合のみmetrics endpointを追加し、認証方法、counter再起動時の意味、集計範囲を定義する。projectId/scanRunIdをmetrics labelに使わない。

完了条件: 意図的なscan/Writer/provider失敗をrun IDとerrorCodeで追跡でき、秘密値を含まない。ログ障害で主処理を壊さない。metricsを見送る場合は理由と既存healthによる運用手順を残す。

12. P08 capability宣言とcoverage（中 / L）

対象: StaticScannerAdapter manifest/registry、coverage、execution plan、関連fixture。

既存ScanCapabilityIdに沿ってadapterの能力を宣言する。static以外のDAST・artifact等はそれぞれの実行計画の能力情報へ結び付ける。coverageは登録情報・適用可否・ruleset・実行結果・証跡を集計し、tool ID分岐を減らす。ControlIdへの対応はcoverage側の方針として分離する。

完了条件: 現行scannerのcovered/gap/not_applicable/unknown結果が保持される。fixture adapter追加にreport/coverage/handoffのtool分岐追加を要しない。宣言だけでcoveredにならず、未実行・失敗・複数adapter・実行順変更を扱える。

13. P09 shim移行とscripts責務分割（中 / M〜L）

対象: scans直下、旧normalizers、import参照、行数予算、1000行超script。

  1. shim参照と直下ファイルの所有先を一覧化する。公開入口・registry等の正当な直下ファイルは維持する。
  2. 内部importを所有先へ移行し、互換期間が必要なshimだけdeprecatedにする。参照ゼロ・外部利用確認後に削除する。
  3. scriptsをローカル行数予算の対象に追加し、既存超過は理由付きbaselineとして登録する。新しい肥大化を防ぎつつ段階解消する。
  4. scanner-e2e等をcase定義・実行・証跡出力で分割する。既存分割先を再利用し、移動と挙動変更を分ける。

完了条件: 対象の旧参照がなく、主要entrypointが動作し、証跡schema・終了コード・後片付けが変わらない。所有表と実ファイルを照合する。期限だけによる削除や全ファイル一律800行化は行わない。

14. P10 コマンドの発見性（中 / S）

利用開始、日常スキャン、診断、設定、開発検証の用途別一覧とhelpを作る。package.jsonの既存コマンドを参照し、実在しないコマンドを掲載しない。既存191 scriptの一括削除やgate CLIへの全面置換は行わない。

完了条件: 初回利用と障害診断に必要なコマンドを一覧から見つけられる。help自体がscanやDB変更を起動せず、既存コマンドが互換のまま利用できる。

15. P11 Markdown防御強化とCSP（中 / M〜L）

先にsafe-markdownの既存raw HTML・画像・危険scheme制限を維持したまま、最終HTMLの許可リスト処理を共通化する。sanitize-htmlをブラウザへ追加する場合は互換性・bundle増分を確認し、wikiとの許可機能差は明示的なpolicyとして扱う。

次にinline style、CSS-in-JS、動的位置・幅などを棚卸しし、静的クラス化または必要なnonce対応を実施する。style-srcのunsafe-inline削除は依存UIが動くことを確認した段階で行う。

完了条件: 危険scheme、entity、event属性、不正HTML、通常のtable/link/codeを回帰確認する。レポート・editor・wikiの表示が保たれる。CSP適用後の主要画面にスタイル欠落がない。依存ライブラリが障害になる場合は例外範囲と解消条件を残し、CSP完了とはしない。

16. P12 dynamic artifact収集（低 / M）

固定shell wrapperの入力経路を確認し、envやargvがコードとして再解釈されないことを確かめる。artifactのパス、symlink、出力量、timeout、非root・read-only条件のテストを先に整える。その上で固定helperへの切出し等が契約を簡素化する場合に限定して変更する。

完了条件: 空白・引用符・shell metacharacterを含む名前をデータとして処理する。artifactが出力境界を越えず、上限・終了コード・cleanupを維持する。置換の利益がなければ固定wrapperと入力契約を文書化して完了し、未確認のシェル注入修正とは表記しない。

17. P13 legacy機能の境界（低 / L）

chat/search/rag/knowledgeのroute、UI、MCP、retriever、DB、provider初期化への依存を一覧化する。補助機能として利用される経路は維持する。必要なら現行有効状態を保った明示フラグを導入し、無効時はrouteだけでなくUIと不要な初期化も停止する。

完了条件: 有効時の既存経路と無効時のscan主経路を検証する。保存データを削除せず再有効化できる。別package化・既定off・削除は利用調査後の別判断とし、本作業は依存表と境界改善または維持理由の記録までを必須とする。

18. P14 API契約の試行（低 / L）

P03で整理したproject等の一領域を選び、request/response/error/authを含む契約を定義する。既存Hono型共有とOpenAPI生成の双方を比較し、外部CLI利用・仕様公開に必要な方式を選ぶ。採用時も共通Zod schemaを正として重複定義を避ける。

完了条件: 一領域でサーバー検証・仕様・Web型が一致し、誤ったresponseを検出できる。既存web/src/api.tsの認証・refresh retry・unauthorized処理を維持する。ローカルで生成結果を再現できる。全面移行は試行結果とコストを記録した後の範囲として切り分ける。

19. P15 引き継ぎ・復旧・名称整合（中 / M）

30分程度で構造と作業入口を把握するonboardingを作る。初回起動、project境界設定、scan、証跡の読み方、Writer障害、backup/restore、変更時の検証、既知の限界を含める。役割と未割当の代替担当を記し、自動レビューを代替保守者とは数えない。

使い捨て環境と非機密fixtureで手動のclean checkout・backup復元演習を行い、手順の不足と結果を残す。秘密は文書へ複製しない。リポジトリ表記のtypoはURL・badge・clone例・外部参照への影響を調べ、ローカル文書の名称を整理する。GitHub上のrenameやremote変更は本計画の実装対象に含めず、必要性と移行案を記録する。

完了条件: 新しい作業環境で起動・fixture scan・復元・停止を手順から実行できる。別担当による演習を実施できない場合はその事実を残し、バス係数が改善したとは主張しない。

20. 検証・移行・完了管理

  • 各Pに変更前後の結果、実行コマンド、差分理由、残課題を記録する。プロバイダー資格情報なしで実行可能なfixtureテストを先行する。
  • API・設定変更はtypecheckと対象route/moduleテスト、UI変更はbuildと主要操作、共通scan変更は関連fixtureと必要範囲の全体テストを行う。横断変更の区切りで既存のローカルverifyを使う。
  • Docker・実コーパス確認はunit testと区別し、前提不足による未実行を明記する。単なるmock成功を隔離や検出能力の実証としない。
  • データ変更が必要ならWriter経由の後方互換migrationを用意し、既存project・設定・証跡の読取りと復元を確認する。証跡を破壊的に再生成しない。
  • P01の設定不足で利用が止まった場合は管理者による許可ルート設定で復旧する。安全境界を無効化する自動rollbackはしない。その他の移行も戻せる単位で実施する。
  • 状態は未着手・実装中・検証待ち・完了・判断済み見送りを区別する。条件付き項目の見送りには調査根拠・再検討条件を残す。

計画全体の完了条件: P01〜P15がそれぞれの完了条件を満たすか、条件付き項目として根拠付きで判断済みとなり、対応表・検証結果・残存リスクが更新されていること。CI/CDの追加を完了の前提にしない。実装完了と検出能力基準の達成を混同しない。
