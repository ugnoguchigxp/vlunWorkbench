1. 結論

アーカイブまでの作業を次の3スライスへ限定し、順序を固定する。

  1. AR-01でscanner hardening baseline commit以後の残差だけを分類する。既存commitを rewriteまたは分割せず、closeout変更のscopeと所有計画を固定する。
  2. AR-02で親計画の17個の完了条件、Remediation計画の残件、11 failure caseをstable IDと 実測証跡へ結び付ける。証拠がない条件は完了扱いにせず、不足するtestまたはverifierを実装する。
  3. AR-03でscanner E2E evidenceとqualificationを、検証対象commit、todolist snapshot、canonical final reportへ拘束する。clean checkoutの全local gateと同一commitのprotected CIを通し、 CI artifactを検証してから両計画のstatus、DoD、index、archive配置を更新する。

3スライスを同時に完了扱いにしない。AR-01、AR-02、AR-03の順でhandoffし、前段の acceptanceが不合格なら後段を開始しない。

6.2 Scope contract

scanner-hardening-closeout-scope.v1.jsonは次を必須にする。

  • schemaVersion: 1
  • planningBaselineCommitの完全な40桁commit hash
  • changeSetBaseCommitの完全な40桁commit hash
  • expectedBaselineChangeCount: 78
  • baselineInventoryのpath、status、classification、stable reason code。 renameは旧path、新path、similarityを一組で持つ。
  • allowedResidualPatternsの完全pathまたは末尾/**だけを許すprefix
  • excludedResidualPatterns。一致pathは必ずunknownとして停止する。
  • generatedPathsと生成command
  • requiredResidualPaths。candidate commit treeに欠落すれば停止する。

..、absolute path、symlink escape、空prefix、repository root全体の /**は禁止する。unknown pathが1件でもあればexit 3で停止する。

6.3 Implementation sequence

  1. git diff --name-status 40e77d31562d47bdf6225374e191219d81398b9a..9cc83f97087a20efcd33662072f922fa0818e421 で既存78 pathを取得する。
  2. renameは旧pathと新pathの両方を検査し、deleteもscope対象として扱う。
  3. 78 pathをscanner、separate、generatedへ割り当て、unknownを0件にする。
  4. scanner pathのcanonical patchとseparate pathのcanonical patchを独立に生成し、各 SHA-256をscope reportへ保存する。
  5. planning baseline以後に追加するcloseout実装はscanner scopeだけをexplicit pathspecでstageする。
  6. git diff --cached --checkとscope checkerを実行する。
  7. production changeに対応testがない、またはseparate pathが増えた場合は停止する。
  8. implementation commitを作り、そのcommitからdetached clean worktreeを作る。
  9. AR-02とAR-03のacceptance runはclean worktreeだけで実行する。

自動化はgit reset、git checkout --、git clean、 git stashを実行してはならない。scope外変更を発見した場合はpath一覧を返して停止する。

8. AR-03 — Evidence binding and strict closeout receipt

8.1 Evidence and qualification binding

authoritative release artifactはまだ発行されていない。individual bundleとqualificationは schema version 2、full-profile evidenceはschema version 1のままstrict fieldを追加し、旧shapeを rejectする。3成果物の全てに次を保存する。

  • applicationCommit: clean checkoutの40桁HEAD。引数だけを信用せずGitで照合する。
  • target.repository、target.commit、 target.snapshotSha256: reviewed contractと実際のarchive bytesから導出する。
  • scannerManifestHash、toolboxImageDigest、case別 scannerIdentityHash。
  • individual evidence bundle、repeat bundle、full-profile evidenceのSHA-256と、full-profileの execution plan/normalized evidence hash。
  • case別およびfull-profile run別のcanonicalFinalReportSha256。report IDだけでは qualificationを生成しない。

qualification builderはindividual evidenceとfull-profile evidenceを同時入力とし、commit、target、 manifest、toolbox identityが一件でも異なればnon-zeroにする。regulated admission loaderは新fieldを 全て検証し、commitそのものは利用者scanのsource revisionと混同しない。

8.2 Runner contract

scripts/scanner-hardening-closeout.tsはclean checkoutでだけ動作し、次を順番に 実行する。各commandは固定argvをshell展開せず子process側で通常fileへredirectし、親processが stdout/stderrを増分転送しながら個別fileへ保存する。全commandに30分のdeadlineとstdout/stderr 合計32 MiBの上限を適用し、超過時はchildを停止してnon-zeroにする。pipelineや最後のconsole lineから合否を推測しない。

  1. full 40桁commit、clean status、scope contractを検証する。
  2. production DB、production artifact root、todolist HEAD/statusのbefore digestを採取する。
  3. bun run test:scanner-e2eを実行する。同commandはcontract、2回のindividual bundle、individual verifier、full-profile 2 run、full-profile verifier、最後にqualification build/verifyの順へ変更する。
  4. bun run scanner-e2e:failureとfailure verifierを実行する。
  5. bun run verify:strictを実行する。
  6. 全scanner evidence verifierをもう一度read-onlyで実行する。
  7. finallyで所有process、container、listener、temporary targetを停止・検査する。
  8. before/after digestを比較し、DoD predicateを評価する。
  9. protected CI receipt未指定なら全local gate合格後もverdict: blocked、exit 4のlocal receiptを生成する。--ci-receiptで同一commitのprotected receiptを渡し、 bytes・qualification・target・toolbox bindingを再検証できた場合だけ verdict: passedへ昇格する。

SIGINTまたはSIGTERMを受けた場合は実行中childへ同じsignalを転送し、cleanupを完了してから non-zeroで終了する。中断runのpartial logはdiagnosticとして残せるが、closeout receiptへ昇格しない。

8.4 Log and evidence policy

  • run rootはartifacts/scanner-hardening-closeout/<run-id>/とする。
  • 既存run rootへは書かず、exclusive createを使う。
  • raw log、SQLite、scanner artifactはGitへ追加しない。

  • receiptにはrelative path、SHA-256、size、exit codeだけを保存する。

8.8 Protected CI and archive handoff

8.8.1 CI caller contract

  1. reviewedなowner/name形式のtodolist取得元をrepository variable TODOLIST_E2E_REPOSITORYへ設定する。現在のlocal todolistにはremoteがないため、 値を推測またはvulnWorkbench repositoryへfallbackしない。
  2. .github/workflows/verify.ymlからreusable scanner-e2e-real.ymlを無条件で呼ぶ。target refは d87bfdd9f29aa64e484a0c4d1ad02956136dc6b0へ固定し、contractとの同期testを追加する。
  3. reusable workflowの最初にrepository input、target ref、checkout後HEAD、clean statusを検証する。 input欠落、ref不一致、private repository token不足はskipせずjob failureにする。
  4. verify jobとscanner-e2e-real jobは同じgithub.shaを CI receiptへ保存する。PR headとmerge commitのevidenceを混在させない。

immutable target sourceを設定できない間はtarget_source_unavailableでAR-03のCI promotionを blockedにする。後続計画への移管だけで本計画をarchiveしてはならない。

8.8.2 CI artifact and verification

CI artifact scanner-hardening-closeout-<github.sha>は次を必須にする。

  • GitHub repository、workflow name、run ID、run attempt、40桁commit SHA
  • 同一runのverify / verifyとscanner-e2e-real / scanner-e2e-realがsuccessであることを示すrequired job台帳
  • individual/repeat/full-profile/failure evidenceとqualification、および各SHA-256
  • target commit/snapshot digest、toolbox image digest、scanner manifest hash
  • qualificationに拘束されたcanonical final report digest
  • protected mainで昇格する場合は、GitHub branch APIとrules APIから取得したbranch protection evidence、およびそのSHA-256

verify:strictとscanner gateのraw logはGitHub run logをrun IDで参照し、artifactへ 二重複製しない。cleanup counts、DoD/disposition、各commandのexit codeとlog digestは、CI receipt取得後に同じimplementation commitのclean checkoutで実行する最終closeout receiptへ保存する。これによりCI receiptとlocal closeout receiptの責務を分離し、循環参照を作らない。

scripts/verify-scanner-hardening-ci-receipt.tsを追加し、download済みartifactに対して schema、全file digest、commit、target、qualification binding、required job IDを再検証する。 protected mainではcapture-scanner-hardening-branch-protection.tsがGitHub APIを read-onlyで呼び、verify / verifyとscanner-e2e-real / scanner-e2e-realがrequired status checkであることを確認する。このAPI evidenceがないlocal receiptやPR receiptはcandidateに限定し、archive可と判定しない。

branch protection evidenceはCI receipt生成前15分以内に同じrepository・main refから取得したもの だけを受理する。receipt verifierは取得時刻、regular-file性、realpath containment、file digestを 再検証し、古いAPI responseやsymlink差し替えをpromotion根拠にしない。

verify.ymlのscanner-hardening-receipt jobは、同一runの verifyとscanner-e2e-realがともにsuccessした場合だけevidenceを取得し、 CI receiptを生成・再検証・再uploadする。PRまたは未保護refではverdict: candidate、protected mainかつAPI evidenceがexact required check setを含む場合だけverdict: passedとする。branch protection確認前にpassedを生成してはならない。
