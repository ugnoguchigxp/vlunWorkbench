Target: 保存済みraw finding、evidence、既存issue grouping snapshotを変更せず、改修依頼生成時だけ 同種警告を親、検出場所を子としてまとめる。10件以上の同種警告を1つのwarning groupとしてLLMへ渡し、 全issueとfindingへの追跡性をserver-side manifestで維持したまま、各prompt messageを文字数予算内へ収める。

1. 結論

実装は既存issue groupingを置き換えず、その後段へLLM handoff専用のrollup projectionを追加する。

  1. finding-dedupe-v1のissueは、同一脆弱性の同一発生箇所を表す監査単位として維持する。 異なる場所のissueを同一rowへ統合せず、既存table、snapshot hash、UI/reportの意味を変更しない。
  2. 改修依頼bundleの構築時に、同じ修正方針で扱えるissueをwarning groupへ投影する。 10件以上のeligible issueが同じ決定論的keyを持つ場合だけ、親1件とlocation child複数件へまとめる。 10件未満はsingleton warning groupとして扱う。
  3. LLMは短いwarningGroupIdだけを返す。serverは保存済みmanifestからissue ID、raw finding IDを 再計算し、現行ScanImprovementRequestのcoverage契約を満たす。LLMへraw finding IDを渡さない。
  4. 50件固定chunkを廃止し、実際にrenderしたscans.improvementRequestInputの文字数を使って warning group単位でchunkする。targetは48,000文字、hard limitは60,000文字とし、既存64,000文字 guardへ到達する前にfail closedする。
  5. LLMが作る改修本文へ、serverが決定論的なlocation appendixを付与する。同じ警告の説明は1回だけ記載し、 子には場所と個別差分の最小情報だけを記載する。

3. Scope

3.1 In scope

  • 改修依頼専用warning group contract、決定論的key、version、manifest
  • 10件以上のeligible issueを親1件とlocation childへ投影するrollup builder
  • secret/source/IaC/dependency向けの保守的な同種判定
  • LLMへ渡す共通context、evidence、locationのcompact projection
  • rendered prompt文字数に基づくbudget-aware chunking
  • LLM responseのwarning group参照検証とissue/finding IDへのserver-side展開
  • 改修依頼Markdownへ付与する親子形式のlocation appendix
  • prompt budget failureのtyped error、監査metadata、UI分類
  • unit、contract、runner、web、314件相当のsynthetic regression test

3.2 Out of scope

  • findings、finding_evidence、finding grouping tableの変更またはmigration
  • finding-dedupe-v1のpair判定、asset境界、location重複条件の緩和
  • UI issue一覧またはreportのdefault単位をwarning groupへ変更すること
  • 10件未満の一般的な修正単位統合を、LLMやembeddingで自動判定すること
  • web/API/business logic/unknown issueのlocation横断rollup
  • scanner rule tuning、finding suppression、false positive判定
  • providerのcontext windowや既存64,000文字guardを拡大すること
  • 過去にcompletedとなった改修依頼reviewの再生成またはbackfill

4. 用語と責務境界

issue
現行grouping snapshotに保存された監査単位。同一発生箇所に対するscanner間重複をまとめる。 warning rollupの入力であり、本計画では永続化内容を変更しない。
warning group
改修依頼生成時だけ作る派生単位。同じ決定論的warning keyを持つeligible issueが閾値以上なら親となり、 それ以外はissue 1件のsingletonとなる。UI/reportのissue groupとは別概念である。
location child
warning group配下の検出場所。path、line/range、resource、必要な場合だけmethod/parameter、severityを持つ。 scanner snippet、raw secret、raw finding IDを持たない。
warning group manifest
warning group、issue、finding、evidence、locationの対応を保持するserver-side audit data。 LLM promptからはissue/finding membershipを除外する。
prompt projection
LLMの判断に必要な親情報、compact child、共通contextだけを含むJSON。監査manifestとは分離する。
location appendix
LLM responseの受信後にserverまたはweb rendererが決定論的に生成する親子一覧。 LLMに場所一覧を再生成させない。

5. Non-negotiable invariants

  1. warning rollup前後でissue ID集合とraw finding ID集合が一致する。
  2. 1回の改修依頼生成内で、各issueは正確に1つのwarning groupへ所属する。
  3. 1つのwarning groupを複数LLM chunkへ分割しない。
  4. 10件未満のcandidate setはrollupせず、issueごとのsingleton warning groupにする。
  5. eligibleでないissue kindは件数にかかわらずsingletonとする。
  6. 親severityはchild issueの最大severityと一致し、severity別件数を保持する。
  7. LLMへraw finding ID、member issue ID一覧、raw secret、secret snippetを渡さない。
  8. LLMが返したwarning group IDは保存済みmanifestだけで検証し、未知IDを拒否する。
  9. LLM responseの全implementation taskを展開した結果が全issueをcoverする。
  10. 同じsnapshotと同じalgorithm versionから、取得順に依存しない同じwarning group順序とhashを得る。
  11. 各rendered user promptは60,000文字以下であり、通常経路は48,000文字以下を目標とする。
  12. 文字数を収めるためにissue、location、coverageを黙って削除しない。
  13. 過去reviewのScanImprovementRequestとMarkdown表示を壊さない。

6. Target flow

completed scan
  -> current deterministic finding grouping snapshot (unchanged)
  -> issue prompt source projection
  -> buildWarningGroups(issue[])
       -> eligible kind + exact warning key + count >= 10: parent + children
       -> otherwise: singleton warning group
       -> server-side warningGroupManifest
  -> build compact improvement-request context
  -> pack warning groups by rendered character budget
       -> target 48,000 chars
       -> hard limit 60,000 chars
       -> oversized parent: deterministic compression tiers
  -> LLM returns tasks with warningGroupIds
  -> validate group references and per-chunk coverage
  -> expand warningGroupIds -> issueIds -> findingIds
  -> merge chunk responses
  -> persist existing ScanImprovementRequest + coverage/audit metadata
  -> render task body once + deterministic location appendix

rollupとprompt budgetは同じpipelineで実行するが責務は分離する。rollup builderはLLMやprompt templateを知らず、 budget packerは脆弱性の同種判定を行わない。

7. Shared contracts

7.1 Constants and version

shared/schemas/finding-group.schema.tsへ次の値を追加する。

export const IMPROVEMENT_WARNING_ROLLUP_VERSION = "improvement-warning-rollup-v1";
export const IMPROVEMENT_WARNING_ROLLUP_THRESHOLD = 10;
export const IMPROVEMENT_PROMPT_TARGET_CHARS = 48_000;
export const IMPROVEMENT_PROMPT_HARD_CHARS = 60_000;
export const MAX_WARNING_GROUP_EVIDENCE = 6;
export const MAX_WARNING_LOCATION_SAMPLES = 20;

既存MAX_RENDERED_PROMPT_MESSAGE_CHARS = 64_000はsystem-wide guardとして維持する。 新しい60,000文字limitは改修依頼bundle固有のpreflightである。target超過は圧縮または次chunkへの移動を行い、 hard limit超過はproviderを呼ぶ前にtyped errorとする。

7.2 Warning group key

warning keyはlocationとseverityを除外し、修正内容を変える識別子を含める。title、descriptionの類似度は使用しない。

version 1のeligible key
issue kind key parts location childへ移す値
secret issueKind + sourceTool + ruleId + detectorFamily path、line/column range、severity
source issueKind + sourceTool + ruleId + sorted concrete familyKeys path、line range、symbolが保存済みの場合だけsymbol
IaC issueKind + sourceTool + ruleId + policy family path、line range、resource
dependency issueKind + ecosystem + package + installedVersion + sorted advisoryIds manifest/lockfile/SBOM target path
web/API/business logic/unknown version 1ではeligibleにしない issueごとのsingletonを維持

key partが不足するcandidateはsingletonへ倒す。dependencyでpackageまたはadvisoryが不明、sourceでconcrete familyと tool-scoped ruleの両方が不明な場合は、自動rollupしない。severityが異なるissueは同じ親へ所属できるが、親に severityCountsと最高severityを保存し、全件が同一severityであるように表現しない。

7.3 Warning group contract

type ImprovementWarningGroup = {
  warningGroupId: string;            // invocation-scoped compact ID: wg-000001
  stableKey: `sha256:${string}`;      // server-side audit
  kind: "rollup" | "singleton";
  issueKind: FindingIssueKind;
  title: string;
  description: string;
  severity: FindingSeverity;
  severityCounts: Partial<Record<FindingSeverity, number>>;
  occurrenceCount: number;           // issue count
  rawFindingCount: number;
  scannerSignals: Array<{
    sourceTool: string;
    ruleId: string;
    severity: FindingSeverity;
  }>;
  familyKeys: string[];
  representativeEvidence: Array<{
    id: string;
    kind: string;
    artifactId: string | null;
    snippet: string | null;
  }>;
  locations: ImprovementWarningLocation[];
  locationSummary: {
    total: number;
    included: number;
    omitted: number;
    digest: `sha256:${string}`;
  };
};

type ImprovementWarningLocation = {
  ref: string;                        // canonical path:line or resource ref
  path: string | null;
  startLine: number | null;
  endLine: number | null;
  resource: string | null;
  method: string | null;
  parameter: string | null;
  severity: FindingSeverity;
};

warningGroupIdはscan-wideの安定sort後に付ける短いordinalで、同じ入力では同じ値になる。 永続的なidentityには使用せず、監査はfull stableKey、grouping snapshot hash、manifest hashで行う。 ordinal衝突は構造上発生させず、重複IDを検出した場合はbundle構築を失敗させる。

7.4 Server-side manifest

type ImprovementWarningGroupManifestEntry = {
  warningGroupId: string;
  stableKey: `sha256:${string}`;
  issueIds: string[];
  memberFindingIds: string[];
  evidenceIds: string[];
  locations: ImprovementWarningLocation[];
};

manifestはscan_reviews.input_bundleに保存し、prompt binding前に除外する。 location childの完全一覧とissue/finding membershipはmanifestを正とする。既存JSON columnを使用するためmigrationは不要である。

llmIssueImprovementRequestSchemaを直接拡張せず、新しい llmWarningGroupImprovementRequestSchemaを追加する。priority planとimplementation taskは warningGroupIdsだけを返し、issue ID、finding IDを返さない。

  objective: string;
  scope: string[];
  priorityPlan: Array<{
    priority: "critical" | "high" | "medium" | "low";
    rationale: string;
    warningGroupIds: string[];

response parse後、manifestでwarningGroupIds -> issueIds -> findingIdsを展開して既存 ScanImprovementRequestへ変換する。completed reviewのpublic contractは維持し、warning group情報は review output metadataとlocation appendixへ追加する。 展開時にtask indexとwarning group IDの対応をtaskWarningGroupBindingsとして別途返し、 既存schemaが追加fieldをstripしてもUIの親子対応を失わないようにする。

8. Rollup algorithm

  1. current completed deterministic grouping snapshotから全issueを取得し、既存sortを固定する。
  2. representative findingからkind別warning key partを投影する。raw finding metadataは書き換えない。
  3. eligible issueだけをfull warning keyでbucket化する。不完全keyはsingleton候補へ送る。
  4. bucket sizeが10以上ならrollup parentを1件作る。1から9件なら各issueをsingletonに戻す。
  5. 親title/descriptionは既存representative選択規則で決め、secretは固定redacted文言を使用する。
  6. severityは既存rankの最大値、scanner signalとfamily keyはcanonical sortして重複を除く。
  7. location childはcanonical referenceを作り、同一refとseverityの重複を除いてsortする。
  8. evidenceは親全体でdedupeし、source-locationを優先して上限6件とする。childごとにsnippetを複製しない。
  9. secretでは全snippetをnullにし、locationにもcolumn以外の検出値を含めない。
  10. 全warning groupをseverity、issue kind、stable keyでsortし、scan-wide ordinal IDを付ける。
  11. 全issueが1回だけmanifestへ現れることをassertしてからprompt projectionを作る。

10という閾値はrollup表示のactivation thresholdであり、同種判定の証拠ではない。同種判定はwarning keyだけで行う。 titleが似ている、説明文が同じ、severityが同じという理由だけでは同じbucketへ入れない。

9. Prompt projection and character budget

9.1 Compact shared context

buildScanReviewBundle(maxFindings: 0)の戻り値をそのまま全chunkへ複製しない。 改修依頼専用のImprovementRequestSharedContextを作り、次だけを含める。

  • scan ID、profile、profile outcome、完了状態
  • project ID、name、default branch
  • severity/issue/findingの集計値
  • tool name、version、status、exit codeのcompact list
  • 参照可能なartifact ID、kind、format
  • verificationの件数と保存済みoutcome。長いerror messageやscan execution planは含めない。
  • grouping run ID、snapshot hash、algorithm version、rollup version

現在約12,000文字ある共通contextは4,000文字以下を目標とする。削除した情報はaudit input bundleには保持できるが、 LLMが修正方針を判断する根拠として使わない情報をpromptへ戻さない。

9.2 Budget-aware packing

  1. warning groupを確定sortし、空chunkへ1件ずつ追加する。
  2. 候補chunkをbindImprovementRequestUserMessage()で実際にrenderする。
  3. 48,000文字以下なら追加を確定する。
  4. 48,000文字を超えた場合、現在chunkを確定し、warning groupを次chunkの先頭へ移す。
  5. warning group 1件だけで48,000文字を超える場合は、9.3の圧縮を適用する。
  6. 全chunk確定後、実際のchunk count/offsetを入れて再renderし、60,000文字以下であることをassertする。
  7. 60,000文字を超えたchunkは末尾groupを次chunkへ移して再計算する。1件chunkで超える場合はtyped errorとする。
  8. provider呼び出し直前にも既存assertPromptInvocationを通し、system-wide 64,000文字guardを残す。

chunk countの桁数やJSON escapeを見積もりで処理せず、最終rendered textを計測する。 warning group数やissue数から文字数を推測する実装は禁止する。

9.3 Oversized parent compression

1親がtargetを超える場合、次の順に決定論的に圧縮する。

  1. location childから重複するevidence IDとartifact IDを除き、canonical location refだけにする。
  2. 同一pathの複数lineをpath: line1,line2,line3形式へまとめる。
  3. 親のrepresentative evidenceを6件から3件へ減らし、snippetを300文字から120文字へ短縮する。
  4. 全locationを入れるとtargetを超える場合、canonical先頭20件、path別件数、全件数、omitted件数、location digestを promptへ入れる。完全一覧はserver-side manifestと最終location appendixへ残す。

圧縮tierをprompt auditへ保存する。同じ親をlocation pageとして複数LLM callへ分割しない。 LLMは共通修正方針を作る役割であり、完全な場所一覧はserverが正確に付加する。

9.4 Final handoff budget

コピー/Markdown出力される最終指示書も親子構造にする。task bodyはwarning groupごとに1回だけ表示し、 「対象場所」節へcanonical childを短いlistで付ける。最終Markdownは60,000文字を上限目標とする。 完全一覧が上限を超える場合はpath別件数と先頭sampleを本文へ載せ、同時に完全な warning-locations.jsonをdownloadできるようにする。このfallbackを導入する場合も、UI内の監査表示では 全locationへ到達できなければならない。

10. Validation and merge

  1. 各chunk responseの全warningGroupIdsがそのchunk manifestに存在することを検証する。
  2. 各chunkのimplementation task全体が、そのchunkの全warning groupを正確に1回coverすることを検証する。同じgroupを複数taskへ割り当てたresponseは拒否する。
  3. evidence referenceは親のrepresentative evidence、artifact、promptに含めたlocationだけを許可する。
  4. warning group IDをmanifestからissue IDへ展開し、さらに既存manifestからfinding IDへ展開する。
  5. 全chunk merge後にwarning group、issue、findingの3段階でcoverageを再検証する。
  6. task truncationまたはfallback task生成後もIDを再展開し、coverage driftを許可しない。
  7. priority planはchild severityの最大値を超えるpriorityを拒否または補正する。
  8. 最終ScanImprovementRequestは既存schemaでparseし、過去consumerとの互換性を確認する。

LLM responseがwarning groupを欠落させた場合、現在と同様にstructured validation failureとする。 server fallback taskは欠落groupを一括coverできるが、LLMの未知ID、別chunk ID、架空evidenceは補正せず拒否する。

11. Persistence and audit

scan_reviews.input_bundleへ次を追加する。

  • rollup.version、threshold、eligible kinds
  • warning group count、rollup parent count、singleton count、location child count
  • warning group manifestとmanifest SHA-256
  • source grouping run ID、finding set hash、snapshot hash
  • prompt target/hard/system limit
  • chunkごとのwarning group数、issue数、rendered chars、compression tier

scan_reviews.outputへ次を追加する。

  • coverage.totalWarningGroupsとcoveredWarningGroups
  • 既存total/covered issues、total/covered findings
  • warning group、issue、finding ID集合の各digest
  • task index、warning group ID、展開後issue IDの対応を持つtaskWarningGroupBindings
  • location appendixのdigestとincluded/omitted count
  • 既存prompt audit、response content digest

manifestとaudit metadataにraw secretまたはsnippet本文を保存しない。既存evidence tableを参照するIDとredacted locationだけを使う。 JSON column追加だけで実装し、SQLite schema migrationを作らない。

12. Failure contract and UI

12.1 Server error

次のtyped errorを追加する。

improvement_request_prompt_budget_exceeded:
  chunk=<index>
  renderedChars=<number>
  hardLimit=60000
  largestWarningGroupLocations=<number>
  compressionTier=<number>

error metadataへprompt本文、path、snippet、secretを含めない。共通contextだけでhard limitを超えた場合と、 単一warning groupを最終tierまで圧縮しても超えた場合を区別する。

12.2 Web failure classification

classifyScanReviewFailureへprompt_budget_failureを追加し、現在の 「不明なエラー / raw errorを確認してください」を次へ置き換える。

  • label: 入力サイズ上限エラー
  • next action: 検出結果の親子集約またはprompt圧縮に失敗しました。再試行で続く場合は保存済み診断値を確認してください。
  • raw errorは詳細欄へ残すが、利用者向け主文にしない。

通常の314件ケースがこのerrorへ到達しないことをrelease条件にする。UI改善だけでbackend failureを隠さない。

16. Definition of Done

  1. 10件以上の同種eligible issueが親1件・location child複数件としてpromptへ入る。
  2. 10件未満、ineligible kind、不完全keyが誤ってrollupされない。
  3. 314件相当fixtureの全prompt messageが60,000文字以下である。
  4. LLMへraw finding ID、member issue ID一覧、raw secretが送信されない。
  5. server-side展開後のcovered warning group、issue、findingがそれぞれtotalと一致する。
  6. 同じ親が複数chunkまたは複数implementation taskへ重複して現れない。
  7. コピー/Markdown出力で共通修正方針とlocation childを親子関係として確認できる。
  8. 過去completed reviewの表示とexportに回帰がない。
  9. budget failureがtyped errorとして保存され、UIで不明なエラーに分類されない。
  10. 実測対象scanの改修依頼再生成がcompletedになり、coverage 314/314を保存する。
  11. 対象unit、runner、web、typecheck、lint、docs、source size、critical coverage gateが通る。
  12. 実装差分が本計画のscope内に限定され、scanner normalizerの同時変更を含まない。

17. Rollback and compatibility

  • DB migrationを行わないため、rollbackはproduction codeとprompt/schema変更のrevertだけで行える。
  • 既存completed reviewは同じScanImprovementRequestを保持し、再保存しない。
  • running reviewは現行runnerと同様、process restart時にinterrupted failureへ遷移させる。
  • 新しいinput/output metadataを知らないclientは既存fieldsだけを読み、追加fieldsを無視できる。
  • rollback後に新形式のfailed reviewが残っても、completed review selectorを妨げない。
  • warning rollup失敗時に旧50件chunkへ自動fallbackしない。再び64,000文字超過を起こすためである。

18. Implementation handoff

実装担当はWR-00から開始し、warning keyとmanifest invariantをtestで固定してからbundleを変更する。 既存finding grouping engineを緩和して問題を解決しようとしてはいけない。prompt sizeはfixture JSONの長さではなく、 実際のbindImprovementRequestUserMessage(...).content.text.lengthで検証する。

WR-03では既にsource size budget対象となっている scan-improvement-request-builder.tsへrollup処理を追加し続けず、warning groupのvalidationと展開を 別moduleへ分離する。各sliceの最後にissue/finding coverageとsecret redactionを確認し、文字数だけを満たして 監査情報を失う変更を受け入れない。
