1. Executive Decision

この計画では新しいontology、graph、provenance、vocabulary、contract versioningを実装しない。 既に存在するProject Exploration Catalog V2とNightWorkersの専用consumerを使い、coding agentの広い事前探索を小さなcatalog queryで置き換える価値があるかだけを判定する。

技術的な正しさはproducer testとMCP smokeで確認済みだが、2026-08-09のpilotでは正式catalog run 5件すべてがtool call前にprovider capacity failureとなった。このため、現時点の判断は価値が低いという NO-GOではなく、価値を測れていないINSUFFICIENT_EVIDENCEである。

本計画の終了時には、必ず次のいずれか一つを記録する。

  • GO: 限定consumer rolloutを検討する価値が実測された。
  • NO-GO: safety incidentが発生した、または有効sampleを得たが価値・品質gateを満たさなかった。
  • INSUFFICIENT_EVIDENCE: sample、telemetry、provider、実験統制の不足で価値を判定できなかった。

GOであっても、default ON、対象repository拡大、namespace移動、parked ontology planの一括再開は承認しない。GO後の変更は別decisionと小さなvertical sliceを必要とする。

2. Decision Question and Hypothesis

2.1 Decision question

同じrepository revisionに対する構造解析結果を一度作り、coding agentが実装開始前に一回のbounded catalog queryを使うと、task completionとverification品質を落とさずに、広いworkspace探索とinput tokenを実際に減らせるか。

2.2 Value hypothesis

Catalogは、変更候補を完全予測するものではない。agentが最初の有力なfile、module、related test、verification candidateへ到達するまでの不要なlist/search/readを減らす、revision-boundな探索目録である。

2.3 Null hypothesis

Catalog callが通常探索へ追加されるだけ、候補の誤りでreplanが増える、またはcompletion / verificationが悪化するなら、 現行Catalogにrollout価値はない。将来ontology機能を増やしてこの結果を説明してはならない。

3. Authority and Precedence

  1. 実験の価値metricとprivacy boundaryは本計画を正本とする。
  2. path-first bindingとfail-open規則は NightWorkers path-first Static Intelligence MCP handoffを維持する。
  3. producer / consumer correctnessの実装根拠は Project Intelligence Foundation Hardening Implementation Planを参照する。
  4. 実コードと文書が矛盾する場合、実行を止めてbaselineを更新し、protocol versionを上げる。
  5. 実験中にgateやtask promptを結果に合わせて変更しない。

7. Experiment Design

7.1 Unit of comparison

一つのpairは、同じtask prompt digest（課題本文）、target repository HEAD、provider endpoint、model、thinking depth、timeout、 runtime laneを使う2 runで構成する。各runは同じbase commitから作る別worktreeで実行し、agent history、 tool output、mutationを共有しない。

route名だけで同一性を判断しない。非secret provider設定、prompt-construction contract、tool manifest、runtime code、 evaluator profileからfingerprintを作り、両armとpre-registrationで 一致させる。taskとarmによって動的にrenderされるsystem prompt hashはarmごとのraw evidenceへ残すが、 単一値として一致を要求しない。provider sessionはarmごとに新規作成し、 continuationやshared conversationを使わない。

Pair arms
Arm Feature state Tool policy
Baseline Project Exploration feature flag OFF 通常workspace探索だけ。catalog tool definitionをproviderへ送らない
Catalog 対象repositoryのrun開始時だけON availableならbroad exploration前にfocus-only catalogを一回呼び、その後は通常toolを使える

7.2 Task set

  • 既存のPILOT_TASKS 10件をそのまま使用する。
  • 第一候補targetは前回と同じtodolist commit d87bfdd9f29aa64e484a0c4d1ad02956136dc6b0とする。このrevisionを取得できない、または task qualificationが成立しない場合、current HEADへ黙って置換せず新しいprotocol / pilot IDを作る。
  • frontend、backend、shared contract、database、security policy、test / observabilityを含む。
  • task文、acceptance criteria、順序scheduleのSHA-256をformal run前に保存する。
  • 結果を見た後のtask削除、文面変更、容易な予備taskへの差替えを禁止する。
  • 実装箇所を直接pathで教えるtaskや、外部network availabilityが主因になるtaskを追加しない。
  • 各taskにmodel非公開のevaluatorProfileId、verification command、timeout、expected assertionを対応付ける。これらもpromptと同時にhash固定する。
  • Evaluatorはmodel terminal後に、固定cwd、環境変数allowlist、timeout、network policyで実行する。 stdout / stderrはbounded digestと必要なsanitized failure summaryだけをcommitし、結果をagentへ戻して修正させない。
  • Acceptanceの正本となるfixture / assertionはassigned worktree外のcontroller-owned read-only assetとしてhash固定する。 Agentが追加・変更したtestだけを根拠にpassしない。
  • 選択したtarget commit上で各evaluatorが未実装状態を検出し、positive qualification fixtureまたはowner確認済み reference worktreeで成功を検出できることをformal前に確認する。

7.3 Order control

  • 奇数pairはbaseline → catalog、偶数pairはcatalog → baselineとする。
  • pair member間とpair間のcooldown秒数をpre-registrationで固定する。
  • pairを並列実行しない。
  • provider routeを途中で切り替えた場合、その時点でprotocolを停止し別pilot IDにする。
  • pilot用LLM settings fileをisolated runtimeへcopyした後のhashを固定し、formal中の変更を拒否する。

7.4 Valid pair

次をすべて満たすpairだけを価値比較へ含める。

  • 両armのbase ref、task prompt digest、route fingerprint、model、thinking depth、timeout、 prompt-construction contract、tool manifest、evaluator profileが一致する。task / armごとに変化し得る 実行時system prompt hashは比較統制値ではなく、生証跡として保存する。
  • 両armが独立worktreeで開始し、開始時HEADとclean stateが一致する。
  • 両armのevent、時刻付きmeasured LLM usage、terminal status、agent verification、独立evaluator結果が保存されている。
  • Catalog armでavailability pinが成功し、schema-validな専用toolをbroad exploration前にexactly once呼んでいる。
  • task outcomeが失敗またはneeds_humanでも、実験統制が保たれていればvalidとする。

providerが最初の有効応答前にcapacity failureとなった、run recordが失われた、routeがずれた等は infrastructure-invalid attemptとして保存し、value sampleから除く。悪いtask outcomeを理由に除外してはならない。

7.5 Sample rule

  • 判定には10 valid pairが必要。
  • 各taskは一つのvalid pairだけを持つ。
  • invalid attemptの再実行は同じtask / pair IDにattempt numberを付け、古いattemptを残す。
  • 各taskにつき最大2 attempt、全体で最大14 pair attemptをstop-lossとする。
  • 最大attemptで10 valid pairへ届かなければINSUFFICIENT_EVIDENCEとする。

7.6 Retry and resume rules

  • provider内部のbounded retryは、model content、tool call、mutation eventが一件も生成されていないretryable capacity failureだけに許可する。回数とdelayをpre-registerし、全retryをraw evidenceへ残す。
  • contentまたはtool event生成後のrunを同じarmとして再開しない。新しいworktreeとrunを持つ次attemptにする。
  • resumeは完了済みpair境界からだけ行い、片方のarmだけを別protocol / routeで再利用しない。
  • source、consumer、producer、task、evaluator、settings hashが変わった場合は新しいpilot IDを発行する。
  • Catalog contract / parse failureはprovider retryへ畳み込まず、formal reliability failureとして停止する。

8. Preflight and READY Gate

formal pairを一件でも投入する前に、preflight evidenceをREADYにする。

  1. vulnWorkbench、NightWorkers、target repositoryのcommit SHAを固定し、全worktreeをcleanにする。
  2. registration artifactのschema、task / evaluator / schedule hash、route / settings / prompt-construction contract / tool manifest fingerprintを検証する。
  3. NightWorkersのformal runで--allow-dirty-consumerと--allow-live-apiを禁止する。
  4. isolated launcherが新しいNightWorkers専用DBを作り、runtime leaseを取得することを確認する。
  5. 明示的なvulnWorkbench pilot DBを新規作成し、target projectを事前登録する。MCP serverへその DATABASE_URLとSTATIC_INTELLIGENCE_PROJECT_CREATION_POLICY=registered_onlyを渡す。
  6. 事前登録はexact target一件だけをallowlistにしたbootstrap MCP sessionで既存prepare actionを一回使う。 bootstrap sessionを切断後、formal sessionをregistered_onlyで再接続し、project countが一件であることを確認する。
  7. NightWorkers / vulnWorkbenchの各pilot DBに対するowner processが意図した一つだけで、operational DBとpath / inodeが異なることを記録する。
  8. feature flagの初期値がOFFで、abort後にもOFFへ戻ることをdrillする。
  9. producerのprepare / status / catalog toolがexact nameで揃うことを確認する。
  10. target HEADとcatalog source revisionが一致し、response hard capとredactionを満たす。
  11. 固定10 taskの独立evaluatorがbase HEADで未達を検出し、positive qualificationで成功を検出する。 scripts/qualify-project-exploration-pilot-evaluators.ts --manifest … --output …が、worktree pathを artifactへ出さず、この結果を再計算する。formal runは--evaluator-qualificationでそのREADY artifactを 必須入力にし、target commit・全task・各profile fingerprint・base fail・positive pass・clean状態を再検証する。
  12. Evaluator assetがtarget worktree外にあり、model toolから変更できないことをnegative testする。
  13. 同じrouteでbaseline canaryとcatalog canaryを一回ずつ完了する。NightWorkers runnerの --preflight-canary --output …は正式10 task外の固定marker taskを独立worktreeでpaired実行し、 commit・route・settings・prompt-construction contract・tool manifest・exactly-one Catalog callをartifactへ固定する。
  14. formal task setとは別のcanary taskで、catalog canaryがbroad exploration前にtoolをexactly once呼び、 独立evaluatorまで到達する。
  15. raw DB、run inventory、sanitized reportを生成して再読込できることをdry-runする。

canaryはformal 10 pairへ含めない。いずれかが失敗した場合、formal pilotはBLOCKEDであり、 NO-GOやINSUFFICIENT_EVIDENCEをまだ宣言しない。

READY artifactはchecklistの手動チェックではなく、commit / hash / tool list / evaluator qualification / cleanup drillを再計算するcommandの出力とする。READY発行後に入力が変わった場合は自動的に失効する。

Authoritative conceptと既存reportに合わせ、Primary reductionは (median(baseline) - median(catalog)) / median(baseline)で判定する。baseline medianが0、 measured tokenが一件でも欠損、またはusage modeがestimated / mixedなら、そのPrimary metricは判定不能である。

10. Decision Gates

10.1 Hard safety and integrity gates

一件でも未達ならGOにできない。wrong binding、privacy leak、operational DB接続等の safety incidentはsample数に関係なく直ちにNO-GOとする。sample / telemetry不足だけを INSUFFICIENT_EVIDENCEに分類する。

  • 10 valid pairと全attemptの記録がある。
  • same base ref / task definition / route fingerprint / model / reasoning / timeout / prompt-construction contract / tool manifest / evaluatorと独立worktreeが全pairで成立する。
  • Catalog armのschema-valid successful call countが各arm exactly one、catalog-before-broad-exploration rateが100%である。
  • formal attemptにunexpected Catalog contract / parse / transport failureが0件。
  • NightWorkers / vulnWorkbench双方でoperational DB accessが0件。wrong project、wrong revision、unsafe pathが0件で、model projectionまたはcommitted evidenceへのsource body、secret、absolute path leakが0件。
  • Catalog failureがtask failureへ伝播した件数が0件。
  • independent completion / verification、measured usage、token、tool telemetryが全valid armで揃う。
  • feature flagが終了・停止後にOFF、pilot MCP connectionが切断、active pilot runが0件である。

10.2 Value gates

GOには次をすべて満たす必要がある。

  • pre-registered arm-median pre-mutation exploratory tool call reductionが20%以上。
  • pre-registered arm-median pre-mutation non-cached input token reductionが15%以上。
  • Catalog armのindependent evaluator completion countがbaseline armより少なくない。
  • Catalog armのindependent verification pass countがbaseline armより少なくない。
  • baseline pass / Catalog failとなるcompletion regression pairが0件。
  • baseline pass / Catalog failとなるverification regression pairが0件。
  • Catalog armのmedian replan countがbaseline armを超えない。
  • v1ではcatalog clueと後続correctionの因果を機械的に判定しない。independent evaluator、 completion regression、verification regression、Catalog contract failureを観測可能なquality gateとし、 decision recordでは相関を因果として書かない。観測されたwrong-file mutationまたはverification omissionは safety / task outcomeとしてattemptに残し、GOを正当化する材料にしない。

time-to-first-relevant-read、time-to-first-mutation、unique file read、preparation costは解釈を補助する。 Primary 2 metricが未達なのに、supporting metricだけを理由にGOへ変更しない。

10.3 Decision matrix

decision writerは次の優先順位で判定し、下位条件で上位結果を上書きしない。

  1. Safety incidentまたはdeterministic Catalog reliability failureが一件以上なら、sample数に関係なく NO-GO。
  2. Safety / Catalog reliability failureはないがevidence completenessが未達ならINSUFFICIENT_EVIDENCE。
  3. Evidence completeで全value / quality gateがpassならGO。
  4. Evidence completeで一つ以上のvalue / quality gateがfailならNO-GO。

Decision Condition Authorized next action

NO-GO Safety incident、deterministic Catalog reliability failure、または10 valid pair取得後にvalue / quality gateが未達 flag OFFを維持し、ontology投資を再開しない。原因別の小さな診断だけ許可
INSUFFICIENT_EVIDENCE Safety / Catalog reliability failureなしで、10 valid pair、telemetry、provider安定性、統制のいずれかが不足 実験基盤だけを修正し、同じ価値仮説で再pilotする

11. Stop and Rollback

次の事象を一件でも観測したら新しいpair投入を止める。

  • wrong project / revision、source change後のstale clue、symlink / unsafe path
  • source body、secret、absolute path、internal database IDのmodel projectionまたはcommit evidenceへの混入
  • run record、event、usage、verification evidenceの消失またはforeign-key failure
  • いずれかのpilot DBを所有する想定外process、runtime lease不整合、operational DBへの接続
  • feature flagがpair外repositoryやbaseline armでONになる
  • 同じrouteで連続2回のprovider capacity failure、またはroute設定の途中変更
  • Catalog armでtoolがexactly once呼ばれずbroad explorationへ進む、またはresult parseが失敗する
  • target / consumer worktreeがrun中に変化する

停止処理は次の順序で行う。

  1. 新規run投入を停止し、進行中runを安全にterminalまたはcancelへ移す。
  2. repository feature flagをOFFへ戻す。
  3. pilot MCP serverをdisconnect / disableする。
  4. raw DB、run ID inventory、stderr progress log、sanitized checkpointを保持する。
  5. active pilot runが0件であることを確認する。
  6. 停止reason codeと再開に必要なcontrolをdecision evidenceへ記録する。

Safety incidentまたはdeterministic Catalog reliability failureによる停止は直ちにNO-GO decisionへ進む。provider、telemetry、process等のshared infrastructure停止は、保持したattemptを基に INSUFFICIENT_EVIDENCEまたは再開可能なBLOCKEDとして扱う。両者を同じreasonへ畳み込まない。

12.3 Evidence rules

  • raw reportとcommitted reportを分け、commit前にstrict schemaで再parseする。
  • Sanitizerはunknown field、duplicate JSON key、absolute path / secret-shaped nested string、禁止IDをfail-closedで拒否する。 黙って削除してGO evidenceを生成しない。
  • absolute path、database path、worktree path、repository ID、MCP server ID、task/run内部IDをcommitしない。
  • commit SHA、prompt / evaluator digest、route / settings / prompt-construction contract / tool manifest fingerprint、 contract / schema version、sanitized reason codeは保持する。
  • controls.promptContractFingerprintは、clean consumer commitに結び付く prompt-construction contract fingerprintを表す。task / armごとに変化し得る実行時system prompt hashは各raw armにのみ残し、registrationやaggregateの同一値と誤認しない。pairの sameTaskPromptは共通の課題本文digestの一致を表し、Catalog arm固有の protocol instructionとの完全一致を意味しない。
  • verifierはsameTaskPrompt: trueを自己申告として扱わず、両armの taskPromptFingerprintがpairのdigestに一致すること、 sameBaseRef: trueなら両armのbase refが一致することを再検証する。
  • committed resultのcontrolsはsanitizerのclosed schemaに限る。DB owner processの確認は raw local preflightのactivePilotRunsDrainedとisolated runtime recordで行い、存在しない singleConsumerDatabaseOwnerのようなfieldをresultへ手書きしない。
  • invalid attemptを削除せず、理由、順序、route、terminal statusを残す。
  • 集計値からvalid pair、valid pairからraw local run inventoryへ辿れるsanitized refとcontent hashを持つ。 database内部IDだけを監査linkにしない。
  • decision writerはsafety precedence、evidence completeness、value gateの順に再計算し、手入力decisionとの不一致を拒否する。
  • sealed registrationはDRAFT status、zero fingerprint、未割当pilot owner、owner-retained policy以外のretentionを拒否する。 result verifierはregistration textのstrict hashとsealed shapeを確認してからraw resultをsanitizeする。

12.4 Raw evidence retention

  • isolated runtime rootはownerだけが読めるpermissionで保存し、operational runtimeと分離する。
  • 両pilot DBとworktreeにはpath、structure、source / tool outputが含まれ得るため、共有driveやrepositoryへcopyしない。
  • raw evidenceはownerだけが読めるlocal runtimeに保持する。自動削除日を設けず、削除が必要になった場合だけ 別の明示的な作業として対象と理由を記録する。
  • 削除する場合は対象pilot ID、raw hash、削除日、ownerをsanitized destruction recordへ残す。
