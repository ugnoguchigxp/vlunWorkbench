1. Outcome and milestones

公開profileは現時点で12種類を目標とする。ただし、12という件数自体を仕様にはしない。 profileは利用目的、capabilityは検査能力、execution profileは現在のorchestratorが実行する定義、 strictnessは実行欠落の判定、result policyはfindingの扱い、safety classは実行可能な環境を表す。 これらを別の型とregistryで管理する。

本計画には二つの完了点がある。

4. Scope and invariants

4.1 In scope

  • use-case起点のcanonical profile catalog
  • catalog、execution definition、policy、safety、availabilityの分離
  • 最大21件のenabled legacy IDと2件のdisabled definitionを扱うlegacy resolution
  • API、CLI、Web、NightWorkers、Oracleで共通のresolver
  • 実行前入力、availability、launchability、limitationの一貫表示
  • machine-readable baseline、migration test、closeout evidence

4.2 Out of scope

  • network、cloud、AD、mobile、wireless、social engineering診断
  • production対象へのactive attack
  • arbitrary scriptまたは無制限fuzzing
  • 新しいexecution step kindとexecution plan v2
  • historical scan_runsの一括backfill
  • NightWorkers contract v2またはOracle output contract変更
  • profile数を12に固定するschema rule

4.3 Non-negotiable invariants

  1. 旧IDで起動したscanのstep、scope、required flag、failure policyを移行だけで変えない。
  2. planned profileとmissing execution definitionをgetProfileByIdから返さない。
  3. NightWorkers allowlistはalias解決前のrequested IDへ適用する。
  4. scan_runs.profileとhistorical metadataを一括更新しない。
  5. catalog entry hashとexecution profile hashを同じ意味で使わない。
  6. R1/R3の既存policy、reset、cleanup要件を弱めない。
  7. coverage unknown、blocked、not executedをcoveredへ変換しない。

Git worktreeは変更分離には使えるが、.git、host process、DB、cache、外部serviceを隔離しない。 R1/R3のsecurity boundaryにはしない。

5.3 R1/R3 disposable execution lifecycle

R1/R3 profileのcatalog接続は、次のlifecycleを既存dedicated flowが満たす場合だけ許可する。 worktreeは入力materializationの一方式であり、containerまたは同等のsandboxと組み合わせる。

  1. 元repositoryのpathと状態を記録し、元repositoryを実行時の書込先にしない。
  2. commitまたは明示snapshotから一時workspaceを作る。未commit変更はsnapshot化してdigestを固定する。
  3. 非特権、resource limit、原則network none、専用DB/cacheのsandboxだけでcodeまたはattackを実行する。
  4. R3はdisposable target、RoE、reset strategy、egress policyを実行前に検証する。
  5. evidenceを一時workspace外へコピーし、secretを除いたcleanup receiptを保存する。
  6. finallyでcontainer、worktree、一時volumeを片付ける。元repositoryへresetやcleanを実行しない。
  7. cleanupまたはresetの確認失敗は成功扱いにせず、blockedまたはincompleteにする。

PC-04はengineを作り直すsliceではない。dynamic-run-policy.ts、dynamic-docker-executor.ts、zap-active-policy.ts、container-fixture-reset.ts、active-container-target-gateway.ts、business logic/reproduction runnerの既存contract testを証跡として確認し、不足があればcatalog entryをexperimentalかつ非起動のまま残してGap Completionへ戻す。

result policyはrun parameterでadvisoryまたはgateへ変更できるが、 profile IDを増やす理由にしない。policy変更はresolved run metadataへ保存する。 result policyをadvisoryへ変えてもrequired stepの失敗やblockerは成功にならない。 planned profileのpolicyは昇格前に実行せず、human decisionはresult policyと別recordにする。 Milestone Aの全entryはallowedResultPolicies: ["advisory", "gate"]、 gateSeverityThreshold: "high"で登録する。

legacy IDは既存実行の完了意味を変えないため、明示的なresultPolicy指定がない限り advisoryとして解決する。canonical IDはcatalogのdefaultを用いる。

6.4 Result policy contract

result policyはscannerの運用成否とfinding判定を混ぜない。Milestone Aでは次の固定規則を実装する。

6.4 Gate decision rules
Condition gateDecision Run status effect
resultPolicy = advisory not_requested なし
required executionがblocked/incomplete/failed blocked 既存profileOutcomeを維持
severity unknownのfindingが1件以上 blocked scan自体はcompletedのままでもよい
閾値以上のfindingが1件以上 fail scan自体はcompleted、CLI gate exitは3
上記以外 pass なし

既定閾値はhighとし、severity順はinfo、low、medium、high、criticalで固定する。 gateDecision、閾値、severity countはrun metadata、result、reportへ保存する。 scanner process failureをfinding gate failへ変換せず、false-positive等の後続reviewでimmutableな run時decisionを書き換えない。review後のrelease判断は別recordで扱う。対話CLIはgate failを exit 3で返すが、executionSurface=webのchild processはterminal run保存後にexit 0とし、 supervisorへprocess failureとして通知しない。

resolverは次の順で判定する。

  1. requested IDをcanonicalまたはlegacy registryから一度だけ解決する。
  2. availabilityとsurface opt-inを確認する。
  3. target supportを確認する。
  4. required/forbidden inputからexecution variantを一つ選ぶ。
  5. requested result policyが許可されることとgate閾値を確認する。
  6. profile_orchestratorならexecution definitionの存在とenabledを確認する。
  7. entry/variant/execution definitionをhashし、secret値を含まないimmutable resolutionを返す。

preview、preflight、dry-run、enqueue、実行は同じresolveProfileSelectionと normalizeProfileResolutionInputを使う。route、CLI、Webごとにvariant選択を 再実装しない。各request境界では一度だけresolveし、start APIはraw requested ID、typed input、expectedCatalogEntryHashをrunProfileScanへ渡す。 orchestratorは実行直前に再解決し、preview/preflight時のcatalog hash、preflight binding hash、plan hashのいずれかが異なれば実行しない。

error codeは次に固定する。

profile_not_found
profile_not_launchable
profile_experimental_not_enabled
profile_target_not_supported
profile_input_missing
profile_input_invalid
profile_result_policy_not_allowed
profile_definition_missing
profile_alias_cycle

generic Web/APIでexperimental entryを起動するにはrequestの allowExperimental: trueを必須とする。R1/R3ではこの値だけで許可せず、dedicated routeの既存feature flag、approval、RoE policyを優先する。includeDeprecatedは list/read用途だけで使用し、start routeでは常にfalseとする。

Phase 56はprofessional claim、一般化評価、 製品入口、交換形式、配布、保守性を扱う。本計画はcatalog、resolution、legacy migration、consumer表示を扱い、 Phase 56のclaimや評価値を置き換えない。

Security Capability Gap Completion はPC-07の外部dependencyである。同文書がGC-00以降のfile、test、exit gate、closeout schemaを 定義し、same-commit evidenceを生成できる状態になるまで、PC-07はblockedとする。 このblockerはPC-00〜PC-06の完了を妨げない。

15. Normative references and design consequences

  • OWASP Web Security Testing Guide — Web Application Security Testing: passiveとactiveを別profile・別安全境界にし、単一tool実行を包括診断と表示しない根拠とする。
  • ZAP Docker User Guideと ZAP Baseline Scan: baselineは受動、full/API scanはactiveを含むため、runtime-passiveとactive-technical-labを 同じgeneric profileへ統合しない。
  • NIST SP 800-115: planning、execution、finding analysis、mitigationを証跡付きphaseとして扱う。
  • NIST SP 800-218 SSDF 1.1: change-gateとsource-assuranceをSDLC内の継続的な検査入口として扱う。
  • OWASP ASVS 5.0: authentication、authorization、business controlはtool名ではなく検証capabilityとして表す。
  • SLSA v1.2 Provenance: SBOM/SCAだけをprovenance検証済みとせず、attestationとtrust policyが揃うまで dependency-supply-chainをplannedに保つ。
