1. 結論

最初に直すのはscannerの検出精度ではない。artifactの上書き、terminal updateによる metadata消失、不安定なreason code、実行versionとmanifestの不一致を先に閉じる。 これらが残ったまま再scanしても、結果を独立検証できず、個別scannerの成否も比較できない。

実装と検証の順序を次で固定する。

  1. todolistのtarget identityと隔離されたacceptance環境を固定する。
  2. artifactをtool run単位で一意に保存し、上書きをfail closedする。
  3. scan terminal updateをatomic metadata mergeへ変更し、preflightを失わない。
  4. preflight codeとscanner provenanceをtyped contractへ変更する。
  5. 各scannerを一つずつtodolistへ実行し、DBとartifactの両方を検証する。
  6. todolist runtimeを一度だけ起動し、DAST、Nuclei、ZAPを個別に検証する。
  7. Schemathesisのnot-applicable経路と明示schema経路を分けて検証する。
  8. 最後にfull-security-scanを連続2回実行し、再現性とcleanupを確認する。
  9. missing binary、timeout、壊れたJSON、重複artifact、target停止を障害注入する。

UI component、画面文言、routing、visual stateは本計画のmerge条件に含めない。backendの JSON contractは固定するが、UIがそのcontractを利用する作業は別PRで扱う。

4.2 Target safety rules

  • test開始時と終了時にtargetのHEADとgit status --porcelainを比較する。
  • dirty target、HEAD不一致、unmerged fileがある場合はscanを開始しない。
  • targetのtracked file、.env、database、lockfileをtestから変更しない。
  • runtime testはtodolistのimmutable source snapshotから作った一時container/sandboxを使い、 原本をprocess cwdにしない。
  • 依存treeが必要な場合は既存treeのread-only snapshotを使い、scan中にinstallしない。
  • database、tool-specific cache、XDG cache、temporary fileはrun root配下へ隔離する。
  • target commitとsnapshot SHA-256を全acceptance evidenceへ保存する。
  • absolute home path、credential、target source bodyは共有evidenceへ保存しない。

4.3 Runtime shape

scanner個別testとtarget起動testを分離する。scanner個別testではacceptance harnessが todolistのpinned target imageを一度起動し、確定したloopback gateway originをscannerへ 渡す。auto target testではproductionのRuntimeTargetProvider interface、readiness、stop処理を通す。 これによりscanner failureとtarget lifecycle failureを混同せず、target project codeをhost processとして実行しない。

  • bindは127.0.0.1だけとし、portはOSから動的に確保する。
  • target imageはscan前の準備段階でtodolist commitとbun.lockから作り、image digestをevidenceへ保存する。scan中にbuildやdependency downloadを行わない。
  • 外向きnetworkはscanner data準備段階を除いて無効にする。
  • runtime databaseは一時workspace内でmigrationし、run終了時に削除する。
  • readinessは/api/healthだけを使い、status 200と固定JSON bodyを照合する。
  • stop後にport、child process、Docker containerが残っていないことを検査する。
  • state-mutating APIをSchemathesis、crawler、Nuclei、ZAPのseedへ入れない。

5. 先に固定するbackend contract

5.1 Artifact identityと保存

artifact pathは表示名ではなくowner identityから生成する。

{scanRunId}/tools/{toolRunId}/raw/{role}.{extension}
{scanRunId}/tools/{toolRunId}/logs/stdout.log
{scanRunId}/tools/{toolRunId}/logs/stderr.log
{scanRunId}/scan/{scanRunId}/{role}.{extension}
{scanRunId}/reports/{reportId}/report.md
{scanRunId}/dast/{dastRunId}/raw/result.json
{scanRunId}/diagnostics/{diagnosticRunId}/{role}.json
  • filesystem writeはflag: "wx"、file mode 0600、directory mode 0700のexclusive createとし、既存pathを上書きしない。
  • storage_keyはOSに依存しないPOSIX separatorで組み立てる。 absolute path、.、..、空segment、backslashを受理しない。
  • runnerへArtifactStorageそのものを渡さない。tool run作成後に生成した ScanArtifactSinkをrun inputへ渡す。
  • roleはraw_result、sbom、diff_manifest、stdout、 stderr、report、diagnosticに限定する。 Trivy filesystem JSONとCycloneDXはそれぞれraw_resultと sbomを使う。
  • DBには新規write用のnullable storage_keyを追加し、partial unique indexを張る。
  • new writerはpathとstorage_keyへ同じrelative pathを保存する。 readerはstorage_key ?? pathを使い、pathは本計画では削除しない。
  • legacy rowはstorage_key=NULLのまま保持し、履歴を捏造して修復しない。
  • sinkはfile作成後にDB rowをinsertし、insert失敗時はそのfileを削除して元のerrorを再throwする。 file作成失敗時はDB insertを開始しない。
  • download時はbuffer読取と同時にsizeとSHA-256を検証し、不一致ならbyteを返さず 409 artifact_integrity_mismatchにする。DB rowがありfileがない場合も404ではなく409とする。
  • report生成前に参照artifactを検証し、不一致artifactをvalid evidenceへ数えない。

5.2 Atomic scan state

  • updateScanRunStatus(..., metadata: fullObject)による全置換をterminal pathから除去する。
  • repositoryにpatchScanRunMetadataとtransitionScanRunTerminalを設ける。 いずれもreadを先行させず、SQLite json_patchを含む単一statementで実行する。
  • terminal transitionは一度だけ成功し、遅延workerの古いsnapshotで上書きできない。
  • scanPreflight、sourceRevision、resolvedProfileHash、 runtimeAssessmentCoverageをterminal rowに必須とする。
  • automated diagnosticの後続metadata追加もpatch mergeだけを使う。

5.3 Lifecycle statusとassessment outcome

次の2軸を混ぜない。

status: queued | running | completed | failed | cancelled
profileOutcome: completed | completed_with_warnings | failed
  • migration後のcanonical valueはnullableなscan_runs.profile_outcomeであり、 shared/schemas/scan.schema.tsのscanRunSchemaにもnullable enumとして追加する。
  • 移行中のreaderはscanRun.profileOutcome ?? parseLegacyMetadataOutcome(...)を使う。 new writerはcolumnとmetadataの両方へ同じ値を書き、S8でmetadata fallbackの削除可否を別判断する。
  • optional step失敗はstatusをcompletedにできるが、outcomeをcompletedにしない。
  • required stepのblocked/failedはstatusとoutcomeの両方をfailedにする。
  • report、CLI JSON、API summaryは同じoutcome resolverを使う。

5.4 Preflight contract

  • 例外messageからreason codeを推定しない。
  • target plannerとscanner probeはcodeを持つPreflightErrorをthrowする。
  • unknown errorはcomponent別のstable fallback codeへ落とす。
  • shared/schemas/scan-preflight.schema.tsへ scanPreflightReasonCodeSchemaを追加し、未知codeをDBへ保存しない。
  • qualification runではpreflight modeをenforcedに固定する。
  • expected/observed version不一致をscanner_binary_version_mismatchにする。
  • version不一致時はreproducible=falseとし、required stepを開始しない。
  • profile内のschema applicabilityはrepositoryまたは明示schemaだけでtarget startより先に判定する。 schema-only stepはHTTP候補を探すためにtargetを起動しない。
  • 正常なnot-applicableはwarningまたはcoverage gapへ変換しない。 coverageEffectSchemaへnot_applicableを追加し、 optionalToolFailedを立てない。 
export class PreflightError extends Error {
  constructor(
    readonly code: ScanPreflightReasonCode,
    message: string,
    readonly cause?: unknown,
  ) {
    super(message);
  }
}

export function preflightReasonCode(
  error: unknown,
  fallback: ScanPreflightReasonCode,
): ScanPreflightReasonCode {
  return error instanceof PreflightError ? error.code : fallback;
}

version比較はobserved文字列から最初のSemVer major.minor.patch[-prerelease]を抽出し、manifestのexpected versionと完全一致させる。 parse不能はscanner_binary_version_unparseable、不一致は scanner_binary_version_mismatchとする。expectedがnullのSchemathesisは存在確認だけを行い、 observed versionをprovenanceへ保存する。

9. Backend test case詳細

9.1 Artifact tests

  • 同一scan内で4 toolがstderrを生成しても4つの異なるstorage keyになる。
  • Trivy filesystemとSBOMを連続実行し、両方のSHA/size/content typeが一致する。
  • 同じstorage keyへの逐次writeと同時writeを両方拒否する。
  • DB insert失敗時にorphan fileを残さず、file write失敗時にDB rowを作らない。
  • download前のhash mismatch、missing file、symlink escapeを拒否する。
  • legacy collision rowはlegacy_integrity_unverifiableとして返す。
  • finding evidenceが別scanまたは別toolのartifactを参照できない。

9.2 Scan state tests

  • preflight保存後のterminal completionでpreflightが残る。
  • tool実行中にmetadata patchが追加されてもterminal completionが失わない。
  • completed scanへ遅延workerがfailed/completedを再適用できない。
  • cancelとtool completionが競合してもterminal stateが一つだけになる。
  • source revision、profile hash、preflight bindingがreportとDBで一致する。
  • diagnostic metadata追加後もoriginal scan metadataが変わらない。

9.3 Preflight tests

  • 全reason codeがschema enumに含まれ、自然文断片を受理しない。
  • todolistのstart planがBun/Vite、loopback、dynamic portとして解決される。
  • missing schemaはtarget start前にnot-applicableとなる。
  • required scannerのversion mismatchはenforced modeでprocessを起動しない。
  • optional scannerの不足はgapとなり、profile outcomeへ伝播する。
  • preview bindingと実行時bindingの差をfail closedする。
  • preflightはbinary/database/browser/imageをdownloadしない。

9.4 Backend API tests

  • scan launchはserver-owned preflightとexpected bindingを必須にする。
  • scan detail、summary、events、artifactsが同じoutcomeを返す。
  • artifact downloadはownershipとhash/sizeの両方を確認する。
  • integrity failureは404へ丸めず、stable error codeを返す。
  • findings pagination中に別scanのfinding/evidenceを混ぜない。
  • UI response shapeのsnapshotではなくschema validationでcontractを固定する。

10.8.2 Container lifecycle

  1. image buildはscan case開始前のprepare phaseで行う。tagは vuln-workbench-acceptance-todolist:<12-char-commit>、build contextはarchive展開先とする。

  6. cleanupはscanner gateway、scanner container、target container、networkの順にstop/removeする。 success時もfailure時もfinallyから同じidempotent methodを呼ぶ。

18. Rollback

  • S1 rollbackではmigrationを残し、該当profile/adapterをdisableしてartifact-producing scanをfail closedする。 legacy共通path writerへ戻さない。

  • S4-S6のscanner adapter failureは該当adapterをdisableし、他adapterへ影響させない。
  • rollback時もnew artifactをlegacy共通pathへ書き戻さない。
  • 既に採取したacceptance evidenceはimmutableとして残し、後続runで置換しない。
