1. Executive decision

現在の問題を「14 profileに14種類の不具合がある」とは扱わない。公開catalog、legacy execution definition、canonical execution definition、frontend dispatch、dedicated route、preflight、E2E registry、stability baselineが異なるprofile集合を参照していることを構造的な原因とする。

修正方針は次の4点に固定する。

  1. profileを実装本体ではなく、単一のProfileDefinition registryに保存する宣言とする。
  2. 14 profileを6種類の共通execution engineと1種類のrun-group coordinatorへ割り当てる。
  3. 全profileを同じserver-side lifecycleと永続化event ledgerへ通す。dedicated flowは例外経路ではなく engine driverとして接続する。
  4. stableを手動表示値ではなく、現在のsource、catalog、driver、image digest、platformに 対するqualification結果から導出するrelease claimへ変更する。

既存profileを一括置換しない。まずGolden Path 2系統を新契約へ適合させ、DB状態、結果、event、 cleanupが既存の完了runと同等であることを確認してから、engine family単位で移行する。

3. Scope, non-goals, and prohibitions

3.1 In scope

  • 14件の公開scan profileと、それらが参照するlegacy execution definition。
  • Web、CLI、Security Oracle、NightWorkersからのprofile解決と起動。
  • readiness、preflight binding、Execution Plan、event、cleanup、terminal state。
  • Docker image、scanner binary、host capability、platformの依存資格。
  • profile/variant/engine単位のqualificationとavailability claim。
  • 既存runとlegacy profile IDの互換読取。

3.2 Non-goals

  • scanner ruleや脆弱性判定方式の全面的な変更。
  • R3 profileを安全条件未達の通常repositoryで強制実行すること。
  • 全profileを全projectへ適用可能と見せること。
  • 既存run metadataを破壊的に書き換えること。
  • professional-fullを単一の巨大execution profileとして実装すること。
  • この移行と無関係なreport、finding、integrationの再設計。

3.3 Prohibitions during migration

  • frontendへ新しいprofile ID条件分岐を追加しない。
  • profile固有のDocker image fallbackを追加しない。
  • :local、:latestなどのmutable tagを実行bindingへ保存しない。
  • Execution Planを保存せずにrunをrunningへ遷移させない。
  • cleanup未完了またはreceipt未保存のrunをcompletedにしない。
  • qualification未達のprofileを件数合わせでstableへ変更しない。

4. Golden Path contract

4.1 Source Assurance Golden Path

「ソースセキュリティ保証」をR0 repository engineのreference implementationとする。既存の Gitleaks、OSV-Scanner、Trivy、Semgrep applicability、immutable source snapshot、tool result、 finding import、cleanupを維持する。

Golden Path認定は「過去に一度完了した」ことではなく、同じfixture、binding、platformでSection 9.4のqualification successを3回連続して満たすことを条件とする。

4.2 Runtime Passive Golden Path

「安全な実行時Web診断」(runtime-passive)をR2 passive runtime engineのreference implementationとする。runtime target準備、read-only HTTP DAST、Nuclei safe、ZAP baseline、 runtime resource cleanupを共通planへ統合する。

このprofileは完了実績と失敗実績の両方があるため、現時点ではcertified Golden Pathではない。 ready判定後の全step failure、tool run未生成、失敗証跡の保持を修正し、Section 9.4のqualification successを3回連続で満たした時点でreference implementationとして固定する。

4.3 Golden Path coverage limit

上記2系統はR0とR2しか保証しない。R1とR3のpromotion前に、公開profileとは別の内部qualification fixtureを追加する。

  • R1 canary: networkなし、read-only source、制限付きartifact writeでtest commandを実行する。
  • R3 canary: system-owned disposable targetを変更し、reset receiptと初期状態復元を検証する。

5. Target architecture

5.1 Single ProfileDefinition registry

新しいProfileDefinition registryを、公開表示と実行の唯一の正本とする。catalog、UI、 preflight、plan、E2E registryはこの定義から生成または検証する。 

type ProfileDefinition = {
  id: CanonicalProfileId;
  availabilityPolicy: AvailabilityPolicy;
  safetyClass: "R0" | "R1" | "R2" | "R3" | "mixed";
  engineId: ExecutionEngineId;
  inputSchema: VersionedInputSchema;
  variants: ProfileVariantDefinition[];
  applicability: ApplicabilityEvaluator;
  readiness: ReadinessEvaluator;
  dependencyManifest: DependencyRequirement[];
  planFactory: ExecutionPlanFactory;
  progressContract: ProgressContract;
  cleanupContract: CleanupContract;
  qualificationPolicy: QualificationPolicy;
  legacyAssociations: LegacyProfileAssociation[];
};

registry登録時に、ID一意性、engine存在、inputとvariantの整合、全stepのprogress定義、cleanup、 qualification policy、legacy association重複を検証する。公開entryの不足はapplication起動時ではなく build/test時に失敗させる。

5.3 Common server-side lifecycle

Launch Attempt persisted
  -> Resolve ProfileDefinition and variant
  -> Evaluate applicability and project readiness
  -> Resolve qualified dependencies
  -> Compile immutable Execution Plan
  -> Persist plan and admission binding
  -> Mark run running
  -> Execute engine driver steps
  -> Append step and evidence events
  -> Cleanup resources and persist receipts
  -> Finalize run outcome

dedicated routeは上記lifecycleを迂回しない。既存のdynamic、DAST auth、active assessment、business logic、reproduction runnerは、共通lifecycleが呼び出すdriver adapterとして段階的に接続する。

5.4.1 Execution Plan V4

dedicated flowを含む新規runはScanExecutionPlanV4を保存する。V4はV2の共通fieldを継承し、 V3のruntimeIsolationをoptionalにし、次を追加する。 

type ScanExecutionPlanV4 = ScanExecutionPlanV2 & {
  schemaVersion: 4;
  canonicalProfileId: CanonicalProfileId;
  profileVariantId: string;
  engine: { id: ExecutionEngineId; version: 1 };
  inputBindingHash: Sha256Digest;
  dependencyQualificationHash: Sha256Digest;
  availabilityClaimHash: Sha256Digest | null;
  progressContract: ScanProgressContractV2;
  runtimeIsolation?: ScanExecutionPlanV3["runtimeIsolation"];
};

step kindは一つのschemaからplan、normalized result、progress eventへ再利用する。既存7種に dynamic_test、sanitizer、fuzz、 auth_session、active_transaction、 authorization_matrix、zap_active、 business_scenario、reproduction、 child_profileを追加する。3箇所へ別々のenumを複製しない。

5.4.2 Engine driver contract

interface ScanExecutionEngine {
  readonly id: ExecutionEngineId;
  preview(context: Readonly<ScanPreviewContext>): Promise<EnginePreview>;
  execute(context: Readonly<AdmittedScanContext>): Promise<EngineResult>;
  cleanup(context: Readonly<CleanupContext>): Promise<CleanupReceipt[]>;
}

type EngineResult = {
  stepResults: NormalizedProfileStepResult[];
  coverageLedger: CoverageLedger;
  evidenceRefs: string[];
  profileOutcome: "completed" | "completed_with_warnings" | "failed";
};
  • previewはDB設定やproject fileを変更しない。
  • executeは保存済みV4 planだけを実行し、applicabilityを再計算しない。
  • executeはrun statusを直接更新しない。common lifecycleだけがstatusを更新する。
  • cleanupは冪等で、同じleaseへ複数回呼び出せる。
  • driverはprofile IDを条件分岐せず、registryから渡されたvariant contractを使用する。

Start admissionではcached qualification receiptとhashだけを検証し、image pull/build、container起動、database作成、target起動を 行わない。receiptがmissing/staleならStart内で長時間probeせず409または503を返し、Preview再実行またはsetup actionへ戻す。 admitted後の準備はV4 planのphase eventとして実行する。Start responseのservice目標はp95 2秒以内とする。

5.5.2 Setup boundary

canonical Start APIはauth context、DAST target、engagement、scenario、custom dynamic configを作成・更新しない。 それらは既存setup APIで事前作成し、Start inputにはIDとpreviewで計算したrevision hashを渡す。唯一の例外は runtime-passiveとapi-readonlyのauto project runtimeであり、これはExecution Plan上のleased resourceとして作成し、同じrunでcleanupする。

public Start requestからrunner、dockerImage、networkを削除する。 execution engineとDependency Manifestだけがこれらを決める。compatibility adapterは旧fieldを受理しても、 policyと異なる値を指定された場合はlegacy_execution_override_rejectedで拒否する。

8. Execution Plan, progress, and cleanup

8.1 Execution Plan contract

全runは実行開始前にversioned Execution Planを保存する。各stepは次を持つ。

  • stepId、driver adapter、目的、必須/任意、failure policy。
  • dependency binding、timeout、resource policy。
  • 期待するartifact/evidence kind。
  • cleanup actionとcleanup必須条件。

profileに適用しないstepはplanから消さず、plan compile時にnot_applicableとして確定させるか、 variantとして別planにする。進捗分母が実行中に変化しないことを保証する。

8.2 Progress event contract

全engineが最低限、次のeventを共通repositoryへ書き込む。

  • scan.queued、scan.started。
  • 各phaseのscan.phase.started、scan.phase.finished。
  • scan.readiness.evaluated、scan.plan.compiled。
  • 各stepのscan.step.started、scan.step.progress、scan.step.finished。
  • scan.cleanup.started、scan.cleanup.finished。
  • scan.completedまたはscan.failed。

eventには単調増加するseq、plan hash、step ID、reason code、timestampを含める。UIはprofile定義や frontend timerではなく、保存済みplanとeventだけから進捗を再構築する。

9. Qualification and availability

9.1 Five-level guarantee

  1. Definition integrity: registry entryが完全である。
  2. Environment qualification: dependency adapterを現在環境で起動できる。
  3. Profile qualification: profile claimを固定fixtureで再現できる。
  4. Project readiness: 現在projectで適用条件と入力条件を満たす。
  5. Per-run conformance: plan、event、evidence、cleanupがrunごとに整合する。

「稼働保証」は、readyと判定されたprofileがadmissionされ、全工程を観測可能な状態で実行し、 lifecycle contractを満たしてterminal stateへ到達することを指す。検査claimの成功はSection 9.4の qualification successを別途満たす必要がある。全projectで全profileを適用可能にする意味ではない。

9.2 Required qualification matrix

各public profileとvariantに、該当する次のcaseを登録する。

9.3 Derived availability

qualification receiptはruntime DBの認可入力にしない。release evidenceとして保存し、promotion manifestが profile、variant、commit、catalog hash、driver hash、dependency digest、platform、case resultを集約する。 build/release時にmanifestを検証し、配布catalogのavailability claimを生成する。

  • stable: 必須platformと必須caseのcurrent receiptが揃う。
  • experimental: engineは存在するが、claimまたはplatform qualificationが不足する。
  • planned: driverまたは安全境界が未完成で起動不可。
  • deprecated: replacementとusage evidenceに基づく移行期間中。

9.4 Success semantics and qualification counting

次の3つを同じ「成功」という語で扱わない。

  • Lifecycle conformance: success/failureを問わず、plan、event、terminal state、cleanupが整合する。
  • Failure observability: 意図的なmissing dependency、timeout、crash等が具体的reasonで終了する。
  • Qualification success: profileが掲げる検査claimを実scannerと固定fixtureで完遂する。

repeatabilityとstable promotionに数えるのは、qualification caseの purpose="qualification_success"で次をすべて満たすrunだけとする。

  1. run statusがcompleted、profile outcomeがcompletedである。
  2. 全required stepがcompleted、全required coverage itemがcoveredである。
  3. profile policyが要求するevidenceとartifactが1件以上あり、digest検証に成功している。
  4. 全必須cleanup receiptが成功し、active leaseが0件である。
  5. 実行したdependency digest、plan hash、input binding hashがqualification bindingと一致する。
  6. 許可されていないwarning、false pass、secret leak、host mutationが0件である。

completed_with_warningsは運用上のterminal stateとして保持するが、初期の許可warning listは空とし、qualification successには数えない。failure fixtureは purpose="failure_observability"、N/A fixtureはpurpose="readiness_classification"とし、 lifecycleを満たしても3回連続成功やpromotionの分子へ入れない。

10. Ordered work packages

packageは番号順に実施する。各packageのexit gateを満たすまで後続familyへ進まない。期間見積りはbaseline test時間と1 familyの実測throughputを得た後に別途作成する。

WP-00 — Baseline, freeze, and reachability inventory

目的: 実装開始時点の事実を固定し、表示されるが到達不能なprofileを増やさない。

  • HEAD、dirty tree、runtime settings、platform、Docker/image digestを記録する。
  • 14 profileについてcatalog、UI、resolver、route、driver、plan、progress、cleanup、E2Eの対応表を生成する。
  • 到達不能または依存未資格のprofileは、削除せずreadinessをunavailable/blockedとして表示する。
  • Golden Pathの成功・警告・失敗runからsafe baseline artifactを生成する。

Exit gate: 公開profile全件が対応表に存在し、未対応欄が空欄ではなくreason codeを持つ。

WP-01 — ProfileDefinition registry and invariants

目的: profile集合の正本を一つにする。

  • profile-definition.tsとengine registryを追加する。
  • 既存catalogとexecution definitionをadapterで読み、初期段階では挙動を変えない。
  • API catalog、launch contract、qualification inventoryをregistryから生成する。
  • verify:scan-profile-architectureとqualify:scan-profile:allを package.jsonへ追加し、script本体の直接実行と同じ結果になることをtestする。
  • 全entryのdriver/input/readiness/plan/progress/cleanup/qualification完全性testを追加する。

Exit gate: profile追加・削除・variant追加時に、契約不足がcompile/test failureになる。 UIまたはE2Eだけから欠落するprofileを作れない。

WP-02 — Launch Attempt and common lifecycle

目的: 起動前失敗からcleanupまでを同じ状態機械へ通す。

  • launch attempt schema/repositoryを追加する。
  • common lifecycle serviceとengine driver interfaceを追加する。
  • run作成、plan保存、running遷移のtransaction順序を固定する。
  • step event、terminal event、cleanup receiptのinvariantを実装する。
  • process crashと期限切れleaseのreconciliation testを追加する。

Exit gate: preflight block、driver起動失敗、step timeout、cleanup失敗を再現し、すべての attemptとterminal reasonをDBから説明できる。

WP-03A — Golden Path dependency manifests

目的: WP-03が未定義imageやhost toolに依存せず、同じbindingで再現できるようにする。

  • Gitleaks、OSV-Scanner、Trivy、Semgrep、Nuclei、ZAP、runtime/database imageをmanifestへ登録する。
  • container imageをdigest pinし、daemon、inspect、entrypoint、adapter dry-runを資格確認する。
  • artifact storeのwrite/read/deleteとruntime port leaseを資格確認する。
  • current platformのreceiptを生成し、source-assurance/runtime-passiveのpreview bindingへ結合する。

Exit gate: Golden Pathに必要な全dependencyがqualifiedか、profile previewで個別reason codeを持つ blocked_environmentになり、実行中に初めてdocker_image_unavailableにならない。

WP-03 — Golden Path adapters

目的: 新しい共通契約を既存の2系統で証明する。

  • source-assuranceをrepository driverへ接続する。
  • runtime-passiveをpassive-runtime driverへ接続する。
  • 既存finding、summary、artifact、result policyとの互換性を比較する。
  • runtime-passiveのready後全step failureとtool run未生成をfailure fixtureとして固定する。
  • 両Golden PathでSection 9.4を満たすqualification successを3回連続実行し、resource leakを検査する。

Exit gate: vulnerable/fixed/failure fixtureでplan、event、tool run、finding、cleanupが 期待どおり一致し、旧経路をfallbackにせず新経路を既定にできる。

WP-04 — Dependency qualification

目的: Docker/image/host toolの不整合をprofile個別問題から環境状態へ移す。

  • Dependency Manifest、probe、receipt cacheを追加する。
  • WP-03Aのregistryを残りprofileへ拡張し、Schemathesis、Cosign、dynamic/R1/R3 imageを登録する。
  • auto-configをmanifest resolverへ置換し、空値とmutable fallbackを拒否する。
  • current platform用のminimal adapter fixtureを実行する。

Exit gate: imageなし、daemon停止、entrypoint不一致、binaryなし、未対応platformをそれぞれ 別reason codeで起動前に判定できる。

WP-05 — Unified consumer launch and progress

目的: Web/CLI/Oracle/NightWorkersの独自dispatchと独自進捗stateを除去する。

  • catalog APIへreadiness、input schema、launch action、plan previewを追加する。
  • frontendのprofile ID条件分岐をschema-driven formと単一Start APIへ置換する。
  • CLI flag、Oracle request、NightWorkers scheduleをSection 9.6のcanonical schema adapterへ置換する。
  • progressは保存済みplan/eventからだけ構築する。
  • ready以外の状態に、原因、必要入力、修復actionを表示する。

Exit gate: catalogが公開する全profileで適切なreadinessが表示され、全consumerが同じengine/variantへ到達する。 到達不能profileがenabledになること、実行中に0 / 0となることがない。

WP-10 — Remaining R0 engines

change-gateをrepository engineへ、dependency-supply-chainと release-artifactをsupply-artifact engineへ移行する。Cosign、attestation、image/tar入力を typed dependency/input contractへ接続する。variant、input、step、fixtureはSection 9.5の行をそのまま実装する。

Exit gate: R0全profileがlegacy execution IDを経由せず資格matrixを満たす。

WP-20 — Remaining passive R2 profiles

api-readonlyとauthenticated-webをpassive-runtime engineのvariantとして 移行する。schema discovery、read-only operation policy、auth contextをSection 9.5のplan inputに固定する。

Exit gate: runtime target、schema、auth contextの不足が実行failureではなくreadinessで 判定され、全stepが共通progress contractを満たす。

WP-30 — R1 isolated code profiles

R1 internal canaryを先にqualificationし、その後dynamic-verification、 sanitizer-fuzz-lab、custom-dynamic-labをisolated-code engineへ移行する。

  • parent runのcanonical profile IDとvariantを正しく認可する。
  • network、mount、resource、timeout、artifact出力をplanへ保存する。
  • Go、Cargo、sanitizer、fuzzer等はdetectorとqualified dependencyの両方を満たす場合だけreadyにする。
  • built-inとcustom configの入力境界、step ID、fixtureをSection 9.5どおりに実装する。

Exit gate: 3 profileすべてにUI launch、escape negative test、cleanup test、3回E2Eがある。

WP-40 — R3 controlled active profiles

R3 canary完了後、active-technical-labとbusiness-logic-labを controlled-active engineへ移行する。system-owned disposable target、RoE、reset plan、quarantineを 共通lease contractへ接続する。 active request unionとbusiness scenario参照はSection 9.5から拡張しない。

Exit gate: reset成功、reset失敗、target drift、同意不足、RoE期限切れをE2Eで検証し、 reset receiptなしで成功しない。

WP-50 — Remediation replay

remediation-verificationを独自再実装ではなく、元runのprofile、variant、safety、input、 dependency bindingを安全に再構成するreplay engineへ移行する。

Exit gate: 対応scanner/driverだけが再実行され、元runより安全境界が緩和されず、共通eventと cleanupを満たす。

WP-60 — Professional run group

professional-fullは単一profile driverにしない。project readinessに基づき、qualifiedな child profileを選択し、run groupとして実行・集約する。R3は明示同意と専用targetがある場合だけ別groupへ 含める。

  • api/modules/scans/execution/professional-run-group.tsの既存immutable parent contractとcapability mappingを再利用する。
  • 不足しているchild schedulerをcommon launch service上に実装し、child preview bindingを再検証する。
  • parent step eventはchild run IDを参照し、childのstatusやresource leaseを複製しない。
  • 技術run group完了とhuman review pending/approved/rejectedを別fieldで保持する。

Exit gate: child runごとのclaimとlimitationを保持し、未実行capabilityを包括的に 「診断済み」と表示しない。

WP-70 — Legacy retirement

  • 新規runがlegacy execution IDを保存しないことをusage evidenceで確認する。
  • legacy IDはread compatibility adapterへ限定する。
  • scanner E2E registryとstability inventoryをProfileDefinition registry由来へ変更する。
  • frontend/dedicated routeのprofile固有dispatchを削除する。

Exit gate: legacy定義をproduction execution surfaceから除いても全public profileの qualification matrixが変化しない。

WP-80 — Closeout and release claim

  • bun run qualify:scan-profile:allでcurrent commitの全profile qualification manifestを生成する。
  • catalog、Web、CLI、Oracle、NightWorkersのcontract testを実行する。
  • bun run verify:scan-profile-architectureでSection 9.5の14行とregistry/consumer/fixtureを照合する。
  • active lease、orphan process/container、欠落artifactを検査する。
  • rollback rehearsalを実行し、旧read pathと新write pathの境界を確認する。
  • 完了した旧計画の残項目を本書のpackageまたは別計画へ明示的に移管する。

Exit gate: Section 12のDefinition of Doneをすべて満たす。

11. Rollout and rollback

11.1 Strangler rollout

  1. registry adapterを追加し、既存レスポンスとのsnapshot比較を行う。
  2. Golden Pathだけを新lifecycleへ切り替える。
  3. engine familyごとに新write pathへ切り替える。
  4. 旧runはcompatibility readerで表示し続ける。
  5. qualification完了後に旧write pathを削除する。

11.2 Rollback rules

  • schema migrationはadditiveにし、旧readerが未知fieldを無視できることをtestする。
  • family feature flagはserver側に置き、profile IDごとのfrontend flagを作らない。
  • rollback時も新形式のattempt、plan、eventを削除しない。
  • 新engineで作成したresource leaseを旧engineへ引き継がず、reconcilerで解放する。
  • rollback後のavailability claimは対応するqualification manifestへ戻す。

12. Definition of Done

本計画は、次の条件をすべて満たした場合だけ完了とする。

  1. 公開14 profileが単一registryに存在し、1つのengineまたはrun-groupへ解決される。
  2. Section 9.5の14行すべてが、一意なinput branch、variant、step ID、fixture manifestを持つ。
  3. planned profileを除く全profileにreadiness、input schema、plan、progress、cleanupがある。
  4. Web/CLI/Oracle/NightWorkersにprofile ID固有のrunner dispatchがなく、同じlaunch serviceを使う。
  5. Webが空のprofile stepsを生成せず、server plan previewを表示する。
  6. 全Start試行がlaunch attemptとして永続化される。
  7. runningのrunには保存済みExecution Planがある。
  8. 全plan stepがstarted後に一度だけterminal eventを持つ。
  9. 必須cleanup receiptがないrunはcompletedにならない。
  10. terminal runのactive resource leaseが0件である。
  11. 実行metadataにmutable image referenceがない。
  12. stable profileにcurrent qualification manifestがある。
  13. 全public profile/variantが必須qualification matrixに登録される。
  14. failure/N/A caseがrepeatabilityまたはpromotionの成功数へ算入されない。
  15. completed_with_warningsが許可listなしにqualification successへ算入されない。
  16. 対応platformごとにGolden Pathと各family canaryがSection 9.4を満たして3回連続成功する。
  17. professional-fullが全childをcommon launch serviceからscheduleし、child coverageとreview stateを集約する。
  18. 既存run、report、finding、artifactがcompatibility readerで参照できる。
  19. 現在projectに対する各profileがready、needs_input、 needs_setup、not_applicable、blocked_environment、 unavailableのいずれかで説明され、generic errorだけを返さない。

13. Stop gates

次のいずれかが発生した場合、後続packageへ進まず、本書または該当contractを改訂する。

  • Golden Pathの既存finding、result policy、safety境界が意図せず変化する。
  • 新registryと公開catalogでprofile集合またはclaimが一致しない。
  • frontend分岐を残さないとprofileを起動できない。
  • preflight readyと実adapter probeが同じbindingへ結合できない。
  • cleanup failureをterminal stateへ安全に反映できない。
  • qualification fixtureが実scannerではなくmock結果だけで成功する。
  • dirty treeの利用者変更を上書きしないと移行できない。
