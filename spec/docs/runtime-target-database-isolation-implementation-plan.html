1. Conclusion

「破棄可能なsource snapshot」はoriginal working treeの保護には有効だが、target processが snapshot内の.envや設定を読み、host network経由で共有DBへ接続することまでは防がない。 したがって、同意checkboxはDB汚染を防ぐsecurity boundaryとして扱わない。

実装後のruntime executionは次の一経路に固定する。

  1. scanner入力とは別に、credential-bearing fileを除外したruntime source projectionを作る。
  2. project codeをhost processとして起動せず、digest固定されたserver-owned Node runtime imageを使う。
  3. --network noneのnamespace ownerへtarget、ephemeral DB、scannerを --network container:<owner>で参加させる。
  4. DB接続値はrunごとに生成し、target data storeはcontainer/tmpfs内だけに置く。
  5. preflight、execution plan、resource lease、cleanup receiptを同じisolation plan hashへbindする。
  6. 条件を証明できないproject、engine、Docker runtimeでは起動せず、fail-closedにする。

qualification完了後、runtime-passiveとapi-readonlyからproject code execution同意checkboxを削除する。dynamic-verificationは同じruntime source projectionと data isolation contractへ移行した時点で同意checkboxを削除する。旧同意値は移行期間中に受理しても、 unsafe executionを許可するauthorityとして使用しない。

1.2 Implementation reader contract

各work packageは次の順序で実装する。順序を入れ替えない。

  1. packageのcharacterization/negative testを追加し、修正前の挙動を固定する。
  2. shared schemaとpure functionを先に変更し、型checkを通す。
  3. Docker/process mutationより前にpreflightをblockedへ倒す。
  4. providerとconsumerを接続し、unit/integration testを通す。
  5. cleanup failure injectionとredaction testを通す。
  6. package固有commandとSection 9.4の累積commandを実行する。

package内のすべてのexit gateを満たすまで次packageを開始しない。型errorを as any、unchecked cast、optional fallbackで回避しない。実装途中のproviderを有効化する feature flag、UI、catalog変更は同じpackageへ混ぜない。

2. Planning baseline and gap register

2.1 Current facts

  • source scopeは**/*をincludeし、mandatory excludeは主に.git、 artifacts、generated output、installed dependencyである。Gitでignoreされた .env*はruntime用copyから自動除外されない。
  • local target preparationはpackage/framework start planを推論し、許可されたplanを Bun.spawnでhost上に起動できる。HOMEと代表的なenvironment variableは差し替えるが、 filesystem、process、network namespaceはhostと共有する。
  • Bunは既定で.env、mode別.env、.env.localを読み込むため、 parent environmentからDATABASE_URLを除くだけではDB credentialを遮断できない。
  • npm start plannerはproject scriptを選択しながら requiresProjectCodeConsent: falseを返す。preflightはこの値をsandbox availabilityの 代理として使うため、consent不要とisolation済みを区別できない。
  • Java/Python start planはhost sandbox不在時にfail-closedとなるが、production用の一般 RuntimeTargetProvider実装はWeb/CLI起動経路へ接続されていない。
  • dynamic executionはDocker、non-root、read-only rootfs、resource limit、既定network noneを使う。 一方、original repositoryをread-only mountし、writable workdirへ全内容をcopyするため、 .env*をtest processから不可視にするcontractはない。
  • scan_resource_leases、release/quarantine、expired lease reaperが既にある。 新しいruntime resource lifecycleはこの仕組みを再利用できる。
  • execution plan v2はnetwork policy、approval、cleanup requirementを持つが、runtime source、 runtime/dependency image、DB provider、network namespace、cleanup receiptを一つにbindするfieldはない。

  6. Docker socket、host home、original repositoryのread-write mountを渡してはならない。

4.1 Separate scanner and runtime source projections

generic target-scope.tsへ.env*のglobal excludeを追加しない。

  • scanner source snapshotは現行scopeを維持し、Gitleaksなどがcredential-bearing fileを検査できる。
  • 新規materializeRuntimeSourceProjectionはoriginal repoではなく、 materializeScopedSourceSnapshotが返した FullSourceSnapshot.projectPathだけを入力にする。
  • policy constantはRUNTIME_SOURCE_PROJECTION_POLICY_V1とし、次のexact globを additionalScope.excludeGlobsへ追加する: .env、.env.*、**/.env、**/.env.*、 .npmrc、**/.npmrc、.pypirc、 **/.pypirc、.netrc、**/.netrc、 .aws/**、**/.aws/**、.config/gcloud/**、 **/.config/gcloud/**、*.pem、**/*.pem、 *.key、**/*.key、*.p12、**/*.p12、 *.pfx、**/*.pfx、*.db、**/*.db、 *.sqlite、**/*.sqlite、*.sqlite3、 **/*.sqlite3、*.sock、**/*.sock。
  • createScopedWorkspaceは現在internal symlinkをfileとしてcopyしないが、 policy testで全symlinkがprojectionに存在しないことを固定する。symlink追跡機能を追加しない。
  • return typeは { rootPath, projectPath, sourceSnapshotDigest, projectionDigest, policyVersion: 1, includedFileCount, excludedCategoryCounts, cleanup } とする。projectionDigestはrelative path、file modeの実行bit、bytesをpath順でhashする。
  • excluded path名はartifact/eventへ保存せず、category countだけを保存する。 runtime generated configurationはprojection外のserver-owned temporary directoryで作るが、 raw credentialを含むfileは作らず、Docker --env-fileも使用しない。
  • copy失敗時は作成途中rootを削除してruntime_source_projection_failedを返す。 cleanupはidempotentで、receipt persistence失敗を成功扱いにしない。

4.2 Runtime isolation recipe

repositoryが明示設定を必要とする場合は.vuln-workbench/runtime-target.v1.jsonを使用する。 DB modeがnone以外の場合は必須である。このfileはversion control対象とし、credential、 hostname、port、DSN、image、Docker option、arbitrary shellを禁止する。 

{
  "schemaVersion": 1,
  "startPlannerId": "start.npm.package-script",
  "dependencyAdapterId": "npm-package-lock-v1",
  "database": {
    "mode": "postgres_ephemeral",
    "environmentBindings": [
      { "key": "DATABASE_URL", "valueKind": "url" }
    ]
  },
  "readinessPaths": ["/api/health"]
}
  • database.modeはnone、sqlite_ephemeral、 postgres_ephemeral、mysql_ephemeralだけを許可する。
  • environmentBindings[].keyは DATABASE_URL、DB_URL、POSTGRES_URL、 MYSQL_URL、SPRING_DATASOURCE_URL、 SPRING_DATASOURCE_USERNAME、SPRING_DATASOURCE_PASSWORD、 DB_HOST、DB_PORT、DB_NAME、 DB_USER、DB_PASSWORD、SQLITE_PATHだけを許可する。
  • valueKindはurl、jdbc_url、host、 port、database、username、password、 file_path、file_urlのenumとする。modeと両立しない組はschema refinementで拒否する。
  • recipe不在時に許すのは、DB indicatorが0件でplannerが一意なdatabase.mode=noneだけである。 dependency/設定からDB indicatorが1件でも検出された場合は runtime_database_recipe_required、engine候補が複数なら runtime_database_mode_ambiguousでblockedにする。
  • dependencyAdapterIdはserver registryに存在するIDだけを許可する。V1でreadyになれるのは root package-lock.jsonと整合するnpm-package-lock-v1だけである。
  • readinessPathsは1〜5件、各値はquery/fragmentを持たないrelative HTTP pathとし、 schema不在時はstart plannerのpathsを使う。target portはrecipeで指定せず18080固定とする。
  • application startupがmigration/seedを行うことは許可するが、project-owned migration commandを 別host phaseとして実行しない。migration失敗はtarget readiness failureとしてbundle cleanupへ進む。

DB indicator検出はruntime projection rootのpackage.jsonと次の既知config pathだけを読み、 source本文やignored fileをheuristic scanしない。

4.3 Isolated npm dependency preparation plane

V1はproject固有imageをbuildしない。deployment設定でdigest固定されたNode runtime imageをtargetとdependency fetchに使い、project sourceとnode_modulesをrun専用volumeへ materializeする。既存ApprovedBuildRecipeは別用途のattestation contractなので拡張しない。 canonical hash helperの実装patternだけを再利用する。

providerがbundle leaseを取得した後、internal RuntimeWorkspacePreparer.prepare(plan, runtimeProjection, bundleContext)を次の順序で実行する。 runtimeProjectionはSection 4.1のhandleであり、project pathとdigestを持つがplan/public metadataへserializeしない。bundleContextはserver-generated bundle/scan/lease ID、role label builder、updateActiveReceipt callbackだけを持つ。

  1. runtime projectionのrootにpackage.jsonとpackage-lock.jsonが各1件あること、 lockfileVersionが2または3であること、recipeのplanner/adapterと一致することを検証する。
  2. lock内のresolved URLを走査し、schemeがHTTPS、hostが registry.npmjs.org、URL credentialなし、root entryを除く全external packageに integrityあり、 git+/file:/link:/workspace: dependencyなしを要求する。 違反はruntime_dependency_lock_unsupportedでblockedにする。
  3. bundle label付きのdependency volume、workspace volume、internal build network、egress build networkを作る。いずれも既存volume/networkを再利用しない。
  4. server-owned materializer containerを--network noneで起動し、dependency volumeへpackage manifest 2件だけをcopyする。original repo、runtime projection全体、host HOME、host package cacheはmountしない。
  5. digest固定allowlist proxyをinternal/egress build networkの両方へ接続する。proxyは registry.npmjs.org:443へのCONNECTだけを許可し、request body/headerをlogしない。 dependency fetch containerはinternal networkだけへ接続する。
  6. digest固定Node imageをnon-root、--cap-drop ALL、 --security-opt no-new-privileges、read-only rootfs、tmpfs HOMEで起動する。 dependency volumeだけを/workspaceへRW mountし、次の固定argvをshellなしで実行する。 npm ci --ignore-scripts --no-audit --no-fund --cache /workspace/.npm-cache。 HTTP_PROXY/HTTPS_PROXYはproxy、 NO_PROXYは空、registryはhttps://registry.npmjs.org/へ固定する。
  7. fetch完了後、fetch/proxy containerと両build networkを削除する。削除確認前にproject sourceを扱う次phaseへ進まない。
  8. server-owned materializerを再度--network noneで起動し、sanitized runtime projectionとdependency volume内のnode_modulesをworkspace volumeへcopyする。 .npm-cacheはcopyしない。copy後manifestを作り、projection digest、lock digest、 runtime image digest、dependency tree digestをworkspace receiptへbindする。

dependency phaseへDB environment、project environment、request由来proxy/image/registryを渡さない。 lifecycle scriptを必要とするpackage、native buildのため--ignore-scriptsで起動不能なproject、 monorepo/workspace、private registryはV1では runtime_dependency_adapter_unqualifiedでblockedにする。失敗後にhost npm installへfallbackしない。

全imageはruntime-image-registry.tsのplatform別 repository@sha256:digestだけを使う。preflightはdocker image inspectでlocal存在と digest一致を確認し、scan/preview/start中にdocker pullまたはdocker buildを行わない。 未配置はruntime_image_missing、digest不一致は runtime_image_digest_mismatchでblockedにする。

4.4 Network-none namespace bundle

targetとDBの通信にはuser-defined bridgeを使わない。runごとにnamespace owner containerを --network noneで作り、残るcontainerを同じnetwork stackへ参加させる。

10. Rollout and rollback

10.1 Rollout order

  1. DBI-00のnegative fixtureとbaselineを先に固定する。
  2. DBI-01〜04を入れ、new schema/preflightをshadow計算する。host target fallbackはこの時点で削除する。
  3. DBI-03/05/06をfeature gate offで接続し、DBなし/SQLite bundleをexperimental qualificationする。
  4. DBI-07完了後、Milestone A evidenceがあるplatformだけでruntime scannerをinternal allowlistへ入れる。
  5. DBI-08/09でPostgreSQL/MySQLとdynamicを同じqualificationへ追加する。
  6. DBI-10のcompatibility/UI codeをgate behindでdeployする。
  7. DBI-11 same-commit qualification後にprofile/engine allowlistを有効化し、consent UIを非表示にする。
  8. 一つのcompatibility period後にdeprecated API/CLI inputを削除する。

10.2 Feature gate

  • single gate runtimeDatabaseIsolationV1でnew provider compositionを制御する。
  • gate disabled時はruntime auto-start profileをblockedにし、host implementationへfallbackしない。
  • gate valueはbooleanでなくqualified platform/profile/DB engine tupleのserver-owned allowlistとする。
  • rollbackはUI/API表示とprovider promotionを戻せるが、host project-code executionを復活させない。

10.3 Data/schema compatibility

  • 新しいreceiptはJSON metadataとexisting resource lease receiptへ保存し、初期sliceでDDLを増やさない。
  • V1/V2 saved recordはversion別readerで読み、新fieldを旧schemaへoptional追加しない。
  • 新規runtime runはV2 preflight/V3 planだけを書き、missing bindingをlegacy fallbackで補わない。
  • credentialやDSNを一度でも保存したmigrationを作らない。
