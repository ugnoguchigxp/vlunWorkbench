Target: 組み込み済みのGitleaks、OSV-Scanner、Trivyだけで基本profileを成立させたまま、 Semgrepなどの外部scannerを任意能力として安全に追加し、scanner preset、専用workflow、Lab、 campaignの境界を公開catalogと実行結果で一貫させる。

実装結果

公開scan catalogは13件へ整理し、professional-fullは別のcampaign catalogへ移した。campaignはschedulerやhuman reviewを未実装のまま planned / unavailableとして公開し、scan start APIでは拒否する。 これは未実装能力をscanとして見せないという本計画の判断に沿う。

Semgrepはcore toolboxへ同梱せず、disabled、preferred、requiredの契約を実装した。 Semgrep非搭載imageでGitleaks、OSV-Scanner、Trivyがnetworkなしで実行できることを確認した。 API read-onlyはJSON/YAML OpenAPIとQuery-only GraphQL、任意の認証contextまで拡張し、 実Schemathesisを使ったcontainer qualificationを追加した。

最重要の非回帰条件

Semgrepが未導入、未設定、または実行不能でも、change-gateと source-assuranceはGitleaks、OSV-Scanner、Trivyで実行できなければならない。 Semgrepを明示的にmust-run指定した場合だけ、Semgrepの欠落を起動blockerにできる。

0. Document authority

本書は、次の事項に関する実装計画の正本である。

  • scanner dependencyの必須、条件付き、任意という意味とreadiness判定
  • Semgrepを本体の成立条件にしない任意統合
  • 公開profileのproduct上の分類と表示
  • 追加scannerの採用順序と採用gate
  • professional-fullをscan profileからcampaignへ移す段階的な移行

共通Execution Plan、event ledger、engine driver、cleanup、qualificationの基盤設計は Scan Profile Execution Architecture Migration Planを引き続き正本とする。本書はその実行基盤を置き換えず、optional scannerとproduct分類の 要件を追加する。

professional-fullについては、本書の「公開scan profileにはしない」という判断を優先する。 既存のrun-group contractは削除せず、campaign catalogへ移すまで内部contractとして保持する。

planning時のworkspaceには利用者の未commit変更がある。実装開始時にはHEADとdirty file一覧を evidenceへ記録し、reset、checkout、stash、上書きを行わない。

1. Executive decision

  1. change-gateとsource-assuranceの成立条件は、組み込み済みの Gitleaks、OSV-Scanner、Trivyとする。Semgrep SASTは追加coverageであり、既定では成立条件にしない。
  2. 外部scannerを追加できることと、すべてのprofileがscannerだけで自動化できることを同一視しない。 認証、active scan、business logic、fuzzは対象側の設定またはscenarioを必要とする専用workflowとして残す。
  3. 実現できないclaimを削除する。実装済みの限定機能やLab基盤は、scanner presetでないことを理由に削除しない。
  4. professional-fullは公開scan selectorから除外し、複数runと人手reviewを束ねるcampaignへ移す。 campaign schedulerとreview lifecycleが完成するまでlaunchableにしない。
  5. 新しいscannerは「インストール可能」という理由だけでは採用しない。既存coverageとの差、license、 structured output、offline性、安全境界、保守負担を満たしたものだけをadapter化する。

4. Optional scanner contract

optional scannerの選択状態はdisabled、preferred、 requiredの3値とする。既存の VULN_WORKBENCH_OPTIONAL_SCANNER_ADAPTERS=semgrepは互換性のため preferredへ解決する。

4.1 Semgrep readinessと実行結果
Selection Semgrep readiness Profile admission Step policy Coverage表示
disabled probeしない core dependencyだけで判定 planへ追加しない source_sast: gap
preferred unavailable warning付きでready skipped / capability_unavailable source_sast: gap
preferred ready ready required: false、warn_and_continue 成功時covered、失敗時gap
required unavailable blocked_environment 実行しない must-run未充足
required ready ready required: true、fail_profile 成功時のみcovered

profileのprocess statusとcapability coverageを分離する。core scannerが完了し、preferred Semgrepが欠落または失敗したrunは、profile自体をcompletedにできるが、 source_sastをcoveredとしてはならない。UI、report、APIはこの二つを混ぜない。

optional scannerのbinary、container image、rule bundleは本体のcore distributionへ混在させない。 provenance、version、digest、rule sourceは実行receiptへ保存する。外部licenseへの同意や別配布が必要な scannerは、設定画面から明示的に有効化する。

6. Work packages and implementation order

各work packageは前段のexit gateを満たしてから開始する。P0完了前に新scannerを増やさない。

SP-00 — Baseline and contract freeze

Purpose: 現在の挙動を再現可能な形で固定し、変更後の差分を判定できるようにする。

  1. 実装開始時のHEAD、dirty files、runtime platform、scanner version/image digestを記録する。
  2. Semgrep無効と有効の両方でcatalog、resolved profile、readiness、dry-run planを保存する。
  3. baseline時点の14 entryについてlaunchability、launch destination、required input、実行engineをmatrix化する。
  4. 現在のstability baselineがcurrent sourceへbindされているか検証し、stale metadataを分離する。

Exit gate: Semgrep欠落時にsource profileがblockされる現象を自動testで再現し、既存core scannerの successful fixtureを保存していること。

SP-01 — Dependency applicability and readiness

Purpose: dependencyの欠落を一律blockerにする現在のreadinessを修正する。

  1. dependency manifestのrequirementとoptional scanner selectionを結合し、 dependencyごとにapplicable、blocking、probe結果を解決する。
  2. readiness responseへblocking reasonとwarningを分けて返す。 preferred scanner欠落はwarning、required dependency欠落だけをblockerにする。
  3. readiness hashとplan hashへselection、applicability、probe結果を含め、preview/start間の変更を検出する。
  4. filesystemやgenerated resourceの実probeを未実装のままready扱いしない。

Primary files: shared/schemas/scan-profile-definition.schema.ts、 shared/schemas/scan-dependency-manifest.schema.ts、 shared/manifests/scan-dependencies.v1.json、 api/modules/scans/profile-definitions.ts、 api/modules/scans/execution/dependency-registry.ts、 api/modules/scans/execution/scan-readiness-service.ts。

Exit gate: core dependencyがreadyなら、Semgrep無効またはpreferred/unavailableの change-gateとsource-assuranceがreadyを返すこと。

SP-02 — Optional Semgrep execution and reporting

Purpose: readiness修正と実行・reportを同じoptional契約へ揃える。

  1. optional scanner設定を3値へ正規化する。既存env設定はpreferredとして後方互換を維持する。
  2. canonical profile builderがpreferredとrequiredでrequiredと failurePolicyを切り替えるようにする。
  3. Semgrepを実行しない場合も、coverage ledgerへsource_sastのgap reasonを保存する。
  4. summary、report、Webで「profile完了」と「SAST実施済み」を別の状態として表示する。
  5. Semgrepのversion、rule digest、config source、network policyをreceiptへ保存する。

Primary files: api/modules/scans/optional-scanner-adapter-config.ts、 api/modules/scans/canonical-scan-profiles.ts、 api/modules/scans/static-scanner-adapters.ts、 api/modules/scans/coverage/coverage-ledger.ts、scan summary/report、Web result components。

Exit gate: Section 4.1の全caseでplan、run status、coverage status、artifactが一致し、 preferred Semgrepの欠落・失敗がcore scannerの実行を止めないこと。

SP-03 — Catalog classification and consumer migration

Purpose: scannerでないflowを削除せず、利用者に正しい場所と前提を示す。

  1. experienceKindをcatalog schemaへadditive fieldとして追加し、13 scan entryと1 campaign entryをSection 3.2へ固定する。
  2. catalog説明、limitation code、required inputを実装済み範囲へ合わせる。
  3. Web selectorをscanner preset、workflow、Lab、advancedへ分ける。consumer側のID hard-codeを増やさない。
  4. CLIとintegrationにはkindとlaunch destinationを返すが、既存IDの互換解決は維持する。
  5. professional-fullは現在の非表示・起動不可を維持する。campaign catalog導入後に scan catalog entryを削除する。

Primary files: shared/schemas/scan-profile-catalog.schema.ts、 api/modules/scans/profile-catalog.ts、scan profile API、 web/src/api/scans-execution.ts、web/src/domains/scans/、 NightWorkers capability response。

Exit gate: UIにprofessional-fullがscanとして表示されず、専用flowがgeneric startへ 誤送信されず、legacy profile IDの保存・解決が変わらないこと。

SP-04 — API read-only claim correction and expansion

Purpose: 先に過大claimをなくし、安全にqualificationできたschema形式だけを追加する。

  1. 現行catalogを「JSON OpenAPI/Swagger対応」へ修正し、未対応のGraphQL表記を削除する。
  2. repository内のYAML schema parseを追加し、外部参照、巨大schema、循環参照のbudgetを定義する。
  3. 既存auth contextをSchemathesis起動入力へbindし、secretをargv、log、artifactへ残さない。
  4. GraphQLはQuery-only variantとして追加し、Mutationとsubscriptionを明示的に拒否する。
  5. 各形式を別qualification caseにし、一つの成功fixtureで全形式をstable扱いしない。

Exit gate: JSON OpenAPI、YAML OpenAPI、GraphQL Query-onlyの各caseでread-only policyが通り、 Mutation、state-changing HTTP method、認証secret露出のnegative testが通ること。

SP-05 — TLS scanner adoption spike

Purpose: testssl.shをruntime-passiveへ任意追加できるか判断する。

  1. licenseと配布方式をspec/decisions/third-party-scanners.htmlへ記録する。
  2. 本体toolboxへ混在させず、pinned external imageまたは利用者指定binaryで検証する。
  3. JSON output normalizer、HTTPS applicability、timeout、connection budget、redactionをprototype化する。
  4. Nuclei/ZAPと重複しないTLS protocol/cipher evidenceが得られるか測定する。

Exit gate: license、provenance、structured output、安全budget、追加coverageの全項目が承認された場合だけ preferred optional adapterとして採用する。一項目でも満たさなければ実装せず、spike結果だけを残す。

Result: 不採用。licenseとstructured JSONは確認できたが、現在の自動runtime targetはHTTPであり、 既存HTTP gatewayではraw TLS connection budgetを強制できない。したがって runtime-passiveへTLS coverageを追加せず、TLS診断をclaimしない。

SP-06 — Campaign separation and legacy compatibility

Purpose: professional-fullをscan名ではなく上位campaignへ移す。

  1. campaign catalogとcampaign ID schemaをscan profile schemaから分離する。
  2. 既存professional run-group contractはscan実行契約から切り離し、将来のcampaign coordinator用contractとして保持する。
  3. child preview、immutable binding、scheduler、result aggregation、human review gateが揃うまで、 campaignをplanned / unavailableから昇格させない。
  4. legacy full-security-scanは既存execution presetとして維持し、 professional campaignと同等だと表示しない。usage evidenceなしにredirectまたは削除しない。
  5. professional-fullをscan catalogとcanonical scan IDから削除し、campaign catalogだけに置く。

Exit gate: scan start APIがcampaign IDを拒否し、campaign catalogが未実装のschedulerやreviewを launchableと表示せず、既存full-security-scanの実行内容が変わらないこと。campaignの launchable昇格には、child runの成功、失敗、not-applicable、review未完了を集約する別実装と qualificationを必要とする。

SP-07 — Qualification, rollout, and closeout

Purpose: schema整合性だけでなく、current source上の実行結果で完了を証明する。

  1. unit、contract、integration、real scanner qualificationをSection 8のmatrixで実行する。
  2. receiptをsource tree digest、catalog entry hash、execution definition hash、tool/image digestへbindする。
  3. 同一caseを規定回数実行し、normalized result、cleanup、network requestの再現性を検証する。
  4. current HEADと異なる古いcommit metadataをstable根拠として再利用しない。
  5. claim matrix、README、設定画面説明、運用runbookを実装結果へ合わせる。

Exit gate: Section 11のDefinition of Doneをすべて満たし、rollback rehearsalとmaintainer reviewが完了していること。

9. Rollout, migration, and rollback

  1. Stage A — shadow preview: 新readinessを旧readinessと並行計算し、差分をmetadataへ保存する。 admission結果はまだ変更しない。
  2. Stage B — optional Semgrep: source profileだけ新readinessへ切り替える。Semgrepなしのreal executionを 先に通し、その後preferred modeを有効化する。
  3. Stage C — catalog classification: APIへadditive fieldを出し、Web、CLI、integrationを順に移行する。 consumer移行完了前に旧fieldを削除しない。
  4. Stage D — capability expansion: API YAML、認証、GraphQL Query-onlyを個別qualification後に導入する。 TLS adapterは採用gate未達のため導入しない。
  5. Stage E — campaign separation: professional entryをscan catalogから外し、planned/unavailableな campaign catalogへ分離する。campaign APIとUIは実行機能を持つまでlaunchableにしない。

rollback時は新しいoptional scanner selectionとexperience groupingを無効化し、core scanner profileと legacy ID解決を維持する。schemaやmetadataはadditiveに残してよいが、新しいreceiptを古い実行契約の stable evidenceとして再利用しない。DB migrationを追加する場合はexpand/contractを分け、同一releaseで column削除を行わない。

実装時のworkspaceには利用者の未commit変更が存在するため、本作業ではcommit、stash、resetを 行っていない。既存qualification schemaが要求するclean candidate commit receiptは、変更を 所有者がcommitした後のrelease promotion gateで生成する。これは実装能力の未完了を意味せず、 uncommitted sourceを別commitの証跡として誤認しないための境界である。

  • Semgrepなしのchange-gateとsource-assuranceがcore scanを完了する。
  • Semgrep preferred/requiredのreadiness、failure policy、coverage表示がSection 4.1と一致する。
  • Gitleaks、OSV-Scanner、Trivyの必須性と既存gate挙動に回帰がない。
  • 13 scan entryと1 planned campaign entryにproduct分類、launch destination、安全境界、実装範囲の 正確なclaimがある。
  • scanner presetでないflowが通常selectorから分離され、機能自体は失われていない。
  • professional-fullはscanとして起動できず、legacy full-security-scanは互換維持される。
  • API read-onlyはqualification済みのschema形式だけをclaimし、state-changing requestを拒否する。
  • 追加scannerはlicense、provenance、structured output、安全budget、追加coverageの採用gateを通っている。
  • unit、contract、integration、real scanner、failure injection、rollback testが成功している。
  • qualification receiptがcurrent source、catalog、definition、scanner version/image digestへbindされている。
  • README、設定画面、catalog、reportの説明が同じ能力範囲を示している。

12. Out of scope

  • Semgrepまたは第三者scannerのlicense条件を回避する同梱・再配布
  • 任意scannerがない環境でSASTを実施済みとみなすfallback
  • OAuth/OIDC/MFA、business logic、fuzz harnessを設定なしで網羅するというclaim
  • release artifactの自動build、製品署名、provenance生成
  • 既存scannerと重複するtoolの件数目的の追加
  • 利用実績を確認しないlegacy profile IDの削除
