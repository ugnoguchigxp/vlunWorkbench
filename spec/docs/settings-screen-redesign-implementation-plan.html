2. 結論

現在の設定画面は、Runtime、System Context、Runtime Settings、LLM Providers、Task Routingを一つの長い縦画面に配置している。既存機能は保たれているが、目的の設定を探すまでの スクロール量が多く、保存対象と管理者専用領域も把握しにくい。

改修後は、URLと連動する設定カテゴリを左側に固定し、右側には選択中のカテゴリだけを 表示する。既存APIと保存単位は維持し、画面の分割、状態表示、文言、レスポンシブ対応を フロントエンド内で実現する。

  1. カテゴリと権限を型付きの設定レジストリへ集約する。
  2. /settings?section=...を選択状態の正とする。
  3. 共通シェル、概要、検索、保存状態を先に実装する。
  4. 既存パネルをカテゴリ単位へ移し、Runtime Settingsだけを3領域へ分割する。
  5. 管理者・一般ユーザー、狭い画面、キーボード操作、既存APIを回帰検証する。

3. 目的

  • 設定画面を開いて3秒以内に、目的のカテゴリと現在の主要状態を判別できる。
  • 一画面に一つの設定カテゴリだけを表示し、長い縦スクロールを解消する。
  • URL共有、再読み込み、ブラウザの戻る・進むで同じカテゴリを復元する。
  • 一般ユーザーに管理者専用設定や検索結果を表示せず、管理者APIも呼ばない。
  • 未保存、保存中、保存済み、入力エラー、通信失敗を区別して表示する。
  • 既存のLLM provider、task route、runtime、system context機能を失わない。
  • 390px幅からデスクトップまで、横スクロールなしで主要操作を完了できる。

4. 対象外

  • 設定API、SQLite schema、暗号化方式、権限middlewareの変更。
  • 新しいLLM provider種別、task種別、scanner設定項目の追加。
  • グローバルナビゲーションまたは他画面の全面的な日本語化。
  • 汎用i18n frameworkの導入。
  • provider healthの自動定期監視。
  • 設定値の自動保存。
  • モックアップに含まれないテーマ切り替えやユーザープロフィール設定。

5. 参照モックアップ

モックアップは情報設計と視覚優先順位の基準であり、表示する状態値は実データから導出する。 モックアップ上の「接続済み」などの例示値を固定文言として実装しない。

7.2 URLとカテゴリ選択

  • 既存パス/settingsは変更しない。
  • 任意の検索パラメータsectionを追加する。
  • overviewはURLから省略し、canonical URLを/settingsとする。
  • 省略時と未知の値ではoverviewを表示し、未知の値を別の文字列へcoerceしない。
  • カテゴリ項目はbuttonのlocal stateではなく、Linkとして実装する。
  • カテゴリ移動はブラウザ履歴へ追加し、戻る・進むで選択を復元する。
  • 一般ユーザーが管理者専用sectionへ直接アクセスした場合は、管理者APIを呼ばず、 replace: trueで/settingsへ戻す。
  • provider選択、検索語、折りたたみ状態は画面内の一時状態とし、URLには保存しない。

URL例:

/settings?section=ai-models
/settings?section=system-context

新規web/src/settings-route-search.tsの公開契約は次で固定する。

export const settingsSectionIds = [
  "overview",
  "ai-models",
  "task-routing",
  "scan-execution",
  "system-context",
  "security",
  "advanced",
] as const;

export type SettingsSectionId = (typeof settingsSectionIds)[number];
export type SettingsSearch = { section?: Exclude<SettingsSectionId, "overview"> };

export function parseSettingsSearch(
  search: Record<string, unknown>,
): SettingsSearch;
export function resolveSettingsSection(search: SettingsSearch): SettingsSectionId;
export function buildSettingsSectionSearch(section: SettingsSectionId): SettingsSearch;
  • parseSettingsSearchは既知値だけを返し、overviewと未知値は{}に正規化する。
  • resolveSettingsSectionはsearch.section ?? "overview"を返す。
  • buildSettingsSectionSearch("overview")は{}を返す。
  • settingsRouteへvalidateSearch: parseSettingsSearchを追加する。 Appへsection propは追加しない。
  • SettingsPanel内でuseSearch({ from: "/settings" })と useNavigate({ from: "/settings" })を使う。route hookは子panelへ分散させない。

7.4 設定検索

  • 検索対象は設定値ではなく、静的なカテゴリ名、説明、項目keywordだけとする。
  • secret、token、system context本文を検索indexへ含めない。
  • 検索結果は現在のユーザーが閲覧できるカテゴリだけに限定する。
  • 対象は7件の静的レジストリだけなのでdebounceを追加せず、入力ごとに同期filterする。
  • 結果を選択すると対応するsectionへ遷移し、検索語をクリアする。
  • 0件時は「該当する設定はありません」を表示する。
  • 結果は検索欄直下のulにLinkとして表示し、独自combobox roleを実装しない。
  • Escapeで結果を閉じ、入力欄には常時可視のlabelを付ける。

7.5 概要

概要は設定値の編集画面にせず、既存データから次の状態だけを短く表示する。

  • アプリ状態、service名、Git branch、commit。
  • 管理者の場合は、LLM provider数、Codex利用可否、runtime isolation設定状態。
  • System Contextの最終更新日時。
  • 注意が必要な状態から対応カテゴリへ移動するリンク。

providerの接続状態は、Codex statusまたは利用者が実行したhealth checkだけを根拠にする。 endpointが入力済みという理由だけで「接続済み」と表示しない。

  • 初回選択はCodex SDK。Codexが存在しない場合は最初のproviderとする。

  • Codexは既存の認証元、model source、detected models、adapter状態を表示する。
  • generic providerは既存のkind別入力項目を維持する。
  • 新規providerは保存完了までhealth checkを無効化する。
  • provider設定に未保存変更がある間もhealth checkを無効化し、「保存後に確認できます」と表示する。
  • provider削除は対象名を示す確認を経てdraftから除外し、保存時に確定する。
  • model select labelの詳細入力は折りたたみ可能な「表示名の詳細設定」に置く。

7.8 Runtime設定の分割

RuntimeSettingsResponseと更新payloadは分割しない。3つのpanelは同じ runtimeSettings draftを部分編集し、保存時は既存の完全なpayloadを送信する。

  • スキャン実行: 日常的に確認するexecution modeとDocker resourceを表示する。
  • セキュリティ: runtime isolationの資格状態、必須image / hash、DAST keyを表示する。
  • 詳細設定: process limit、queue、timeout、任意imageを表示する。
  • 自動設定とDAST key生成は即時にサーバーへ保存する既存動作を維持し、通常の保存と区別する。
  • 自動設定中は、3つのRuntimeカテゴリの競合操作を無効化する。
  • 不足中の必須field数とfield名は、既存のfail-closed応答を根拠に表示する。

7.8.1 即時Runtime操作の競合防止

  • autoConfigureRuntimeIsolationはrequest bodyを送らずserver上の現在値を更新するため、 runtimeDirty中はbuttonを無効化する。未保存draftを破棄して実行する選択肢は追加しない。
  • generateDastAuthEncryptionKeyはRuntime draft全体を送信するため、意図しない同時保存を 防ぐ目的でruntimeDirty中はbuttonを無効化する。
  • 両buttonのhelper textは「先に変更を保存してください」とする。
  • 通常保存の成功後にのみ両buttonを有効化する。
  • 即時操作の成功responseはRuntimeのdraftとbaselineの両方へ設定し、dirtyを解除する。
  • 即時操作の失敗時はdraftとbaselineを変更せず、Security panel内にerrorを表示する。

7.9 保存状態と画面遷移

  • 取得または保存に成功した値をresourceごとのbaseline snapshotとして保持する。
  • LLM、Runtime、System Contextごとにdirty状態を純粋関数で導出する。
  • 変更なしでは保存buttonを無効化し、「すべての変更は保存済み」と表示する。
  • 変更ありでは「未保存の変更があります」と表示する。
  • 保存中はbutton labelとaria-busyを更新し、二重送信を防ぐ。
  • 保存成功後にbaselineを更新し、serverが返した正規化済み値を表示する。
  • 保存失敗時はdraftを保持し、再試行できる状態にする。
  • カテゴリ間移動ではdraftを破棄しない。同じresourceを共有する別カテゴリへ移動しても保持する。
  • 設定画面から離れる操作は7.9.1の離脱確認で保護する。

比較対象は表示用response全体ではなく、既存APIへ送るcanonical inputとする。

type LlmSettingsInput = Pick<
  LlmSettingsResponse,
  "providerEndpoints" | "taskRoutes"
>;

function toLlmSettingsInput(value: LlmSettingsResponse): LlmSettingsInput;
function toRuntimeSettingsInput(
  value: RuntimeSettingsResponse,
): RuntimeSettingsUpdate;

const llmProviderDirty = !sameJson(
  draft.providerEndpoints,
  baseline.providerEndpoints,
);
const taskRoutingDirty = !sameJson(
  ensureRoutes(draft.taskRoutes),
  ensureRoutes(baseline.taskRoutes),
);
const llmDirty = llmProviderDirty || taskRoutingDirty;
const runtimeDirty = !sameJson(
  toRuntimeSettingsInput(runtimeDraft),
  toRuntimeSettingsInput(runtimeBaseline),
);
const systemContextDirty = systemContextText !== savedSystemContextText;
const settingsDirty = llmDirty || runtimeDirty || systemContextDirty;
  • sameJsonはこの既存のJSON互換設定型に限りJSON.stringify比較を使う。
  • updatedAtとRuntimeのread-only派生fieldはdirty比較から除外する。
  • ********を含むmasked secretもserver responseの一部として比較し、特別に空文字へ変換しない。
  • load成功時はdraftとbaselineを同じ正規化済みresponseから設定する。
  • save成功時はserver responseからdraftとbaselineを同時に更新する。
  • savedSystemContextTextはmount時とsystemContextUpdatedAt変更時だけ systemContextTextへ同期し、入力中のprop変更ではbaselineを動かさない。
  • AI・モデルとタスクルーティングの保存buttonは、どちらもLLM draft全体を保存する。
  • llmProviderDirtyだけの時は「AI・モデルに未保存の変更があります」、 taskRoutingDirtyだけの時は「タスクルーティングに未保存の変更があります」、 両方なら「AI・モデルとタスクルーティングに未保存の変更があります」と表示する。
  • provider healthを無効化するのはllmProviderDirtyであり、routeだけのdirtyでは無効化しない。

7.9.1 離脱確認

  • SettingsPanelPropsへonDirtyChange: (dirty: boolean) => voidを追加する。
  • AppはsettingsDirtyを保持し、SettingsPanelのmount終了時にfalseへ戻す。
  • SettingsPanelはuseBlockerを一度だけ使用する。 current.pathnameとnext.pathnameが共に/settingsならblockしない。
  • dirty中に別pathnameへ移動する場合は、native confirm「未保存の変更があります。設定画面を離れますか？」を 表示し、cancel時だけblockする。
  • enableBeforeUnloadはsettingsDirtyと同じ条件にする。
  • Logoutはnavigation blockerより先にSettingsPanelがunmountする可能性があるため、 App.handleLogoutでも同じ文言を確認し、cancel時はlogout APIを呼ばない。
  • 確認dialogの独自componentはこの計画では追加しない。

7.10 Loading、Empty、Error

  • LLMとRuntimeは別々に取得し、一方の失敗で他方を非表示にしない。
  • 初回loadingは対象panel内に「設定を読み込んでいます…」と表示し、skeletonは追加しない。
  • 取得失敗は対象resource内に再試行button付きで表示する。
  • provider 0件は「プロバイダーがありません」と追加buttonを表示する。
  • global errorは既存の認証失効・session errorだけに使用する。

useSettingsPanelModelへ追加する状態とloaderは次で固定する。

Resource別の状態と取得単位
Resource 状態 Loader
LLM settings llmSettings、llmBaseline、llmLoading、llmSaving、llmError loadLlmResource
Codex status codexStatus、codexLoading、codexError loadLlmResource内で並列取得、再確認時はreloadCodexStatus
Runtime runtimeSettings、runtimeBaseline、runtimeLoading、runtimeSaving、runtimeError loadRuntimeResource
System Context 既存props、savedSystemContextText、systemContextError 取得は既存App.loadSystemContextを維持
  • 管理者だけがLLMとRuntimeのloaderをmount時に一度ずつ開始する。カテゴリ選択では再取得しない。
  • loadLlmResourceはfetchLlmSettingsとfetchCodexStatusを Promise.allSettledで並列実行する。
  • LLM settings成功・Codex失敗時もprovider editorを表示し、Codex status cardだけにerrorと再確認buttonを出す。
  • LLM settings失敗時はprovider editorを出さず、AI・モデルとタスクルーティングに再試行buttonを出す。
  • Runtime失敗はRuntime 3カテゴリだけに影響させる。
  • Codex再確認成功時はensureCodexEndpointをdraftとbaselineの両方へ適用し、 detected modelの追加だけでdirtyにならないようにする。
  • 設定resourceの取得・保存errorにはsetErrorTextを使わずpanel内errorを使う。 401は既存UNAUTHORIZED_EVENT_NAMEでApp全体へ通知される。

8. 実装アーキテクチャ

画面、状態、APIの責務は次の境界で分ける。

/settings?section=ai-models
└─ SettingsPanel
   ├─ useSettingsPanelModel
   │  ├─ LLM settings draft / baseline / load / save
   │  ├─ Runtime settings draft / baseline / load / save
   │  └─ System Context draft / baseline / save
   └─ SettingsPanelView
      └─ SettingsShell
         ├─ SettingsSearch
         ├─ SettingsNavigation
         └─ selected section panel
  1. URLがカテゴリ選択の正。 再読み込み可能なnavigationとする。
  2. 設定レジストリが情報設計の正。 label、説明、keyword、icon、adminOnlyを重複定義しない。
  3. hookがmutationの正。 表示componentからAPIを直接呼ばない。
  4. controllerの大規模分割は行わない。 既存のSettingsPanelModelを各panelへ渡す形を維持し、この変更ではdomain hookや Contextを新設しない。必要な純粋関数だけをsettings-panel-model.tsへ追加する。
  5. API型を維持する。 表示都合の別payloadやas anyを追加しない。
  6. server stateをstatusの正とする。 接続、資格、更新日時をfrontendだけで捏造しない。

9.1 書き込み境界と停止条件

Terraが編集してよい範囲は、9の表にあるfrontend、test、本計画書だけとする。 spec/index.htmlとモックアップは既に登録済みのため、リンク切れ修正以外では変更しない。

次のいずれかが起きた場合は推測で範囲を広げず、作業を止めて報告する。

  • 既存API responseだけでは7の表示状態を作れない。
  • 設定保存にbackend schemaまたはmigration変更が必要になる。
  • ユーザー所有の変更と同じ行を編集しなければ実装できない。
  • 新しいpackage依存が必要になる。
  • 全field所属testを型安全に作れず、as anyが必要になる。
  • 対象test以外の失敗が3回連続して同じ外部要因で再現する。

停止報告には、失敗command、最初のerror、影響するWork Package、変更済みファイル、 安全に継続できる代替案を含める。

11.0 Test fixture方針

  • repositoryに@testing-library/reactはないため追加しない。純粋関数はVitest、 静的componentはrenderToStaticMarkup、interactionとhook orchestrationは Playwrightで検証する。
  • Linkを含むSettingsPanelViewの静的testは、 createMemoryHistory、最小route tree、RouterProviderで囲み、 await router.load()後にrenderする。production routerをtest用に変更しない。
  • tests/e2e/settings.spec.tsはpage.route("**/api/**")で設定APIをmockし、 provider保存、Runtime保存、鍵生成、自動設定を実環境へ送信しない。
  • admin fixtureはLLM、Codex、Runtime、health、system context、app health、source healthを全て固定値で返す。
  • member fixtureはLLM、Codex、Runtime routeへのrequestが発生した時点でtestを失敗させる。
  • PUT / POST mockはrequest bodyを記録し、responseへupdatedAtを付けて返す。
  • save失敗caseは最初のPUTだけ500を返し、2回目を成功させる。1回目の後もinput valueが残ることを確認する。
  • Runtime field所属はDOM文言だけでなく、3カテゴリを順に開いて各inputのaccessible labelが一度だけ 現れることをcomponent testで確認する。
  • 実serverの権限境界は既存release-readiness.spec.tsだけで確認し、 新E2Eから実設定を変更しない。
