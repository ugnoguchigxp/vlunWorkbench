1. Purpose

persisted Static Intelligence generationからontology handoffを公開する直前に、ZodによるJSON shape validationだけでは検出できないgraph-wideな意味制約を検証する。検証結果を決定的な machine-readable reportとしてAPI、knowledge source manifest、NightWorkers consumerへ渡し、 不正なhandoffをtask / run contextへ利用させない。

この計画はSemantic Handoff Validationだけを実装可能な粒度へ具体化する。claim provenance、 security vocabulary alignment、contract diff、competency question、rule inferenceは本計画で設計・実装しない。

2. Target Outcome

persisted generation
  -> build deterministic ontology handoff projection
  -> validate identity / graph / module / summary constraints
  -> emit structured validation report
  -> merge report into readiness
  -> publish diagnostic payload
  -> consumer activates only passed or passed_with_warnings payload
  • validなhandoffは既存と同じprojectionを返し、validation reportを追加する。
  • warningだけの場合はhandoffを利用可能なままdegradedにする。
  • errorがある場合もgenerationとreportは保持するが、handoff statusをfailedにする。
  • NightWorkersはfailed reportを受け取ってもmodule / task contextへ取り込まない。
  • 同一generationから常に同じreport orderingと同じmanifest content hashを生成する。

4. Fixed Decisions

  • 初期validatorはTypeScriptのpure functionとして実装する。
  • RDF変換、SHACL file生成、pySHACL、Semantica runtime dependencyを導入しない。
  • validationはpersisted generationを削除または無効化せず、handoffの利用可否だけを制御する。
  • validation reportは時刻を持たず、generationだけから決定的に生成する。
  • error / warningの判定はrule profileで固定し、consumerがmessage文字列を解析しない。
  • API / CLIの実行成功とontology conformanceを分離する。
  • consumer-first migrationを採用し、NightWorkersがoptional reportを読める状態を先にreleaseする。
  • 既存のcandidateOnly semantic queryはgraphへ投影されていないため、本計画のrule対象にしない。

8. Validation Contract

8.1 Shared Schema

const ontologyValidationViolationSchema = z.object({
  code: z.string().regex(/^ontology\.[a-z0-9_.]+$/),
  severity: z.enum(["error", "warning"]),
  focusRef: z.string().min(1),
  path: z.string().min(1).optional(),
  message: z.string().min(1),
  sourceRefs: z.array(z.string().min(1)),
}).strict();

const ontologyValidationReportSchema = z.object({
  version: z.literal("v1"),
  profile: z.literal("static-intelligence-ontology-handoff-v1"),
  generationId: z.string().min(1),
  status: z.enum(["passed", "passed_with_warnings", "failed"]),
  conforms: z.boolean(),
  summary: z.object({
    errorCount: z.number().int().nonnegative(),
    warningCount: z.number().int().nonnegative(),
  }).strict(),
  violations: z.array(ontologyValidationViolationSchema),
}).strict();
  • codeはforward-compatibleなstringとし、consumerは未知codeを安全に扱う。
  • messageは人間向けであり、control flowには使用しない。
  • focusRefはnode / edge / module / generationの安定IDを使う。
  • pathはgraph.edges.toのような論理field名とし、array indexへ依存しない。
  • sourceRefsへabsolute path、raw evidence snippet、secretを含めない。
  • 時刻fieldは持たせない。reportはgeneration contentだけから再生成可能にする。

8.2 Derived Field Invariants

  • errorが1件以上ならstatus=failed、conforms=false。
  • errorが0件でwarningが1件以上ならstatus=passed_with_warnings、conforms=true。
  • error / warningが0件ならstatus=passed、conforms=true。
  • summary countはviolations配列から算出し、caller入力を受け取らない。
  • violation orderingはseverity、code、focusRef、path、sourceRefsの順で固定する。

8.3 Wire Placement

  • StaticIntelligenceOntologyHandoff.validation: producer APIの詳細report
  • StaticIntelligenceKnowledgeSourceManifest.ontologyValidation: CLI consumer用report
  • StaticIntelligenceBuildResult.ontologyValidation: build / refresh diagnostic
  • manifest fieldはconsumer-first migrationのためschema上optional、producer emissionは必須とする。
  • ontology handoff builderが返すreportはproducer側で常に必須とする。

9.3 Warning Rules

warningはhandoffをdegradedにするが利用を停止しない
Code Condition Reason
ontology.graph.artifact_reference_unresolved stored_as target artifact nodeが存在しない。 現行builderがconfidence 0.5で表す既知degradationを維持する。
ontology.handoff.module_candidates_empty structure fileがあるのにmodule candidateが0件。 現行module_candidates_missingと整合する。
ontology.handoff.module_dependency_unresolved internal dependency path prefixに対応するcandidateがない。 partial structure analysisを直ちにinvalidへしない。

9.4 Explicitly Valid Unknowns

  • file:unknownとconfidence 0のlocated_inはinvalidにしない。
  • findingが0件のgraphをinvalidにしない。
  • review / verification nodeが0件のgraphをinvalidにしない。
  • scanner / artifact nodeがfindingから未参照でも、source inventoryとして許可する。
  • semantic indexがmissing / staleでもontology graph validation自体は実行する。

10. Validator Design

10.1 Public Functions

buildStaticIntelligenceOntologyHandoffProjection(generation)
  -> handoff fields without status and validation

validateStaticIntelligenceOntologyHandoff({ generation, projection })
  -> OntologyValidationReport

buildStaticIntelligenceOntologyHandoff({ generation, status? })
  -> projection + merged status + validation

applyOntologyValidationReadiness({ current, report, scope })
  -> IntelligenceCapabilityReadiness

projection生成とvalidationを分離し、testが意図的に壊したprojectionをvalidatorへ渡せるようにする。 public API builderは常にreportを付加し、callerがvalidationを省略できないようにする。

10.2 Complexity and Determinism

  • node、edge、module、source refを先にMap / Setへindexする。
  • rule evaluationはO(nodes + edges + modules + sourceRefs)とする。
  • validation中にDB、filesystem、network、clock、LLMを呼ばない。
  • errorをthrowして最初の違反で止めず、全violationを収集する。
  • programming errorだけをthrowし、data violationはreportへ変換する。

11. Readiness and Publish Policy

11.1 Status Precedence

ontology handoff statusの優先順位を次で固定する。

failed semantic validation
  > stale generation
  > existing degraded condition or validation warning
  > available
validation reportからreadinessへの写像
Report evidenceGraph ontologyHandoff Stable reason code
passed 現行statusを維持 現行statusを維持 追加なし
graph warning degraded degraded ontology_semantic_validation_warning
handoff-only warning 現行statusを維持 degraded ontology_semantic_validation_warning
graph error failed failed ontology_semantic_validation_failed
handoff-only error 現行statusを維持 failed ontology_semantic_validation_failed

capability reasonCodesへ個々のviolation codeを展開しない。詳細はreportを参照し、 readiness contractはboundedな2 reasonだけを使用する。

11.2 Publish Semantics

  • buildはsemantic validation errorでもgeneration artifactsを保存する。
  • build resultはpartialとなり、validation stageとreportを返す。
  • ontology handoff APIはHTTP 200でfailed reportを返し、diagnostic visibilityを維持する。
  • knowledge source CLIもJSON生成に成功した場合はexit 0でreportを返す。
  • HTTP 200 / CLI exit 0はconformanceを意味しない。consumerはreport statusを確認する。
  • NightWorkersはfailed reportをunavailableへ変換し、task contextへactivateしない。

12. Manifest and Hash Policy

  • ontologyValidationをmanifest top-level optional fieldとして追加する。
  • producerはpersisted generationからmanifestを作るすべての経路で必ずreportを渡す。
  • reportはcontentHashInputへ含め、validation内容の差をcontent hashへ反映する。
  • reportは時刻を持たないため、同じgenerationのrebuildでcontent hashを変えない。
  • manifest builderはreport generation IDとgeneration IDの不一致をthrowする。
  • readinessは従来どおりcontent hash対象外とし、validation reportとは区別する。

13. NightWorkers Consumer Policy

parsed manifestの分類
ontologyValidation Handoff result Behavior
absent available / validationStatus=not_reported legacy producer互換。既存挙動を維持する。
passed available / validationStatus=passed manifest artifactを保存して利用可能にする。
passed_with_warnings available / validationStatus=passed_with_warnings 利用可能。summaryだけをdiagnostic eventへ残す。
failed unavailable / semantic_validation_failed module / task contextへ取り込まず、bounded summaryだけをwarning eventへ残す。

failed manifestのgraphやmoduleをNightWorkers側で修復しない。producer側のreportを診断として扱い、 Security Oracle evidenceの既存fallbackを維持する。

15. Implementation Slices

Slice 0: Baseline and Fixture Lock

Goal: 新しいvalidationを入れる前に、現行graphとtest harnessを固定する。

  1. 代表generation fixtureをzero finding、normal finding、missing artifactの3種類に固定する。
  2. 現行builder出力に対してprofile v1想定ruleを手動実行し、error 0件であることを確認する。
  3. missing artifactはwarningになることを確認する。
  4. knowledge source CLIの空stdout failureを再現し、contract testを安定実行できる最小修正だけを行う。
  5. dirty-state failureは別baselineとして記録し、本sliceへ混ぜない。

Exit: golden fixtureとbaseline pass / fail listがreview可能である。

Slice 1: Shared Contract and Pure Validator

Goal: product pathへ接続せず、report contractと全ruleをunit testで完成させる。

  1. shared schemaを追加する。
  2. projection builderを分離する。
  3. identity、graph、module、summary ruleをpure validatorとして実装する。
  4. violation sortingとderived statusを実装する。
  5. 各ruleへ最低1 positive / 1 negative testを追加する。
  6. 10,000 nodes / 25,000 edges benchmark fixtureで線形性を確認する。

Exit: validatorだけを呼び出したunit suiteがgreenで、product outputはまだ変わらない。

Slice 2: NightWorkers Consumer Tolerance

Goal: producerが新fieldを出す前にconsumerをforward-compatibleにする。

  1. NightWorkers schemaへoptional reportを追加する。
  2. legacy / passed / warning / failed分類をpure helperにする。
  3. failed reportをunavailableへ変換する。
  4. unknown violation codeでもschema parseと安全な拒否 / 表示ができることを確認する。
  5. consumer PRをreleaseし、legacy producerとの回帰がないことを確認する。

Exit: NightWorkersがfield absent / presentの両方を安全に処理する。

Slice 3: Producer Handoff and Readiness Integration

Goal: API / build resultへreportを追加し、readinessへ意味検証を反映する。

  1. public ontology handoff builderへ必須reportを追加する。
  2. build-serviceへvalidation stageを追加する。
  3. read-model resolverへ同じreadiness impact helperを接続する。
  4. errorでもgenerationを保持し、handoff statusだけをfailedにする。
  5. API transport testでdiagnostic payloadが失われないことを確認する。

Exit: APIとrefresh resultが同一generationに対して同じreport statusを返す。

Slice 4: Manifest and CLI Emission

Goal: NightWorkersが実際に使うCLI manifestへreportを載せる。

  1. manifest schema / builderへoptional fieldを追加する。
  2. reportをcontent hashへ含める。
  3. CLIがpersisted generationをpure validateしてreportを渡す。
  4. failed reportでもJSON commandは成功し、consumerがsemantic failureを判断できるようにする。
  5. redaction、hash stability、legacy consumer fixtureを検証する。

Exit: NightWorkers integration fixtureでpassedはavailable、failedはunavailableになる。

Slice 5: Enforcement Qualification

Goal: report emissionをproduction-readyなpublish gateとして認定する。

  1. 利用可能なsanitized persisted generation corpusへvalidatorを実行する。
  2. unexpected error 0件を確認する。warningはcode / count / sourceをreviewする。
  3. API、CLI、build result、NightWorkers eventのstatus一致を確認する。
  4. performance、payload size、content hash差分を記録する。
  5. rollback rehearsalを実施する。

Exit: Definition of Doneを満たし、実装計画をarchive可能なevidenceが揃う。

16. Migration Sequence

  1. vulnWorkbench Slice 0 / 1をmergeする。wire outputは変更しない。
  2. NightWorkers Slice 2をmerge / releaseし、legacy fixtureがgreenであることを確認する。
  3. vulnWorkbench Slice 3でAPI / readinessを更新する。
  4. vulnWorkbench Slice 4でmanifest / CLI emissionを有効にする。
  5. NightWorkers live-equivalent fixtureでfailed reportがactivateされないことを確認する。
  6. Slice 5 evidenceが揃うまで新ruleを追加しない。

producerを先にreleaseするとNightWorkersのstrict schemaがunknown top-level fieldを拒否するため、 この順序を変更しない。

17. Test Plan

17.1 Rule Matrix

  • validation messageへraw node metadataをJSON stringifyしない。
  • file focus refはproject-relative pathだけを許可する。
  • sourceRefsへraw artifact body、evidence snippet、review output、secretを含めない。
  • NightWorkers eventはprofile、status、errorCount、warningCount、bounded reasonだけを保存する。
  • consumerはreport messageをcommand、path、promptとして実行しない。
  • validatorはnetwork / filesystem accessを持たないため、validation inputからside effectを起こさない。

19. Performance and Payload Budget

  • validator complexityはO(N + E + M + R)を維持する。
  • 10,000 nodes / 25,000 edges / 1,000 modulesで100ms以内をqualification targetとする。
  • 同一violationの重複発行を防ぎ、report最大件数は1,000件でtruncateする。
  • truncate時はontology.report.truncated warningを末尾へ1件追加する。
  • normal fixtureのreport追加payloadは10KB未満をtargetとする。
  • 巨大なinvalid graphでもraw objectをviolationへ複製しない。

20. Observability

  • build stageへduration、status、bounded reason codeを記録する。
  • refresh responseへreportを含め、error / warning countを確認可能にする。
  • readinessには詳細codeを展開せず、reportへの導線だけを保つ。
  • NightWorkers warning eventはvalidation summaryだけを保持する。
  • validation report専用DB tableやlong-term telemetryは本計画では追加しない。

21. Rollback Plan

21.1 Rollback Triggers

  • 既存valid generationがunexpected errorとなる。
  • NightWorkersがlegacy manifestまたはnew manifestをschema_invalidにする。
  • content hashが同一generationの反復実行で変化する。
  • validationによりCLI timeout / payload limitを超える。
  • absolute path、raw evidence、secretがreportへ漏れる。

21.2 Rollback Order

  1. vulnWorkbench manifest emitterからontologyValidation出力を停止する。
  2. API / build readinessへのenforcementを外し、pure validatorとtestは残す。
  3. 必要ならontology handoffのreport fieldをoptional emissionへ戻す。
  4. NightWorkersのoptional parserはlegacy compatibilityのため残す。
  5. persisted generationは削除・再生成しない。

rollbackでscanner、finding、artifact、review dataを変更しない。DB migrationがないためschema down migrationも不要である。

22. Definition of Done

  • profile v1の全ruleとseverityがコードと本書で一致している。
  • 各ruleにpositive / negative testがある。
  • 同一generationからreport orderingとmanifest content hashが決定的に生成される。
  • graph errorがevidenceGraph / ontologyHandoff readinessをfailedにする。
  • handoff-only errorがontologyHandoffだけをfailedにする。
  • warningはdegradedになるがconsumer利用を停止しない。
  • failed generation artifactsが診断用に保持される。
  • NightWorkers consumer-first migrationが完了し、legacy / new fixtureが両方greenである。
  • NightWorkersがfailed reportをtask contextへactivateしない。
  • redaction、performance、payload budgetを満たす。
  • targeted verification、typecheck、lint、docs checkがpassする。
  • full suiteのbefore / after差分と既知baseline failureが記録される。
  • 実装外のontology候補へscopeが広がっていない。

24. GO / NO-GO Gate

24.1 GO

  • NightWorkers consumer-first release順をownerが承認した。
  • profile v1 rule / severityに異論がない。
  • 代表generation baselineでunexpected errorが0件である。
  • CLI contract testを安定して実行できる。

  • 現行valid corpusでerror / warning境界を説明できない。

25. Implementation Handoff

実装開始時はSlice 0だけを最初の作業単位とする。Slice 0のbaselineとfixtureがreviewされるまで、 shared schema、wire output、NightWorkers consumerを変更しない。各sliceは個別にtest evidenceを残し、 後続sliceを先取りしてまとめて完了扱いにしない。
