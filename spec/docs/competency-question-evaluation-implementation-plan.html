1. Purpose

Static Intelligenceのontologyを、node数、edge数、schema field数ではなく、consumerが必要とする問いへ 正しいfact、provenance、assertion kind、利用不能理由を決定的に返せるかで評価する。question、fixture、期待atom、adapter、判定結果をsource control下のversioned profileとして管理し、ontologyまたはconsumer queryの変更をquestion単位の回帰として検出する。

本計画が実装するのはCompetency Question Evaluationだけである。semantic handoff validator、claim ledger、security vocabulary mapping、ontology contract diff、scan instance diffを再実装しない。未実装の能力を必要とする問いはplanned_dependencyとして可視化し、active baselineの合否分母へ入れない。

2. Target Outcome

source-controlled evaluation profile
  -> validate question registry and dependency state
  -> build a synthetic generation with fixed identities
  -> execute closed, deterministic adapters over production services
  -> normalize answers into assertion-aware atoms
  -> compare required / allowed / forbidden atoms and unavailable reasons
  -> enforce provenance and candidate-only safety invariants
  -> aggregate non-masking metrics by question and capability
  -> emit a canonical machine-readable regression report
  -> compare the report with the reviewed baseline profile
  -> gate ontology and query changes after an advisory stabilization period
  • 同じprofileとfixtureから同じcase resultとevaluationHashを生成し、同じenforcement policyを加えた時だけ同じreportHashを生成する。
  • 自然言語questionの語句ではなく、stable question IDとclosed adapter IDで評価を実行する。
  • semantic candidateは存在してもよいが、observed / deterministic required factを満たせない。
  • factの出自を示すassertionKindと、consumerがどう扱うべきかを示す consumerBoundaryを別軸で検証する。
  • empty answer、expected unavailable、unexpected unavailable、incorrect answerを区別する。
  • 1件のunsafe confirmationを平均点で隠さず、case単位でreleaseをfailさせる。
  • planned questionは不足能力を説明するが、active answerabilityを水増しも低下もさせない。

4. Fixed Decisions

  1. 初期personaはcoding_agentとする。現行agent query、route、MCPに最も具体的なread surfaceがあり、human reviewerとNightWorkers用adapterはconsumer contractが確定してから追加する。
  2. 初期実装はOption A、すなわちTypeScriptのclosed registry、synthetic fixture、既存production service adapter、deterministic evaluatorとする。汎用question authoring serviceは作らない。
  3. question textは人間向け説明であり、制御入力にしない。questionId、 adapterId、typed input、expected atomだけが実行を決める。
  4. expected answerはdisplay textやresponse全体のsnapshotではなく、stable source ref、semantic property、assertion kind、provenance refの集合で固定する。
  5. baseline fixtureはsynthetic dataだけで構成する。sanitized real fixtureはidentityとredaction policyを別reviewで確定した後にadvisory profileへ追加する。
  6. evaluatorはtest / CI専用で開始し、product API、MCP tool、DB table、browser UIを追加しない。
  7. current responseに明示assertion kindがない間は、closed adapter mappingでnormalizationする。Claim Provenance profileが公開された後は明示fieldを正本とし、adapter推定を削除する。
  8. 現行agent queryのfinding / evidence / artifactがsource-backedでも、consumer boundaryは candidate_onlyのまま維持する。assertion kindをobservedへ分類しても確認済み conclusionへの昇格を意味しない。
  9. active questionは現在のproduction surfaceで決定的に評価できる問いだけとする。依存機能待ちの問いは planned_dependencyにし、active denominatorへ入れない。
  10. case passはrequired atom、forbidden atom、provenance、unavailable reason、safety invariantの全条件を case単位で満たした場合だけとする。aggregate scoreでcase failureを相殺しない。
  11. semantic provider、LLM、network、production database、wall clock、localeにCI結果を依存させない。
  12. evaluation / report hashからgeneratedAt、duration、host、absolute path、run IDを除外する。performance metadataはnon-canonical completed payload fieldへ分離する。
  13. safety invariantは導入時からblockingにする。answerabilityとlatencyの一般gateはadvisory期間後に昇格する。

8. Terminology and Truth Model

Question
consumerが必要とする安定した能力。人間向けquestion textとstable IDを持つ。
Case
questionを特定fixture、typed input、expected atomへ具体化した実行単位。
Answer atom
一つのfactまたはavailability assertionをstable refとassertion kindで表した正規形。
Observed
scanner result、persisted evidence、artifact、source file等のsource recordから直接運ばれたfact。
Deterministic derived
固定ruleと入力refsから再現可能に導出したfile risk、readiness、graph relation等のfact。
Semantic candidate
embedding、community、類似性等から提案された未確認候補。confirmed factではない。
Consumer boundary
normalized answer全体の利用境界。agent query由来はcandidate_only、readiness判定は readiness_statusとし、factの出自を示すassertion kindとは分離する。
Unavailable
必要能力またはdataがないため回答を確定できず、fixed reason codeで説明できる状態。
Unsafe confirmation
candidateまたはprovenance不足のatomをobserved / deterministic required factとして受理した状態。
Planned dependency
問いは有効だが、所有計画のproduction contractが未実装でcaseをactive化できない状態。

9.1 Profile Canonicalization

  1. strict parseと全invariant検証を完了してからhash用valueを作る。
  2. questionsをquestion ID、casesをcase IDのcode-point ascending順へ正規化する。
  3. capabilities、dependency plan IDs、atom refs、reason codes等のset-like arrayは重複をerrorにしてから同じ comparatorでsortする。answer orderに意味があるarrayはsortしない。
  4. shared/canonical-json.tsでserializeし、SHA-256をprofileHashとする。
  5. source fileの挿入順、object key順、locale、wall clockをprofile hashへ影響させない。

9.2 Registry Invariants

  • profile ID / version、question ID、case ID、fixture ID、adapter IDは重複不可とする。
  • active questionは1件以上のactive caseを必須とする。
  • profile全体でexpectedAvailability="answered"のactive caseを1件以上、required atomを1件以上 必須とし、answerability / provenance metricの0 denominatorを禁止する。
  • planned_dependencyは1件以上のdependency plan / capabilityを必須とする。
  • retired questionを削除せず、replacement IDまたはretirement reasonを保持する。
  • retiredはactive caseを0件とし、retirementReasonを必須にする。replacementがある場合は registry内の別questionへ解決し、replacement cycleを禁止する。
  • active / planned questionではreplacementQuestionIdと retirementReasonを禁止する。
  • question text、label、説明文をadapter selectionやexpected answer生成に使わない。
  • unknown question / adapter / statusはskipせずprofile validationをfailさせる。
  • registryは最大128 questions、active casesは最大1,024件とする。
  • active化、retire、adapter semantics変更、required capability変更はowner reviewを必須とする。
  • baseline 1.0.0ではchangeReceiptを禁止する。1.0.0以後のprofileは直前のreview済みversion / hashを exactに参照するreceiptを必須とし、履歴を飛ばせない。
  • comparatorが導出するminimum bumpをdeclaredBumpで弱められない。affected IDsはcurrentまたはprevious profileへ解決し、change kind、diff、approval refsと一致しなければpreflight failureとする。

10.1 Synthetic Fixture Profile

fixture IDはstatic-intelligence-cq-baseline-v1とし、以下を固定値で構築する。UUID、scan revision、source ref、path、scanner、rule IDはfixture codeに明示し、実行ごとに生成しない。

  • project 1件、scan revision 2件。ただし初期active casesは単一revisionだけを読む。
  • finding 3件: exact evidenceあり、evidence欠落、semantic-only related candidateの各状態。
  • evidence 3件、artifact 2件、source file 3件、scanner 2種、rule 3種。
  • same-file / same-rule relationと、fixed embeddingから得るsemantic candidate 1件。
  • available / missing / stale / revision mismatchを作るreadiness variant。
  • raw snippet、secret-like canary、absolute pathを入力へ置き、outputに出ないことをnegative検証する。
  • generatedAt、source revision、content hash、embedding vectorを固定し、wall clockとexternal providerを参照しない。

DB-backed production service testでは明示IDをinsertする。pure evaluator testでは同じfixture builderが返す normalized source recordsを使う。期待値をproduction responseから自動更新する--update機能は作らない。

fixtureHashはDB rowやSQLite fileをhashせず、builder入力となるstrict CompetencyFixtureManifestV1を正本にする。manifestはfixture ID、fixed timestamps、project / scan identity、source records、graph relations、readiness variants、fixed embedding vectorsを持つ。set-like arrayを code-point順へ正規化し、shared/canonical-json.tsでserializeしてSHA-256を生成する。DB seed後はmanifestの全stable refsがproduction exportへ一度ずつ解決することをassertする。

10.2 Atom Comparison

  • answer atom比較の前にconsumerBoundaryがcase expectationと一致することを検証する。
  • atom identityはkind、subject、predicate、object / value、assertion kindのtupleとする。
  • provenance refsはset比較し、最低限必要なrefsがすべて含まれることを要求する。
  • actual unavailable reasonsはrequiredUnavailableReasonsを全て含み、 allowedUnavailableReasonsの部分集合でなければならない。初期19 casesでは両配列を同値にしてexact matchとする。
  • required unavailable reasonはallowedにも存在しなければならず、両配列の重複を禁止する。
  • requiredAtomsは全件必要、forbiddenAtomsは1件でも存在すればfailとする。
  • allowedAtomsは存在してもよいoptional atomsであり、required atomsを重複登録しない。forbidden atomsはrequired / allowedのどちらとも重複できない。
  • requireCompleteAnswerSet=trueではrequiredAtoms ∪ allowedAtoms外のatomもfailとする。初期19 casesは全てtrueに固定する。 falseを必要とするadvisory discoveryは別schema / profileとし、baseline release profileでは表現できなくする。
  • title、summary、message、scoreの丸め値、配列入力順はatom identityへ含めない。

  3. route / MCP parityは既存contract testsで別途検証し、evaluatorの責務へ重複させない。
  4. adapterは入力responseをmutateせず、bounded normalized atomだけを返す。
  5. agent query adapterは全result itemのcandidateOnly=trueを検証して consumerBoundary="candidate_only"を返す。欠落またはfalseはfail closedにする。
  6. readiness adapterだけはconsumerBoundary="readiness_status"を返し、agent queryの候補境界と 混在させない。
  7. current free-form degraded reasonは§12の固定mapping tableで正規化する。
  8. unknown item kind、unknown reason、schema parse failureは空集合へ落とさずfail closedにする。
  9. raw internal error、SQL、stack、absolute pathをresultへ含めない。

14. Evaluator Algorithm

  1. profileとfixtureをstrict schemaでparseし、size / uniqueness / referential integrityを検証する。
  2. questionをquestion ID、caseをcase IDのcode-point ascending順に並べる。
  3. active caseだけをcase ID順に逐次実行し、planned / retiredは実行せずdependency summaryへ載せる。
  4. closed adapterを実行し、responseをschema parseしてnormalized atomsへ変換する。
  5. 全atomのsource / provenance refがfixtureまたはproduction response ref setに存在するか検証する。
  6. expected consumer boundaryとagent queryのcandidate-only invariantを先に評価し、違反時は他の一致に関係なく unsafe confirmationとする。
  7. expectedAvailabilityに従い、atom 0のunavailable、required atomを伴うexpected gaps、完全answerの3状態を排他的に判定する。
  8. unavailable reasonがある場合、atomとの同時存在policyとallowed reasonを検証する。
  9. required / allowed / forbidden atomとprovenance setを比較する。
  10. case outcomeと固定failure reasonを生成する。
  11. question / capability別metricを計算し、hard invariantとprofile quality policyからevaluation statusを決める。
  12. enforcement policyを適用してCI verdictを決め、canonical reportとhash対象外run metadataを生成する。

canonical orderingにlocaleCompareを使わず、UTF-16 code unit comparatorまたはshared canonical comparatorを使う。production responseの順序が意味を持たない箇所はsetへ正規化し、環境locale差を吸収する。

1 runは専用temporary DBまたはrollback可能なtest transactionを使い、別runとstateを共有しない。profile / fixture / policy invalid時はcaseを1件も実行しない。個別adapter failure時は残りcaseをboundedに評価して全gapをreportするが、evaluationはhard nonconformant、CI verdictは必ずfailedとする。case timeoutは2秒、初期suite timeoutは10秒とし、timeoutをunavailableへ変換しない。

16.2 Baseline / Candidate Comparison

PR regression summaryはmutableな「latest artifact」を参照せず、CIがbase commitとcandidate commitを別checkoutで同じ commandにより評価した2つのfull completed payloadから生成する。comparator自身はDB、service、networkを呼ばない。

  • 両completed payload / reportをstrict parseし、report hashと内包するevaluation / profile / fixture / policy hashを再検証する。
  • profile / fixture hashが同じ場合、stable question / case IDごとのoutcome、violation、metricを比較する。durationやruntime versionなどのrun metadataは差分へ表示してもcorrectness regression判定には使わない。
  • profileまたはfixture hashが異なる場合、共通case IDだけの結果比較と、added / removed / status-changed IDsを分けて返す。 ID再利用は常にfailureとし、removed active caseまたは期待条件緩和はvalid MAJOR change receiptがなければfailureとする。
  • 期待条件緩和はrequired / forbidden atomまたはrequired reasonの削除、allowed atom / reasonの追加、consumer boundaryの弱化、complete-answer requirementの解除、activeからplanned / retiredへの変更として機械分類する。
  • policyだけが異なる場合、evaluation hashは一致を要求し、enforcement verdict差を別fieldへ記録する。
  • valid change receiptがあるbreaking changeはapproved_breaking_changeとして通常regressionと分離し、receipt refsとderived bumpをcomparison outputへ残す。
  • base / candidateのBun version、fixture identity、command failureをsummaryから隠さない。
  • comparison JSONもstrict / boundedとし、question 128、case 1,024、4 MiB上限を適用する。

comparatorは--baseline-payload / --candidate-payloadでCI workspace内の明示fileを読むが、real project dataを含まないevaluation completed payloadだけを許可する。pathをrealpath化し、CI artifact root外、symlink、device fileを拒否する。

ontology contract versionとevaluation profile versionは別物である。contract candidateはexact evaluation profile version / hashをpinして実行し、registryのlatestを暗黙選択しない。

fixture manifestを独立に書き換えない。fixture hash変更は必ずprofile変更と同じPRで行い、active source record、ref、 readiness state、expected answerへ影響する変更はprofile MAJOR、意味を変えない説明metadataだけはPATCH、planned-only variant追加はMINORとする。

1.0.0以後のreleaseはchange receiptを必須とし、previous hash、derived minimum bump、affected IDs、rationale、3件以上の owner approval refsを検証する。receiptはbreaking changeを自動的に安全にするものではなく、比較結果で通常regressionと 分離し、review済みの意図的変更であることを証明する。

17.1 Enforcement Policy Versioning

  • PATCH: mode、budget、promotion条件を変えない説明 / approval ref訂正、またはprofile PATCHへのexact pin更新。
  • MINOR: advisory-onlyな観測field追加、またはprofile MINORへのexact pin更新。既存active判定を変えない。
  • MAJOR: advisory / blocking変更、profile MAJORへのpin更新、performance budget変更、hard violation set / severity変更。
  • profileとpolicyを同時変更する場合、candidate profile hashを先に生成し、そのexact hashをpolicyへpinしてから両方を atomicにreviewする。
