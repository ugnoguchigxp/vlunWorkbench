Status

  • Date: 2026-08-24

本書は、既存実装を置き換える新画面の提案ではない。現在のProject Intelligenceを土台として、複数の観測結果とProject文脈を重ねるためのUI拡張を定義する。後続の実装計画では、本書の段階分けと責務境界を入力として、API、read model、migration、testを具体化する。

1. Decision

Primary Navigationへ新しいIntelligenceメニューは追加しない。 Project Intelligenceの入口は、現在と同じProjects > Project > Intelligenceとする。 

Primary navigation
Projects | Scans | Knowledge | Chat | Search | Settings

Project navigation
Overview | Scans | Intelligence

Project Intelligence
構造サマリー | モジュール | 関係マップ | Ontology連携

既存4タブは、それぞれProject構造、構造単位、関係、外部連携という明確な責務を持つ。このため、Overview、Explore、Assessments、Contextなどの類似タブを新設しない。相互作用によって増える情報は、既存画面へProjectionとして重ねる。

ここでいうProjectionとは、Security、Architecture、Change、Testなどの観測をProject構造へ対応付けた派生表示である。元のFindingやOntology Entityを書き換えるものではない。

2. Verified Baseline

本コンセプトは、次の既存実装を前提とする。

1. Existing UI and responsibility
Area Current route / UI 既に存在する責務 本書での扱い
Project Overview /projects/:projectId Scan状態とIntelligence状態、Recent Scans、次のaction 入口として維持する。横断dashboardを別に作らない
Project Intelligence /projects/:projectId/intelligence generation context、構造、module、relationship、Ontology handoff 本コンセプトの拡張対象
Scans /scans?projectId=...&scanRunId=... 実行、Finding、Evidence、Coverage、Review、Report Securityの正本として維持する
Ontology連携 Project Intelligence内の既存タブ handoff readiness、provenance、候補payload、Agent Bundle preview 相互作用とconflictの可視化を追加する

既存のProject Intelligenceには、すでに次が実装されている。

  • 構造サマリー: structure readiness、metrics、module候補、analysis coverage、Security evidence overlay
  • モジュール: master-detail、filter、entrypoint、依存方向、package、exported symbol、関連fileとrisk overlay
  • 関係マップ: module dependency、typed reference、evidence graph、選択moduleの詳細
  • Ontology連携: canonical ownershipとの境界、handoff payload、参照、verification candidate、MCP pull command
  • Generation Context: generation ID、status、生成日時、source scan、readiness、refresh、Scan Workspaceへの導線

このbaselineにより、「新しいProject Intelligence Home」「独立Explore」「独立Context」「Finding一覧の複製」は追加価値にならない。後続実装は既存機能との差分だけを対象にする。

3. Responsibility Boundaries

2. Ownership boundary
Area Owns Does not own
Scans Scan Run、Finding、raw Evidence、Coverage、scanner severity、review、report Project全体の意味、canonical Ontology、複数sourceの統合優先度
Project Intelligence Project構造read model、関係、Projection、文脈付き評価、handoff候補、provenance Findingの正本、Scan実行、canonical Ontologyの直接編集
Ontology consumer / owner 採用済みEntity、Relation、意味、宣言、invariant、revision 個々のScanner結果や未検証candidateの自動採用

Project Intelligenceは、SecurityとOntologyの中間にあるコピー層ではなく、両者を参照して判断可能な形へ投影する接続面である。

4. UI Goals

  1. Security Scan単体の実行・確認・報告を、Project Intelligenceなしでも完結させる。
  2. Scannerの結果と、Project文脈を加えた結果の差を一目で説明する。
  3. Ontology由来の意味がどのProjectionに使われたかを追跡可能にする。
  4. Security観測から生まれたOntology候補を、自動採用せずにhandoffできるようにする。
  5. 同じsubjectをScansとProject Intelligenceの間で往復しても、選択状態を失わない。
  6. source不足、解析失敗、stale、snapshot不一致を、単なる「データなし」にまとめない。

5. Target Information Architecture

5.1 Existing navigation is retained

Primary Navigation、Project Navigation、既存routeは維持する。Project一覧とProject Overviewが入口として機能しているため、Intelligence専用の横断Homeは設けない。

5.2 Tab policy

3. Tab evolution
Tab 現在の中心 追加するUI
構造サマリー 構造、coverage、module、Security evidence overlay Enrichment Delta、capability別readiness、重要な相互作用
モジュール module単位の構造と証跡 Projection Inspector、semantic claim、文脈付きsecurity/architecture signal
関係マップ 依存、typed reference、evidence graph Structure / Security / Architecture / Semantic Lens
Ontology連携 candidate handoff、provenance、Agent Bundle consumed / produced / conflictの双方向trace

初期段階では4タブを増やさない。変更前後のgeneration比較が実装された時だけ、変更影響を第5タブとして追加できる。比較データがない状態で空のタブを先に置かない。

6. Generation Context and Source Readiness

画面上部の既存Generation Contextを、単一Scanの選択欄から、Project Snapshotと複数capabilityの状態を確認できるstripへ段階的に拡張する。 

┌ Project Intelligence ──────────────────────────────────────────────┐
│ Snapshot 8f31…  main@a3c9e2   Generated 14:32   [Change snapshot] │
│ Structure Ready  Security Ready  Semantic Degraded  Handoff Ready │
│ Source scan: run-1842                          [Details] [Refresh] │
└────────────────────────────────────────────────────────────────────┘

6.1 Behavior

  • 選択中のProject、revision、generation、生成日時を常に確認できる。
  • 現在のIntelligence source選択は、backend移行中も互換UIとして残す。
  • 将来はScan RunではなくProject Snapshot / Intelligence Generationを主選択にする。
  • Security Scanは複数inputの一つとしてsource欄に表示する。
  • Detailsはdrawerまたはpopoverで開き、専用Sources画面は作らない。

6.2 Capability Details

capabilityごとに、少なくとも次を表示する。

  • status: ready / stale / degraded / missing / failed / unsupported
  • producerとversion
  • 対象revisionまたはsnapshot
  • 生成日時とfreshness
  • coverageと既知のlimitation
  • 再生成または正本へ移動するaction

7. 構造サマリー: Enrichment Delta

既存の構造サマリーへ、元の観測結果とProject文脈による追加判断を並べるEnrichment Deltaを加える。Security件数を再集計するdashboardではなく、「統合によって何が新たに分かったか」を示す。 

Enrichment Delta
┌ Base observation ───────────────┬ Project Intelligence added ────────────┐
│ Finding: SQL injection          │ Reachable from public endpoint         │
│ Scanner severity: High          │ Crosses trust boundary                 │
│ Confidence: 0.91                │ Touches customer-data resource         │
│ Evidence: 3 locations           │ Contextual priority: Immediate         │
│ [Open in Scan Workspace]        │ Why: 3 claims / 5 relations            │
└─────────────────────────────────┴────────────────────────────────────────┘

7.1 Display invariants

  • scannerSeverity、scannerConfidence、Finding statusは変更しない。
  • 派生値はcontextualPriority、reachability、blastRadius、boundaryCrossingなど別fieldで表示する。
  • 各派生値から、入力したFinding、Relation、Semantic Claimへ辿れる。
  • Project文脈が利用できない場合でも、base observationは表示できる。
  • 「影響なし」と「未観測」と「解析不能」を別状態にする。

7.2 Summary cards

既存metricsを置き換えず、その下に少数のinteraction cardを追加する。

  • Context-raised priority: 文脈により優先度が上がった観測
  • Boundary crossings: trust / domain boundaryを横断する経路
  • Semantic conflicts: 宣言と観測が矛盾している候補
  • Unresolved coverage: 判断に必要だが観測できていない範囲

cardは詳細一覧を複製せず、該当moduleまたは関係マップをfilter済みで開く。

8. モジュール: Projection Inspector

既存のmodule master-detailへ、選択subjectに関する複数ProjectionをまとめるInspectorを追加する。独立したExploreタブは設けない。 

┌ Modules ───────────┬ Existing module detail ───────────┬ Projection Inspector ┐
│ auth               │ Entrypoints                       │ Subject               │
│ billing  selected  │ Inbound / Outbound                │ Security              │
│ catalog            │ Packages / Symbols / Files        │ Architecture          │
│ ...                │ Reasons / Evidence                │ Semantic claims       │
│                    │                                   │ Provenance / Unknowns │
└────────────────────┴───────────────────────────────────┴──────────────────────┘

8.1 Inspector sections

  1. Subject: stable ID、種類、module、file / symbol、対象snapshot
  2. Security: 関連Finding、reachability、sensitive resource、base severityとの差
  3. Architecture: fan-in / fan-out、boundary crossing、cycle、blast radius
  4. Semantic: entity候補、relation候補、declared / observed / inferred、confidence
  5. Evidence and provenance: source ref、producer、freshness、coverage、limitation
  6. Actions: Scan Workspace、関係マップ、Ontology連携の該当箇所へ移動

8.2 Behavior

  • desktopでは右pane、狭い画面ではbottom sheetまたはfull-width detailとして表示する。
  • 選択subjectをURLへ保存し、reloadと共有後も復元する。
  • 利用できないProjectionはpane全体を消さず、理由と次actionを表示する。
  • Findingのreviewやstatus変更はInspector内で行わず、Scansへ遷移する。
  • Ontology Entityのcanonical編集はInspector内で行わず、handoff候補として扱う。

9. 関係マップ: Projection Lenses

既存のmodule dependencyとevidence graphを維持し、同じbounded subgraphへ表示内容を重ねるLensを追加する。Lensは別々のGraphを作る機能ではない。

4. Relationship lenses
Lens Purpose Examples
Structure 現在の標準表示。構造と依存を理解する imports、calls、contains、module dependency
Security FindingがProject構造のどこへ到達するかを見る entrypoint、data flow、sink、trust boundary、evidence
Architecture 構造上の影響と境界違反を見る cycle、unexpected dependency、fan-out、blast radius
Semantic Ontologyの意味と観測構造の対応を見る candidate entity、declared relation、conflict、unmapped subject

9.1 Lens rules

  • defaultはStructureとし、既存の探索体験を変えない。
  • Graphは選択subject周辺のbounded subgraphとして取得する。
  • node / edgeの意味を色だけに依存させず、label、shape、legendを併用する。
  • List / Tableで同等の関係を確認できるようにする。
  • Lens切替後も選択subject、depth、filterを可能な範囲で維持する。
  • 複数Lensの同時表示は初期scope外とし、視覚的な過密を避ける。

10. Ontology連携: Reciprocal Interaction

既存のhandoff画面に、Project IntelligenceとOntologyの双方向の関係を示す。新しいContextタブは作らず、Agent Bundleとhandoff payloadは現在のタブに残す。

10.1 Consumed from Ontology

Project Intelligenceが判断に使用したsemantic inputを表示する。

  • Entity / Relation / Invariant ref
  • canonical revision
  • 使用したProjectionと派生結果
  • snapshotとの整合状態
  • staleまたはconflict時の影響範囲

10.2 Produced for Ontology

Securityや構造解析から生まれたcandidateを表示する。

  • candidate typeとstable subject ref
  • observed / derived / inferredの区別
  • supporting evidenceとproducer
  • confidence、limitations、conflict
  • handoff readinessとverification候補

10.3 No automatic promotion

candidateはcanonical Ontologyへ自動昇格しない。UI上のactionは「採用」ではなく、候補payloadの確認、export、consumer側での検証に限定する。canonical側の変更結果は次generationで再取得する。

11. Scansとの双方向Cross-navigation

現在はProject IntelligenceからScan Workspaceへ移動できる。一方、Scansから同じsubjectのProject Intelligenceへ戻る精密な導線は不足している。これを優先して補う。

11.1 Scans to Project Intelligence

Finding detailへView in Project Intelligenceを追加する。

  • 対応moduleが一意ならモジュールを開き、Projection InspectorでFindingを選択する。
  • 経路情報があるなら関係マップをSecurity Lensで開く。
  • 対応付けが複数なら候補一覧を表示し、暗黙に一つへ決めない。
  • Intelligence未生成なら、Findingを保持したまま生成actionを提示する。

11.2 Project Intelligence to Scans

既存のScan Workspace導線を、可能な限りFindingまたはEvidence単位へ精密化する。

  • ProjectとScan Runを固定する。
  • Finding fingerprintまたはstable finding refで該当detailを選択する。
  • 元Findingが削除または再生成されている場合は、近似一致へ黙って移動しない。
  • snapshot不一致の場合は遷移前または遷移先で明示する。

11.3 Round-trip invariant

Scans → Project Intelligence → Scansと往復した際、Project、source Scan、Finding、subject、generationの選択を可能な限り維持する。相互作用のUI価値は、この往復が成立して初めて得られる。

12. Later Option: 変更影響

変更影響は既存4タブと異なる時間軸を扱うため、将来の第5タブ候補とする。ただし、Project SnapshotとGenerationの比較契約が成立するまで実装しない。 

構造サマリー | モジュール | 関係マップ | 変更影響 | Ontology連携
                                                ^ later phase only

12.1 UI

  • base generationとtarget generationを明示的に選択する。
  • module / relation / semantic claim / security contextの追加、削除、変更を分ける。
  • raw diffではなく、影響を受けるsubjectと根拠経路を表示する。
  • 「観測が消えた」と「問題が解消した」を区別する。
  • 変更前後のsource coverage差を常に併記する。

12.2 Entry conditions

  • Intelligence GenerationがscanRunIdから独立して識別できる。
  • 両generationが同一Projectの比較可能なsnapshotを参照する。
  • stable subject IDとrelation IDが定義されている。
  • source coverageの差を取得できる。

13. Primary User Flows

13.1 FindingからProject文脈を確認する

  1. ユーザーがScansでFindingとraw Evidenceを確認する。
  2. View in Project Intelligenceを選ぶ。
  3. 関係マップがSecurity Lensと対象subjectを保持して開く。
  4. reachability、boundary、resource、semantic meaningを確認する。
  5. Projection Inspectorでbase resultとEnrichment Deltaを比較する。
  6. reviewやstatus変更が必要なら、同じFindingを選択したScansへ戻る。

13.2 Moduleから複数の観測を確認する

  1. ユーザーがProject Intelligenceのモジュールタブでmoduleを選ぶ。
  2. 既存の構造detailを確認する。
  3. Projection InspectorでSecurity、Architecture、Semanticを順に確認する。
  4. 関係の根拠が必要なら、選択を保持したまま関係マップへ移動する。
  5. raw findingまたはcanonical meaningが必要なら、それぞれの正本へ移動する。

13.3 Security観測をOntology候補としてhandoffする

  1. Security観測が既存Entityと対応する、または新しい意味候補を示す。
  2. Project Intelligenceがcandidateとsupporting evidenceを生成する。
  3. Ontology連携タブでconfidence、conflict、provenanceを確認する。
  4. consumerへcandidate payloadを渡し、canonical側で検証する。
  5. 更新済みrevisionを次generationが入力として取り込み、使用箇所を表示する。

14. State and Error Model

Project全体とcapabilityごとの状態を分離する。

5. Required states
State Meaning UI behavior
available 選択generationで利用可能 通常表示
stale 新しいsource revisionが存在する 現在の内容を残し、対象revisionとrefresh actionを示す
degraded 一部capabilityまたはcoverageが不足 利用可能範囲と不足範囲を分ける
missing 必要sourceが存在しない 必要条件と取得actionを示す
failed 生成処理が失敗 base sourceを隠さず、retryと診断情報を示す
unsupported 対象projectまたはsourceがcapability非対応 missingと区別し、無効なretryを出さない
snapshot_mismatch sourceのrevisionが一致しない 統合値を生成せず、比較対象を明示する
not_observed 対象範囲を観測できていない 「該当なし」と表現しない
conflict 宣言、観測、推論が矛盾 勝者を暗黙に決めず、双方のrefを示す

15. URL and Data Contract Direction

15.1 Route

既存routeを維持する。

/projects/:projectId/intelligence

15.2 Query state

既存queryとの互換性を保ちながら拡張する。

Existing:

  intelligenceView=overview|modules|relationships|handoff
  focusPath
  moduleId

Candidates:
  generationId
  lens=structure|security|architecture|semantic
  subjectId
  findingRef
  compareToGenerationId   # later phase only

15.3 Identity migration

現在のIntelligence GenerationはScan Runを起点としている。将来の統合では、Project Snapshot、Observation Batch、Intelligence Generationを分離し、Scanをoptional inputとして扱える必要がある。

UIを先に切り替えず、backendのidentityとread modelが成立してから、scanRunId中心のselectorをgenerationId中心へ移行する。移行中は両者の対応を明示し、暗黙にlatestを選ばない。

15.4 Minimum Projection read model

ProjectionResult
  generationId
  projectSnapshotRef
  subjectRef
  capability
  baseObservationRefs[]
  semanticInputRefs[]
  derivedSignals[]
  confidence
  coverage
  freshness
  limitations[]
  conflicts[]
  producer

derivedSignalsはbase resultを上書きせず、計算根拠を参照できることを必須とする。field名とAPI分割は後続実装計画で確定する。

16. Responsive and Accessibility

  • 390px幅でもProject、generation、主要status、primary actionを確認できる。
  • Projection Inspectorは右pane固定にせず、小画面で独立detailへ変形する。
  • Graphだけを唯一の探索手段にせず、table / listを提供する。
  • keyboardでtab、module、subject、Lens、Inspector sectionを移動できる。
  • statusとLensを色だけで区別しない。
  • drawer / dialogはfocus trap、close、focus returnを備える。
  • 大量nodeを一括描画せず、depthと件数budgetを明示する。

17. Delivery Stages

Stage 1: Boundary and navigation completion

  • Primary Navigationと既存4タブを維持する。
  • ScansからProject Intelligenceへのreverse deep linkを追加する。
  • Generation Contextにcapability readinessとsource detailsを追加する。
  • stable subject / finding refとURL stateを定義する。

Stage 2: Enrichment Delta and Inspector

  • 構造サマリーへEnrichment Deltaを追加する。
  • モジュールへProjection Inspectorを追加する。
  • base observationとderived signalの表示境界を固定する。
  • provenance、coverage、unknown stateを表示する。

Stage 3: Relationship lenses and Ontology interaction

  • 関係マップへSecurity / Architecture / Semantic Lensを段階追加する。
  • Ontology連携へconsumed / produced / conflict traceを追加する。
  • bounded subgraph APIとtable fallbackを実装する。

Stage 4: Generation independence

  • Project Snapshot、Observation Batch、Generationのidentityを分離する。
  • Security Scanをoptional observation sourceへ移行する。
  • selectorとroute queryをgenerationId中心へ移行する。

Stage 5: Change impact, if justified

  • 比較契約とstable identityが成立した後に限り、第5タブを追加する。
  • 2つのgeneration、coverage、source revisionを固定して差分を計算する。

18. Non-goals

  • Primary Navigationへの新しいIntelligenceメニュー追加
  • /intelligenceという新しい横断Homeの追加
  • ScansのFinding一覧、review、reportをProject Intelligenceへ複製すること
  • 既存のモジュール／関係マップと重複するExploreタブの追加
  • 既存のAgent Bundleと重複するContextタブの追加
  • Security FindingとArchitecture signalを混在させたAssessments一覧の追加
  • Security未実行を理由にProject Intelligence全体を利用不能にすること
  • Semantic candidateのcanonical Ontologyへの自動昇格
  • Scanner severityやFinding statusの上書き
  • 全Project、全Entity、全Evidenceを一度に描画するGraph browser

19. Concept Acceptance Criteria

  1. 新しいPrimary Navigation itemを追加せず、既存routeから全機能へ到達できる。
  2. 既存4タブの責務が維持され、追加UIがどのタブに属するか明確である。
  3. Security ScanはProject IntelligenceとOntologyがなくても単体で完結する。
  4. base Findingと文脈付き派生値が視覚的・データ的に区別される。
  5. すべての主要な派生値からsource refとproducerへ辿れる。
  6. ScansとProject Intelligenceの相互deep linkで選択subjectを維持できる。
  7. Ontology inputの使用箇所と、Ontology向けcandidateの双方を確認できる。
  8. SecurityまたはSemantic capabilityが欠けても、利用可能な構造情報を表示できる。
  9. missing、failed、stale、unsupported、not observed、snapshot mismatchを区別できる。
  10. 既存Project Intelligenceのzero finding、legacy URL、retry、mobile、accessibilityの動作を壊さない。
  11. 変更影響タブは、比較可能なGeneration契約が成立するまで追加されない。

20. Inputs Required for a Future Implementation Plan

実装計画を作成する際は、少なくとも次を決定する。

  1. stable subject ID、finding ref、relation IDの形式とlifecycle
  2. Project SnapshotとScan Runのrevision整合規則
  3. Projection producerのplugin contractとreadiness contract
  4. base observationとderived signalを分けるAPI response
  5. 既存scanRunIdqueryとの互換期間とmigration
  6. Projection Inspectorのdesktop / mobile component境界
  7. Lensごとのbounded graph queryとbudget
  8. Scansとのround-trip deep link contract
  9. Ontology consumerとのcandidate / revision / conflict protocol
  10. 既存E2Eを維持した追加test matrix

最初の実装計画はStage 1とStage 2だけを対象にする。Stage 3以降は、Projection read modelとstable referenceが実データで検証できてから別planとして起票する。
