Finding Deduplication and Issue-grouped Handoff Implementation Plan

Status: Implemented locally and archived — 2026-08-21

Planning baseline commit: 9d8ae3e18b7956646400380dc6079693d54f0ee2

Planning baseline date: 2026-08-21

Owner: vulnWorkbench maintainers

Target: 複数scannerが同じ問題を異なるrule、title、severityで検出した場合に、raw findingと証跡を 失わず、画面、レポート、件数、LLM改修指示書では1 issue group = 1問題として扱う。 自動統合に十分な根拠がないfindingは別問題のまま残す。

1. 決定事項とリリース境界

  1. findingsとfinding_evidenceはscannerが保存したraw recordとして維持し、 重複排除を理由に削除、上書き、代表findingへの付け替えを行わない。
  2. raw findingの上位に永続化されたissue groupを追加し、全findingを必ず1つのgroupへ 所属させる。統合不能なfindingもmember 1件のsingleton groupとして表現する。
  3. 初回production releaseは決定論的matcherだけをcurrent snapshotとして使用する。 同じscan、同じ対象資産、一致または重なる位置、同じ脆弱性family、hard conflictなし、 という複合条件が揃った場合だけ自動統合する。
  4. LLM意味判定は独立したshadow機能として実装できるが、UI、report、改修指示書のcurrent snapshotには使用しない。production有効化は本計画のDefinition of Doneに含めない。
  5. LLM改修指示書にはgroupごとのcanonical issueを1件だけ渡す。member findingの重複本文を渡さず、 scanner/rule/severity差、member件数、重複を除いたevidence参照を補足する。全member IDはserver-side audit manifestにだけ保存する。

1.1 Required release R1

FG-00からFG-06までがこの計画で必ず完成させるproduction scopeである。R1完了時には、決定論的 groupingをUI、report、改修指示書が共通利用し、LLM providerがなくても全機能を利用できる。

1.2 Optional shadow R2

FG-07はCLIから明示実行するsemantic shadowである。結果と監査情報は保存するが、current selectorは 必ずdeterministic runを選ぶ。semantic結果をproductionへ昇格する変更は、review済みcorpus、固定した precision gate、運用時の無効化手段を含む別計画で行う。したがって、閾値を決める作業やsemantic auto-mergeの有効化を本計画の実装者へ残さない。

2. 用語と責務境界

raw finding
scanner normalizerが既存findings tableへ保存する検出事実。source tool、rule、title、 description、severity、location、fingerprint、metadataを所有する。
dedupe identity
scanner横断の候補抽出に使用するversion付きの正規化projection。raw findingを読み出した時点で生成し、 raw metadataを書き換えない。group member rowへ計算時snapshotを保存する。
issue group
同じscan内で実質同一と決定できた1件以上のraw findingを束ねる上位単位。UI、report、改修指示書の default表示単位とする。
representative finding
group detailの初期表示、canonical title、canonical descriptionの選択に使うmember。代表以外のmemberや evidenceを消す意味ではない。
grouping run
1つのscanのraw finding集合、algorithm version、判定結果を拘束したimmutable snapshot。 consumerはcurrent completed deterministic runだけを使用する。
suppressed duplicate
raw findingとして存在するが、default issue一覧では独立行を持たないsupporting member。 削除済み、false positive、または無効なfindingを意味しない。

5. Non-negotiable invariants

  1. rawFindingCount = 全groupのmemberFindingIdsの合計である。
  2. completed grouping run内で、各raw findingは正確に1groupへ所属する。
  3. representative findingは同じgroupのmemberでなければならない。
  4. issueCount <= rawFindingCountであり、差がsuppressed countになる。
  5. group severityはmember severityの最大値と一致する。
  6. 異なるscan run、asset kind、asset occurrenceをまたいで自動統合しない。
  7. hard conflictまたはambiguousなpairをLLM scoreや推移律で統合しない。
  8. uncertain、timeout、provider unavailable、budget超過は別groupへ倒す。
  9. grouping失敗を理由にfindingを非表示にしない。失敗時は全件singleton fallbackを返す。
  10. 同じ保存済み入力とalgorithm versionから、取得順に依存しない同一snapshotを作る。
  11. LLMへ送るcontextと永続化payloadにraw secret、credential、auth query valueを含めない。
  12. UI、report、改修指示書は同じcompleted grouping run IDとsnapshot hashを参照する。

6. Target flow

scanner raw output
  -> existing normalizer and persistence (unchanged)
  -> projectFindingDedupeIdentity(raw finding)
  -> candidate blocks by issue kind and asset occurrence
  -> deterministic pair decisions and hard-conflict rejection
  -> deterministic complete-link clustering
  -> publish immutable deterministic grouping run
       -> UI: one row per issue
       -> report: issue body + raw appendix
       -> improvement request: one issue per LLM input item
       -> raw finding detail/evidence: unchanged

optional CLI only:
  ambiguous deterministic pairs
  -> bounded semantic adjudication
  -> separate semantic shadow run and metrics
  -> never selected by R1 consumers

groupingはpresentation snapshotでありscanのtruthを変更しない。grouping失敗でscan statusをfailedへ 変更しない。reportまたは改修指示書がsnapshotを使った場合は、run ID、finding set hash、snapshot hash、 algorithm versionをoutput metadataへ保存する。

7. Shared contracts and constants

7.1 Dedupe identity

shared/schemas/finding-group.schema.tsへ次のversion 1 schemaを追加する。 projectFindingDedupeIdentity(finding)が既存finding fieldsとmetadataから毎回生成し、 normalizerやraw finding rowは変更しない。 

type FindingDedupeIdentityV1 = {
  version: 1;
  issueKind: "dependency" | "secret" | "source" | "iac" | "web" | "api" |
    "business_logic" | "unknown";
  assetKey: string | null;
  location: {
    kind: "source" | "url" | "package" | "resource" | "unknown";
    path: string | null;
    startLine: number | null;
    endLine: number | null;
    startCol: number | null;
    endCol: number | null;
    method: string | null;
    parameter: string | null;
    resource: string | null;
  };
  familyKeys: string[];
  advisoryIds: string[];
  packageKey: string | null;
  anchor: string | null;
  limitations: string[];
};
  • 全string setはtrim、case normalization、重複除去、昇順sortを行う。
  • pathはseparator、先頭./、workspace prefixを正規化しproject-relativeにする。
  • URLはcredential、fragment、query valueを除き、origin、path、method、parameter名を分離する。
  • package keyはecosystem、package、installed version、manifest/target occurrenceを含める。
  • advisory IDはprimary ID、aliasを大文字へ正規化する。一般rule IDはadvisoryへ混ぜない。
  • family:unknown同士は一致根拠にしない。
  • secretはpath、range、detector familyだけを使い、secret本文またはそのdigestを作らない。
  • identity作成時のschema validation失敗はthrowせずissueKind: unknownへ倒す。

7.3 Representative and canonical fields

representativeは次のstable sortの先頭とし、reviewやhuman decisionを参照しない。

  1. confidence: runtimeをstaticより前にする。
  2. severity: critical、high、medium、low、info、unknownの順にする。
  3. identity completeness: assetKey、具体的family、location、advisory/package keyの非null項目数が多い順。
  4. sourceTool lowercase、ruleId、finding IDの昇順。
  • group severityは全memberの最大severityとする。
  • dependency titleは{packageName}@{version}: {preferredAdvisoryId}とする。
  • dependency以外のtitleとdescriptionはrepresentativeから取る。LLMに生成させない。
  • stable keyはalgorithm versionとsorted member IDsのSHA-256であり、別run間の永続IDではない。

pair decision tableへ全candidate pairを保存してはならない。deterministic runでは各supporting memberとrepresentativeのsame decisionだけをproof rowとして保存し、semantic runでは実際にLLMへ送った 最大100 pairを保存する。different/ambiguousの総数はrun countへ保存し、必要なら同じ入力から再計算する。 これによりpair row数はraw finding数とsemantic budgetに対してboundedになる。

countの定義は固定する。issue_count = group row数、 suppressed_count = raw_finding_count - issue_count、 ambiguous_count = ambiguousまたはbudget未評価となったcandidate pair数である。 ambiguous countをfinding件数またはgroup件数として表示しない。

8.2 Hashes and current selection

finding_set_hash
current raw集合が変わったかを判定する。scan run IDと、finding ID、fingerprint、sourceTool、ruleId、 severity、confidence、location、identity projection、persisted title/descriptionのSHA-256をfinding ID順で canonical JSON化してSHA-256にする。secret本文はそもそも保存済みfindingへ入れず、hash inputにも足さない。
semantic_decision_hash
semantic pair decisionのcanonical projectionをpair ID順にhashする。deterministic runは空文字固定。
snapshot_hash
published group/member projection、counts、algorithm versionをgroup stable key順にhashする。reportと 改修指示書の再現性、stale判定に使用する。
comparison_hash
algorithm version、ordered finding IDs、両identity、redact/truncate後のtitle/description SHA-256をcanonical JSON化してhashする。semantic cacheは同じcomparison hash、provider、model、prompt sequence hashの completed decisionだけを再利用する。

selectCurrentDeterministic(scanRunId)は次の順で選ぶ。

  1. 現在のraw findingsからfinding_set_hashを再計算する。
  2. status=completed、mode=deterministic、algorithm version=current、finding set hash=currentのrunだけを検索する。
  3. 複数ある場合はcompletedAt降順、ID降順の先頭を返す。
  4. semantic run、古いfinding set hash、running/failed runは返さない。

8.3 Writer-safe publish

file-backed DBではdb.transaction(async callback)を使用してはいけない。repositoryは writerClientForDatabaseでWriterの有無を判定し、file-backed DBでは atomicDrizzleBatch、in-memory test DBではrunInProcessDbTransaction内の同期 .run()を使用する。

  1. 同じscanで15分以上経過したrunning runをstatus=failedへrecoveryする。
  2. 同じactive keyのcompleted runがあればそれを返す。
  3. run rowをstatus=runningで作る。partial unique競合時は既存rowを100ms間隔、最大5秒再読し、completedなら それを返す。5秒後もrunningならephemeral singletonとgrouping_in_progress limitationを返す。
  4. group、member、pair decisionを最大250 statementのatomic Writer batchへ分割して保存する。 running runはconsumerから見えないため、batch間にprocessが落ちても部分snapshotは使用されない。
  5. repositoryでmember総数、一意membership、representative membership、severity、issue/suppressed countを再読して検証する。
  6. 最後のatomic updateでsnapshot hash、counts、completedAtを設定しstatus=completedへpublishする。
  7. 例外時はerrorをredact/truncateしてstatus=failedへ更新する。15分以上のrunning rowは次回ensureまたはCLIで failedへrecoveryする。failed rowのchildはaudit用に残してよいがcurrentにはならない。

9. Deterministic matching

9.1 Candidate blocking

全pairの総当たりを禁止する。まずscanRunId + issueKind + assetKeyでblockを作り、同一block内だけを 比較する。assetKeyがnull、business_logic、unknownのfindingはsingletonにする。

block内candidate pairはfinding ID順で列挙し、scan全体で50,000比較を上限にする。上限後の未評価pairは ambiguousとしてmergeせず、run limitationsへdeterministic_pair_budget_exceededを追加する。 したがってbudget超過はduplicateを残すことはあってもfalse mergeやfinding非表示を起こさない。

issue kind別の決定論的統合条件
Kind Candidate asset same条件 hard conflict
dependency manifest/target occurrence、ecosystem、package、installed version advisory ID集合が交差する。OSV aliasとTrivy primary IDも同じ集合として扱う。 別occurrence、package、version、または既知advisory集合が非交差
secret project-relative path、line/column range 両scannerにcolumnを含むexact rangeがあり、rangeが重なり、detector familyが同じ。 非重複range、異なるfamily、同じ行の別column token
source project-relative path、rangeまたはnon-secret anchor range/anchorが一致し、具体的family keyが同じ。 family不一致、別parameter、別source/sink trace
iac path、resource/block、overlapping range resourceと具体的policy familyが一致する。 別resource、異なる設定項目、別remediation
web/api normalized origin/path、method、parameter method、parameter、具体的weakness familyが一致する。 別parameter、別method、header subtypeまたはweakness family不一致
business_logic/unknown candidateなし なし。常にsingleton。 常に自動統合禁止

CWE一致、title類似、同じ行、同じseverity、同じremediationのいずれか1条件だけではsameにしない。 sameにもdifferentにも確定できないpairはambiguousにする。

9.2 Family mapping

api/modules/scans/finding-dedupe-families.tsへversion管理されたmappingを置く。 title/descriptionの自由文substringを主根拠にせず、既存rule ID、CWE、scanner metadataを優先する。

  • Semgrepはmetadata.risk.cweIdsとscanner metadataを使用する。
  • Trivy vulnerabilityはpurl、target、vulnerability IDを使用する。
  • OSVはmanifest path、package、version、primary ID、aliasesを使用する。
  • Gitleaks/Trivy secretはdetector rule mappingを使うが、Trivyにcolumnがない場合はsameにしない。
  • Trivy config/Semgrep IaCはpath、resource/block metadata、policy familyが揃う場合だけ比較する。
  • ZAP/NucleiはURL、method、parameter、CWE、template/plugin familyを使用する。
  • mapping未登録ruleはfamily:unknownとし、unknown同士を一致扱いにしない。

9.3 Safe clustering

推移律によるbridge mergeを避けるため、次のcomplete-link algorithmを固定する。

  1. findingsとpair keysをID昇順へsortし、最初は全件singleton groupとする。
  2. group pairをsorted member ID列のlexical orderで列挙する。
  3. 2group間の全cross pairがverdict=sameの場合だけmerge可能とする。
  4. merge可能な最初のgroup pairを統合して列挙をやり直す。merge不能になるまで繰り返す。
  5. cross pairにdifferentまたはambiguousが1件でもあればmergeしない。

10. Semantic shadow contract

本節はFG-07を実装する場合だけ適用する。semantic runnerはdeterministicでambiguousになったpairだけを 最大100件まで処理し、別modeのrunを作る。R1 consumer selectorはこのrunを読まない。 

{
  "verdict": "same_issue|different_issue|uncertain",
  "confidence": "high|medium|low",
  "canonicalFamily": "family key or unknown",
  "reasonCodes": ["same_root_cause", "same_remediation"],
  "rationale": "保存済み入力だけに基づく300文字以下の説明"
}
  • same_issue + highだけをsemantic run内のsame decisionへ変換する。
  • different_issue、uncertain、medium/low、timeout、invalid JSONはmergeしない。
  • deterministic hard conflictはLLMへ送らず、LLM結果でも上書きしない。
  • titleとdescriptionはredact後にそれぞれ200/600文字へ切り、identity/locationとともに untrusted.jsonとして送る。raw artifact、repository file、secret、credentialは送らない。
  • system promptでuntrusted scanner text内の命令を無視するよう指示し、strict schemaでparseする。
  • provider、model、prompt sequence hash、response content SHA-256、短いrationaleをpair rowへ保存する。
  • route未設定/provider unavailable時、CLIはfailed runを監査保存してnon-zero終了する。deterministic runは維持する。

LLM task finding_deduplicationを api/modules/llm-settings/llm-settings.schema.tsのschema/policy、frontend task type/label、 system context catalog/bindingへ追加する。contextは contexts/scans/findingDeduplication.context.tomlと contexts/scans/findingDeduplicationInput.context.tomlの2つに分ける。

11. Run lifecycle and API

11.1 ensureCurrentDeterministic

ensureCurrentDeterministic(scanRunId: string): Promise<GroupingSnapshot>;
getSingletonFallback(scanRunId: string, limitation: string): Promise<GroupingSnapshot>;
  • scan statusがcompleted、failed、cancelledならdeterministic snapshotをensureし永続化する。
  • scan statusがqueuedまたはrunningなら永続化せず、現在取得できるraw findingsのephemeral singletonを返す。 runId/snapshotHashはnull、group IDはsingleton:{findingId}、limitationは scan_not_terminalとする。
  • finding 0件のterminal scanもcounts=0のcompleted runを永続化する。
  • groupingの計算/保存失敗時はephemeral singletonを返し、limitationへgrouping_failedを入れる。
  • raw集合が変わればfinding set hashが変わるため、古いrunをcurrentにしない。

12. Consumer integration

12.1 Scan workspace

  • view stateをissues | rawとし、defaultはissuesにする。
  • issues viewはgroups APIの全groupを1行ずつ表示する。finding paginationの現在pageへ依存しない。
  • headerに12 issues / 19 raw findings / 7 duplicates grouped相当を表示する。
  • row clickはrepresentative findingを既存detail/action対象として選択する。
  • member expansionから任意のraw memberを選択し、既存review、decision、evidence操作へ進める。
  • group単位のdecision/review操作は追加しない。
  • severity disagreement、source tools、reason codes、limitationsをgroup summaryへ表示する。
  • singleton fallback時も全findingを表示し、grouping失敗を空状態として表示しない。

12.2 Report

  • Executive Summaryとseverity tableはissue count基準にする。
  • main findings sectionは1group 1sectionとし、representative title/description/locationを使う。
  • 各sectionにscanner signals、member count、deduplicated evidence参照を付ける。
  • appendixは全raw finding ID、tool、rule、severity、group IDを列挙する。
  • headingでissue countとraw finding countを明示し、従来値との意味変更を隠さない。
  • report metadataへgrouping run ID、finding set hash、snapshot hash、algorithm versionを保存する。 scan-finalization-service.tsのcanonical report refresh判定へsnapshot hash差分を加える。
  • ephemeral singletonしか得られない場合はraw基準reportを生成し、limitationを本文へ明記する。

12.3 LLM improvement request

dedicated ScanImprovementRequestRunnerだけをissue-firstへ変更する。 generationKind = improvement_requestでないautomated diagnostic reviewは本計画で変更しない。 

type ImprovementRequestIssueBundle = {
  grouping: {
    runId: string;
    findingSetHash: string;
    snapshotHash: string;
    algorithmVersion: string;
    rawFindingCount: number;
    issueCount: number;
  };
  issueManifest: Array<{
    issueId: string;
    memberFindingIds: string[];
  }>; // persisted audit only; promptへrenderしない
  issues: Array<{
    issueId: string;
    representativeFindingId: string;
    rawFindingCount: number;
    title: string;
    description: string;
    severity: FindingSeverity;
    location: FindingLocation;
    familyKeys: string[];
    scannerSignals: ScannerSignal[];
    evidence: EvidenceReference[];
    grouping: { confidence: string; reasonCodes: string[] };
  }>;
};

bundle作成規則を次のように固定する。

  1. completed scanだけを受け付け、current deterministic snapshotをensureする。
  2. ensure結果のrunId/snapshotHashがnullならLLMを呼ばず、grouping_snapshot_unavailableで生成を 明示的に失敗させる。raw findingの閲覧には影響させない。
  3. issueをseverity、primary location、issue IDのstable orderへ並べ、50 issueごとにchunkする。
  4. 同じissueのmemberを別chunkへ分割しない。
  5. issueManifestは全memberFindingIdsを保持してpersistするがLLM promptへrenderしない。promptのissue itemには issueId、representativeFindingId、rawFindingCountだけを渡す。scanner signalsはstable uniqueな先頭20件に 制限する。
  6. evidenceは(kind, artifactId, location projection, snippet hash)で重複除去し、source-locationを tool-outputより前にして先頭6件に制限する。snippetは300文字、descriptionは400文字へ切る。
  7. 上限超過はbundle limitationsへ記録する。raw ID coverageはpromptではなくissueManifestで保証する。

12.4 Improvement request schema compatibility

既存scanImprovementRequestSchemaを破壊しない。priorityPlanとimplementationTasksへ issueIds: z.array(z.string().uuid()).max(5000).default([])をadditiveに追加し、既存required findingIdsを残す。これによりscanReviewOutputSchemaと保存済みlegacy outputを維持する。

LLM応答parse専用にllmIssueImprovementRequestSchemaを追加する。このschemaは各plan/taskで issueIdsをrequiredとし、findingIdsを受け付けない。処理順は次で固定する。

  1. LLM responseをstrict llmIssueImprovementRequestSchemaでparseする。
  2. unknown issue ID、bundle外evidence ID、全issue未coverageをrejectする。
  3. serverがcurrent bundle manifestからissueIdsを全raw findingIdsへ展開する。
  4. 展開後のpublic objectを既存scanImprovementRequestSchemaでparseする。
  5. 全raw finding coverageとissue/finding ID hashを検証してからpersistする。

chunk mergeは現行の上限を維持して次のように行う。各chunkは、そのchunkに含まれる全issueを implementationTasks.issueIdsで最低1回coverしなければならない。chunk順、task順を維持して title/body/issueIdsが同じtaskを重複除去し、先頭20taskを採用する。未coverage issueは最大5,000 IDごとの server-generated fallback taskへまとめ、合計30task以内にする。fallback追加で30taskを超える場合はLLM taskを捨て、全issueをfallback taskだけで再構成する。それでも30taskを超える場合は永続化せず明示的に失敗する。 priorityPlanは先頭20件までとし、task coverageのsource of truthには使用しない。最後に各taskのissueIdsを findingIdsへ展開するため、truncation後もraw coverageを失わない。 

{
  "coverage": {
    "totalIssues": 12,
    "coveredIssues": 12,
    "totalFindings": 19,
    "coveredFindings": 19,
    "issueIdsHash": "sha256",
    "findingIdsHash": "sha256"
  }
}
  • frontend quality判定はissue coverageが存在すればそれを優先し、legacy recordでは既存finding coverageへ fallbackする。
  • Markdownはissue IDを主表示し、raw finding IDsはaudit appendixへ移す。
  • prompt変更対象はcontexts/scans/improvementRequest*.context.tomlだけとする。
  • generic scanReview.context.toml、finding review、diagnostic assessmentは変更しない。

17. Failure and security

  • grouping run failureをscan failure、finding 0件、安全宣言へ変換しない。
  • 不正または欠落identityはsingletonにし、title fallbackで自動統合しない。
  • scanner title/descriptionはuntrusted dataとして扱い、semantic prompt内の命令に従わせない。
  • LLM verdictはscanner fact、severity、status、review、human decisionを書き換えない。
  • group API/detail APIは既存scan ownership checkを必ず通す。
  • candidate budget、prompt size、evidence count、description/snippet lengthの固定上限を守る。
  • grouping auditにはraw secret、auth query value、cookie、token、credentialを含めない。
  • 同時再計算はpartial uniqueにより同じscan/mode/version/finding setで1 active runへ収束させる。
  • batch途中のprocess停止ではrunning partial snapshotをconsumerへ公開しない。
  • scan deleteは全grouping dataをcascadeし、project deletion cleanupを妨げない。

18. Definition of Done

次の全項目を満たせばR1完成である。FG-07はR1完成条件ではない。

  1. 全raw findingとevidenceが変更前と同じIDで取得でき、raw rowをmigration/backfillで更新していない。
  2. 全completed deterministic runでmembership、representative、severity、count invariantが機械検証される。
  3. golden same caseが1group、different/ambiguous caseが別groupになり、bridge mergeしない。
  4. scan input順、DB取得順、process再実行に依存せず同じsnapshot hashになる。
  5. running scanまたはgrouping失敗時もsingleton fallbackで全findingが表示される。
  6. scan workspaceのdefault一覧が1group 1行になり、raw viewと全member evidenceへ戻れる。
  7. UI、summary、reportが同じrun ID、snapshot hash、issue/raw/suppressed countを示す。
  8. report本文がissue単位、appendixがraw finding単位になり、snapshot変更で再生成される。
  9. 改修指示書LLM inputで各issueが1回だけ現れ、同じissueをchunk分割しない。
  10. strict issue ID validation後にserverが全raw finding IDsを展開し、dual coverageを検証する。
  11. 保存済みlegacy scan、legacy groups caller、findingIds-only improvement requestを閲覧できる。
  12. secret leakage、prompt injection、cross-user access、race、partial publishのnegative testが通る。
  13. focused tests、full test inventory、typecheck、lint、docs checkが通る。
  14. semantic modeはproduction current selectorから到達不能であり、LLM routeなしでもR1が動作する。

19. Terra implementation handoff

実装はFG-00から順に行う。各sliceでschema、implementation、testsを同じ変更単位に含め、acceptance gateを 通してから次へ進む。既存grouping-builder.tsのkey調整だけ、UIだけのfilter、promptだけの重複除去を 完了扱いにしない。永続化した同一deterministic snapshotをUI、report、改修指示書の3consumerへ接続することが R1の中心である。

実装中に本書と既存型が衝突した場合は、raw finding不変、false merge回避、Writer-safe publish、public schemaの backward compatibilityを優先する。R1の挙動を変える未記載の選択肢が必要になった場合だけ実装を止めて仕様を 更新する。file分割、関数名の軽微な調整、test fixtureの配置は、責務とacceptanceを変えない範囲で実装者が行ってよい。
