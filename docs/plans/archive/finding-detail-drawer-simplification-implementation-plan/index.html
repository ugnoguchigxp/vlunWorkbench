この文書は、finding詳細Drawerを「検出された問題、重大度、検出位置、保存済みの観測事実を 確認する画面」へ整理するための規範仕様である。実装担当は、本文に記載していない値や機能を 補わず、Work Package 0から順番に実装する。

1.1 ドキュメントレビューの結論

改訂前の計画は目的と対象外が妥当だった一方、相対URLとsource pathの判定、evidenceの選択順、 表示modelとUIの責務、既存Markdown componentの移設、testの所有範囲に実装判断が残っていた。 本改訂では、その判断を3章の規範仕様と4章の実装順序へ集約した。

  • 画像内の例示値を実データとして固定表示しない。
  • 値を取得できない項目は推測せず、項目自体を表示しない。
  • 既存の検証tab以外に、新しい検証導線を作らない。
  • review・Decisionの非表示に伴う通信やcontrollerの整理は行わない。
  • API responseとモックアップが競合する場合は、保存済みAPI responseを優先する。

2. Use when

次の条件をすべて満たす変更に本計画を使用する。

  • finding詳細Drawerの概要表示を簡素化する。
  • 利用者がfinding名、重大度、検出位置を最初のviewportで確認できるようにする。
  • source findingでは、保存済みの場合だけプロジェクト相対pathと行番号を表示する。
  • Web findingでは、保存済みの場合だけoriginを除いたURL pathとHTTP methodを表示する。
  • 保存済みevidenceに具体的な観測値がある場合だけ、一件を短く表示する。
  • review、修正管理、Decision、report workflowをDrawerの概要から外す。

2.1 参照モックアップ

次の画像要素は実装しない。

  • GET /、CSP header、tool確度など、画像内の例示値の固定表示。
  • 新規の「検証タブで確認」button。
  • 実データがない場合の「観測済み」「未検証」などの推測状態。
  • scanner responseに存在しないfinding固有の影響説明。

3.3 検出位置の導出

evidenceはcreatedAt昇順、同値ならid昇順に並べる。locationは次の順で 最初に安全に解釈できた一件だけを採用する。

  1. evidenceのlocation.urlにあるHTTP(S) URL。
  2. primaryLocation.urlにあるHTTP(S) URL。
  3. kind === "url"またはoriginを持つlocationのpath。
  4. HTTP(S) URLになっているprimaryLocation.path。
  5. Web scannerのprimaryLocation.path。
  6. primaryLocationのsource path。
  7. source-location evidenceのsource path。

3.3.1 Web location

Web scanner判定は、lowercase化したsourceToolが次のいずれかの場合に限る。 

const WEB_FINDING_TOOLS = new Set([
  "zap-baseline",
  "nuclei-safe",
  "zap-active",
  "dast-http",
  "dast-browser",
  "schemathesis",
  "business-logic",
  "authorization-matrix",
]);
  • 絶対URLはhttp:またはhttps:だけを受け入れる。
  • 表示値はpathname || "/"とし、origin、credential、query、fragmentを捨てる。
  • 相対URLはnew URL(value, "http://scope.invalid")で解析し、得たpathnameを既存の normalizeRelativeHttpPathで検証する。
  • { kind: "url", origin, path }ではoriginを表示せず、pathだけを同じ規則で検証する。
  • methodは、採用したlocationのmethod、次にfinding.metadata.methodを読む。 1〜16文字の英字またはhyphenだけを受け入れてuppercase化する。
  • 保存済みmethodがない場合にGETを補完しない。
  • Web scannerのpathをWeb locationとして解釈できなければ、source pathへfallbackしない。

3.3.2 Source location

  • 同じlocation内ではpath、file、uriの順に読む。
  • slashを/へ統一し、先頭の./と各.segmentを除去する。
  • 空値、制御文字、..segmentを含む値は拒否する。
  • 相対pathは末尾を省略せず、プロジェクト相対path全体を表示する。
  • UnixまたはWindows形式の絶対pathは、同じ規則で正規化したprojectRootと一致するか、 projectRoot + "/"で始まる場合だけ相対化する。範囲外なら非表示にする。
  • file:// URIはURLとして解析してから、同じprojectRoot境界を適用する。
  • 行番号は採用したlocationのstartLine、次にlineを読む。
  • numberまたは10進整数文字列から得た正の整数だけを表示する。
  • 既存のshortPathは使用しない。

3.4 検出内容と観測値

3.4.1 検出内容

  • finding.descriptionを正とし、DB値を変更しない。
  • 既存のread-only MarkdownEditorを使い、unsafe HTMLとunsafe linkの除去を維持する。
  • sourceToolがzap-baselineまたはzap-activeの場合だけ、最初の \n\nSolution:以降を表示用descriptionから除外する。
  • 除外前の部分が空になる場合は元descriptionを使う。
  • 自動翻訳、LLM要約、影響説明、修正案を追加しない。

3.4.2 検出した事実

  1. source locationではsource-location、Web locationではtool-output、locationなしでは source-locationを優先する。
  2. 優先kindに非空snippetがなければ、もう一方のkindを確認する。
  3. scan-logは観測値として使用しない。
  4. tool-output snippetがJSON objectで、非空のevidence文字列を持つ場合はその値だけを使う。
  5. JSON解析に失敗した場合、またはevidenceがない場合は元snippetを使う。
  6. 前後の空白を除去し、descriptionと完全一致する値は重複表示しない。
  7. Unicode文字単位で先頭2,000文字を上限とする。超過時はtruncated: trueを返し、UIに 「先頭2,000文字を表示」と明記する。
  8. 観測値がなければ空cardや「不明」を表示せず、sectionを省略する。

3.5 技術詳細

通常の読み順を妨げないよう、native detailsを閉じた状態で表示する。

  • source toolとrule IDは常に表示する。
  • ZAPのmetadata.zapConfidenceLabelは、False Positive、Low、 Medium、High、Confirmedのいずれかだけを 「ツール確度（scanner申告）」として表示する。
  • finding.confidence === "static"をtool確度や真陽性確率として表示しない。
  • CWEはmetadata.cweIdとmetadata.risk.cweIds、WASCは metadata.wascIdから、非空文字列または正数を文字列化して重複排除する。
  • artifactは整列済みevidenceからartifactId単位で重複排除し、最初のtitleをlabelに使う。 空titleはartifact ${artifactId.slice(0, 8)}とする。
  • hrefは既存の/api/scans/${scanRunId}/artifacts/${artifactId}/downloadを使用する。
  • 観測値として選ばなかったsnippet、metadata JSON全体、fingerprint、内部IDは表示しない。

  4. 条件付きsection: 「検出位置」。
  5. 条件付きsection: 「検出した事実」。

5.5 受け入れ条件

  1. Drawer内でfinding titleと重大度が一度だけ表示される。
  2. 概要の主表示が検出内容、検出位置、観測値に限定されている。
  3. source findingで、保存済みの安全なプロジェクト相対pathと行番号を表示できる。
  4. Web findingで、保存済みURLからoriginを除いたpathnameを表示できる。
  5. 保存されていないmethod、path、観測値、tool確度を推測表示しない。
  6. 重大度とtool確度を別の概念として表示する。
  7. LLM review、Decision、修正計画、優先度、担当、期限が表示されない。
  8. 証跡score、強い・弱いbadge、report readiness、handoff不足情報が表示されない。
  9. 「検証タブで確認」など新しい未実装buttonが追加されていない。
  10. 既存の検証tab、loading、close、dialog semanticsが回帰していない。
  11. API、DB、loader、controller、scanner normalizerに差分がない。
  12. 390pxからdesktopまで横崩れせず、長い値が規定どおり収まる。
  13. 関連testとWeb buildが成功し、本変更由来のtype errorがない。

6. Avoid

  • LLM review、review履歴、review生成buttonをDrawerへ残す、または追加する。
  • 状態、優先度、担当、期限、修正方針をDrawerへ残す。
  • Decision、report分類、report readiness、handoff情報をDrawerへ残す。
  • 独自の証跡scoreをscanner confidenceとして表示する。
  • 保存されていないURL、method、source path、line、観測値を推測する。
  • Web scannerの不正なpathをsource pathとして表示する。
  • モックアップの例示値をhard-codeする。
  • 新しい検証button、自動遷移、verification APIを追加する。
  • review・Decision履歴取得やpollingを、UI非表示のついでに削除する。
  • component、API route、DB columnを未使用という理由だけで削除する。
  • as any、新しい依存package、feature flag、backend fallbackを追加する。
  • 既存shortPathを変更し、finding一覧などDrawer外へ影響を広げる。
  • 対象外の設定画面、scanner、runtime isolation、spinner差分を修正・整形・rollbackする。

7. Definition of Done

  • Work Package 0〜5を順番に完了している。
  • 5.5の受け入れ条件をすべて確認している。
  • 変更前後のscreenshotで情報密度と読み順を比較している。

  • 禁止項目と未実装buttonがDrawerに存在しない。
