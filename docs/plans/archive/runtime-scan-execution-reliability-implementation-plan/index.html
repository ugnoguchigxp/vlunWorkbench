1. Executive decision

今回の障害は三scannerの個別障害ではなく、共通runtime target lifecycleの障害である。

  1. 共通runtime targetのreadiness確認が最初に失敗した。
  2. 失敗処理がprovider所有のruntime source projectionを早期削除した。
  3. 後続stepが同じproviderを再実行し、削除済みprojectionのmount作成で失敗した。
  4. Docker stderrとcontainer logを保存せずcleanupしたため、最初のprocess-level causeを復元できなかった。

実装判断を次に固定する。

  1. 一profile runにつき一つのruntime target sessionを持つ。
  2. target準備はsingle-flightとし、成功または失敗を同じrun内で再利用する。
  3. 共通依存の失敗後はdependent stepを再実行せずblockedにする。
  4. cleanup前にbounded、redacted、access-controlledな診断証跡を保存する。
  5. unit testとは別に実Docker acceptanceをrelease gateとする。

5. Runtime target session contract

5.1 State machine

idle --ensure()--> preparing
preparing --resolved--> ready
preparing --rejected--> failed
ready --ensure()--> same PreparedRuntimeTarget
failed --ensure()--> same RuntimeTargetPreparationError
idle | ready | failed --dispose()--> disposed
disposed --ensure()--> runtime_target_session_disposed
disposed --dispose()--> no-op

実装interfaceを次に固定する。

type RuntimeTargetSessionState =
  | "idle"
  | "preparing"
  | "ready"
  | "failed"
  | "disposed";

interface RuntimeTargetSession {
  ensure(): Promise<PreparedRuntimeTarget>;
  getState(): RuntimeTargetSessionState;
  getFailure(): RuntimeTargetPreparationError | null;
  dispose(): Promise<void>;
}

ensure()は一つのPromiseを保持する。同時・連続callerがあってもproviderの prepare()は一度だけ実行する。失敗はtyped stateとして保持し、後続callerは同じ root failureを参照する。

5.2 Resource ownership

5.2 Ownership and cleanup boundary
Resource Owner Created Destroyed
Full source snapshot Profile orchestrator profile前 outer finally
Runtime source projection Runtime provider session provider factory provider dispose()
Runtime bundle attempt Docker bundle lifecycle session ensure() stopまたはfailed-attempt cleanup
Shared prepared target Runtime target session first successful ensure() session dispose()
Diagnostic artifacts Scan artifact repository failure evidence collection scan artifact retention

providerのprepare()失敗時は、そのattemptのDocker resourceだけをcleanupする。 provider構築失敗とouter dispose()だけがprojection cleanupを行う。

5.3 Dependent step semantics

auto_project_start DAST、runtime scanner、runtimeを使うAPI schema scannerは同じ dependency groupに属する。最初にsession準備を要求したstepで失敗した場合、そのstepは failed、後続dependent stepはblockedとする。後続resultは reasonCode=runtime_target_unavailable、blockedByStepId、 rootReasonCodeを持ち、scanner processを起動しない。独立static stepだけが既存の continueOnToolFailure規則に従う。

既存result unionを次の規則で拡張する。

status: "completed" | "failed" | "skipped" | "blocked";
reasonCode: string | null;
blockedByStepId?: string | null;
rootReasonCode?: string | null;
diagnosticArtifactIds?: string[];
  • DastStepResultへreason code、blocked relation、artifact IDを追加する。
  • CoverageStepResultのstatusへblockedを追加する。
  • blocked stepをruntime coverageのattemptedまたはfailedへ加算しない。
  • failureDelta()の文字列部分一致によるruntime failure判定をtyped mapperへ置き換える。

観測済みrunの期待結果はDASTがfailed、NucleiとZAPが blocked、bundle作成回数1、scanner process起動回数0である。

6. Failure and diagnostic contract

6.1 Typed Docker error

type RuntimeDockerCommandError = Error & {
  code: RuntimeFailureReasonCode;
  phase: RuntimeBundlePhase;
  role: RuntimeBundleRole | null;
  operation: RuntimeDockerOperation;
  exitCode: number | null;
  terminationReason: string | null;
  stderrExcerpt: string | null;
  stdoutExcerpt: string | null;
  retryable: false;
};

Docker command errorはbundle cleanup後、sessionへ返す前に次の公開internal contractへ包む。

class RuntimeTargetPreparationError extends Error {
  reasonCode: RuntimeFailureReasonCode;
  phase: RuntimeBundlePhase;
  role: RuntimeBundleRole | null;
  operation: RuntimeDockerOperation;
  exitCode: number | null;
  terminationReason: string | null;
  safeExcerpt: string | null;
  evidence: RuntimeFailureEvidence | null;
  diagnosticArtifactIds: string[];
  cleanupFailure: RuntimeDockerCommandError | null;
}

lifecycleのexecute()はargvからphaseを推測せず、callerがphase、role、operationを 渡す。error messageへ完全なargv、environment値、host absolute path、secretを含めない。

6.2 Stable reason codes

runtime_target_readiness_timeout 期限内に許容HTTP statusなし port、bind address、pathを確認

6.3 Evidence before cleanup

  1. 最初のtyped failureを確定し、後続errorで上書きしない。
  2. receiptに記録済みのcontainerだけを対象にする。
  3. target、dependency-fetch、probe、scannerのbounded logを取得する。
  4. state、exit code、OOMKilled、startedAt、finishedAt、image IDだけをinspectから取得する。
  5. redactorを通し、合計1 MiB以下のRuntimeFailureEvidenceをメモリ上で確定する。
  6. 証跡回収の成否にかかわらずDocker resourceをcleanupする。
  7. leaseをreleasedまたはquarantinedへ確定する。
  8. evidence付きtyped errorをsessionへ返す。
  9. sessionがartifactを一度だけ永続化し、最大4 KiBのsafe excerptとartifact IDをeventへ記録する。

environment、mount元absolute path、raw inspect JSON、header、cookieは保存しない。回収はcontainer cleanup前、永続化はcleanup後とする。artifact永続化の失敗は元reason codeを維持したまま runtime_evidence_collection_failed limitationを追加する。

6.4 Lifecycle observer and data flow

RuntimeIsolationProviderFactoryのrun単位inputへ次のobserverを追加する。

interface RuntimeTargetLifecycleObserver {
  emit(event: RuntimeTargetLifecycleEvent): Promise<void>;
  persistFailureEvidence(input: {
    bundleId: string;
    stepId: string;
    evidence: RuntimeFailureEvidence;
  }): Promise<string[]>;
}

profile-orchestratorがScanRepository、ArtifactRepository、ArtifactStorageからobserverを 構築する。Docker lifecycleへDB repositoryを直接渡さない。phase event保存に失敗してもcleanupを 続行し、scanを成功扱いにしない。evidence persistenceはfailed sessionごとに一度だけ実行する。

6.5 Runtime diagnostic artifact

scanArtifactKindSchemaとScanArtifactSinkのlocation mapへ runtime_diagnosticを追加する。DB columnはtextであるためmigrationは追加しない。 scan_diagnostic_runsは自動review pipeline用であり、本contractでは使用しない。

ownerは{ scanRunId, kind: "scan", id: "runtime-" + bundleId }、filenameは runtime_diagnostic.jsonとする。失敗bundleにつきartifactは一件だけ保存し、内容を次に固定する。 

{
  schemaVersion: 1,
  bundleId: string,
  stepId: string,
  rootFailure: {
    reasonCode: RuntimeFailureReasonCode,
    phase: RuntimeBundlePhase,
    role: RuntimeBundleRole | null,
    operation: RuntimeDockerOperation,
    exitCode: number | null
  },
  containers: Array<{
    role: RuntimeBundleRole,
    status: string | null,
    exitCode: number | null,
    oomKilled: boolean | null,
    stdout: string,
    stderr: string,
    truncated: boolean
  }>,
  readiness: {
    timeoutMs: number,
    attempts: number,

}

downloadは既存scan artifact routeとproject ownership checkを使う。RBACやadmin横断閲覧を追加せず、 運用上はadmin accountがproject ownerであることを前提とする。保持期間はscan artifact lifecycleに従う。

7.2 Progress V3

既存ScanProgressSnapshotV2はblocked、skipped、runtime preparation detailを表現できない。 GET /api/scans/:scanRunId/progressを次のV3へ切り替え、Web clientを同時更新する。 

type ScanProgressStepStatus =
  | "pending"
  | "running"
  | "completed"
  | "failed"
  | "blocked"
  | "skipped"
  | "not_applicable";

type ScanProgressSnapshotV3 = {
  schemaVersion: 3;
  runId: string;
  planHash: string;
  currentPhase: ScanProgressPhase;
  runtimeTarget: {
    status:
      | "not_required"
      | "pending"
      | "preparing"
      | "ready"
      | "failed"
      | "cleaning"
      | "cleaned";
    phase: RuntimeBundlePhase | null;
    safeMessage: string | null;
    rootReasonCode: string | null;
    diagnosticArtifactIds: string[];
  };
  steps: ScanProgressStepV3[];
  completedStepCount: number;
  terminalStepCount: number;
  totalStepCount: number;
  lastEventSeq: number;
};

completed countはcompletedとnot_applicableだけ、terminal countはcompleted、failed、blocked、skipped、 not_applicableを数える。画面の100%はterminal countから計算し、成功判定には使用しない。

7.3 Required presentation

  • 実行準備の現在phase、完了phase、経過時間を表示する。
  • first causeをfailure panelの先頭に表示する。
  • blocked stepへ「共通対象を準備できなかったため未実行」と表示する。
  • project ownerにはdiagnostic artifact downloadとredacted excerptを表示する。
  • cleanup成功時はscan outcomeがfailedでも完了処理をcompletedと表示する。
  • cleanup失敗時だけ完了処理をfailedと表示する。

7.4 Cancellation and worker crash

本改修ではprocess supervisorからruntime providerへ新しいAbortSignal transportを追加しない。 正常終了、step failure、step timeoutはsessionのdispose()で即時cleanupする。supervisorによる 強制終了またはworker crashでは、永続化済みbundle receiptと既存RuntimeBundleLeaseJanitorを回収の 正本とする。user cancellationはruntime failureへ変換せず、scan statusはcancelledを維持する。

cancellation acceptanceはtest専用の短いlease TTLを使用し、janitorを明示実行してorphan 0を確認する。 productionのTTLをtest都合で短縮してはならない。

11. Rollout, rollback, and stop conditions

11.1 Rollout order

  1. schemaとreaderの後方互換を先に入れる。
  2. backend session lifecycleを有効化する。
  3. Web progress表示を有効化する。
  4. runtime-passiveの実Docker qualificationを更新する。
  5. runtime profile familyへ横展開する。

11.2 Rollback rule

rollback時もhost executionやmutable imageへ戻さない。安全な実行を保証できない場合は対象profileを temporarily_unavailableにし、既存run、event、artifactのreaderを維持する。

11.3 Stop conditions

  • 既存未コミット変更と同一行で意図不明な競合が発生した。
  • diagnostic artifactからsecretまたはhost private pathが検出された。
  • cleanup failure injection後にlabel付きresourceが回収不能になった。
  • 成功のためhost executionまたはnetwork境界緩和が必要になった。
  • 実Docker evidenceをimage digestまたはdaemon identityへbindできない。
